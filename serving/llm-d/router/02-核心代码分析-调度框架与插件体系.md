## 0. 一句话定位

EPP 的**核心代码不做决策**。01 篇看到的 `Director` 和 `Scheduler` 只有约 2400 行，它们唯一的工作是「按顺序调用插件」。所有实际行为都在插件里。

推论：**读核心代码看不出 EPP 的行为，必须配着 `EndpointPickerConfig` 看。** 这也是排障第一步——把生效的配置 dump 出来。

## 1. 八类扩展点

### 1.1 基础契约

所有插件都嵌入同一个最小接口：

```go
// pkg/epp/framework/interface/plugin/plugins.go:23-89（节选）
type Plugin interface {
	TypedName() TypedName          // {Type, Name}，Type 是 YAML 里的 type，Name 是实例名
}

type ConsumerPlugin interface {
	Plugin
	Consumes() DataDependencies    // 声明「我要读哪些数据」
}

type ProducerPlugin interface {
	Plugin
	Produces() map[DataKey]any     // 声明「我产出哪些数据」
}
```

`Consumes` / `Produces` 是 Data Layer 的数据依赖声明，用来做两件事：**构建插件实例化的拓扑序**、**在运行时拦截未声明的读写**（01 篇 §7 那个「静默丢弃」的坑就源于此）。

### 1.2 调度层四类

```go
// pkg/epp/framework/interface/scheduling/plugins.go:43-78
type ProfileHandler interface {
	plugin.Plugin
	// Pick selects the SchedulingProfiles to run from a list of candidate profiles, while taking into consideration the request properties
	// and the previously executed SchedluderProfile cycles along with their results.
	Pick(ctx context.Context, request *InferenceRequest, profiles map[string]SchedulerProfile,
		profileResults map[string]*ProfileRunResult) map[string]SchedulerProfile

	// ProcessResults handles the outcome of the profile runs after all profiles ran.
	// It may aggregate results, log test profile outputs, or apply custom logic. It specifies in the SchedulingResult the
	// key of the primary profile that should be used to get the request selected destination.
	// When a profile run fails, its result in the profileResults map is nil.
	ProcessResults(ctx context.Context, request *InferenceRequest,
		profileResults map[string]*ProfileRunResult) (*SchedulingResult, error)
}

// Filter defines the interface for filtering a list of pods based on context.
type Filter interface {
	plugin.Plugin
	Filter(ctx context.Context, request *InferenceRequest, pods []Endpoint) []Endpoint
}

// Scorer defines the interface for scoring a list of pods based on context.
// Scorers must score pods with a value within the range of [0,1] where 1 is the highest score.
// If a scorer returns value greater than 1, it will be treated as score 1.
// If a scorer returns value lower than 0, it will be treated as score 0.
type Scorer interface {
	plugin.Plugin
	Category() ScorerCategory
	Score(ctx context.Context, request *InferenceRequest, pods []Endpoint) map[Endpoint]float64
}

// Picker picks the final pod(s) to send the request to.
type Picker interface {
	plugin.Plugin
	Pick(ctx context.Context, scoredPods []*ScoredEndpoint) *ProfileRunResult
}
```

注意 `Filter` **没有 error 返回值**。这是个有意的设计约束：Filter 只能「剔除」，不能「让请求失败」。它砍空了候选集，由框架统一转成 429（01 篇 §3.1）。

`Scorer.Category()` 是个纯声明性的东西，标记这个 scorer 的偏好方向：

```go
// pkg/epp/framework/interface/scheduling/plugins.go:28-39（节选）
const (
	// Affinity indicates a scorer that prefers endpoints with existing locality, such as kv-cache or session-related state,
	// and therefore tends to give higher scores to the same endpoints.
	Affinity ScorerCategory = "Affinity"

	// Distribution indicates a scorer that prefers spreading requests evenly across all candidate endpoints to avoid
	// hotspots and improve overall utilization.
	Distribution ScorerCategory = "Distribution"

	// Balance indicates a scorer that its preference is balanced between Affinity and Distribution.
	Balance ScorerCategory = "Balance"
)
```

**这个分类值得记住**，因为它揭示了 scorer 配置的本质矛盾：`prefix-cache-scorer`（Affinity）想把相同前缀的请求都塞给同一个 pod，`queue-scorer`（Distribution）想把请求摊平。**权重配置就是在这两股力之间调平衡**——07 篇会讲这个权衡怎么调。

## 2. YAML 如何变成运行时插件

### 2.1 注册表

插件类型名（YAML 里的 `type:`）到构造函数的映射，是一张全局 map：

```go
// pkg/epp/framework/interface/plugin/registry.go:26-72（节选）
// FactoryFunc is the definition of the factory functions that are used to instantiate plugins
// specified in a configuration. The framework provides a strict decoder
// (DisallowUnknownFields) over the plugin's raw parameters...
type FactoryFunc func(name string, parameters *json.Decoder, handle Handle) (Plugin, error)

// Register registers a factory function for the given plugin type along with its stability level.
func Register(pluginType string, stability StabilityLevel, factory FactoryFunc) {
	Registry[pluginType] = factory
	RegistryMetadata[pluginType] = PluginMetadata{
		Type:      pluginType,
		Stability: stability,
	}
}

// RegisterAsDefaultProducer registers a factory ... and records it as the default producer for the given data key.
func RegisterAsDefaultProducer(pluginType string, stability StabilityLevel, factory FactoryFunc, key DataKey) {
	Register(pluginType, stability, factory)
	DefaultProducerRegistry[key.String()] = pluginType
}

// RegisterWithPluginDependencies registers a factory ... and records it as dependent on other plugins
// referenced in the configuration struct returned by the plugin's configuration parser function.
func RegisterWithPluginDependencies(pluginType string, stability StabilityLevel, factory FactoryFunc, parser ConfigParserFunc) {
	Register(pluginType, stability, factory)
	PluginsWithPluginDependencies[pluginType] = parser
}
```

四种注册方式的分工：

| 函数 | 额外登记了什么 | 用于 |
|------|---------------|------|
| `Register` | 只有类型和稳定性 | 普通插件 |
| `RegisterAsDefaultProducer` | 「谁是这个 DataKey 的默认生产者」 | 自动补齐缺失的 producer（§4.2） |
| `RegisterWithPluginDependencies` | 参数解析函数（用于扫 `pluginRef`） | 插件参数里引用其他插件的情况 |
| `RegisterDeprecated`（`registry.go:75`） | 弃用版本 + 替代类型 | 启动时打 DEPRECATION 日志 |

**所有内建插件的注册集中在一个函数**：`registerInTreePlugins()`（`cmd/epp/runner/runner.go:573-736`），在 Phase One 被调用（`runner.go:764`）。想知道「这个版本到底有哪些插件」，读这 160 行就够了。

### 2.2 严格解析：未知字段直接报错

`StrictDecoder`（`registry.go:41-48`）对插件参数开了 `DisallowUnknownFields`。这意味着**参数名打错一个字母，EPP 启动就失败**，而不是静默忽略：

```yaml
- type: prefix-cache-scorer
  parameters:
    prefixMatchInfoProducerNam: precise   # 少了个 e
```

→ `failed to create plugin 'prefix-cache-scorer' (type: prefix-cache-scorer): json: unknown field "prefixMatchInfoProducerNam"`

这是好事。作为对比，07 篇会讲几个**没有**这层保护、配错了会静默不生效的地方。

### 2.3 实例化：按依赖 DAG 拓扑序

```go
// pkg/epp/config/loader/configloader.go:276-298
func instantiatePlugins(configuredPlugins []configapi.PluginSpec, handle fwkplugin.Handle, logger logr.Logger) error {
	orderedPlugins, err := buildPluginDAG(configuredPlugins, handle)
	if err != nil {
		return fmt.Errorf("failed to build plugin dependency graph: %w", err)
	}

	for _, spec := range orderedPlugins {

		if meta, ok := fwkplugin.RegistryMetadata[spec.Type]; ok && meta.Deprecated {
			logger.Info("DEPRECATION warning: plugin is deprecated", "plugin", spec.Name, "type", spec.Type)
		}

		factory := fwkplugin.Registry[spec.Type]
		plugin, err := factory(spec.Name, fwkplugin.StrictDecoder(spec.Parameters), handle)
		if err != nil {
			return fmt.Errorf("failed to create plugin '%s' (type: %s): %w", spec.Name, spec.Type, err)
		}

		handle.AddPlugin(spec.Name, plugin)
	}

	return nil
}
```

`buildPluginDAG`（`configloader.go:300-334`）用**反射**扫插件配置结构体上的 `pluginRef` tag，做拓扑排序。为什么需要：`prefix-cache-scorer` 的参数里写着 `prefixMatchInfoProducerName: precise`，它构造时需要那个 producer 实例已经存在。

## 3. 打分：数字是怎么出来的

这一节回答 01 篇示例里「为什么选 D3」。

### 3.1 值域约定与两次 clamp

`Scorer` 接口注释规定返回值必须在 `[0,1]`，超出被截断。框架不信任插件，自己再 clamp 一次（`enforceScoreRange`，`scheduler_profile.go:427-434`）。

### 3.2 权重包装

配置解析时，每个 scorer 被包一层 `WeightedScorer`：

```go
// pkg/epp/config/loader/configloader.go:398-405
			// Wrap Scorers with weights.
			if scorer, ok := plugin.(fwksched.Scorer); ok {
				weight := DefaultScorerWeight
				if pluginRef.Weight != nil {
					weight = *pluginRef.Weight
				}
				plugin = scheduling.NewWeightedScorer(scorer, weight)
			}
```

`DefaultScorerWeight` = `1.0`（`defaults.go:42-43`）。

### 3.3 累加，但不归一化

```go
// pkg/epp/scheduling/scheduler_profile.go:244-255（节选）
	// Iterate through each scorer in the chain and accumulate the weighted scores.
	for _, scorer := range p.scorers {
		scores := runScorer(ctx, tracer, tracingActive, scorer, request, endpoints)
		for endpoint, score := range scores { // weight is relative to the sum of weights
			weightedScorePerEndpoint[endpoint] += enforceScoreRange(score) * scorer.Weight()
		}
	}
```

**三个必须记住的事实**：

1. **公式就是 `Σ(scoreᵢ × weightᵢ)`**，没有除以 `Σweightᵢ`。那句 `// weight is relative to the sum of weights` 是语义描述而非代码行为。
2. **scorer 串行执行**，不是并行。`for _, scorer := range p.scorers` 单 goroutine 走完。上游架构文档写着「future: parallel execution」。
3. **最终分值的绝对尺度随权重配置变化**。optimized-baseline 的权重是 2+2+3+2=9，所以理论最高分是 9 分而不是 1 分。跨配置比较分数没有意义。

### 3.4 用示例算一遍

请求 A 的场景：D1..D4 四个 decode pod，配置用 optimized-baseline 的权重。假设采到的状态：

| pod | 等待队列 | KV 利用率 | 前缀命中 |
|-----|---------|----------|---------|
| D1 | 8 | 0.62 | 0/1 block |
| D2 | 2 | 0.30 | 0/1 block |
| D3 | 3 | 0.35 | 1/1 block（B 请求时） |
| D4 | 12 | 0.71 | 0/1 block |

各 scorer 的算法：

- **`queue-scorer`**：候选集内 min-max 归一化，`(max-q)/(max-min)`，全相等时给 1.0（`queuedepth/queue.go:100-106`）
- **`kv-cache-utilization-scorer`**：直接 `1 - KVCacheUsagePercent`
- **`prefix-cache-scorer`**：默认只用 match ratio = `matchBlocks/totalBlocks`（04 篇 §5）
- **`no-hit-lru-scorer`**：给「最近没被选中过」的 pod 加分，用于分散冷请求

**请求 A**（无前缀命中，四个 pod 都是 0）：

```
queue-scorer:  min=2, max=12
  D1: (12-8)/(12-2)=0.40   D2: (12-2)/10=1.00   D3: (12-3)/10=0.90   D4: 0.00
kv-scorer:
  D1: 1-0.62=0.38          D2: 0.70             D3: 0.65             D4: 0.29
prefix-scorer: 全 0（首次请求，没人有这个前缀）
no-hit-lru:    假设都未被选过 → 全 1.0

加权和（queue×2 + kv×2 + prefix×3 + lru×2）：
  D1: 0.80+0.76+0+2.00 = 3.56
  D2: 2.00+1.40+0+2.00 = 5.40   ← max-score-picker 选 D2
  D3: 1.80+1.30+0+2.00 = 5.10
  D4: 0.00+0.58+0+2.00 = 2.58
```

**请求 B**（假设 A 落在了 D2，那 12 个 token 的前缀现在在 D2 上；上表的「前缀命中」列改为 D2 命中）：

`prefix-scorer` 给 D2 加 `1.0 × 3 = 3.0`，而 `no-hit-lru` 因为 D2 刚被选过要扣分。**这就是 Affinity 与 Distribution 两股力的正面对撞**——权重 3（前缀）压过了权重 2（分散），所以 B 大概率还是落 D2，命中前缀缓存。

这个例子也说明了为什么 `prefix-cache-scorer` 的权重在官方配方里是最高的 3：**前缀命中省下的是整个 prefill 阶段的计算**，比队列长一点的代价大得多。

### 3.5 平局怎么办

`max-score-picker`（`picker/maxscore/picker.go`）先做确定性轮转，再稳定排序：

```
RotateScoredEndpoints（picker.go:91-93）  → 轮转起点，等分时轮流中选
stable sort by score desc（picker.go:95-103）
```

参数 `maxNumOfEndpoints`（默认 1）控制返回几个 endpoint。返回多个时 Envoy 的 destination 是逗号分隔列表——用于 data parallel 等场景。

### 4.2 DataProducer 自动补齐

这一步不在 `defaults.go`，而在 Phase Two 之后（`runner.go:807` 调 `CreateMissingDataProducers`，实现在 `data_graph.go:65-72`）。

机制：插件用 `Consumes()` 声明需要某个 `DataKey`，如果没有任何插件 `Produces()` 它，就从 `DefaultProducerRegistry` 找默认生产者建一个。

| 需要的数据 | 默认 producer |
|-----------|--------------|
| `PrefixCacheMatchInfo` | `approx-prefix-cache-producer` |
| `TokenizedPrompt` | `token-producer` |
| `InFlightLoad` / `UncachedRequestTokens` | `inflight-load-producer` |
| `LatencyPredictionInfo` | `predicted-latency-producer` |
| 多模态 embedding 缓存 | `mm-embeddings-cache-producer` |
| `SessionID` | `session-id-producer` |

注册见 `runner.go:668-677`。

**这解释了 optimized-baseline 配置里的一个现象**：它显式配了 `approx-prefix-cache-producer`，但如果只写 `prefix-cache-scorer` 不写 producer，也能工作——框架会自动补一个近似 producer。**想用精确版本必须显式配**，否则默默用了近似的。

#### 5.2.1 两个必须知道的 scorer 缺陷

**`precise-prefix-cache-scorer` 已弃用**（`precise_prefix_cache.go:87-89` 启动即打 DEPRECATION 日志）。正确写法是 `precise-prefix-cache-producer` + `prefix-cache-scorer`（后者设 `prefixMatchInfoProducerName` 指向前者）。04 篇 §5 给完整配置。

**`load-aware-scorer` 信息不足**，注释直接承认：

```go
// pkg/epp/framework/plugins/scheduling/scorer/loadaware/load_aware.go:77-80（节选）
// Currently metrics contains number of requests waiting in the queue, there is no information about
// number of requests that can be processed... Pod with empty waiting requests queue is scored with 0.5
```

**后果**：空闲的 pod（队列为 0）全部得 0.5，彼此**无法区分**。而 03 篇会讲到，指标抓取失败时 `WaitingQueueSize` 也是 0——所以「pod 全空闲」和「指标全挂了」在这个 scorer 眼里一模一样。生产环境用 `queue-scorer` + `kv-cache-utilization-scorer` 比用 `load-aware-scorer` 更可控。

**`multicluster-*` scorer 的三件套依赖**（`plugins/README.md:36-37`）：必须同时配 `multicluster-metrics-data-source` + `multicluster-metrics-extractor`，否则加载失败。

### 5.3 Picker

| YAML type | 文件 | 算法 | 参数 |
|-----------|------|------|------|
| `max-score-picker` | `picker/maxscore/picker.go` | 最高分；平局确定性轮转 | `maxNumOfEndpoints`（默认 1） |
| `random-picker` | `picker/random/picker.go` | 纯随机 | `maxNumOfEndpoints` |
| `weighted-random-picker` | `picker/weightedrandom/picker.go` | 按分数加权随机（A-Res 算法） | `maxNumOfEndpoints` |

`weighted-random-picker` 的用途：`max-score-picker` 会把所有相似请求都打到同一个最优 pod，造成羊群效应；加权随机在保留偏好的同时引入抖动。

### 5.4 ProfileHandler 与 PD Decider

| YAML type | 文件（`.../profilehandler/`） | 作用 |
|-----------|---------------------------|------|
| `single-profile-handler` | `single/single_profile_handler.go` | 单 profile，恒为 primary |
| `disagg-profile-handler` | `disagg/disagg_profile_handler.go` | **P/D/E 分阶段调度**（见下） |
| `header-profile-handler` | `headerprofile/` | 按请求头选 profile（Coordinator 模式用，06 篇 §7） |
| `data-parallel-profile-handler` | `dataparallel/` | DP 多 rank |

`disagg-profile-handler` 的参数结构（`disagg_profile_handler.go:87-97`）：

```yaml
- type: disagg-profile-handler
  parameters:
    stageOrder: decode-first        # 或 prefill-first
    profiles:
      decode: decode
      prefill: prefill
    deciders:
      prefill: prefix-based-pd-decider   # pluginRef
```

**Decider** 决定「这个请求要不要真的走 prefill 分离」：

| YAML type | 文件 | 逻辑 |
|-----------|------|------|
| `always-disagg-pd-decider` | `disagg/always_disagg_pd_decider.go` | 总是分离 |
| `prefix-based-pd-decider` | `disagg/prefix_based_pd_decider.go` | 未命中的 token 数超过 `nonCachedTokens` 才分离 |
| `always-disagg-multimodal-decider` | `disagg/always_disagg_mm_decider.go` | 多模态总是分离 |

`prefix-based-pd-decider` 是生产配方里的默认选择（`deploy/config/pd-epp-config.yaml` 设 `nonCachedTokens: 16`）。**道理**：prompt 短或前缀基本全命中时，分离的网络开销大于 prefill 的计算收益，不如让 decode pod 自己算。

**两个坑**：

1. `single-profile-handler` **不能**用于多 profile，会启动失败（`configloader.go:429-431`）
2. 全局只能有一个 ProfileHandler，配了两个也启动失败（`configloader.go:414-423`）

已弃用：`disagg-headers-handler`、`prefill-header-handler` → 用 `disagg-profile-handler`。

## 6. SchedulingProfiles

### 6.1 API 结构

```go
// apix/config/v1alpha1/endpointpickerconfig_types.go:112-179（节选）
type PluginSpec struct {
	Name       string          `json:"name"`
	Type       string          `json:"type"`
	Parameters json.RawMessage `json:"parameters"`
}

type SchedulingProfile struct {
	Name    string             `json:"name"`
	Plugins []SchedulingPlugin `json:"plugins"`
}

type SchedulingPlugin struct {
	PluginRef string   `json:"pluginRef"`
	Weight    *float64 `json:"weight"`
}
```

`name` 省略时默认等于 `type`（`defaults.go:110-113`）。这就是为什么大多数配置里的 `pluginRef` 直接写 type 名——**同一个 type 要配多个实例时才需要显式命名**，比如两个不同 block size 的前缀 producer。

### 6.2 单 profile vs 多 profile

| | 单 profile | 多 profile（P/D） |
|---|-----------|------------------|
| ProfileHandler | 自动注入 `single-profile-handler` | 必须显式配 `disagg-profile-handler` |
| Pick | 始终返回那一个 profile | 按 stageOrder + decider 迭代 |
| Filter 链 | 一条 | **每个 profile 各一条独立的** |
| Screener | Director 层跑一次，对所有 profile 生效 | 同左 |
| primary | 那唯一一个 | `decode`（默认） |

**Filter 链独立**这点是 P/D 配置的核心：`prefill` profile 里配 `prefill-filter`，`decode` profile 里配 `decode-filter`，两条链互不干扰。而 `prefix-cache-scorer` 可以在两个 profile 里都出现——同一个插件实例，被两条链各调一次。

### 6.3 校验

`buildSchedulerConfig`（`configloader.go:380-434`）在启动时抓这几类错误：

```go
// pkg/epp/config/loader/configloader.go:414-431（节选）
	var profileHandler fwksched.ProfileHandler
	for name, plugin := range handle.GetAllPluginsWithNames() {
		if ph, ok := plugin.(fwksched.ProfileHandler); ok {
			if profileHandler != nil {
				return nil, fmt.Errorf("multiple profile handlers found ('%s', '%s'); only one is allowed",
					profileHandler.TypedName().Name, name)
			}
			profileHandler = ph
		}
	}

	if profileHandler == nil {
		return nil, errors.New("no profile handler configured")
	}

	if profileHandler.TypedName().Type == single.SingleProfileHandlerType && len(profiles) > 1 {
		return nil, errors.New("SingleProfileHandler cannot support multiple scheduling profiles")
	}
```

再加上 `pluginRef` 指向不存在的插件（`configloader.go:394-396`）。**这些都是启动期硬失败**——比运行时静默降级好得多。

## 7. Feature Gates

### 7.1 只有两个

| Gate | 默认 | 作用 | 定义 |
|------|------|------|------|
| `flowControl` | **false** | 启用整个 Flow Control 层 | `flowcontrol/config.go:27` |
| `haPopulateNonLeaderDatastore` | **true** | HA 部署下非 leader 副本也跑 datastore reconciler | `server/controller_config.go:33` |

注册见 `runner.go:761-762`。

### 7.2 CLI 覆盖 YAML

```go
// pkg/epp/config/loader/configloader.go:135-142
	// Appended after the config's own entries because loadFeatureConfig is last-wins,
	// so flag-supplied gates override file-supplied ones.
	if len(extraGates) > 0 {
		rawConfig.FeatureGates = append(rawConfig.FeatureGates, extraGates...)
	}
```

`loadFeatureConfig`（`configloader.go:436-455`）先填所有已注册 gate 的默认值，再按列表顺序解析，同名后者覆盖前者。格式是 kubelet 风格：`gateName`（= true）或 `gateName=false`。

未知 gate 名会在校验期报错（`loader/validation.go:138+`）。

### 7.3 gate 关闭时配了对应段会怎样

```go
// pkg/epp/config/loader/configloader.go:219-228（节选）
	if featureGates[flowcontrol.FeatureGate] {
		flowControlConfig, err = buildFlowControlConfig(...)
	} else if flowControlSettingsConfigured(rawConfig.FlowControl) {
		logger.Info("WARNING: the flowControl config section is set but the flowControl feature gate is disabled; its settings (other than saturationDetector) are ignored")
	}
```

**只有一行 Info 级 WARNING**，不是错误。这是 07 篇排障清单上的一条：配了 `flowControl:` 但忘了开 gate，除 `saturationDetector` 外全部静默忽略。

## 8. 自己写一个插件

最小可用的 Scorer：

```go
package myscorer

import (
	"context"
	"encoding/json"

	fwkplugin "github.com/llm-d/llm-d-router/pkg/epp/framework/interface/plugin"
	fwksched "github.com/llm-d/llm-d-router/pkg/epp/framework/interface/scheduling"
	dlmetrics "github.com/llm-d/llm-d-router/pkg/epp/framework/plugins/datalayer/extractor/metrics"
)

const MyScorerType = "my-scorer"

type MyScorer struct {
	typedName fwkplugin.TypedName
}

func (s *MyScorer) TypedName() fwkplugin.TypedName { return s.typedName }

func (s *MyScorer) Category() fwksched.ScorerCategory { return fwksched.Distribution }

// Consumes 必须声明要读的数据，否则运行时读取会被 Scope 拦下并静默丢弃，
// 只体现在 plugin_data_scope_violations_total 指标上。
func (s *MyScorer) Consumes() fwkplugin.DataDependencies {
	return fwkplugin.DataDependencies{
		Required: map[fwkplugin.DataKey]any{
			fwkplugin.NewDataKey(dlmetrics.RunningRequestsSizeKey, dlmetrics.MetricsExtractorType): int(0),
		},
	}
}

func (s *MyScorer) Score(ctx context.Context, request *fwksched.InferenceRequest,
	pods []fwksched.Endpoint) map[fwksched.Endpoint]float64 {
	scores := make(map[fwksched.Endpoint]float64, len(pods))
	for _, p := range pods {
		m := p.GetMetrics()
		if m == nil {
			scores[p] = 0
			continue
		}
		// 返回值必须落在 [0,1]；框架会再 clamp 一次。
		scores[p] = 1.0 / float64(1+m.RunningRequestsSize)
	}
	return scores
}

func Factory(name string, params *json.Decoder, handle fwkplugin.Handle) (fwkplugin.Plugin, error) {
	return &MyScorer{typedName: fwkplugin.TypedName{Type: MyScorerType, Name: name}}, nil
}
```

注册（加到 `registerInTreePlugins` 或自己的 runner 里）：

```go
fwkplugin.Register(myscorer.MyScorerType, fwkplugin.Alpha, myscorer.Factory)
```

**四个容易忘的点**：

1. **`Consumes()` 必须声明**，否则读取被静默丢弃（01 篇 §7 最后一条）
2. **返回值必须在 `[0,1]`**，虽然框架会 clamp，但超范围意味着你的权重语义已经乱了
3. **`Alpha` 稳定性需要 `--allow-experimental-plugins`**，否则启动失败
4. **参数结构体要能被严格解析**（`DisallowUnknownFields`），字段名和 YAML 必须完全一致

想在编译期加插件而不 fork 上游，也可以走「自建 runner + import 上游包」的路子——和 [kube-scheduler 06 篇](../../../scheduling/kube-scheduler/06-扩展实战-自定义调度插件开发.md) 的 out-of-tree 插件思路一致。
