## 1. 配方一：optimized-baseline

### 1.1 完整配置

```yaml
# test/perf/config/router-configs/optimized-baseline.yaml:24-44（内嵌的 EPP 配置部分）
apiVersion: llm-d.ai/v1alpha1
kind: EndpointPickerConfig
plugins:
- type: queue-scorer
- type: kv-cache-utilization-scorer
- type: approx-prefix-cache-producer
  parameters:
    maxPrefixTokensToMatch: 100000
- type: prefix-cache-scorer
- type: no-hit-lru-scorer
schedulingProfiles:
- name: default
  plugins:
  - pluginRef: queue-scorer
    weight: 2
  - pluginRef: kv-cache-utilization-scorer
    weight: 2
  - pluginRef: prefix-cache-scorer
    weight: 3
  - pluginRef: no-hit-lru-scorer
    weight: 2
```

**只有 21 行，但每一行都有讲究。**

### 1.2 逐行讲

**没有出现的东西（框架自动补的，02 篇 §4）**：

| 缺什么 | 框架注入什么 |
|--------|------------|
| ProfileHandler | `single-profile-handler`（只有 1 个 profile） |
| Picker | `max-score-picker`（profile 里没配任何 Picker） |
| Parser | `openai-parser` + `anthropic-parser` + `vllmhttp-parser` + `passthrough-parser` |
| Data Layer | `metrics-data-source` + `core-metrics-extractor` |
| DataProducer | `token-producer`（`approx-prefix-cache-producer` 需要分词） |
| Filter | **一个都没有**——所有 endpoint 都是候选 |

**没有 `decode-filter` 意味着**：这是一个单池部署，所有 pod 都能同时做 prefill 和 decode。不需要按角色过滤。

**权重 2:2:3:2 的含义**（02 篇 §3.4 算过一遍）：

```
理论最高分 = 2 + 2 + 3 + 2 = 9
prefix (3)     ← Affinity，最高权重：前缀命中省的是整个 prefill 阶段
queue  (2)     ← Distribution
kv     (2)     ← Distribution
lru    (2)     ← Distribution，专治「冷请求全挤到同一个 pod」
Distribution 合计 6 : Affinity 3 —— 偏向分散，但单项最高是亲和
```

**`no-hit-lru-scorer` 为什么必要**：只有前三个 scorer 时，一批**没有任何前缀命中**的冷请求会全部看到相同的 prefix 分（都是 0），于是完全由 queue + kv 决定——而这两个指标有 50ms 的采集延迟（03 篇 §2.2）。结果是几十个请求在指标更新前全挤到同一个「当时最闲」的 pod 上。`no-hit-lru-scorer` 给「最近没被选中」的 pod 加分，打散这个羊群。

**`maxPrefixTokensToMatch: 100000` 是本配置最贵的参数**。上游 sizing 数据（`docs/operations.md`）：

| 配置 | Req/s | `maxPrefixTokensToMatch` | 峰值 CPU | 峰值内存 |
|------|-------|-------------------------|---------|---------|
| 小 | 5.0 | 4096 | 1.19 核 | 0.26 GiB |
| **大** | 5.0 | **100000** | **3.82 核** | 0.65 GiB |
| 小 | 98.7 | 4096 | 35.17 核 | 2.46 GiB |
| **大** | 98.8 | **100000** | **46.50 核** | 3.41 GiB |

低吞吐下把它从 4096 提到 100000，**CPU 涨 3 倍**。上游文档明说「a large prefix limit ... can increase EPP CPU utilization by over 100%」。

**该怎么设**：按你的真实系统提示长度设，别照抄 100000。agentic 场景（95k 系统提示）需要它；聊天场景（几百 token 提示）设 4096 就够，白省 30% CPU。

### 1.3 调优决策表

| 症状 | 指标依据 | 改什么 |
|------|---------|--------|
| 前缀命中率低 | `request_cached_tokens` 低 | 提高 `prefix-cache-scorer` 权重；检查前缀是否够长（04 篇 §9）；提高 `maxPrefixTokensToMatch` |
| 负载不均 | `std_dev_queue_size` 大 | 降低 prefix 权重；提高 `queue-scorer` 权重 |
| 尖峰时羊群效应 | 短时间内 `per_endpoint_queue_size` 某个 pod 暴涨 | 提高 `no-hit-lru-scorer` 权重；换 `weighted-random-picker` |
| EPP CPU 打满 | `plugin_duration_seconds` 里 prefix scorer 占大头 | **降低 `maxPrefixTokensToMatch`** |
| TTFT 抖动 | — | 上 P/D 分离（§2） |

**权重调整的本质是在 Affinity 与 Distribution 之间移动**（02 篇 §1.2 的 `ScorerCategory`）。两边不可能同时最优：前缀亲和让相同前缀集中，负载分散让请求摊平。

## 2. 配方二：P/D 分离

### 2.1 完整配置

```yaml
# deploy/config/pd-epp-config.yaml（全文 37 行）
# Sample EPP configuration for running with P/D
apiVersion: llm-d.ai/v1alpha1
kind: EndpointPickerConfig
plugins:
- type: approx-prefix-cache-producer
  parameters:
    maxPrefixTokensToMatch: 16384
    lruCapacityPerServer: 31250
- type: prefix-cache-scorer
- type: queue-scorer
- type: prefill-filter
- type: decode-filter
- type: max-score-picker
- type: disagg-profile-handler
  parameters:
    deciders:
      prefill: prefix-based-pd-decider
- type: prefix-based-pd-decider
  parameters:
    nonCachedTokens: 16
schedulingProfiles:
- name: prefill
  plugins:
  - pluginRef: prefill-filter
  - pluginRef: max-score-picker
  - pluginRef: prefix-cache-scorer
    weight: 2
  - pluginRef: queue-scorer
    weight: 1
- name: decode
  plugins:
  - pluginRef: decode-filter
  - pluginRef: max-score-picker
  - pluginRef: prefix-cache-scorer
    weight: 2
  - pluginRef: queue-scorer
    weight: 1
```

### 2.2 与配方一的四个差异

**① 两个 profile，各带自己的 Filter**

```
prefill profile: prefill-filter → 只在 role=prefill 的 pod 里选
decode  profile: decode-filter  → 只在 role=decode  的 pod 里选
```

这两个 filter 读的是 pod label `llm-d.ai/role`（00 篇 §8）。**label 打错 = 对应 profile 的候选集为空 = 429**（01 篇 §3.1）。

**② `disagg-profile-handler` 取代自动注入的 `single-profile-handler`**

多 profile 必须显式配，用 `single-profile-handler` 会启动失败（02 篇 §6.3）。

**③ 同一个 scorer 实例在两个 profile 里各用一次**

`prefix-cache-scorer` 只声明了一次，但被两个 profile 的 `pluginRef` 各引用一次。**是同一个实例，被两条链各调一次**（02 篇 §6.2）。

**④ `prefix-based-pd-decider` 决定要不要真分离**

```yaml
- type: prefix-based-pd-decider
  parameters:
    nonCachedTokens: 16
```

未命中的 token 数 **> 16** 才走 prefill 分离，否则直接 decode（06 篇 §2 的分支 ④）。

**16 这个值是个很激进的默认**：prompt 里只有 17 个 token 没命中就要分离。它意味着「几乎所有请求都分离」，除了完全命中缓存的重复请求。如果你的 P/D 分离网络开销大（跨节点、无 RDMA），应该调高——比如 512，让短请求走本地 decode。

### 2.3 权重差异：2:1 vs 配方一的 3:2:2:2

P/D 配方的权重更简单（prefix 2、queue 1），而且**没有 `kv-cache-utilization-scorer` 和 `no-hit-lru-scorer`**。

为什么：P/D 分离本身已经把 prefill 的负载从 decode pod 上摘走了，decode pod 的 KV 压力模式完全不同。这个配置是个**保守起点**，真实部署应该按 §1.3 的表继续调。

### 2.4 K8s 侧的配套

```
prefill Deployment: label llm-d.ai/role=prefill    只有 vLLM（8100）
decode  Deployment: label llm-d.ai/role=decode     sidecar（8000）+ vLLM（8200）
InferencePool selector 要同时覆盖两组 pod
InferencePool targetPort 指向 decode 的 sidecar 端口（8000）
```

**这是 P/D 部署最容易配错的地方**（06 篇 §1.1）。EPP 选出的 prefill 地址是 prefill pod 的 **vLLM 端口**（sidecar 直接打过去），而 decode 地址是 **sidecar 端口**（Envoy 打过去）。两者端口语义不同。

`deploy/environments/dev/` 下有现成的 kustomize overlay：`p-d/`、`e-p-d/`、`epd/`、`coordinator-epd/`。

## 3. 配方三：精确前缀缓存

### 3.1 完整配置

```yaml
# deploy/config/epp-precise-prefix-cache-config.yaml（全文 47 行）
# Sample EPP config: split precise-prefix-cache pipeline
#   token-producer -> precise-prefix-cache-producer -> prefix-cache-scorer
apiVersion: llm-d.ai/v1alpha1
kind: EndpointPickerConfig
plugins:
  - type: token-producer
    parameters:
      modelName: hf-repo/model-name           # set to the model used in the vLLM deployment
      vllm:
        url: http://localhost:8000
  - type: endpoint-notification-source
  - type: metrics-data-source
  - type: core-metrics-extractor
  - type: single-profile-handler
  - type: decode-filter
  - type: precise-prefix-cache-producer
    parameters:
      tokenProcessorConfig:
        blockSizeTokens: 64
      indexerConfig:
        kvBlockIndexConfig:
          enableMetrics: true       # enable kv-block index metrics (prometheus)
  - type: prefix-cache-scorer
    parameters:
      prefixMatchInfoProducerName: precise-prefix-cache-producer
  - type: kv-cache-utilization-scorer
  - type: queue-scorer
  - type: max-score-picker
dataLayer:
  sources:
    - pluginRef: metrics-data-source
      extractors:
        - pluginRef: core-metrics-extractor
    - pluginRef: endpoint-notification-source
      extractors:
        - pluginRef: precise-prefix-cache-producer
schedulingProfiles:
  - name: default
    plugins:
      - pluginRef: decode-filter
      - pluginRef: prefix-cache-scorer
        weight: 2.0
      - pluginRef: kv-cache-utilization-scorer
        weight: 1.0
      - pluginRef: queue-scorer
        weight: 1.0
      - pluginRef: max-score-picker
```

### 3.2 五个关键点

**① `prefixMatchInfoProducerName` —— 04 篇 §5.3 那个最重要的坑**

```yaml
  - type: prefix-cache-scorer
    parameters:
      prefixMatchInfoProducerName: precise-prefix-cache-producer
```

**漏了这一行，你以为在用精确索引，实际框架自动补了个近似的，没有任何报错。** 这里的值是 producer 的**实例名**——因为配置没写 `name:`，实例名默认等于 `type`（02 篇 §6.1）。

**② `dataLayer` 段必须显式写**

```yaml
dataLayer:
  sources:
    - pluginRef: endpoint-notification-source
      extractors:
        - pluginRef: precise-prefix-cache-producer
```

`precise-prefix-cache-producer` 同时是 DataProducer **和** EndpointExtractor：它需要感知 endpoint 上下线来管理 ZMQ 订阅（04 篇 §1.5）。这个 wiring 不会自动建，必须手写。

**漏了这一段的后果**：producer 存在、scorer 绑定正确，但**从来没有订阅任何 pod**，索引永远是空的。命中率恒为 0，没有报错。

**③ 显式配了 `metrics-data-source` + `core-metrics-extractor`**

配方一里这两个是自动注入的。这里因为要手写 `dataLayer` 段，就得把它们一起写全——**否则自动注入逻辑会认为「用户已经配了 dataLayer，不需要我插手」**（`ensureDataLayer`，02 篇 §4.1）。这是个容易漏的连带影响。

**④ `blockSizeTokens: 64` 与 `token-producer` 的 model name**

```yaml
  - type: token-producer
    parameters:
      modelName: hf-repo/model-name           # ← 必须改成真实模型名
      vllm:
        url: http://localhost:8000
```

`modelName` 必须与 vLLM 部署的模型一致——它参与 `getInitHash(modelName)`（04 篇 §4.3）。**配错了 hash 全不匹配，命中率 0。**

`vllm.url` 指向一个 vLLM 实例做分词。注意这是 EPP 容器视角的地址，`localhost:8000` 只在 EPP 与 vLLM 同 pod 时才对——独立部署的 EPP 要改成 Service 地址。

**⑤ 配置里没有的东西：`replaySocketPort`**

这个示例没配 replay 端口，意味着 **EPP 重启后索引全空、只能慢慢重建**（04 篇 §7.3）。生产要加：

```yaml
      kvEventsConfig:
        podDiscoveryConfig:
          socketPort: 5557
          replaySocketPort: 5558
```

且 vLLM 侧要真的开了那个 ROUTER socket。

### 3.3 vLLM 侧的必要配置

EPP 配好只是一半，vLLM 必须发 KV 事件：

```bash
# vLLM 启动参数（示意，具体见 vLLM 版本文档）
--kv-events-config '{"enable_kv_cache_events": true, "publisher": "zmq", "endpoint": "tcp://*:5557"}'
```

**验证方法**（不要靠猜）：

```bash
# ① vLLM 在监听 ZMQ 端口吗
kubectl exec -it <vllm-pod> -- ss -ltnp | grep 5557

# ② EPP 的索引有没有内容（需 enableMetrics: true）
kubectl exec deploy/epp -- curl -s localhost:9090/metrics | grep -i kv_block

# ③ 最终效果
kubectl exec deploy/epp -- curl -s localhost:9090/metrics | grep request_cached_tokens
```

### 3.4 多 EPP 副本必须用 Redis

03 篇 §8.5 与 04 篇 §3.3 都提过。上游 `docs/operations.md` 的原话：

> **Active-Active mode should be avoided when using approximate prefix routing.** Because EPP replicas do not share prefix state, each replica only has visibility into the prefix state of the requests it has individually handled. This partition of state significantly degrades prefix cache hit rates.

Active-Active + 精确索引 + Redis 后端是唯一能同时要 HA 和前缀命中的组合。而且所有副本的 `hashSeed` 与 `hashAlgorithm` 必须一致（04 篇 §4.3）。

**双 CRD 组共存时的行为**（01 篇没提到的一个坑）：

```go
// pkg/epp/server/controller_config.go:78, 85（节选）
// EPP will prefer the new group and IGNORE legacy resources.
```

同时存在新旧两组 `InferenceObjective` CRD 时，EPP **只读新的、完全忽略旧的**。升级期间如果只改了旧组的对象，priority 配置会静默不生效。

## 5. 资源 sizing

数据全部来自上游 `docs/operations.md`（对 `0.9.0` 镜像 + llm-d-simulator 模拟 Qwen3-8B 压测）。

### 5.1 EPP

**CPU**：

| 规则 | 数值 |
|------|------|
| 经验法则 | **每 1 req/s 分配 0.5~1.0 核**（agentic 负载，约 100k 输入 / 1k 输出） |
| 缩放行为 | 与请求速率线性；随输入 prompt 与输出长度增长 |
| **空闲 CPU** | **随 model pod 数量线性增长**。100 个 pod ≈ **7.5 核空闲** |

**「空闲 7.5 核」这条最容易被低估**。原因是 03 篇 §2.1：每个 endpoint 一个 goroutine、每 50ms 抓一次。100 个 pod = 每秒 2000 次 HTTP 抓取。**pod 多的集群，EPP 的 request 必须按 pod 数而不是按 QPS 来算。**

**内存**：

| 场景 | 内存 |
|------|------|
| 50~100 req/s、1k 输出 token | **4~6 GiB** |
| 同速率、5k 输出 token | **20+ GiB** |
| 开了 Flow Control | 额外 = 各 band `maxBytes` 之和（默认每 band **1G**） |

内存随**并发在途请求数 × 输出长度**增长——因为每个在途请求的状态都留在 EPP 里。

Flow Control 的内存部分（`operations.md` 原文要点）：

- 排队请求**连请求体一起**缓存在 EPP 内存里
- 每 band 上限 = `priorityBands[].maxRequests`（默认 5000）+ `maxBytes`（默认 1G）
- `defaultPriorityBand` 是没列出的 band 的模板
- **全局 `flowControl.maxRequests`/`maxBytes` 默认无限制**——必须显式设一个低于容器 limit 的值
- 原文警告：按 per-band 默认值，**几个 band 就能超过上面的 sizing 建议，而 band 级上限还没触发**
- `noEndpointRequestTTL` 设得长（为 cold start 留时间）会让请求体在整个 TTL 内占内存

**实践结论**：开 Flow Control 就必须设全局 `maxBytes`，否则内存上限完全由 band 数决定，不可控。

## 6. HA 模式

### 6.1 三种模式

| 模式 | 谁服务 ext-proc | 吞吐缩放 |
|------|----------------|---------|
| **Active-Active** | 所有副本 | **近线性**（见下表） |
| **Active-Passive + Priority Routing** | 单个 primary，Envoy 优先级路由 | 不缩放 |
| **Active-Passive + Leader Election** | leader（K8s Lease） | 不缩放 |

Active-Active 的实测缩放因子：

| 副本数 | 缩放因子 |
|--------|---------|
| 1 | 1.0x |
| 2 | 2.0x |
| 3 | 2.7x |
| 4 | 3.5x |

### 6.2 Active-Active 的两个状态分区问题

**① 前缀路由（上游明确警告）**

> Active-Active mode should be **avoided** when using approximate prefix routing.

每个副本只看得到自己处理过的请求的前缀状态。**必须用精确索引 + Redis**（§3.4）。

**② Flow Control（上游明确说明）**

> Flow control state (queues, fairness accounting, and the saturation view) is **per replica and not shared**. In Active-Active mode, priority and fairness are enforced only within each replica's share of the traffic, and per-band capacity limits apply **per replica**, so the fleet-wide queued volume scales with the replica count.

三个推论：

1. **公平性只在副本内部生效**。4 个副本 = 4 套独立的公平性账本，跨副本的租户公平无从谈起。
2. **容量上限乘以副本数**。配 `maxBytes: 1G`、4 副本 = 全集群实际能排 4G。sizing 时要乘。
3. **饱和度视图各自独立**。同一时刻不同副本可能对「后端有多忙」有不同判断。

相关的上游 issue：[#1290](https://github.com/llm-d/llm-d-router/issues/1290)。

### 6.3 Leader Election 的 fail-open

leader 挂了之后，standby 抢到 lease 之前的这段时间，**Envoy 进入 fail-open 模式，直接把流量打到 model server**（绕过 EPP）。

含义：**短时间内失去所有智能路由**（前缀、负载均衡、P/D），但不中断服务。这是个正确的取舍——但要知道这段时间的 TTFT 会变差、P/D 分离完全失效。

配套的 feature gate `haPopulateNonLeaderDatastore`（默认 **true**，02 篇 §7.1）让非 leader 也跑 datastore reconciler，这样接管时不需要冷启动同步 pod 列表。

### 6.4 Priority Routing（仅 Standalone service 模式）

`router.proxy.mode: service` + `router.proxy.priorityRouting.enabled: true`：

```
EPP StatefulSet + headless Service（publishNotReadyAddresses: true）
  Priority 0: <release>-epp-0  ← 100% 稳态流量
  Priority 1: <release>-epp-1  ← 热备
Envoy 主动 gRPC 健康检查 EPP 9002 端口
primary 挂 → Outlier Detection 剔除 → 亚秒级切到 Priority 1
```

比 Leader Election 快（不用等 lease 过期），代价是只在 Standalone service 模式可用。

关键调优参数（`operations.md` §4）：

| 参数 | 默认 | 作用 |
|------|------|------|
| `healthCheckInterval` | `10s` | gRPC 健康检查间隔 |
| `healthCheckUnhealthyThreshold` | `3` | 几次失败判不健康 |
| `healthCheckHealthyThreshold` | `2` | **几次成功才恢复流量**（防抖：新 pod 要先同步完 pod 列表） |
| `connectTimeout` | `0.250s` | 检测不可达 |
| `dnsRefreshRate` | `5s` | headless endpoint 的 DNS 刷新 |
| `healthyPanicThreshold` | `10.0` | 防止剔除 primary 时触发 panic routing |

**`preStop` 钩子 `sleep 5`**：计划性删除时给 Envoy 健康检查时间发现 pod 要走，先把新流量切走再发 SIGTERM，配合 EPP 的 `--drain-timeout`（默认 30s，01 篇 §1.3）让在途 gRPC 流走完。

## 7. 排障手册

### 7.1 按错误码定位

| 错误码 | drop reason header | 含义 | 查什么 |
|--------|-------------------|------|--------|
| **503** | `NoEndpoints` | 池子空 / Screener 砍空 | pod Ready 状态、InferencePool selector、`ready_endpoints` 指标 |
| **429** | `Saturated` | 池子忙 / **Filter 砍空** / FC 队列满 | 日志 `Filter eliminated all endpoints`、后端负载、role label |
| **429** | `TTLExpired` | FC 排队超时（池里有 pod） | `pool_saturation`、`stale_endpoints` |
| **503** | `TTLExpired`+`NoEndpoints` | FC 排队超时且池空了 | 扩容 / scale-from-zero 是否工作 |
| **412** | — | `Prefer: if-available` 无插件处理 | 配置缺 PreRequest 门插件 |
| **503** | `ContextCancelled` | 客户端断开 | 客户端超时设置 |
| **503** | `ShuttingDown` | EPP 关停中 | 正常滚动更新的短暂现象 |
| **502** | — | Mooncake bootstrap 失败 | sidecar 日志、prefill pod 是否重启过 |

**429 vs 503 的分界线**（01 篇 §3.1）值得再强调：**503 = 池子空，503 去查 K8s；429 = 池子忙，429 去查负载与 Filter。** 这个区分是代码里刻意维持的。

### 7.4 排障决策树

```
问题：延迟高 / 命中率低 / 报错
│
├─ 有报错？
│   ├─ 503 → pod Ready？selector 对吗？ready_endpoints 指标？
│   ├─ 429 → grep 'Filter eliminated all endpoints' 看是哪个 filter
│   │         → role label 对吗？后端真的满了吗？
│   ├─ 412 → 配置缺 PreRequest 门插件
│   └─ 502 → sidecar 日志（Mooncake bootstrap / prefill 失败）
│
├─ 无报错但慢 / 命中率低
│   ├─ ready_endpoints < pod 数？
│   │   ├─ datalayer_poll_errors_total 涨  → 网络/端口/pod
│   │   └─ datalayer_extract_errors_total 涨 → engine-type label（表 #7 #8）
│   ├─ request_cached_tokens 低 → 前缀路由没生效
│   │   → 走表 #1~#6 逐条排
│   ├─ std_dev_queue_size 大 → 负载不均 → 调 scorer 权重（§1.3）
│   ├─ plugin_duration_seconds 某插件占大头 → 那个插件的参数（通常是 maxPrefixTokensToMatch）
│   └─ P/D 配了但 TTFT 没改善
│       ├─ prefill pod 的 num_requests_running == 0？ → EPP 没选它（role label / decider 阈值）
│       └─ 两边都在跑但没变快？ → 表 #13（vLLM 未启用 KV connector）
│
└─ 开了 Flow Control
    ├─ pool_saturation ≥ 1
    │   ├─ stale_endpoints > 0 → 假饱和（采集故障），回到上面的 ready_endpoints 分支
    │   └─ stale_endpoints = 0 → 真过载 → 扩容 / 调阈值
    └─ requests_total 按 outcome 看
        ├─ RejectedCapacity 多 → band 容量不够
        └─ EvictedTTL 多 → TTL 太短，或后端真处理不完
```

```bash
kubectl exec -it <prefill-pod> -- curl -s localhost:8100/metrics | grep num_requests_running
kubectl logs <decode-pod> -c pd-sidecar | grep -c "missing 'kv_transfer_params'"   # 期望 0

# ⑤ 无静默降级
kubectl logs deploy/epp | grep -cE 'failed to prepare per request data|data_scope_violations'  # 期望 0
```

### 8.5 必配的告警

| 告警 | 表达式思路 | 为什么 |
|------|-----------|--------|
| **`ready_endpoints` < pod 数** | 与 `kube_pod_status_ready` 对比 | 所有指标类问题的总入口 |
| **`flow_control_stale_endpoints` > 0** | 直接 gauge | Flow Control fail-closed 停摆的唯一前兆（05 §6.4） |
| `datalayer_extract_errors_total` 速率 > 0 | `rate()` | engine-type 配错 / 引擎升级改了指标名 |
| `plugin_data_scope_violations_total` 速率 > 0 | `rate()` | 自定义插件的静默失败 |
| `request_cached_tokens` 均值突降 | 与基线对比 | 前缀路由退化（表 #1~#6 任一） |
| `flow_control_pool_saturation` ≥ 1 持续 | 配合上面的 stale 一起看 | 区分真过载与假饱和 |

### 五条必记

1. **503 查 K8s，429 查负载与 Filter**——这个分界线是代码里刻意维持的。
2. **EPP 不是轻量组件**：空闲 CPU 随 pod 数线性增长（100 pod ≈ 7.5 核），内存随输出长度增长（5k 输出 ≈ 20 GiB）。
3. **前缀路由的失败几乎都是静默的**（表 #1~#6）。上线必须用 `request_cached_tokens` 验证，不能只看配置。
4. **Active-Active + 近似前缀 = 前缀缓存基本失效**。要 HA 就用精确 + Redis。
5. **开了 Flow Control 就必须监控 `stale_endpoints`**——它是 fail-closed 全池停摆的唯一前兆。
