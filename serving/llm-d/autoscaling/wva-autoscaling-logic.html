1整体设计范式

WVA 与常规 Operator 最大的不同：Reconciler 不做扩缩容决策，真正的扩缩容跑在独立的定时轮询循环里。

核心事实 VariantAutoscaling 已不再是真正的 CRD（见 internal/variant/types.go 头注释）——它是从带 llm-d.ai/managed: "true" 注解的 HPA / KEDA ScaledObject 在内存中合成的结构体，从不写入 API server。

Reconciler 的职责（不扩缩容）

Reconciler职责
HPAReconciler把带注解的 HPA 所在命名空间加入跟踪列表（NamespaceTrack/Untrack），缩小后续轮询 List 范围
ScaledObjectReconciler同上，针对 KEDA ScaledObject（仅当 KEDA CRD 存在时注册）
InferencePoolReconciler维护 datastore 中的 endpoint pool
ConfigMapReconciler配置更新；已注册 analyzer 的开关可热生效，首次注册 throughput 需重启；QM 配置含 default 会触发拒绝

真正的引擎循环（leader-only）

cmd/main.go 通过 mgr.Add(RunnableFunc(...)) 注册两个引擎循环，由 executor.PollingExecutor 以固定间隔 OptimizationInterval 驱动（wait.UntilWithContext，失败指数退避上限 4s）：

引擎作用
saturation.Engine.StartOptimizeLoop主扩缩容引擎（本文重点）
scalefromzero.Engine.StartOptimizeLoop专门处理 0→1 冷启动

Prometheus 连不上时 main.go 直接 os.Exit(1)——autoscaling 强依赖 metrics，属于合理 fail-fast。

2一次 tick 的完整触发链路

每个轮询周期 Engine.optimize 默认走 V2 路径 optimizeV2，分四阶段：

TIMER
定时器 tick（间隔 = OptimizationInterval）
↓
阶段 1 · COLLECT
采集 Prometheus 指标：KV cache 用量、队列长度、生成/请求速率、平均 I/O token、调度器队列
↓
阶段 2a · ANALYZE
Analyzer(saturation_v2) 把物理指标转成 token 单位的 供给 / 需求
↓
阶段 2b · THRESHOLD
applyUniversalThreshold 用 0.85 / 0.70 双阈值算出 RequiredCapacity(扩) / SpareCapacity(缩) ← 触发判定核心
↓
阶段 3 · OPTIMIZE
Optimizer 通过 bindingAnchor 选择容量来源，votingResults 过滤投票者；将各自容量缺口 ÷ 各自每副本容量，组合成目标副本数
↓
阶段 4 · ACTUATE
applySaturationDecisions 写 Status + 暴露 wva_desired_replicas 指标
↓
EXTERNAL
HPA / KEDA 读取指标，实际修改 Deployment 的 replicas
记忆点 Analyzer 只算 token 供需 → 引擎用双阈值把供需转成"缺口/富余 token" → Optimizer 把 token 缺口除以每副本容量得到副本增量 → WVA 只发指标，HPA/KEDA 实际改副本。

3阶段一：Analyzer 计算供给与需求

位置 internal/engines/analyzers/saturation_v2/analyzer.go。把"物理指标"转成"token 单位的供需信号"。

3.1 每副本容量 = min(k1, k2)

k1 · 内存受限 
k1 = TotalKvCapacityTokens
        × KvCacheThreshold

KV 显存能容纳的 token 上界。

k2 · 计算受限

四级优先级链：
P1 观测态 → P2 历史滚动均值 → P3 部署参数推导 → P4 回退 k1。

effectiveCapacity = min(k1, k2)

3.2 每副本需求（偏保守，倾向扩容）

replicaDemand = TokensInUse + waitingQueueDemand(role)

本地队列请求按 P/D 角色计费：

角色每请求 token 计费理由
PrefillAvgInput只算 prompt KV，输出在别处生成
Decode / BothAvgInput + AvgOutput用完整输出长度做峰值规划，防止 decode 侧欠配触发抢占重算

3.3 调度器队列需求（还没到任何 pod 的排队请求）

inputTokens  = max(QueueBytes / BytesPerToken, QueueSize × AvgInput)
  × (1 − PrefixCacheHitRate)
outputTokens = QueueSize × AvgOutput
queueDemand  = inputTokens + outputTokens

3.4 模型级三个总量（Analyzer 的最终输出）

量含义公式
TotalSupply总供给Σ ReplicaCount × PerReplicaCapacity
TotalDemand总需求Σ replicaDemand + queueDemand
TotalAnticipatedSupply在途供给Σ (ReplicaCount + Pending) × PerReplicaCapacity
把 pending 副本计入供给，防止重复扩容
注意 Analyzer 只产出这三个 token 数字，本身不判断是否扩缩容。

4阶段二：触发判定核心公式

位置 internal/engines/saturation/engine_v2.go 的 applyUniversalThreshold。这是决定扩还是缩的地方。

RequiredCapacity（扩容信号） 
RC = max(0,
   TotalDemand / scaleUpThreshold
   − TotalAnticipatedSupply)

RC > 0 → 扩容

SpareCapacity（缩容信号） 
SC = max(0,
   TotalSupply
   − TotalDemand / scaleDownBoundary)

SC > 0 → 允许缩容

阈值默认值

常量默认值含义
scaleUpThreshold0.85需求超过供给 85% 才扩（要求留 15% headroom）
scaleDownBoundary0.70需求跌破供给 70% 才缩
滞回带 Hysteresis 70% ~ 85% 之间形成滞回区间，系统保持不动，避免临界点反复抖动。引擎还会校验 scaleUpThreshold > scaleDownBoundary，不满足则回退默认值。对 P/D 解耦模型，RC/SC 会按 role（prefill / decode）分别计算。

5阶段三：Optimizer 换算副本数

位置 internal/engines/pipeline/cost_aware_optimizer.go。

优化器选择

条件优化器行为
默认 (enableLimiter=false)CostAwareOptimizer无限模式，忽略 GPU 配额
GPU 受限 (enableLimiter=true)GreedyByScoreOptimizer受 GPU 配额约束；无法获取约束时安全回退 cost-aware

决策分支

if anyRoleNeedsScaleUp(...) {   // 任一 role 的 RC > 0
    allocateForModelPaired(... costGreedyRolePick ...)  // 扩容
} else {
    scaleDownRoleIterated(...)   // 否则尝试缩容（需 SC > 0）
}

token 缺口 → 副本数换算

k = max( floor(deltaUtil × RC / PerReplicaCapacity),  min(1, n) )
扩容 选成本效率最高（cost / PerReplicaCapacity 最小）的变体加副本；受 MaxReplicas headroom 约束；跳过有 pending 的变体。缺口 >0 时保底至少 +1。
缩容 要求 Enabled 投票集中所有 live analyzer 的 SC > 0 且至少有一个 live 才放行（保守）；从最贵变体开始减；受 MinReplicas 约束；保护最便宜变体至少 1 副本。不做保底 +1，富余不足一个副本时不缩。

产出 VariantDecision，Action ∈ { ScaleUp, ScaleDown, NoChange }，由 target vs CurrentReplicas 比较得出。

6阶段四：决策下发（两条路径）

路径 A · 常规扩缩容（间接，主路径）
  1. 写入内存 VA 的 Status.DesiredOptimizedAlloc.NumReplicas
  2. Actuator.EmitMetrics 暴露 gauge wva_desired_replicas
  3. HPA / KEDA 读取该 External Metric，自己改 Deployment replicas

WVA 本身不直接改 Deployment；即使 NoChange 也照常 emit，保持 HPA 存活。

路径 B · Scale-from-zero（直接，0→1）

scalefromzero.Engine 独立轮询，监测 inference_extension_flow_control_queue_size。有 pending 请求时，通过 DirectActuator 用 client-go/scale 直接改 scale 子资源 0→1。

因为 HPA 在 0 副本时无 metrics、无法自行拉起。

7公式字段完整字典

按数据流从底层原始指标到顶层决策信号，分六组逐字段说明：含义 · 单位 · 来源 · 在公式中的作用。

第 1 组 · Prometheus 原始/派生指标（ReplicaMetrics，每副本一份）

字段含义单位来源
KvCacheUsageKV cache 占用率0.0–1.0 比例vllm:kv_cache_usage_perc
NumGpuBlocksGPU 上分配的 KV block 总数个cache_config_info label（引擎启动 profiling）
BlockSize每个 KV block 容纳的 token 数token/blockcache_config_info label
TotalKvCapacityTokensKV cache 总容量token采集器算= NumGpuBlocks × BlockSize（SGLang 直读 max_total_num_tokens）
TokensInUse已驻留 KV 的 token 数（已消耗需求）token派生 = KvCacheUsage × TotalKvCapacityTokens
QueueLength本地引擎等待队列请求数个vllm:num_requests_waiting
AvgInputTokens (I)每请求平均输入 tokentoken/请求rate(prompt_tokens_sum)/rate(count)
AvgOutputTokens (O)每请求平均输出 tokentoken/请求rate(generation_tokens_sum)/rate(count)
PrefixCacheHitRate前缀缓存命中率0.0–1.0引擎前缀缓存指标
Cost每副本成本无量纲（默认 10）VA spec / 注解

公式里I = AvgInputTokens，O = AvgOutputTokens，是需求估算的两个核心画像参数。

第 2 组 · 副本状态（VariantReplicaState，从 scale target 读）

字段含义单位作用
CurrentReplicas当前副本数个与 target 比较判定 Action
PendingReplicas已创建但未 ready 的副本数（Current−Ready）个计入"在途供给"，防级联扩容
GPUsPerReplica每副本 GPU 数张GPU 配额约束换算
RoleP/D 解耦角色（prefill/decode/both）枚举决定队列计费方式、按角色独立扩缩
MinReplicas副本下界（nil→0，可缩到 0）个缩容下限约束
MaxReplicas副本上界（nil→0，无上限）个扩容 headroom 约束

第 3 组 · 容量计算字段（Analyzer 内部）

字段/符号含义单位公式 / 说明
KvCacheThresholdKV 容量安全水位0.0–1.0配置，默认 0.80，只用总容量这个比例
k1内存受限容量tokenTotalKvCapacityTokens × KvCacheThreshold
k2计算受限容量token四级优先级链推导（算力吞吐上界）
effectiveCapacity每副本有效容量tokenmin(k1, k2)，短板决定实际容量
PerReplicaCapacity变体级每副本代表容量tokenmedian(各存活实例 effectiveCapacity)，优化器换算的分母

k2 推导公式（P3 档，estimateCapacityFromParams）：

N_steady = min( B × O / (I + O),  S )
k2       = N_steady × ( I + O/2 )
符号含义单位来源
B = EffectiveMaxBatchedTokens每步 batch 的 token 预算token--max-num-batched-tokens（默认 V1=8192/V0=2048）
S = MaxNumSeqs最大并发序列数个--max-num-seqs（默认 256）
I / O平均输入 / 输出长度token实时指标
N_steady稳态可并发请求数个中间量，受并发上限 S 截断

I + O/2 是"稳态平均 KV 占用"（请求从 0 增长到 O，均值取 O/2，加固定的 I）。

第 4 组 · 需求估算字段

本地队列需求 waitingQueueDemand：

queueDemand_local = QueueLength × { I        (Prefill)
                                    I + O    (Decode / Both) }
符号含义为什么这样算
QueueLength本地队列请求数每个排队请求都会占用容量
I（Prefill）只算输入prefill 只材料化 prompt KV，输出在别处生成
I+O（Decode/Both）输入+完整输出用峰值（终态 KV 占用）做规划，防欠配

调度器队列需求 estimateSchedulerQueueDemand（还没到任何 pod 的请求）：

inputTokens  = max( QueueBytes / BytesPerToken,  QueueSize × I ) × (1 − HitRate)
outputTokens = QueueSize × O
queueDemand  = inputTokens + outputTokens
符号含义单位来源
QueueSize调度器 flow-control 排队请求数个inference_extension_flow_control_queue_size
QueueBytes排队请求体总字节byteinference_extension_flow_control_queue_bytes
BytesPerToken字节→token 换算系数byte/token常量 4
HitRate前缀缓存命中率0.0–1.0命中部分复用已有 KV，从输入需求扣除

取 max(按字节估, 按条数估) 是为鲁棒性——两个独立信号取较大者，避免低估。

第 5 组 · 模型级总量与决策信号（喂给判定公式）

字段含义单位公式
TotalSupply总供给tokenΣ_v ReplicaCount_v × PerReplicaCapacity_v
TotalDemand总需求tokenΣ_v replicaDemand_v + queueDemand
TotalAnticipatedSupply在途供给tokenΣ_v (ReplicaCount_v + Pending_v) × PerReplicaCapacity_v
Utilization利用率比例TotalDemand / TotalSupply
关键区别 TotalSupply 只算就绪副本；TotalAnticipatedSupply 额外把 pending 副本也算作供给。扩容公式用在途供给做基准——正在启动的 pod 马上能提供容量，不算进去会重复触发扩容。

触发判定公式的字段

扩容信号 RC 
RC = max(0,
   TotalDemand / scaleUpThreshold
   − TotalAnticipatedSupply)
缩容信号 SC 
SC = max(0,
   TotalSupply
   − TotalDemand / scaleDownBoundary)
字段含义单位值/来源在公式中的作用
RC (RequiredCapacity)扩容缺口token计算结果>0 → 扩容，数值=还差多少 token
SC (SpareCapacity)缩容富余token计算结果>0 → 允许缩容，数值=富余多少 token
scaleUpThreshold扩容水位比例默认 0.85需求÷它=要求达到的供给（留 15% headroom）
scaleDownBoundary缩容水位比例默认 0.70需求÷它=缩容后不能超过的供给下限
为什么是"需求 /阈值" 扩容：TotalDemand / 0.85 = "要让利用率≤85% 所需总供给"，减去在途供给即缺口。
缩容：TotalDemand / 0.70 = "缩容后利用率不超 70% 的最低供给"，当前供给减去它才是可安全砍掉的富余。
0.70 < 0.85 形成滞回带：利用率在 70%~85% 间时 RC=SC=0，系统不动，避免抖动。

第 6 组 · 副本数换算字段（Optimizer）

k = max( floor( ΔUtil × RC / PerReplicaCapacity ),  min(1, n) )
符号含义单位说明
k本轮该变体增加的副本数个最终输出
RC待补容量缺口token上面的扩容信号
PerReplicaCapacity每副本容量token分母：一个副本能补多少 token
ΔUtil (deltaUtil)联合提交的利用率步长比例非 P/D 单角色 ≈1；P/D 取各角色瓶颈最小值，保证配对提交
n本轮理论应加副本数个min(1,n) 是保底：缺口>0 时至少加 1
cost efficiency成本效率cost/tokenCost / PerReplicaCapacity，扩容选最小者（最划算）
扩容 vs 缩容的不对称 扩容有 min(1,n) 保底（缺口不足一副本也补 1，宁可多）；缩容没有保底，富余不足整整一个副本时不缩（宁可留），从最贵变体开始砍。

一图看懂字段流转

[原始指标] KvCacheUsage, NumGpuBlocks×BlockSize, QueueLength, I, O, QueueSize/Bytes
     │
     ├─容量─→ k1 = TotalKvCap × 0.80 ┐
     │        k2 = f(B, S, I, O)     ├→ effectiveCap = min(k1,k2) → PerReplicaCapacity = median(...)
     │                ┘
     ├─需求─→ TokensInUse + QueueLength×(I 或 I+O) + queueDemand → TotalDemand
     │
     └─供给─→ Σ ReplicaCount×PerReplicaCap        → TotalSupply
              Σ (ReplicaCount+Pending)×PerReplicaCap → TotalAnticipatedSupply
     │
     ▼ [阈值后处理 0.85 / 0.70]
   RC = max(0, TotalDemand/0.85 − TotalAnticipatedSupply)   ← 扩
   SC = max(0, TotalSupply − TotalDemand/0.70)              ← 缩
     │
     ▼ [Optimizer]
   k = max(floor(RC / PerReplicaCapacity), min(1,n))  → target = Current ± k
     │
     ▼
   wva_desired_replicas → HPA/KEDA 改replicas

8指标来源（在哪采集）

WVA 不直接 scrape pod，而是统一从 Prometheus 查询（internal/prometheus/ 客户端 + collector/source/prometheus）。所有指标的原始暴露端点可归为三个来源。

采集路径 各组件把指标暴露在自己的 /metrics 端点 → Prometheus（通过 ServiceMonitor/PodMonitor）scrape 汇聚 → WVA 用 PromQL 向 Prometheus 查询，而非直接访问 pod。WVA 只暴露自己产出的指标供 HPA/KEDA 读取。

来源 A · 推理引擎 pod 的 /metrics（vLLM / SGLang）

由每个模型服务 pod 自身暴露，指标名带 vllm: 或 sglang: 前缀，按 pod / instance 粒度。是容量与需求分析的主力数据。查询定义见 collector/registration/saturation.go。

10容量数据来源解析

结论 容量值既不来自数据库，也不来自离线压测报告。它是运行时实时算出来的——主要来自 实时 Prometheus 指标，实时数据缺失时才回退到 Deployment 启动参数的公式推导。全程内存态，无 SQL、无落盘。

k1 · 来自实时指标

vLLM :  TotalKvCapacityTokens = num_gpu_blocks × block_size (从 vllm:cache_config_info 读)
SGLang: TotalKvCapacityTokens = sglang:max_total_num_tokens  (直接暴露)

num_gpu_blocks 是 vLLM 引擎启动时自己 profiling 出来的真实显存容量，通过 metrics 暴露。

k2 · 四级优先级链（越靠前越"实测"）

优先级来源数据性质
P1 观测态队列饱和时把当前 TokensInUse 当 k2实时压力下的真实观测（相当于线上自动压测）
P2 历史P1 观测值的内存滚动平均近期实时观测平滑值
P3 推导Deployment 启动参数 + 实时工作负载配置参数 × 实时流量画像
P4 回退取 k1纯内存约束兜底

P3 推导公式（estimateCapacityFromParams）：

N_steady = min(B × O / (I + O),  S)
k2       = N_steady × (I + O/2)
  B = EffectiveMaxBatchedTokens  (--max-num-batched-tokens，默认 V1=8192 / V0=2048)
  S = MaxNumSeqs         (--max-num-seqs，默认 256)
  I, O = 平均输入/输出 token (实时 Prometheus 指标)

CapacityKnowledgeStore · 内存缓存（非数据库）

CapacityRecord.LearnedFrom 标明每条记录血统：

LearnedFrom来源用途
"live"运行中 pod 的实时指标最权威，优先使用
"deployment"Deployment CLI args 解析0 副本 / 冷启动兜底估算
"annotation"资源注解显式覆盖人工指定值

该 Store 是 thread-safe in-memory cache，进程重启即失效，靠 EvictStale（24h）清理，不持久化。

数据来源优先级链

实时指标 (live: cache_config_info + 观测峰值)
   ↓ 缺失
Deployment CLI 参数推导 (deployment: max-num-batched-tokens 等)
   ↓ 缺失
兼容变体借用 (FindCompatible) / k1 内存上界兜底
候选来源是否命中说明
压测数据半命中（在线，非离线）无离线压测文件；k2 的 P1/P2 相当于用线上真实峰值当压测结果
计算 / SQL 数据不命中代码里无数据库、无 SQL、无持久化；Store 是纯内存 cache
初始配置数据部分命中仅作冷启动兜底：解析 Deployment 的 CLI flag 推导

11设计要点与潜在风险

release-0.9 · 投票与容量来源Enabled 决定投票，Live 标记近期容量信号。saturation 始终提供完整变体身份，但禁用后不能否决缩容；日志仍出现不代表投票。bindingAnchor 优先绑定可用且投票的 saturation，否则绑定唯一可用的非 saturation analyzer；无有效来源则保持副本。
release-0.9 · T-sfzthroughput 可复用此前测得的零副本变体容量，reason 为 T-sfz。没有历史容量时 PRC 不会被伪造；真正冷启动仍依赖独立 scale-from-zero 引擎。历史状态不跨进程保留。
1 · 需求侧系统性偏向扩容 队列请求按完整 I+O 峰值计费；kv_cache_usage 与 num_requests_waiting 都取 1 分钟 max_over_time（两峰值不必同时发生，求和可能高估瞬时需求）。有意为之——宁可多一副本，也不愿欠配触发抢占重算。生产中表现为偏激进扩容。
2 · DP 换算时序偏差 扩容瞬间新实例先上报 metrics 而 scale-target status 尚未 ready，len(replicas)/readyCount 比值被抬高，导致 pending 折算过量、RC 被低估（代码有 TODO 标注）。
3 · fallback 单位不一致 模型服务不吐 cache_config_info 时，EffectiveCapacity 是 per-step token 预算，而队列 demand 是绝对 KV token，深队列可能误报饱和。已单独 tracked。
4 · leader-only + fail-fast 多引擎循环靠 controller-runtime leader election 保证单点决策；Prometheus 不可达时直接退出。
