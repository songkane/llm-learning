## 1. 打分公式：overlap 不是加分，是减免工作量

这是本篇最核心的一段。

### 1.1 源码

`lib/kv-router/src/scheduling/selector/default.rs`，`DefaultWorkerScorer::worker_logit`：

```307:347:lib/kv-router/src/scheduling/selector/default.rs
        let effective_overlap_score_credit = weights.overlap_score_credit * overlap_credit_decay;
        let overlap_credit_blocks = effective_overlap_score_credit * device_overlap_blocks
            + kv_router_config.host_cache_hit_weight * cache.host_overlap_blocks
            + kv_router_config.disk_cache_hit_weight * cache.disk_overlap_blocks
            + shared_overlap_blocks;
        let decode_cost_blocks = load.decode_cost_blocks;
        let active_request_cost_blocks =
            kv_router_config.decode_active_request_weight * load.active_requests as f64;
        // ...（decode 分支见 §1.4）
        let adjusted_prefill_blocks = (load.raw_prefill_blocks - overlap_credit_blocks).max(0.0);
        let prefill_cost_blocks = weights.prefill_load_scale * adjusted_prefill_blocks;
        let logit = prefill_cost_blocks + decode_cost_blocks + active_request_cost_blocks;
```

写成公式：

\[
\text{cost} = \underbrace{s_p \cdot \max(0,\ B_{\text{prefill}} - C_{\text{overlap}})}_{\text{还得算多少 prefill}} + \underbrace{B_{\text{decode}}}_{\text{decode 积压}} + \underbrace{w_a \cdot N_{\text{active}}}_{\text{在途请求惩罚}}
\]

\[
C_{\text{overlap}} = c \cdot d \cdot B_{\text{device}} + 0.75 \cdot B_{\text{host}} + 0.25 \cdot B_{\text{disk}} + m \cdot B_{\text{shared}}
\]

**cost 越低越好**（temperature=0 时取 min）。

### 1.2 为什么这个式子是对的

关键在 `max(0, B_prefill − C_overlap)` 这个减法。

一种常见的打分写法是加权求和——`score = w1 · overlap + w2 · (1 − load) + ...`，各项无量纲，权重靠调。**Dynamo 不这么做**：它让所有项的单位都是 **block 数**，overlap 直接从 prefill 工作量里**减掉**。

这在物理上更站得住：命中 N 个前缀块，意味着这 N 块的 prefill **根本不用算**。它不是「让这个 worker 显得更好一点」的加分，而是「这个 worker 的实际工作量就是少了 N 块」。于是整个 cost 有了明确的物理含义——**这个 worker 要为这个请求额外付出多少 block 的计算**。

这带来两个实际后果：

1. **权重不需要靠玄学调**。`overlap_score_credit` 默认 1.0，因为一块命中就是一块不用算，1:1 换算本来就是正确的基线。
2. **`max(0, ...)` 的截断有明确语义**：全命中就是零 prefill 成本，再多的命中也不会让 cost 变负数去挤兑 decode 项。

### 1.3 分层缓存的折价

注意 `C_overlap` 里三个层次的权重不同：

| 命中在哪 | 权重 | 默认值 |
|---|---|---|
| device（GPU 显存） | `overlap_score_credit` | **1.0** |
| host（CPU 内存，KVBM 的 G2） | `host_cache_hit_weight` | **0.75** |
| disk（SSD，G3） | `disk_cache_hit_weight` | **0.25** |

**这就是 Router 和 KVBM 的接缝**：路由器知道 KV 不只在显存里，也知道从 SSD 捞回来只值显存命中的四分之一价值。04 篇讲 KVBM 时会回到这个折价系数——它本质是在编码「各层的回填延迟差」。

### 1.4 负载越高，命中越不值钱

```291:306:lib/kv-router/src/scheduling/selector/default.rs
        // Normalize backlog above the least-loaded eligible worker by this request's
        // size. The rational decay softly trades cache locality for prefill balance,
        // while leaving workers at the load floor with their full device credit.
        let overlap_credit_decay =
            if context.track_prefill_tokens && weights.overlap_score_credit_decay > 0.0 {
                let excess_active_prefill_blocks = load
                    .active_prefill_tokens
                    .saturating_sub(default_context.min_active_prefill_tokens)
                    as f64
                    / context.block_size as f64;
                let normalized_prefill_load =
                    excess_active_prefill_blocks / context.request_blocks as f64;
                1.0 / (1.0 + weights.overlap_score_credit_decay * normalized_prefill_load)
            } else {
                1.0
            };
```

\[
d = \frac{1}{1 + k \cdot \frac{B_{\text{excess}}}{B_{\text{request}}}}
\]

**【逻辑】** 这是在解 KV 亲和路由的经典病：**热点前缀会把所有请求吸到同一个 worker 上**。命中率高 → 都往那发 → 那台过载 → 命中率再高。这个衰减项让「命中信用」随排队积压双曲下降。

三个设计细节值得注意：

- 分子用的是 `excess`——**超出当前最闲 worker 的那部分积压**，不是绝对积压。所以全场都忙的时候不衰减，只有出现明显不均才衰减。
- 分母用 `request_blocks` 归一化——**衰减对小请求更敏感**。一个大请求本来就要算很久，多排一会儿无所谓；小请求排在长队后面则代价相对巨大。
- 默认 `overlap_score_credit_decay = 0.0`，即**默认关闭**。这是个要按负载特征打开的调节旋钮。

### 1.5 decode 池的特殊分支

```316:329:lib/kv-router/src/scheduling/selector/default.rs
        // Decode routers normally force `overlap_score_credit=0` through the
        // per-request override, which preserves load-only disagg routing. When
        // conditional disagg leaves a positive overlap credit in place, prefer
        // cache-hot decode workers while still charging decode backlog.
        if self.worker_type == "decode"
            && !context.track_prefill_tokens
            && weights.overlap_score_credit > 0.0
        {
            // Clamp at zero because downstream taint multipliers assume non-negative scores.
            // This loses ordering between workers whose overlap fully offsets decode load, but
            // avoids inverting taint preference among negative-score workers.
            let overlap_adjusted_decode_blocks =
                (decode_cost_blocks - overlap_credit_blocks).max(0.0);
            let logit = overlap_adjusted_decode_blocks + active_request_cost_blocks;
```

**【逻辑】** P/D 分离时，decode 侧默认 `overlap_score_credit = 0`——**纯按负载选**。理由很直白：KV 反正要从 prefill worker 搬过来，decode 侧的本地缓存命中没意义。

但 conditional disagg（§4）会让一部分请求根本不走 remote prefill，这时 decode worker 的本地缓存又有意义了。这个分支就是为那种情况准备的：保留 overlap 信用，但从 **decode** 成本里减而不是从 prefill 里减。

### 1.6 全部可调权重

`lib/kv-router/src/scheduling/config.rs:951~997`（`KvRouterConfig::default`，各默认值的常量函数在 `:23~104`）：

| 参数 | 默认 | 含义 |
|---|---|---|

| `overlap_score_credit_decay` | **0.0** | 负载衰减强度（默认关） |
| `prefill_load_scale` | 1.0 | prefill 项缩放 |
| `decode_active_request_weight` | **0.0** | 在途请求惩罚（默认关） |
| `host_cache_hit_weight` | 0.75 | CPU 层命中折价 |
| `disk_cache_hit_weight` | 0.25 | SSD 层命中折价 |

单请求可以覆盖这些权重：`RouterConfigOverride`（`default.rs:198`）。

## 2. 前缀索引：压缩 radix 树

### 2.1 四种实现

`lib/kv-router/src/indexer/`（算法内核里最大的一块）：

| 实现 | 文件 | 用途 |
|---|---|---|
| `RadixTree` | `radix_tree.rs` | 单线程基准 |
| `ConcurrentRadixTree` | `concurrent_radix_tree.rs` | 并发版 |
| **`ConcurrentRadixTreeCompressed`** | `concurrent_radix_tree_compressed/` | **生产默认**（配 `ThreadPoolIndexer`） |
| `PositionalIndexer` | `positional.rs` | NestedMap，需要可复现的 seq hash |
| `approximate_lru` | `approximate_lru.rs` | 预测模式下的容量上界 LRU |

节点结构：

```19:52:lib/kv-router/src/indexer/radix_tree.rs
pub(crate) struct RadixBlock {
    state: NodeState,
    children: FxHashMap<LocalBlockHash, SharedRadixBlock>,
    internal: bool,
}
pub struct RadixTree {
    root: SharedRadixBlock,
    lookup: FxHashMap<WorkerWithDpRank, WorkerLookup>,
}
```

**【逻辑】** 边键是 `LocalBlockHash`，不是 token。树里存的是「**哪些 worker 持有这条前缀路径**」，`lookup` 是反向索引，用于 worker 下线时批量摘除。

注意 `WorkerWithDpRank`——**索引粒度到 DP rank，不是到 worker 进程**。数据并行部署下同一个进程里的不同 DP rank 有各自独立的 KV cache，混在一起会算错。

### 2.2 两种 hash

```29:31:lib/kv-router/src/protocols.rs
pub fn compute_block_hash(data: &[u8]) -> LocalBlockHash {
    LocalBlockHash(compute_hash_v2(data, XXH3_SEED))
}
```

- **`LocalBlockHash`**：XXH3，只 hash 这一块的内容，作 radix 树的边键。
- **序列 hash 链**：`seq_hash[i] = hash(seq_hash[i-1], local_hash[i])`（`protocols.rs:214` 起的 `compute_seq_hash_for_block`），用于淘汰查找和跨层标识。

这个「局部 hash 作边、累积 hash 作身份」的双 hash 设计，和 vLLM 的 block hash 链是同一思路（见 [vLLM PagedAttention 篇](../../inference-engine/vllm/)）。LoRA 场景下会做 seed 变异并把 adapter 名混进去，避免不同 adapter 的同 token 前缀互相串味。

块大小 `block_size` 由 `--kv-cache-block-size` / `--router-block-size` 配置，常见 16 或 64，**必须与引擎侧一致**，否则索引对不上。

> `lib/kv-hashing/` 是另一套正在推进的统一 hash 方向（`Request → UniversalBlock/PLH`，XXH3 + salt + 多模态）。radix 树目前仍以 `LocalBlockHash` 为边键，两者并存。KVBM 那边（04 篇）已经在用 `PositionalLineageHash` 了。

## 3. 有 KV 事件 vs 没有：两套维护索引的办法

Router 要知道「D3 上现在有哪些 KV 块」。有两条完全不同的路子。

### 3.1 事件驱动（默认，`--router-kv-events`）

引擎每次存/删 KV 块都发事件出来：

```
vLLM / SGLang / TRT-LLM 引擎
   │  ZMQ（msgpack）
   ▼
publisher/zmq_listener.rs          收
publisher/event_processor.rs       转成 RouterEvent
   ▼
Indexer.store / remove             更新 radix 树
```

入口在 `lib/llm/src/kv_router/publisher/mod.rs:67`，wire 格式在 `lib/kv-router/src/zmq_wire/`（vLLM 和 SGLang 的事件格式不同，这里做适配）。

**这条路的软肋是事件会丢**。所以有一整套 recovery：`lib/llm/src/kv_router/indexer/recovery/` 下的 `subscriber.rs`（订阅监督）、`worker_query*.rs`（向 worker 查快照并 replay）、`recovery_lane.rs`。事件断了就回到 worker 那儿要一份全量状态重建索引。

`components/src/dynamo/kv_state_agent/` 是个可选的集中式 KV 状态托管组件，在 vLLM residency 之类的协议下负责 attachment 与 recovery。

### 3.2 预测式（`--no-router-kv-events`）

不要引擎事件，**Router 自己记账**：

```227:276:lib/llm/src/kv_router/indexer/mod.rs
（use_kv_events == false 时）
  primary indexer 切换为 approximate 模式
  primary_records_routing_decisions: true
```

逻辑很朴素：**我把请求 R 发给了 D3，那 D3 接下来就会有 R 的这些块**。于是每次路由决策后自己往索引里写一笔（`kv_router.rs:1092` `record_routing_decision` → `indexer.process_routing_decision_for_request`）。

因为没人告诉它什么时候块被淘汰了，就得自己猜什么时候作废：

| 淘汰策略 | 实现 | 默认 |
|---|---|---|
| TTL | `indexer/pruning.rs:54`（100ms 分桶） | `router_ttl_secs = 120.0` |
| 容量 LRU（实验） | `indexer/approximate_lru.rs` | 按 worker 的 `total_kv_blocks` 上界 + request lease |

两条路各有短板，而 Dynamo 把它们做成了可叠加的——

### 3.3 混合模式

`use_kv_events = true` **同时**设置 `router_predicted_ttl_secs` 时，会额外起一棵短 TTL 的 side tree（`indexer/side.rs:29`），与主索引**取 max overlap**（`indexer/mod.rs:56` 注释）。

这补的是事件的**延迟**：请求刚发出去、引擎还没来得及发 BlockStored 事件的那几十毫秒里，主索引是不知道的，side tree 靠预测先顶上。**同一个请求的连发（比如 agent 的多轮工具调用）最吃这个**。

### 3.4 顺带澄清两个文件名

- **`active_set.rs`** 不是 KV 状态机，只是 worker 集合的 reconcile 工具（`reconcile_active_workers`）。
- **`lookup_update.rs`** 是 Arc 查找表的增量更新 helper，与预测路由无关。

## 4. P/D 分离下的路由：要不要分离，是每个请求现算的

先分清两个层面：

| 层面 | 决定什么 | 在哪定 |
|---|---|---|
| **部署 / 拓扑级** | 谁是 prefill、谁是 decode | worker 启动时 `--disaggregation-mode` 声明角色，写进 MDC 的 **`WorkerType`** 枚举（`lib/kv-router/src/worker_type.rs:18`：`Prefill` / `Decode` / `Encode` / `Aggregated`），Router 侧按枚举分发（`lib/llm/src/kv_router.rs:310`） |
| **请求级** | 这一条请求要不要走远程 prefill | **conditional disaggregation**，本节主题 |

> ⚠️ **两个已经不存在的旧实现，看外部资料时会撞上**：
> - 「Router 按 component 名是否含 `"prefill"` 判断角色」（`is_prefill_worker`）——1.5 里**已无此函数**，改成了上表的 `WorkerType` 枚举。
> - 「decode worker 的 Python `_should_prefill_locally(...)` 按 `prefill_threshold_tokens` 判断短 prompt 本地 prefill」——1.5 的 `components/src/dynamo/vllm/` 下**已搜不到这个函数和这个参数**。请求级判定整体上移到了 Rust 侧的 Frontend/PrefillRouter，判据也从「prompt 长度」换成了下面的「净新增 token」。
>
> 这两处是 1.4 → 1.5 的实质性重构，不是改名。看到旧写法就说明那份资料的基线是 1.4 或更早。

**conditional disaggregation**：同一个部署里，一部分请求走 P/D 分离，另一部分直接在 decode worker 上聚合跑完，逐请求决定。

`lib/kv-router/src/conditional_disagg.rs`，trait 在第 72 行：


三种策略（阈值常量在 `:16`、`:20`，默认 `conditional_disagg_enabled = false`）：

| 策略 | bypass（跳过 remote prefill，退化成聚合）的条件 |
|---|---|
| `IslBounding` | 净新增 token 数 < 阈值（`DEFAULT_CONDITIONAL_DISAGG_EFF_ISL_THRESHOLD = 2048`）**且** 净新增/prompt < 比例阈值（`..._RATIO_THRESHOLD = 0.7`） |
| `PrefillLoad` | 选中的 prefill worker 正忙 |
| `IslOrLoad` | 上面任一成立 |

```155:166:lib/kv-router/src/conditional_disagg.rs
    async fn should_bypass_remote_prefill(&self, input: ConditionalDisaggDecisionInput) -> bool {
        if !self.enabled { return false; }
        let eff_isl = input.net_new_tokens();
        if eff_isl >= self.eff_isl_threshold { return false; }
        let ratio = eff_isl as f64 / input.prompt_tokens.max(1) as f64;
        ratio < self.eff_isl_ratio_threshold
    }
```

**【逻辑】** 判据是「**净新增** token」而不是 prompt 长度——已经命中缓存的部分不用算，自然也不值得为它跑一趟 P/D 交接。第二个比例条件防的是另一头：prompt 很长但命中率极低时，2048 的绝对阈值可能误判，比例条件把它拦下来。

背后的成本模型很直观：**P/D 交接本身有固定开销**（选 prefill worker、跑一次远程调用、NIXL 建连搬 KV）。短请求的 prefill 计算量还没这个开销大，那就别分离了。

调用点在 `prefill_router/conditional_bypass.rs:39`——只在 decode 侧是 `RouterMode::KV` 且开了 conditional disagg 时才会 preview decode 路由再问策略。这解释了 [01 篇 §5](01-请求的一生-主控制流.md#5-路由决策在最后一环) 里那段「把 decode 的 RoutingHost 反向注入给 PrefillRouter」的代码。

另外还有个 gate（`conditional_disagg.rs:25`）：策略说可以 bypass 了，如果配了 decode busy 阈值，还得 decode 侧确实不忙才真的 bypass。

## 5. 插件化：Filter / Scorer / Picker

`lib/kv-router/src/scheduling/selector/policy.rs`：

三段式的分工是 Filter 筛、Scorer 打分、Picker 定夺。多个 Scorer 的聚合方式是**直接求和、不归一化**：

```450:453:lib/kv-router/src/scheduling/selector/policy.rs
        let mut cost = 0.0;
        for (scorer_index, scorer) in scorers.iter_mut().enumerate() {
            let contribution = scorer.score(context, candidate)?;
            cost += contribution;
```

**但内置默认策略不走这条路**。默认是 §1 那个单一的 `worker_logit`——一个物理量纲一致的 cost 函数。三段式插件是给「你要换算法」准备的逃生口，不是默认实现的组装方式。

> **默认路径是一个统一 cost 函数，插件三段式是可选替换**——这个区别值得记住，因为它决定了你调参时该改哪里。

`required_worker_inputs()` 这个方法很实用——插件声明自己需要哪些 worker 指标，框架据此**只采集用得上的数据**，不做无谓的开销。

### 5.1 注册与示例

- 注册表：`WorkerSelectionPolicyRegistry.register(name, factory)`（`services/selection/policy_registry.rs`）
- 默认镜像里 `lib/router-plugins/catalog/src/lib.rs` 是个**空 catalog**（18 行）——自定义镜像替换这个 crate 并 `register()`
- 组合入口：`WorkerSelectionPolicy::new_with_filters`（`policy.rs:394`）

两个官方示例（`examples/router/custom-policy-example/`）：

|---|---|

## 6. 会话亲和与租约

### 6.1 Hard vs Soft

```17:20:lib/llm/src/session_affinity/mod.rs
pub enum SessionAffinityMode {
    Hard,  // default
    Soft,
}
```

| | Hard（默认） | Soft |
|---|---|---|
| 选择阶段 | `pinned_target` → **只搜索**这一个 worker（`routing_host/kv.rs:36`） | affinity target 作 **advisory** 传给 selector，优先但不绝对 |
| 派发阶段 | 必须命中同一 target，否则 invalidate（`coordinator.rs:659`） | 派到别处则 **rebind** session（`lease.rebind`） |
| 适用 | 有状态会话，KV 隔离要求硬 | 想要亲和但不愿为它牺牲负载均衡 |

多副本 Frontend 之间靠 NATS subject `session_affinity_events` 同步（`session_affinity/replica_sync.rs`）。CLI：`--router-session-affinity-ttl-secs`。

路由层的亲和过滤在 `scheduling/filter.rs:241`——有 affinity target 时只遍历该 worker 的 DP rank。

### 6.2 Request Lease

`lib/llm/src/kv_router/request_lease.rs` 的 `RequestLeaseManager` 用 **CLOCK 算法**（QUIET / TOUCHED / CLAIMED 三态，第 25 行起）管理在途请求的生命周期。释放时同时清理 scheduler booking 和 approximate LRU 的 lease。

兜底扫描周期 `DEFAULT_ACTIVE_REQUEST_EXPIRY_DURATION = 5 分钟`（`sequences/single.rs:40`）。这是防泄漏的最后一道——客户端断连、worker 崩溃等异常路径下，在途请求的记账不会永久挂着。

## 7. 回到统一示例

请求 A 和 B 共享 12 个 token 的系统提示前缀，block_size = 16，所以这段前缀**还不满一块**。

- **A 先到**：索引是空的，`C_overlap = 0`，三个 decode worker 的 cost 只由负载决定。假设 D3 最闲，选 D3。
- **A 跑完**：D3 上产生了若干完整块。事件模式下 vLLM 发 BlockStored 事件，Router 把这些块挂到 radix 树上 D3 的路径下；预测模式下 Router 在派发 A 的当时就已经自己记了一笔。
- **B 到达**：算出 B 的块 hash 链，在 radix 树上走，匹配到 D3 有前缀块 → `B_device` 为正 → D3 的 `adjusted_prefill_blocks` 被减小 → cost 更低 → 选 D3。

**如果那 12 个 token 凑不满一块，就一块都命中不了。** 这是 block 粒度前缀缓存的固有性质，和 vLLM 的 PagedAttention 一样——短前缀不产生任何跨请求收益。想让系统提示真正复用，它得长过一个 block。

## 8. 必记要点

1. **`lib/kv-router` 是纯算法内核，`lib/llm/src/kv_router` 是运行时集成**。拆开是为了让 GAIE 的 EPP 能只依赖前者。
2. **打分公式的所有项单位都是 block 数**，overlap 以减法进入 prefill 成本，cost 的物理含义是「这个 worker 还得多算多少块」。
3. **分层命中有折价**：device 1.0 / host 0.75 / disk 0.25——Router 和 KVBM 的接缝就在这三个系数上。
4. **`overlap_credit_decay` 治热点**，双曲衰减，按「超出最闲 worker 的积压」算，按请求大小归一化；**默认关闭**。
5. **decode 池默认不看 overlap**（P/D 分离下 KV 反正要搬过来），只有 conditional disagg 才启用那个特殊分支。
6. **索引粒度到 DP rank**，不是到 worker 进程。
7. **事件 / 预测 / 混合三种索引维护方式**，混合模式用短 TTL side tree 补事件延迟，与主索引取 max。
8. **要不要走 P/D 分离是每个请求现算的**，判据是「净新增 token」而非 prompt 长度；worker 角色由 MDC 里的 `WorkerType` 枚举决定，不是靠 component 名做子串匹配（那是 1.4 的旧实现）。
9. **三段式插件不是默认路径**——默认是单一 cost 函数，插件是换算法用的逃生口。
10. **block_size 必须与引擎一致**；短于一块的前缀不产生任何命中。
