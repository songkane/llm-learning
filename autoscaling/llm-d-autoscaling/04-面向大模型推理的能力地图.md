# 04 · 面向大模型推理的能力地图

> **源码基线**：[`release-0.9 @ d5d5864`](https://github.com/llm-d/llm-d-autoscaling/tree/d5d586408420fbe0545f827a6ff5dc2f818b16de)（2026-08-07；2026-09-07 核对）。分支与 `v0.9.0` tag 相差 3 个提交，详见 [版本对照](README.md#版本对照与复现)。

> 前三篇讲"怎么实现"，本篇讲"能不能用、怎么用、什么时候别用"。

## 1. WVA 能做好什么

### 1.1 用 token 而不是"CPU 使用率"衡量负载

这是 WVA 存在的根本理由。LLM 推理的资源瓶颈是 **KV cache 显存**与**decode 算力**，两者都不是 CPU/内存能反映的：

| 传统 HPA 指标 | 为什么对 LLM 无效 |
|--------------|-----------------|
| CPU 使用率 | GPU 推理时 CPU 基本闲着，一直是 5%~15% |
| 内存使用率 | vLLM 启动就把显存 `gpu_memory_utilization`（默认 0.9）预分配掉了，**恒定不变** |
| QPS | 一个 8k 输入的请求和一个 100 token 的请求，资源消耗差两个数量级 |
| 并发连接数 | 同上，且不反映 KV 占用 |

WVA 的计量单位是**KV token**（saturation V2）/ **decode token/s**（throughput）；QM 保留设计的单位是满足 SLO 的 QPS（当前不运行）—— 都是与 LLM 服务能力直接相关的量。

用统一示例说明差异：

```
请求 A：8000 输入 + 200 输出   → KV 峰值 8200 token
请求 B：  200 输入 + 2000 输出 → KV 峰值 2200 token

QPS 指标下：A 和 B 都是 1 个请求，权重相同
WVA 指标下：A 占 8200 token，B 占 2200 token —— 差 3.7 倍
```

### 1.2 异构机型的成本感知选择

HPA 只能给"那一个 Deployment"加副本。WVA 能在同一模型的多个变体间选：

```
需要再吃 60000 token 的容量：
  A100 变体：cost 10.0，每副本 90000 token → 成本效率 1.111e-4
  L40S 变体：cost  4.0，每副本 60000 token → 成本效率 6.667e-5  ← 选它
⇒ 加 1 个 L40S，而不是 1 个 A100
```

`llm-d.ai/variant-cost` 可以填任何自定义单位（美元/小时、内部计费点、能耗当量），只要**相对大小正确**就行。

### 1.3 P/D 分离的联合扩容

这是 WVA 最独特的能力，两个独立 HPA 无法做到。03 篇 §4 讲了 Δ_util 匹配，效果是：

```
prefill 侧还有余量、decode 侧是瓶颈时
→ 不会盲目扩 prefill，而是按 decode 能吃下的比例等比扩两侧
```

`role` 从 scale target 上读（`engine.go` 的 `getRoleFromScaleTarget`），支持 `prefill` / `decode` / `both`。

### 1.4 冷启动到 1 副本

`scalefromzero.Engine` 100ms 轮询 EPP 的 flow-control 队列，一有请求就直接捅 scale 子资源。这是 HPA **结构上做不到**的：0 副本时没有 pod 暴露指标，反馈环是断的。

省的钱很实在：一个白天用、晚上闲的模型，`minReplicas: 0` 能省掉一半以上的 GPU 时。代价是首个请求的冷启动延迟（模型加载 + CUDA graph capture，通常 30s ~ 数分钟）。

### 1.5 性能模型与 SLO 能力的边界

当前可用的 throughput analyzer 用 `ITL(k)=A·k+B` 推导吞吐容量，可与 saturation 一起投票，也可单独投票。它仍采用供需双阈值，不提供显式 TTFT/ITL SLO 保证。

queueing-model 的 EKF、`targetTTFT` / `targetITL` 和 `sloMultiplier` 仅为仓库中的保留实现。`release-0.9` 明确拒绝调度它：部署带 `default` 的 QM ConfigMap 会使主循环保持副本，而不是开启 SLO 扩缩容。因此不能把这部分列为当前可落地能力，更不能把平均延迟模型解释成 P95 SLA 保证。

### 1.6 多模型的优先级公平分配

GPU 稀缺时，`GreedyByScoreOptimizer` 按 `priority × demand` 排队；`enableRescale: true` 时还能从低优先级模型回收。这填的是 HPA 完全没有的空白：**HPA 之间没有任何协调机制**，多个 HPA 同时想扩、集群卡不够时，谁先创建 Pod 谁赢，纯随机。

## 2. WVA 做不到什么

### 2.1 不管 Pod 落位

WVA 只产出"副本数应该是几"。Pod 落到哪个节点、有没有 GPU 拓扑亲和、要不要成组调度，都在它的职责之外 —— 由集群里的调度器负责。因此 WVA 本身：

- **不做 NUMA 感知**
- **不做 GPU 拓扑感知**（NVLink 域等）
- **不做 gang**：P/D 分离的联合扩容只保证"目标副本数成比例"，**不保证 Pod 同时起来**

⚠️ **P/D 分离 + gang 是一个真实的缺口**：WVA 把 prefill 和 decode 一起扩到 (3,5)，但如果集群只够起 3 个 decode，实际会是 3 prefill + 3 decode running + 2 decode Pending，比例又歪了。WVA 层面无法解决，只能靠调度器在 Pod 层做成组保证。

### 2.2 不做请求级路由

哪个请求发到哪个 pod、前缀缓存命中该往哪路由 —— 那是 llm-d EPP（Endpoint Picker）的职责。WVA 只**消费** EPP 的指标（队列深度、到达率），不影响路由。

### 2.3 不做 GPU 共享 / 时分复用

没有 vGPU、MPS、MIG 的概念。`gpusPerReplica` 是个整数，一个副本要么占满整张卡（或整组卡），要么不占。

⚠️ 如果集群里实际在跑 vGPU，**WVA 的 GPU 预算会算错** —— 它从 scale target 的 resource requests 读整数 GPU 数，这个数不反映 vGPU 场景下的实际占用。开了 limiter 时尤其要注意。

### 2.4 不直接改 replicas（除 scale-from-zero）

所有决策都要走 `Prometheus → prometheus-adapter → HPA` 这条链。这意味着：

| 代价 | 量级 |
|------|------|
| Prometheus scrape 间隔 | 15s ~ 30s |
| prometheus-adapter 缓存 | ~30s |
| HPA sync 周期 | 15s |
| HPA `stabilizationWindowSeconds` | 由你配置，示例里是 60s |
| **端到端延迟** | **典型 1~3 分钟** |

加上 WVA 自己的 `OptimizationInterval`（15s），**从流量上涨到新 pod 开始服务，2~5 分钟是常态**。对突发流量（burst）这个链路太慢。

> 缓解手段：把 HPA 的 `stabilizationWindowSeconds` 设成 0（示例 `config/samples/hpa/annotations/hpa.yaml` 就是 0），把稳定性交给 WVA 的双阈值死区来保证 —— 反正 WVA 那边已经有防抖动机制了，HPA 再叠一层只会更慢。

### 2.5 状态全在内存，不跨 leader 保留

| Analyzer | 丢失的状态 | 恢复代价 |
|----------|-----------|---------|
| saturation V2 | k2 滚动均值（窗口 10）、CapacityKnowledgeStore | 几个周期，退到 deployment 参数推导 |
| throughput | ObservationWindow（≤20 对 (k,ITL)） | **数分钟**（要重新攒 ≥10 样本 + k 跨度 ≥0.30） |
| queueing-model（保留设计） | ParameterStore 的 (α,β,γ) + 协方差 | 当前不运行 |

leader 切换或 Pod 重启都会清空。throughput 在 Tier-1 预热时可使用 Tier-2，不一定没有信号；其零副本历史容量 `T-sfz` 也会丢失。saturation 只有启用投票且有可用容量时才提供保障。throughput-only 无有效容量来源时，`bindingAnchor` 返回 nil 并保持副本。

### 2.6 没有预测式扩容

当前启用的 analyzer 都是基于**当前观测**的。没有时序预测（不看"每天 9 点会有峰值"）、没有队列到达率的趋势外推。这是与 KEDA 的 `cron` scaler 或商业方案的一个差距。

## 3. 三种落地形态

### 形态 A：最小可用（推荐起步）

```yaml
# saturation ConfigMap
default: |
  analyzers:
    - name: saturation
      score: 1.0
  scaleUpThreshold: 0.85
  scaleDownBoundary: 0.70
  kvCacheThreshold: 0.80
  queueLengthThreshold: 5
  enableLimiter: false
  enableRescale: false
```

- 一个模型一个变体，一个 HPA 打 `llm-d.ai/managed: "true"`
- unlimited 模式，不管集群容量
- 不开 throughput、不开 queueing-model、不开 Coordinator

**收益**：立刻拿到"按 KV token 而不是 CPU 扩缩容"。这一步的价值就已经很大了。

### 形态 B：多变体成本优化

```
同一个 model-id，两个 HPA（两个 Deployment，不同 nodeSelector）
  llama-8b-a100-hpa  → llm-d.ai/variant-cost: "10.0"
  llama-8b-l40s-hpa  → llm-d.ai/variant-cost: "4.0"
```

WVA 自动按成本效率选择加哪个。**注意 `llm-d.ai/model-id` 必须一致**，否则会被当成两个独立模型，各自独立扩缩容（退化成两个 HPA）。

**验证方法**：看 `wva_desired_replicas` 是不是只有便宜的那个在涨。

### 形态 C：多 analyzer + 多租户配额

以下放入 saturation ConfigMap 的 `data`；throughput 首次启用且启动时未注册时，需要重启控制器。EPP 到达率应先验证可用。

```yaml
data:
  default: |
    analyzers:
      - name: saturation
        enabled: true
      - name: throughput
        enabled: true
    scaleUpThreshold: 0.85
    scaleDownBoundary: 0.70
    enableLimiter: true
    priority: 1.0
    limiters:
      - name: ns-quota
        type: quota
        scope: namespace
        namespaceQuotas:
          llm-d-prod: { A100: 8 }
          llm-d-dev:  { L40S: 4 }
  "meta-llama/Meta-Llama-3.1-8B-Instruct#llm-d-prod": |
    priority: 5.0
  "meta-llama/Meta-Llama-3.1-8B-Instruct#llm-d-dev": |
    priority: 1.0
```

确认 QM 配置没有 `default`，否则其拒绝路径会抢先覆盖上述 V2 配置。需要预算内主动再分配时，可在相应预算作用域的 `default` 开启 `enableRescale`；它使用 `bindingAnchor` 的 demand/PRC 换算 GPU。

## 4. 坑与取舍清单

### 4.1 配置类

| 坑 | 症状 | 修法 |
|----|------|------|
| QM ConfigMap 含 `default` | `OptimizationRefused`，副本保持且指标仍发布 | 移除 QM 的 `default`，恢复 V2 配置 |
| saturation `enabled: false` 或从列表省略 | saturation 日志仍出现，但不投票 | 明确承担 throughput-only 的供需信号风险 |
| `limiters:` 配了但 `enableLimiter: false` | 配额完全不生效，日志里有一条 Info 警告 | 两个都设 |
| `analyzers:` 加了 throughput 但没重启 | 不生效；ConfigMap 上有 Warning Event `ThroughputAnalyzerRestartRequired` | 重启 `wva-controller-manager` |
| `enableRescale` / `enableLimiter` / `limiters` 写在 per-model override 里 | 静默无效（它们是 budget-scope 字段，只读 `default`） | 移到 `default` |
| 阈值倒挂（override 把 `scaleDownBoundary` 提到 `scaleUpThreshold` 之上） | 整对**静默退回默认** 0.85/0.70 | 检查合并后的值 |
| `GLOBAL_OPT_INTERVAL: "15"` | 被解析成 **15 纳秒**，然后回退到 15s 默认 | 必须带单位：`"15s"` |
| 多变体的 `llm-d.ai/model-id` 不一致 | 退化成互不相干的多个单变体模型 | 统一 model-id |

### 4.2 指标类

| 坑 | 症状 | 修法 |
|----|------|------|
| shadow-pod 布局缺 `llm-d.ai/variant` label | 某变体完全没有 `wva_desired_replicas` 序列；`wva_pod_mapping_miss_total` 上涨 | 打 pod template label + ServiceMonitor relabeling |
| relabeling 写在 `metricRelabelings` | 同上（`__meta_kubernetes_pod_label_*` 在这个阶段已被剥掉） | 移到 `relabelings` |
| flow-control 队列指标缺 namespace label（上游 #2309） | 同名模型跨 namespace 的调度器队列互相污染（**只影响 `flow_control_queue_size/_bytes` 两条**，`scheduler_attempts_total` 有 namespace 过滤） | 各 namespace 用不同 model-id，或等上游修 |
| 模型服务不暴露 `cache_config_info`（如 inference-sim） | 走 fallback 路径，存在**已知的单位不一致** —— 深队列会误报饱和 | 用真实 vLLM，或接受偏保守 |
| 只看 gauge 不看新鲜度 | 读到最多 5 分钟前的陈旧值 | 告警加 `and wva_saturation_metrics_up == 1` |

### 4.3 行为类

| 坑 | 说明 |
|----|------|
| 开 throughput 但没部署 EPP | TA **不抑制 SpareCapacity**（EPP 缺失、GPS mismatch 都不会置 0），可能基于不可靠的供给估计触发缩容 |
| throughput 的调度器队列需求恒为 0 | **已知 bug**：`engine_v2.go` 从不调 `CollectSchedulerQueueMetrics` |
| scale-from-zero 会拉起同模型的**所有** 0 副本变体 | 源码里的 TODO：还没做"只拉最便宜的" |
| Coordinator 的 maxReplicas 抖动 | 源码明写：瞬时队列噪声让 floor 边界每 15s 翻一次，1 副本反复翻转 |
| Coordinator 只读第一个 ResourceQuota | 正确做法是取所有 quota 的最小值 |
| Coordinator 不支持 scale-to-zero | 队列为 0 时理想目标是 0，但被强制夹到 1 |
| leader 切换后 throughput 状态丢失 | Tier-2 可先估容量；无容量则保持。不能假设未投票的 saturation 会兜底 |
| `enableRescale: true` 会主动降低低优先级模型的副本数 | 这是设计意图，但对被降的模型是**服务能力下降**，要提前和业务方对齐 |

### 4.4 三个刻意的"偏保守"偏差（不是 bug）

这几处源码注释里主动坦白、且明确说"不打算改"的偏差，理解它们能省很多排查时间：

1. **排队请求按 `I+O` 计费，容量按 `I+O/2` 计价** → 需求被高估，倾向扩容。理由：decode 欠配导致的抢占+重算代价高于一个多余副本。
2. **`TokensInUse` 与 `QueueLength` 都取 1 分钟 `max_over_time`，两个峰值不必同时** → 相加可能超过任何真实瞬时值。
3. **`pendingCount` 在 DP>1 时的换算是近似的**（用 `len(replicas)/readyCount` 估 instances-per-unit）→ 扩容期间会高估 pending、从而**低估** `RequiredCapacity`。这一处的方向是**偏保守（少扩）**，与前两条相反。

## 5. 什么时候不该用 WVA

诚实地讲，以下场景 WVA 带来的复杂度大于收益：

| 场景 | 为什么 | 更好的选择 |
|------|-------|-----------|
| 单模型、单变体、固定 2~3 副本 | WVA 的多变体/成本/优先级能力全用不上 | 直接 HPA + vLLM 自定义指标 |
| 突发流量（秒级 burst） | 端到端 1~3 分钟的链路来不及 | 按峰值静态配置 + 队列限流；或 EPP 层做过载保护 |
| 需要按时间表扩缩容（每天 9 点扩） | WVA 只看当前观测，无预测 | KEDA cron scaler（可与 WVA 共存：KEDA 多 trigger 取 max） |
| GPU 共享 / vGPU 为主 | `gpusPerReplica` 算不对 | 手工容量规划 |
| 集群里没有 Prometheus | WVA 启动就 `os.Exit(1)` | 先上 Prometheus |
| 强合规环境、不接受 Alpha 组件 | 多个特性还是 Alpha，源码里 TODO 密集 | 等更成熟的版本 |

**部署前**

- [ ] 源码 / 镜像确实包含 `release-0.9 @ d5d5864` 的行为，不能仅凭 `v0.9.0` 标签判断
- [ ] QM 配置没有 `default`；明确 saturation 是否参与投票
- [ ] Prometheus 可达，且 vLLM/SGLang 的 ServiceMonitor 已生效（`vllm:kv_cache_usage_perc` 有数据）
- [ ] prometheus-adapter 已把 `wva_desired_replicas` 暴露为 External Metric
- [ ] 如需 scale-from-zero：EPP 已部署，`inference_extension_flow_control_queue_size` 有数据
- [ ] 确认 pod→变体映射方式（普通 Deployment/LWS 走 ownerReferences，shadow-pod 需 label + relabeling）
- [ ] leader election 已开（`--leader-elect=true`），三个引擎循环都是 leader-only

**配置**

- [ ] `analyzers:` 段存在（V2）；确认不是无意退回 V1
- [ ] `scaleUpThreshold > scaleDownBoundary`（合并 override 之后也要成立）
- [ ] `GLOBAL_OPT_INTERVAL` 带单位
- [ ] 多变体的 `llm-d.ai/model-id` 一致

- [ ] 如果集群里已有其它组件在管 GPU 配额，确认**只留一套**：要么用 WVA 的 quota limiter，要么 `enableLimiter: false` 交给对方（两边都开会导致 WVA 反复告警"扩不上去"）
- [ ] HPA 的 `stabilizationWindowSeconds` 建议 0（防抖动交给 WVA 的死区）
- [ ] HPA `maxReplicas` 设成真实的容量上限（cost-aware 的溢出逻辑依赖它）

**观测**
