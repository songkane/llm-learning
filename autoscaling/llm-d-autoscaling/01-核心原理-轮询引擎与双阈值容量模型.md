# 01 · 核心原理：轮询引擎与双阈值容量模型

> **源码基线**：[`release-0.9 @ d5d5864`](https://github.com/llm-d/llm-d-autoscaling/tree/d5d586408420fbe0545f827a6ff5dc2f818b16de)（2026-08-07；2026-09-07 核对）。分支与 `v0.9.0` tag 相差 3 个提交，详见 [版本对照](README.md#版本对照与复现)。

> 承接 [00 篇](00-WVA总览与架构.md) 的统一示例（模型 M = `llama-8b`，变体 V1 `llama-8b-a100` / V2 `llama-8b-l40s`）。
> 本篇目标：把 WVA 的**核心公式** —— 那 8 行 `applyUniversalThreshold` —— 讲到能自己手算。

## 1. 为什么需要"双阈值"而不是"一个阈值"

先看 HPA 是怎么做的：

```
HPA:  desired = ceil(current × currentMetric / targetMetric)
```

一个目标值，扩容缩容都用它。问题是：**同一个阈值同时当扩容线和缩容线，必然抖动**。利用率在阈值附近抖 1%，副本数就来回加减。HPA 靠 `stabilizationWindowSeconds` 事后压抖动，属于打补丁。

WVA 的做法是从模型层面就分开两条线：

```
              利用率
    1.0 ┤
        │
   0.85 ┤━━━━━━━━━━━━━━━ scaleUpThreshold ── 之上：算 RequiredCapacity，扩容
        │   ↑
        │   │  死区（hysteresis band）：什么都不做
        │   ↓
   0.70 ┤━━━━━━━━━━━━━━━ scaleDownBoundary ── 之下：算 SpareCapacity，缩容
        │
      0 ┤
```

0.70 ~ 0.85 之间是**滞回带**（hysteresis band，源码注释用词），不是靠时间窗口压出来的。这是 WVA 与 HPA 在扩缩容哲学上最本质的差别。

## 2. 核心公式：`applyUniversalThreshold`

全文在 `internal/engines/saturation/engine_v2.go`。先看注释里给的定义（`engine_v2.go`）：

```go
// applyUniversalThreshold recalibrates RequiredCapacity and SpareCapacity in
// place for the analyzer result and every RoleCapacity entry using the pure
// formula:
//
//	RC = max(0, TotalDemand/scaleUp − TotalAnticipatedSupply)
//	SC = max(0, TotalSupply    − TotalDemand/scaleDown)
//
// TotalAnticipatedSupply is read as-is — zero is a literal value, not a
// sentinel. ...The asymmetry preserves the conservative "don't double-scale
// while replicas are launching, don't count pending as removable" stance.
```

实现：

```go
// internal/engines/saturation/engine_v2.go
func applyUniversalThreshold(r *domain.AnalyzerResult, scaleUp, scaleDown float64) {
	if r == nil {
		return
	}

	if scaleUp > 0 {
		rc := r.TotalDemand/scaleUp - r.TotalAnticipatedSupply
		if rc < 0 {
			rc = 0
		}
		r.RequiredCapacity = rc
	}
	if scaleDown > 0 {
		sc := r.TotalSupply - r.TotalDemand/scaleDown
		if sc < 0 {
			sc = 0
		}
		r.SpareCapacity = sc
	}

	for role, rc := range r.RoleCapacities {      // P/D 分离：每个 role 走同一套公式
		if scaleUp > 0 {
			v := rc.TotalDemand/scaleUp - rc.TotalAnticipatedSupply
			if v < 0 { v = 0 }
			rc.RequiredCapacity = v
		}
		if scaleDown > 0 {
			v := rc.TotalSupply - rc.TotalDemand/scaleDown
			if v < 0 { v = 0 }
			rc.SpareCapacity = v
		}
		r.RoleCapacities[role] = rc
	}
}
```

**【Go】** `for role, rc := range r.RoleCapacities` 里 `rc` 是 map value 的**副本**（`RoleCapacity` 是值类型 struct），所以改完必须 `r.RoleCapacities[role] = rc` 写回去 —— Go 的 map 不支持取 value 的地址，这是很常见的坑。

### 2.1 逐项拆解公式

```
RC = max(0, TotalDemand / scaleUpThreshold − TotalAnticipatedSupply)
SC = max(0, TotalSupply − TotalDemand / scaleDownBoundary)
```

| 项 | 含义 | 单位 |
|----|------|------|
| `TotalDemand` | 当前总需求 | token（V2）/ decode token/s（throughput） |
| `TotalSupply` | **已就绪副本**能提供的总容量 = `Σ ReplicaCount_v × PerReplicaCapacity_v` | 同上 |
| `TotalAnticipatedSupply` | **已就绪 + 正在启动**的总容量 = `Σ (ReplicaCount_v + PendingReplicas_v) × PerReplicaCapacity_v` | 同上 |
| `RequiredCapacity`（RC） | 还差多少容量 → `>0` 表示要扩容 | 同上 |
| `SpareCapacity`（SC） | 还富余多少容量 → `>0` 表示可以缩容 | 同上 |

**为什么 `TotalDemand / scaleUp` 而不是 `TotalDemand × scaleUp`？**

因为要求的是「让利用率降到 0.85 所需的供给量」：

```
目标：TotalDemand / 目标供给 = 0.85
  ⇒ 目标供给 = TotalDemand / 0.85 = TotalDemand × 1.176
  ⇒ 还差 = 目标供给 − 当前(含 pending)供给
```

同理缩容侧：`TotalDemand / 0.70` 是「利用率恰好为 0.70 时需要的供给量」，超出这个数的部分就是可以安全砍掉的富余。

### 2.2 那个刻意的不对称：为什么扩容用 Anticipated、缩容用 Supply

这处不对称在注释里点了但没展开，值得单独拆解。

```
RC 用 TotalAnticipatedSupply （含 pending）
SC 用 TotalSupply            （不含 pending）
```

| 侧 | 用哪个 | 效果 | 防的是什么 |
|----|--------|------|-----------|
| 扩容 | Anticipated（**多**算） | 上一轮扩出来的 pod 还在启动，这一轮就已经计入供给，RC 变小 | **级联重复扩容**。否则 pod 启动的 30s 内每 15s 一轮都会看到"供给不足"，连扩 2~3 次，最后严重超配 |
| 缩容 | Supply（**少**算） | 正在启动的 pod 不算作"可以被砍掉的富余" | **刚扩就缩**。否则新 pod 一起来就被判定为多余，立刻砍掉，形成扩-缩死循环 |

两侧都朝"保守"方向偏，且偏的方向相反 —— 这正是死区之外的第二层防抖动机制。

`PendingReplicas` 的口径见 `saturation_v2/analyzer.go:375-378`：

```go
		readyCount := vs.CurrentReplicas - vs.PendingReplicas
		if readyCount < 0 {
			readyCount = 0
		}
```

### 2.3 阈值从哪来：三级解析

```go
// internal/engines/saturation/engine_v2.go
func resolveThresholds(analyzerName string, cfg config.SaturationScalingConfig) (scaleUp, scaleDown float64) {
	for _, aw := range cfg.Analyzers {
		if aw.EffectiveType() == analyzerName {
			return aw.EffectiveScaleUpThreshold(cfg.ScaleUpThreshold),
				aw.EffectiveScaleDownBoundary(cfg.ScaleDownBoundary)
		}
	}
	return cfg.ScaleUpThreshold, cfg.ScaleDownBoundary
}
```

优先级：**per-analyzer 覆盖 > 该条目的全局值 > 默认值 0.85/0.70**。

配置层的解析顺序（`engine.go`）：

```go
func resolveSaturationConfig(
	configMap map[string]config.SaturationScalingConfig,
	modelID, namespace string,
) config.SaturationScalingConfig {
	base := config.SaturationScalingConfig{}
	if defaultCfg, ok := configMap["default"]; ok {
		base = defaultCfg                                 // 1. default 条目做底
	}
	if override, ok := configMap[modelID+"#"+namespace]; ok {
		base.Merge(override)                              // 2. 逐字段覆盖（非零字段才赢）
	}
	base.ApplyDefaults()                                  // 3. 剩下的零值填默认
	base.ApplyV2ThresholdDefaults()                       // 4. 校准 V2 阈值
	// 合并可能产生倒挂的阈值对，此时整对退回默认值
	if base.ScaleUpThreshold <= base.ScaleDownBoundary {
		base.ScaleUpThreshold = config.DefaultScaleUpThreshold
		base.ScaleDownBoundary = config.DefaultScaleDownBoundary
	}
	return base
}
```

**【逻辑】** 最后那个 `if` 是防御性的：override 只改了 `scaleDownBoundary: 0.9` 而 base 的 `scaleUpThreshold` 是 0.85，合并后就出现 `up ≤ down` 的倒挂 —— 死区变成负宽度，扩缩容条件同时成立。此时**整对退回默认**，而不是只修一个，因为无法判断用户到底想要哪个。

默认值（`internal/config/saturation_scaling.go:238-247`）：

```go
	DefaultKvCacheThreshold     = 0.80
	DefaultQueueLengthThreshold = 5.0
	DefaultKvSpareTrigger       = 0.10   // V1 专属
	DefaultQueueSpareTrigger    = 3.0    // V1 专属
	DefaultScaleUpThreshold  = 0.85      // V2
	DefaultScaleDownBoundary = 0.70      // V2
```

## 3. Analyzer 契约：谁算什么

WVA 把"算供需"和"算阈值"**彻底分离**，这是多 analyzer 架构能成立的基础。

```
┌─────────────────────────────────────────────────────────────┐
│ Analyzer 的职责（domain.Analyzer 接口）                       │
│   输入：AnalyzerInput{ReplicaMetrics, VariantStates,          │
│                       Config, SchedulerQueue, ArrivalRate}   │
│   输出：AnalyzerResult{                                       │
│           TotalSupply, TotalDemand, TotalAnticipatedSupply,  │
│           VariantCapacities[], RoleCapacities{},             │
│           RequiredCapacity = 0,  ← 留空！                     │
│           SpareCapacity    = 0,  ← 留空！                     │
│         }                                                    │
└─────────────────────────────────────────────────────────────┘
                          ↓ 引擎接手
┌─────────────────────────────────────────────────────────────┐
│ 引擎的职责：applyUniversalThreshold 写入 RC / SC              │
└─────────────────────────────────────────────────────────────┘
```

V2 分析器的注释写得很清楚（`saturation_v2/analyzer.go:118-125`）：

```go
	// Phase 4: Per-role aggregation (P/D disaggregation).
	// RequiredCapacity and SpareCapacity are NOT computed here — the engine's
	// universal threshold post-step writes them after Analyze() returns.
	roleCapacities := a.aggregateByRole(variantCapacities, queueDemand.byRole)

	// Phase 5: Build result. RequiredCapacity and SpareCapacity left zero;
	// the engine post-step overwrites them using TotalDemand, TotalSupply,
	// and TotalAnticipatedSupply with the resolved thresholds.
```

**【逻辑】** 为什么非要这样切？因为一旦有 N 个 analyzer，如果每个都自己算 RC/SC，就会出现 N 套不同的阈值语义，优化器根本无法比较它们的输出。把阈值统一收到引擎里，各 analyzer 使用同一种阈值语义，但 RC/SC 仍有各自单位；除以各自 PRC 换算成副本数，才能做 §5 的 any-up / all-down 组合。

### 3.1 线性性不变式

`TotalSupply` 必须严格等于 `Σ ReplicaCount_v × PerReplicaCapacity_v`，这是**优化器能做除法的前提**：

```go
// internal/engines/analyzers/saturation_v2/analyzer.go:98-101
	// Phase 3: Model-level aggregation via shared helpers (enforces linearity invariant).
	totalSupply := aggregation.SumTotalSupply(variantCapacities)
	totalAnticipatedSupply := aggregation.SumTotalAnticipatedSupply(variantCapacities)
	totalDemand := aggregation.SumTotalDemand(variantCapacities)
```

因为优化器要做的事就是 `n = ceil(RC / PerReplicaCapacity)` —— 如果供给不是副本数的线性函数，这个除法就没有意义。所有 analyzer 都被要求走 `internal/engines/aggregation` 里的共享 helper 来聚合，就是为了机械地保证这条不变式。

## 4. 完整数值演算（统一示例）

现在用真实公式把模型 M 的一个 tick 手算一遍。假定配置为默认值。

### 4.1 输入：V1（`llama-8b-a100`）2 个副本的观测

| 指标 | 值 | 来源 PromQL |
|------|----|------------|
| `num_gpu_blocks` | 8192 | `vllm:cache_config_info` label |
| `block_size` | 16 | 同上 |
| → `TotalKvCapacityTokens` | 8192 × 16 = **131072** | 采集器换算 |
| `TokensInUse` | 90000 | `kv_cache_usage_perc × TotalKvCapacityTokens` |
| `QueueLength` | 6 | `max_over_time(vllm:num_requests_waiting[1m])` |
| `AvgInputTokens` (I) | 1000 | `rate(prompt_tokens_sum)/rate(prompt_tokens_count)` |
| `AvgOutputTokens` (O) | 500 | `rate(generation_tokens_sum)/rate(generation_tokens_count)` |
| `PrefixCacheHitRate` | 0.20 | `rate(prefix_cache_hits)/rate(prefix_cache_queries)` |
| `Role` | both | 来自 scale target 的 `llm-d.ai/role` label |

### 4.2 第一步：每副本容量 = min(k1, k2)

```
k1（显存受限）= TotalKvCapacityTokens × kvCacheThreshold
              = 131072 × 0.80
              = 104857   （int64 截断，104857.6 → 104857）
```

```
k2（计算受限）：走四级优先级链（见 02 篇 §3）
  P1 观测态：QueueLength=6 ≥ queueLengthThreshold=5 且 TokensInUse>0
            ⇒ k2 = TokensInUse = 90000  （命中，后面三级不走）
```

```
effectiveCapacity = min(104857, 90000) = 90000
```

对应源码：

```go
// internal/engines/analyzers/saturation_v2/analyzer.go:167-188
	// k1: memory-bound capacity
	k1 := int64(float64(rm.TotalKvCapacityTokens) * config.KvCacheThreshold)

	// k2: compute-bound capacity
	...
	k2, k2Priority := a.computeK2(...)

	effectiveCapacity := k1
	if k2 < k1 {
		effectiveCapacity = k2
	}
```

### 4.3 第二步：每副本需求

```go
// internal/engines/analyzers/saturation_v2/analyzer.go:163-165
	// Compute demand: tokens already resident in KV cache plus the role-aware
	// footprint of requests still waiting in the local engine queue.
	replicaDemand := rm.TokensInUse + waitingQueueDemand(rm, role)
```

`waitingQueueDemand` 按 P/D 角色计费（`analyzer.go:687-719`）：

```go
func waitingQueueDemand(rm domain.ReplicaMetrics, role string) int64 {
	if rm.QueueLength <= 0 {
		return 0
	}

	tokensPerRequest := rm.AvgInputTokens
	if canonicalRole(role) != domain.RolePrefill {
		tokensPerRequest += rm.AvgOutputTokens
	}
	...
	demand := float64(rm.QueueLength) * tokensPerRequest
	if !(demand > 0) || demand >= float64(math.MaxInt64) {
		return 0
	}
	return int64(demand)
}
```

| 角色 | 每请求计费 | 理由（`analyzer.go:640-646`） |
|------|-----------|------|
| Prefill | `I` | 只算 prompt KV —— 输出在别处生成 |
| Decode / Both | `I + O` | 持有 prompt KV 且每生成一个 token 就增长 |

本例 role=both：

```
waitingQueueDemand = 6 × (1000 + 500) = 9000
replicaDemand      = 90000 + 9000 = 99000
```

**为什么 decode 侧要用完整的 O 而不是 O/2？** 注释里专门开了一节解释（`analyzer.go:648-683`）：

> `I+O` 是一个请求在**最后一个 decode step** 的 KV 占用，不是均值。这是刻意选择的"峰值、无抢占"规划口径：一旦请求被接纳，decode 的 KV 单调增长，引擎无法在不抢占+重算的前提下释放它，所以一个要托管该请求的副本必须留出它最终大小的空间。

注释同时坦白了这带来的偏差：
- `estimateCapacityFromParams` 在推导 k2 时按 `I + O/2` 给**并发中**的请求计价，所以排队请求被多收了费，一旦被接纳、开始被 `KvCacheUsage` 观测到，计费又降回去；
- `TokensInUse` 和 `QueueLength` 都来自 1 分钟 `max_over_time`，两个峰值不必同时发生，相加可能超过任何真实瞬时需求。

**两个偏差都朝扩容方向偏，这是有意的**：decode 容量欠配会导致抢占+重算的抖动，代价比多一个副本更高。

### 4.4 第三步：变体级聚合

两个副本观测值相同，走 `aggregateByVariant`（`analyzer.go:390-420`）：

```go
		if len(replicas) > 0 {
			// len(replicas) counts vLLM engine instances (DP ranks), not pods: a DP=8
			// pod hosts 8 independently-capacitied instances. Using the pod count would
			// undercount TotalCapacity by the DP factor.
			capacities := make([]int64, 0, len(replicas))
			for _, rc := range replicas {
				capacities = append(capacities, rc.EffectiveCapacity)
				totalDemand += float64(rc.ReplicaDemand)
			}
			perReplicaCapacity = float64(median(capacities))
			replicaCount = len(replicas)
```

**【逻辑】两个易踩的坑：**
1. **`PerReplicaCapacity` 取中位数而非均值** —— 中位数抗离群点，一个刚启动、KV 还没填满的副本不会把整个变体的容量估计拉低。
2. **`replicaCount = len(replicas)` 数的是 vLLM engine 实例（DP rank），不是 Pod**。DP=8 的一个 Pod 里有 8 个独立容量的 instance，用 Pod 数会把 `TotalCapacity` 少算 8 倍。

```
V1: PerReplicaCapacity = median(90000, 90000) = 90000
    ReplicaCount = 2, PendingReplicas = 0
    TotalCapacity = 2 × 90000 = 180000
    TotalDemand(V1) = 99000 × 2 = 198000
```

假设 V2（`llama-8b-l40s`）当前 0 副本，从 capacity store 取到历史值 `PerReplicaCapacity = 60000`，`ReplicaCount = 0`。

### 4.5 第四步：调度器队列需求

这部分需求**还没到任何 pod**，来自 llm-d EPP 网关的 flow-control 层（`analyzer.go:750-794`）：

```go
	// Estimate input tokens from two signals, take the max for robustness
	tokensFromBytes := float64(sq.QueueBytes) / BytesPerToken       // BytesPerToken = 4
	tokensFromCount := float64(sq.QueueSize) * avgInput
	inputTokens := tokensFromBytes
	if tokensFromCount > inputTokens {
		inputTokens = tokensFromCount
	}

	// Apply prefix cache hit rate reduction to input tokens only
	inputTokens *= (1 - avgHitRate)

	// Estimate output tokens (no cache reduction — output must be generated)
	outputTokens := float64(sq.QueueSize) * avgOutput

	total := inputTokens + outputTokens
```

假设 `QueueSize = 4`，`QueueBytes = 20000`：

```
tokensFromBytes = 20000 / 4 = 5000
tokensFromCount = 4 × 1000  = 4000
inputTokens     = max(5000, 4000) = 5000
                → × (1 − 0.20) = 4000     （前缀缓存折减）
outputTokens    = 4 × 500 = 2000
queueDemand     = 4000 + 2000 = 6000
```

**【逻辑】两处细节值得记住：**
- **取 max 而非 avg**：字节数和请求数是两个**独立**的估计源，取大者是为了鲁棒 —— 任一路失真（比如 EPP 没上报 bytes）也不会低估。
- **前缀缓存折减只作用于 input**：输出 token 必须真实生成，命中不了缓存。而且这个折减**不适用于本地引擎队列**（`analyzer.go:745-749`）—— 那些请求还没做前缀查表。

### 4.6 第五步：模型级汇总 + 双阈值

```
TotalSupply            = 180000 (V1) + 0 (V2)   = 180000
TotalAnticipatedSupply = (2+0)×90000 + (0+0)×60000 = 180000
TotalDemand            = 198000 (V1) + 0 (V2) + 6000 (调度器队列) = 204000

Utilization = 204000 / 180000 = 1.133   （113%，明显过载）
```

代入 `applyUniversalThreshold(result, 0.85, 0.70)`：

```
RC = max(0, 204000 / 0.85 − 180000)
   = max(0, 240000 − 180000)
   = 60000        ← 还差 6 万 token 的容量

SC = max(0, 180000 − 204000 / 0.70)
   = max(0, 180000 − 291428.6)
   = 0            ← 没有富余
```

**结论：RC = 60000 > 0，需要扩容 6 万 token 的容量。**

### 4.7 第六步：优化器换算副本数

`CostAwareOptimizer` 按**成本效率升序**挑变体（`cost_aware_optimizer.go`）：

```go
// sortByCostEfficiencyAsc returns variants sorted by cost/perReplicaCapacity ascending.
func sortByCostEfficiencyAsc(capacities []domain.VariantCapacity) []domain.VariantCapacity {
	...
}

// costEfficiency returns the cost per unit of capacity.
func costEfficiency(vc domain.VariantCapacity) float64 {
	if vc.PerReplicaCapacity <= 0 {
		return math.MaxFloat64
	}
	return vc.Cost / vc.PerReplicaCapacity
}
```

```
V1 (a100): 10.0 / 90000 = 1.111e-4
V2 (l40s):  4.0 / 60000 = 6.667e-5   ← 更便宜，先选它
```

副本数换算（`analyzer_helpers.go`）：

```go
// 返回 max_i ceil(state[i][role] / PRC_i[v])
func roleBottleneckReplicas(s []NamedAnalyzerResult, state RolePairedState, role, v string) int {
	max := 0
	for i, e := range s {
		prc := prcForVariant(e.Result, v)
		if prc <= 0 { continue }
		n := int(math.Ceil(state[i][role] / prc))
		if n > max { max = n }
	}
	return max
}
```

```
n = ceil(RC / PerReplicaCapacity_V2) = ceil(60000 / 60000) = 1
```

**最终决策：`llama-8b-l40s` 0 → 1 副本**（而不是给贵的 A100 加副本）。这就是"cost-aware"三个字的实际含义。

决策被写成 `wva_desired_replicas{variant_name="llama-8b-l40s", namespace="llm-d"} = 1`，KEDA 或启用了相应 scale-to-zero 能力的 HPA 读到后执行 0→1；普通 HPA 的 `minReplicas: 1` 示例不能用于复现零副本起点。

> WVA 发出的 label 名是 `namespace`。若 Prometheus 的 scrape 配置也注入同名 label，指标自带的那个会被重命名为 `exported_namespace` —— 仓库示例里用的正是后者。写 selector 前先实测确认（见 02 篇 §10）。

> 完整的多变体/多角色演算（包括 P/D 联合提交的 Δ_util 匹配）见 [03 篇](03-核心代码分析-Optimizer与Limiter.md)。
> 这一段数值链路的可视化版本（含逐格颜色标注的公式字典）在同目录的 **[`wva-autoscaling-logic.html`](wva-autoscaling-logic.html)** 里，浏览器打开即可。

## 5. 多 Analyzer 组合：any-up / all-down

引擎支持同时挂多个 analyzer。先由 `votingResults` 筛出 `Enabled=true` 的结果，再按**不对称**的规则组合；优化器还需要能构造有效的 `bindingAnchor`（见 03 篇 §1.3）：

> **扩容：投票集合中任一 analyzer 有缺口就进入扩容计算（any-up）**
> **缩容：投票集合中所有 live analyzer 都说能缩才缩，且至少有一个 live（all-down）**

```go
// internal/engines/pipeline/analyzer_helpers.go
func anyRoleNeedsScaleUp(state RolePairedState, roles []string) bool {
	for _, role := range roles {
		for _, m := range state {
			if m[role] > 0 {
				return true
			}
		}
	}
	return false
}
```

```go
// internal/engines/pipeline/analyzer_helpers.go
// needsScaleDownForRole reports whether every live analyzer agrees this role
// has spare capacity (all-down gate, scoped to one role). Non-live analyzers
// (no metrics, error state, never analyzed, or stale) do not veto ...
// Safety floor: if no live analyzer remains, there is no current basis to
// scale down, so this returns false.
func needsScaleDownForRole(s []NamedAnalyzerResult, role string) bool {
	liveCount := 0
	for _, e := range s {
		if !e.Live {
			continue // non-live analyzers do not veto
		}
		if e.Result == nil || e.RoleSpare == nil || e.RoleSpare[role] <= 0 {
			return false
		}
		liveCount++
	}
	return liveCount > 0
}
```

同样的不对称也体现在副本数的换算上：

| 侧 | 取整 | 跨 analyzer 聚合 | 语义 |
|----|------|-----------------|------|
| 扩容 | `ceil` | `max` | 谁要得多听谁的 |
| 缩容 | `floor` | `min` | 谁最保守听谁的 |

```go
// internal/engines/pipeline/analyzer_helpers.go
func safeRemovalReplicasForRole(s []NamedAnalyzerResult, v, role string) int {
	smallest := math.MaxInt
	found := false
	for _, e := range s {
		if !e.Live { continue }          // 非活跃 analyzer 不参与约束
		prc := prcForVariant(e.Result, v)
		if prc <= 0 { continue }
		n := int(math.Floor(e.RoleSpare[role] / prc))
		if n < smallest { smallest = n }
		found = true
	}
	if !found || smallest < 0 { return 0 }
	return smallest
}
```

### 5.1 Liveness 机制：防止"哑掉的 analyzer 永久否决缩容"

all-down 一票否决有个致命风险：如果某个 analyzer 因为指标缺失一直返回 `SpareCapacity = 0`，它会**永久阻塞所有缩容**。

WVA 用 liveness 门解决（`engine_v2.go`）：

```go
	interval := 30 * time.Second
	if e.Config != nil && e.Config.OptimizationInterval() > 0 {
		interval = e.Config.OptimizationInterval()
	}
	now := time.Now()
	threshold := analyzerLivenessStaleCycles * interval      // = 3 × 15s = 45s

	for i := range namedResults {
		nr := &namedResults[i]
		if pipeline.ResultIsInformative(*nr) {
			at := nr.Result.AnalyzedAt
			if at.IsZero() {
				// Fail-safe: an informative result observed this cycle is current by
				// definition, so a forgotten AnalyzedAt cannot silently disarm the veto.
				at = now
			}
			perAnalyzer[nr.Name] = at
		}
		lastGood, ok := perAnalyzer[nr.Name]
		nr.Live = ok && now.Sub(lastGood) <= threshold
	}
```

"有信息量"的判据（`analyzer_helpers.go`）：

```go
func ResultIsInformative(nr NamedAnalyzerResult) bool {
	if nr.Result == nil {
		return false
	}
	for _, vc := range nr.Result.VariantCapacities {
		if vc.Reason != ReasonNoData && vc.Reason != ReasonError {
			return true
		}
	}
	return false
}
```

**【逻辑】关键细节：**
- `analyzerLivenessStaleCycles = 3`（`engine_v2.go`），硬编码，注释里挂了 TODO 说未来可能开放配置。
- **liveness 是 per-(模型, analyzer) 的**，不是 per-analyzer 全局的 —— 一个 Engine 实例服务所有模型，全局按名字建 map 会让模型 A 的新鲜度"泄漏"到模型 B（`engine.go`）。
- **saturation 也不豁免**：注释明写 "Applies uniformly to every analyzer, including saturation — no name-based exemption"。
- 状态**纯内存**，进程重启 / leader 切换后清空。这是安全的：没有任何 live 投票者 → 不允许缩容；若还有其它 live 投票者，则由它们决定。
- `pruneLastGoodAnalysis`（`engine_v2.go`）负责在模型消失后清理，避免 map 无界增长；但 `len(activeKeys) == 0` 时**跳过清理**，防止一个"配置还没加载完"的空周期把累积状态全清掉。

### 5.2 opt-in 语义：注册了 ≠ 参与

```go
// internal/engines/saturation/engine_v2.go
func effectiveEnabled(analyzerName string, cfg config.SaturationScalingConfig) bool {
	for _, aw := range cfg.Analyzers {
		if aw.EffectiveType() == analyzerName {
			if aw.Enabled != nil {
				return *aw.Enabled
			}
			return true // present, not yet defaulted → participates
		}
	}
	return false // absent → opt-in: does not participate
}
```

注释解释了这个"缺省不参与"的原因：

> 代码里注册了但 `cfg.Analyzers` 里**没有**条目的 analyzer **不参与** —— 这防止一个"已注册但未配置"的 analyzer（例如 throughput）返回 `SpareCapacity = 0` 从而**静默否决所有缩容**。

saturation 特殊之处是**总会运行，但不一定投票**：`satVotes = len(config.Analyzers) == 0 || effectiveEnabled("saturation", config)`。显式列表只包含 throughput，或 saturation 设置 `enabled: false`，都会使 saturation 的 `Enabled=false`；它保留完整变体身份信息，但不能阻止 throughput 的缩容。`score: 0` 不是禁用开关，`scoreForAnalyzer` 会把非正权重恢复为 1.0。

`Enabled` 与 `Live` 独立：前者是配置选择，后者是近期是否有可用容量。优化器构造 `bindingAnchor` 时优先选择 enabled + live + informative 的 saturation，否则选择唯一满足条件的非 saturation analyzer；无法选择时保持该模型副本数。

### 5.3 demand liveness：只告警不否决

`detectDemandLiveness`（`engine_v2.go`）是一个**纯观测性**探针：当 throughput analyzer 有活的容量信号、但连续超过 staleness 窗口没报过任何需求时，打一条 INFO 日志：

```go
	if supplyTS.Sub(demandTS) >= threshold {
		logger.Info("throughput analyzer has a live capacity signal but has reported no demand "+
			"for at least the staleness window; the request-arrival query is likely misconfigured "+
			"or EPP is not reporting arrivals — scale-up will not trigger until arrivals are observed",
			...)
	}
```

注释里详细论证了**为什么这里不能做成否决**（`engine_v2.go`）：

> 零需求是一个合法状态，不一定是故障。没有 served-rate 下限时，到达率→0 正确地驱动 `TotalDemand→0`，这只允许缩容、从不强制扩容。缺失或为零的到达信号因此**永远不会导致虚假扩容或虚假否决**，所以以"需求看起来不存在"为由否决，恰恰会打败 liveness 门本身想要放行的那个缩容。

这段推理的可复用之处：**判断一个信号该不该做成 gate，要看它失真时会往哪个方向错。**

## 6. 轮询执行器与错误处理

`executor.PollingExecutor`（`internal/engines/executor/`）用 `wait.UntilWithContext` 驱动：

```go
// internal/engines/saturation/engine.go
	engine.executor = executor.NewPollingExecutor(executor.PollingConfig{
		Config: executor.Config{
			OptimizeFunc: engine.optimize,
		},
		Interval:     cfg.OptimizationInterval(),
		RetryBackoff: 100 * time.Millisecond,
	})
```

每个周期的观测埋点（`engine.go`）：

```go
func (e *Engine) optimize(ctx context.Context) (retErr error) {
	start := time.Now()
	var modelsProcessed int
	defer func() {
		status := "success"
		if retErr != nil {
			status = "error"
		}
		metrics.ObserveOptimizationDuration(time.Since(start).Seconds(), status)
		metrics.SetModelsProcessed(modelsProcessed)
	}()
```

**【Go】** 具名返回值 `(retErr error)` 配合 `defer` 闭包，是 Go 里给函数加"出口埋点"的标准写法 —— `defer` 能读到实际返回的 error。

### 单个 analyzer 崩了不影响整个周期

```go
// internal/engines/saturation/engine_v2.go
func runRegisteredAnalyzer(...) (result *domain.AnalyzerResult) {
	defer func() {
		if r := recover(); r != nil {
			// Plugin failure is non-fatal; log at debug to avoid spamming
			// operator logs every optimize cycle.
			logger.V(logging.DEBUG).Info("registered analyzer panicked; result discarded",
				"name", entry.name, "modelID", modelID, "panic", fmt.Sprintf("%v", r))
			result = nil
		}
	}()
	var err error
	result, err = entry.analyzer.Analyze(ctx, input)
	if err != nil {
		logger.V(logging.DEBUG).Info("registered analyzer failed; result discarded",
			"name", entry.name, "modelID", modelID, "error", err)
		return nil
	}
	return result
}
```

**【逻辑】** 外部注册的 analyzer 是插件，panic 被 recover、结果丢弃，主 saturation analyzer 照常跑。返回 nil 的失败结果**当轮就不会进入投票列表**，不会等 3 个周期才失去否决权。3 周期窗口用于仍返回结果但缺少信息量的条目。throughput-only 若没有有效容量来源，则 `bindingAnchor=nil`，保持该模型副本数。

### analyzer 注册在 Start 后冻结

```go
// internal/engines/saturation/engine.go
func (e *Engine) RegisterAnalyzer(name string, a domain.Analyzer) error {
	if e.started {
		return errors.New("RegisterAnalyzer: called after StartOptimizeLoop")
	}
	for i := range e.analyzers {
		if e.analyzers[i].name == name {
			return fmt.Errorf("RegisterAnalyzer: duplicate analyzer name %q", name)
		}
	}
	e.analyzers = append(e.analyzers, analyzerEntry{name: name, analyzer: a})
	return nil
}
```

```go
// internal/engines/saturation/engine.go
func (e *Engine) StartOptimizeLoop(ctx context.Context) {
	e.analyzersSnapshot = make([]analyzerEntry, len(e.analyzers))
	copy(e.analyzersSnapshot, e.analyzers)
	e.started = true
	...
	e.executor.Start(ctx)
}
```

**【逻辑】** 用"启动前可写、启动后只读快照"替代运行时加锁 —— 优化 goroutine 只读 `analyzersSnapshot`，天然无竞争。代价是**新增启动时未注册的 analyzer 需要重启控制器**；已注册 analyzer 的 enabled 开关由每周期配置决定（`throughput-analyzer.md:26-27` 明确说了这一点）。

为了不让运维静默踩这个坑，`ConfigMapReconciler` 会在检测到"live 配置的 throughput 启用状态与启动时冻结的注册决定不一致"时，在 ConfigMap 上打一个 Warning Event（reason `ThroughputAnalyzerRestartRequired`）。这个"冻结决定 + 检测漂移 + 发 Event"的三段式，是处理"必须重启才能生效的配置"的一种通用做法。

## 7. 本篇速查表

### 核心公式

| 公式 | 位置 |
|------|------|
| `RC = max(0, TotalDemand/scaleUp − TotalAnticipatedSupply)` | `engine_v2.go` |
| `SC = max(0, TotalSupply − TotalDemand/scaleDown)` | `engine_v2.go` |
| `effectiveCapacity = min(k1, k2)` | `saturation_v2/analyzer.go:185-188` |
| `k1 = TotalKvCapacityTokens × kvCacheThreshold` | `analyzer.go:168` |
| `replicaDemand = TokensInUse + QueueLength × (I [+O])` | `analyzer.go:165, 687-719` |
| `inputTokens = max(QueueBytes/4, QueueSize×I) × (1−hitRate)` | `analyzer.go:763-771` |
| `n_up = max_i ceil(Remaining_i / PRC_i)` | `analyzer_helpers.go` |
| `n_down = min_i floor(RoleSpare_i / PRC_i)` | `analyzer_helpers.go` |
| `costEfficiency = Cost / PerReplicaCapacity`（升序选） | `cost_aware_optimizer.go` |

### 必记要点

1. **双阈值 0.85 / 0.70 之间是滞回带**，不靠时间窗口压抖动。
2. **扩容用 Anticipated（含 pending）、缩容用 Supply（不含 pending）** —— 刻意的不对称，两端都偏保守。
3. **Analyzer 只算 Total\*，RC/SC 由引擎统一写** —— 这是多 analyzer 能互相比较的前提。
4. **`TotalSupply` 必须是副本数的线性函数**，否则优化器的除法无意义。
5. **只对 Enabled 投票集组合：扩容 any-up + ceil + max；缩容 all-down + floor + min。**无有效 bindingAnchor 时保持该模型。
6. **liveness 是 per-(模型, analyzer)、3 个周期、纯内存**；非 live 不参与否决。
7. **analyzer 缺省不参与（opt-in）**，防止未配置的 analyzer 静默否决缩容。
8. **注册在 `StartOptimizeLoop` 后冻结**，新增启动时未注册的 analyzer 要重启；已注册 analyzer 的 enabled、阈值、limiters、scale-to-zero 按周期配置热更新。
