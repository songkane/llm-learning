## 1. SGLang 是什么

SGLang = **S**tructured **G**eneration **Lang**uage + Runtime。它包含两部分：

- **前端 DSL**（`python/sglang/lang/`）：一套用于结构化生成的编程接口（多轮、分支、并行、约束解码等）。
- **后端运行时 `srt`**（`python/sglang/srt/`）：高性能推理与服务引擎——**本系列聚焦这里**。

`srt` 的核心竞争力来自几个设计：**RadixAttention 前缀缓存**、**连续批处理（Continuous Batching）**、**CPU/GPU 重叠调度（Overlap Scheduler）**、**可插拔的 Attention 后端**，以及对 **多种并行策略与 PD 分离** 的支持。

## 2. 进程模型：为什么是多进程

一个 SGLang 服务实例由以下进程组成：

```
主进程 (main process)
├── FastAPI HTTP Server          ← 对外暴露 REST 接口
└── TokenizerManager             ← 异步中枢，管理在途请求

Scheduler 子进程 × (tp_size × pp_size 个 / 每 DP rank)
└── TpModelWorker → ModelRunner  ← 真正跑 GPU 前向的地方

DetokenizerManager 子进程
└── 增量解码：token id → 文本
```

### 2.1 为什么拆进程而不是拆线程？

因为 **Python GIL**。tokenize / detokenize 是纯 CPU 工作，如果和 GPU 调度跑在同一进程的不同线程里，会因 GIL 互相抢占，导致 GPU 调度循环被拖慢。拆成独立进程后：

- Scheduler 子进程可以**心无旁骛地喂 GPU**；
- Tokenize / Detokenize 各自在独立进程并行处理；
- 进程间只传 **token id**（几 KB 的小数据），成本极低。

这是「**控制平面与数据平面分离**」思想的体现：ZMQ 只传控制信息和小数据，真正的大块数据（KV Cache）始终待在 GPU 显存里，不搬来搬去。

### 2.2 进程如何被拉起

无论是 HTTP Server 启动还是离线 `Engine` 使用，最终都汇聚到同一个方法：

```
Engine._launch_subprocesses()   # python/sglang/srt/entrypoints/engine.py:765
```

它负责：
1. 用 `multiprocessing.Process` 拉起 Scheduler 子进程（每个 TP rank 一个）；
2. 拉起 DetokenizerManager 子进程；
3. 在主进程内创建 TokenizerManager。

启动入口链：

```
sglang serve                                    (python/sglang/cli/serve.py)
   或 python -m sglang.launch_server            (launch_server.py:run_server, 第15行)
        └─▶ http_server.py:launch_server()       (第2717行)
              └─▶ Engine / _launch_subprocesses() (engine.py:765)
```

## 3. 进程间通信：ZMQ 通道设计

所有 ZMQ 通道在 `server_args.py` 的 `class PortArgs` 中定义。四条关键通道构成数据流的骨架：

| 通道字段 | 方向 | 传什么 |
|----------|------|--------|
| `scheduler_input_ipc_name` | TokenizerManager → Scheduler | token 化后的请求 |
| `detokenizer_ipc_name` | Scheduler → DetokenizerManager | 生成的输出 token id |
| `tokenizer_ipc_name` | DetokenizerManager → TokenizerManager | 还原后的文本 |
| `rpc_ipc_name` | Engine ↔ Scheduler | 控制类 RPC |
| `nccl_port` | 各 TP rank 之间 | 张量并行的集合通信（走 NCCL，非 ZMQ） |

- 单机默认用 `ipc://<临时文件>`（Unix domain socket，本机高效）。
- 多机分布式时切换为 `tcp://`。

> 注意区分：**ZMQ** 用于「进程间控制流」；**NCCL** 用于「GPU 之间的张量数据流」（TP/PP/EP 通信）。两者各司其职。

## 4. 一次请求的关键流程（宏观）

以最常见的 `/generate` 流式请求为例，宏观流程如下（细节数据结构见文档 02）：

```
① 用户 HTTP 请求
     http_server.py  →  /generate 路由 (FastAPI, 主进程)
                        │
② TokenizerManager.generate_request()            [tokenizer_manager.py:624]
     - 文本 tokenize 成 input_ids
     - 通过 ZMQ 发给 Scheduler
                        │
③ Scheduler 主循环 (子进程)                        [scheduler.py:event_loop_normal:1676]
     while True:
       a. recv_requests()          收请求、入队
       b. get_next_batch_to_run()  组 batch（prefill 优先，否则 decode）
       c. run_batch()              调 GPU 前向 + 采样
       d. process_batch_result()   处理结果、写回前缀缓存、发给 Detok
                        │
④ DetokenizerManager (子进程)                      [detokenizer_manager.py:event_loop:166]
     - token id 增量 detokenize 成文本
     - 通过 ZMQ 回传主进程
                        │
⑤ TokenizerManager._handle_batch_output()         [tokenizer_manager.py:1899]
     - 聚合结果
     - http_server 以 SSE 流式返回用户
```

decode 阶段每生成一个 token 就走一遍 ③→⑤ 的循环，直到遇到 EOS 或达到 `max_new_tokens`。

## 5. Scheduler 主循环：系统的心脏

Scheduler 是整个系统最核心的模块。它有两种主循环实现（`scheduler.py`）：

### 5.1 `event_loop_normal`（第 1520 行）—— 教学版

```python
while True:
    recv_reqs = self.request_receiver.recv_requests()   # ① 收请求
    self.process_input_requests(recv_reqs)              #    入队
    plan = self.get_next_batch_to_run(...)              # ② 组 batch
    batch = plan.batch_to_run
    if batch:
        result = self.run_batch(batch)                  # ③ GPU 前向 + 采样
        self.process_batch_result(batch, result)        # ④ 处理结果
    self.last_batch = batch
```

这就是 **Continuous Batching** 的骨架：这是一个死循环，每转一圈处理「一步」。每一圈都可以：
- 加入刚到达的新请求；
- 剔除刚完成的请求；
- 对正在运行的请求各生成一个 token。

不需要等一整个 batch 全部结束才处理下一批——这正是「连续」的含义，显著提升了 GPU 利用率。

### 5.2 `event_loop_overlap`（第 1554 行）—— 生产版

生产环境默认走 overlap 版本。核心优化：**把「处理上一批结果」延后到「本批 GPU 前向已经启动之后」**，让 CPU 整理结果的时间与 GPU 计算重叠。

```python
batch_result = self.run_batch(batch)          # 先把这批异步发给 GPU
self.result_queue.append((batch.copy(), batch_result))
if self.last_batch:                            # 再回头处理上一批的结果
    pop_and_process()                          #   （此时 GPU 正忙）
```

源码中还有一个细节（第 1632 行注释，中译）：

> 「对于连续两个 prefill 批，我们禁用 overlap 以改善第一批的 TTFT（首 token 延迟）。这可能轻微损害吞吐，因此用环境变量控制。」

即在延迟敏感的场景做了针对性权衡。

> `--disable-overlap-schedule` 参数可关闭 overlap，退回 normal 循环（调试时有用）。

## 6. 核心设计点提炼

### 6.1 RadixAttention（前缀缓存）
把不同请求**共享的公共前缀**（如相同 system prompt、多轮对话历史）的 KV Cache 只算一次，存进一棵**基数树（Radix Tree）**，后续请求命中前缀即可直接复用，跳过重复 prefill。文件：`mem_cache/radix_cache.py`。这是 SGLang 相比早期方案的招牌优化，在多轮/多分支生成场景收益巨大。

### 6.2 Prefill / Decode 两阶段
- **Prefill（EXTEND）**：一次性处理整段输入 prompt，多 token 并行计算，**计算密集**。
- **Decode**：每步只生成 1 个 token，**访存密集**（读全部历史 KV），batch 越大越划算。

Scheduler 的调度策略是 **prefill 优先**：有新请求可 prefill 时优先 prefill，否则对运行中的请求做 decode。二者对应不同的 Attention kernel 优化路径。

### 6.3 Overlap 调度
如 5.2 所述，CPU 调度与 GPU 计算重叠，压榨 GPU 空闲时间。

### 6.4 可插拔 Attention 后端
`AttentionBackend` 抽象基类（`layers/attention/base_attn_backend.py`）定义统一接口，具体实现有 FlashInfer、FlashAttention3、Triton、MLA 专用后端等，通过 `attention_registry.py` 注册选择。可用 `--attention-backend` 指定。

### 6.5 多种并行 + PD 分离
- **TP / DP / PP / EP**：张量 / 数据 / 流水线 / 专家并行，覆盖从单卡到大规模集群。
- **PD 分离**：Prefill 与 Decode 拆到不同节点，各自独立扩缩容，KV Cache 通过 RDMA（Mooncake/NIXL 等）跨节点传输。由 `--disaggregation-mode` 一个开关切换角色。

详见文档 05。

## 7. 小结与下一步

本篇建立了全局认知：
- SGLang `srt` 是**多进程 + ZMQ + NCCL** 架构；
- 数据流是 **Tokenize → Schedule/Forward → Detokenize** 三段式；
- Scheduler 主循环 + Continuous Batching 是心脏；
- RadixAttention、Overlap 调度、可插拔后端、并行/PD 分离是核心设计点。
