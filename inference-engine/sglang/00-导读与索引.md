## 二、一张图看懂 SGLang

SGLang（SGL RunTime，简称 `srt`）是一个高性能 LLM 推理与服务引擎。它的服务端本质是一个**多进程流水线**：

```
 ┌──────────────────────── 主进程 (main process) ─────────────────────────┐
 │   FastAPI HTTP Server                                                    │
 │        │                                                                 │
 │        ▼                                                                 │
 │   TokenizerManager  ── 负责：文本→token、请求状态管理、结果聚合           │
 └────────┬───────────────────────────────────────────▲────────────────────┘
          │ ZMQ: scheduler_input_ipc                   │ ZMQ: tokenizer_ipc
          ▼                                            │
 ┌─────────────────────────┐   ZMQ: detokenizer_ipc  ┌─┴──────────────────────┐
 │  Scheduler (子进程)       │ ───────────────────────▶│  DetokenizerManager     │
 │   每个 TP rank 一个        │                         │   (子进程)               │
 │   ├─ 调度决策 (组 batch)   │                         │   token id → 文本(增量)  │
 │   ├─ RadixCache (前缀缓存) │                         └─────────────────────────┘
 │   └─ TpModelWorker         │
 │        └─ ModelRunner (GPU 前向)  ── NCCL ──▶ 其他 TP rank
 └─────────────────────────┘
```

**三段式数据流**：
1. **Tokenize 段**（主进程）：TokenizerManager 把文本变成 token id。
2. **Schedule + Forward 段**（Scheduler 子进程）：组 batch → GPU 前向 → 采样出新 token。
3. **Detokenize 段**（Detok 子进程）：把 token id 增量还原成文本，回传主进程。

**为什么拆成多进程？** Python 有 GIL（全局解释器锁）。把 CPU 密集的 tokenize/detokenize 从 GPU 调度循环里剥离出去，Scheduler 才能专心喂 GPU，避免 CPU 工作阻塞推理主循环。

## 三、核心概念速查表

| 概念 | 一句话解释 | 详见 |
|------|-----------|------|
| **Continuous Batching** | 每一步迭代都能动态增删请求，而非等整个 batch 跑完 | 01 / 03 |
| **RadixAttention / RadixCache** | 用基数树缓存并复用请求间共享的前缀 KV，省掉重复 prefill | 06 |
| **Prefill / Decode** | prefill=一次处理整段输入 prompt（计算密集）；decode=每步生成 1 个 token（访存密集） | 02 / 03 |
| **Overlap Scheduler** | 让 CPU 调度与 GPU 计算重叠执行，提升吞吐 | 03 |
| **ForwardMode** | 一次前向的模式：EXTEND / DECODE / IDLE / MIXED 等 | 02 |
| **KV Cache Pool** | GPU 显存里存放注意力 KV 的池子，槽位由 allocator 管理 | 02 / 03 |
| **Attention Backend** | 可插拔的注意力内核实现（FlashInfer / FA3 / Triton…） | 03 |
| **TP / DP / PP / EP** | 张量并行 / 数据并行 / 流水线并行 / 专家并行 | 05 |
| **PD Disaggregation** | 把 Prefill 与 Decode 拆到不同节点，KV 通过 RDMA 传输 | 05 |

## 五、贯穿全系列的统一示例（请记住这个设定）

后面每篇都会回到**这一个例子**，你会看到同一份数据在各层的形态变化。

### 5.1 场景设定

启动一个单机服务：
```bash
python -m sglang.launch_server --model-path Qwen/Qwen2.5-7B-Instruct --port 30000
```
并发发来两个**共享同一段 system prompt** 的请求（故意这样设计，用来演示前缀缓存复用）：

- **请求 A**：`"你是一个助手。请问 1+1 等于几？"`
- **请求 B**：`"你是一个助手。请问天空为什么是蓝色的？"`

为了让数字干净，本系列统一约定（真实分词会有出入，但不影响理解）：

| 量 | 值 | 说明 |
|----|----|----|
| 公共前缀 `"你是一个助手。请问"` | `[101,102,103,104,105]` | 5 个 token，A/B 共享 |
| A 独有部分 `"1+1 等于几？"` | `[201,202,203]` | 3 个 token |
| B 独有部分 `"天空为什么是蓝色的？"` | `[301,302,303,304]` | 4 个 token |
| `page_size` | 1（默认） | 一个 page 存 1 个 token 的 KV |
| `max_new_tokens` | 64 | 最多生成 64 个 token |

于是：A 的输入 = `[101,102,103,104,105,201,202,203]`（8 token），B 的输入 = `[101,102,103,104,105,301,302,303,304]`（9 token）。

### 5.2 数据「一路变形」总览（本系列主线）

```
"你是一个助手。请问1+1等于几？"        (Python str)
        │ tokenize (TokenizerManager)                 [02篇]
        ▼
[101,102,103,104,105,201,202,203]     (list[int])
        │ ZMQ → Scheduler，构造请求对象                [02/03篇]
        ▼
Req(origin_input_ids=[...], output_ids=[], prefix_indices=[...])
        │ 组批 + RadixCache.match_prefix（B 命中 A 的前缀！）  [06篇]
        ▼
ScheduleBatch(reqs=[A], forward_mode=EXTEND, out_cache_loc=[...])   (CPU 调度对象)
        │ ForwardBatch.init_new                       [02/03篇]
        ▼
ForwardBatch(input_ids=<GPU tensor>, forward_mode=EXTEND, ...)     (GPU 张量对象)
        │ ModelRunner.forward → logits → sample       [03篇]
        ▼
next_token = 501
        │ 追加 output_ids；RadixCache 写回缓存；ZMQ → Detokenizer  [06篇]
        ▼
"2"  (增量 detokenize)                                 [02篇]
        │ ZMQ → TokenizerManager → SSE
        ▼
返回给用户: "2。"
```

> 「B 命中 A 的前缀、共享 KV 槽」这个机制是真实的，06 篇会用源码证明。

## 六、vLLM ↔ SGLang 机制对照表（熟悉 vLLM 的读者速看）

两者都是高性能 LLM 推理引擎，核心思想相通（多进程、连续批处理、前缀复用），但在**前缀缓存的数据结构**上走了不同的路——这是二者最大的区别。

### 6.1 术语/组件对照

| 维度 | vLLM (v1) | SGLang (srt) | 说明 |
|------|-----------|--------------|------|
| 引擎心跳 | `EngineCore.step()`（busy loop） | `Scheduler.event_loop_normal/overlap()` | 都是死循环，每轮推进一步 |
| 调度器 | `Scheduler.schedule()` | `Scheduler.get_next_batch_to_run()` | 每步决定跑哪些请求 |
| 请求对象 | `Request` | `Req` | 请求生命周期状态载体 |
| 任务清单 | `SchedulerOutput` | `ScheduleBatch` → `ForwardBatch` | 调度决策交给 GPU 的接口 |
| 前缀缓存 | **PagedAttention + Prefix Caching**（block 分页 + 哈希链） | **RadixAttention**（基数树 Radix Tree） | **核心差异，见下** |
| 缓存单元 | `KVCacheBlock`（固定 block，默认 16 token） | `TreeNode`（变长 key，按 page 对齐） | |
| 复用判据 | block 哈希匹配（带父哈希链） | 基数树最长公共前缀匹配 | |
| 防误删机制 | `ref_cnt`（引用计数） | `lock_ref`（引用计数）+ evictable/protected | 思想一致 |
| 逐出策略 | LRU（自造双向链表） | LRU（可插拔 eviction_strategy + 堆） | |
| 显存不足 | `_preempt_request`（抢占，丢 KV 退回队列） | `retract_decode`（抢占，回收 KV 重新入队） | 思想一致 |
| KV 内存管理 | `BlockPool` + block_table | `ReqToTokenPool` + `TokenToKVPool` + allocator | |
| 进程通信 | ZMQ + msgspec | ZMQ + NCCL | |
| Detokenize | 主进程 | 独立 `DetokenizerManager` 子进程 | SGLang 拆得更彻底 |
| PD 分离 | `KVConnectorBase_V1`（scheduler/worker 分身） | `disaggregation/` 各 Mixin + `KVSender/Receiver` | 思想一致 |

### 6.2 最关键的区别：Block 分页 vs 基数树

- **vLLM PagedAttention**：把 KV 切成**固定大小的 block**（如 16 token/块），像操作系统分页一样管理，前缀共享靠「block 哈希匹配」。优点是显存零碎片、实现规整。
- **SGLang RadixAttention**：用一棵**基数树（Radix Tree）**把所有请求的 token 序列按公共前缀合并存储，前缀匹配是「树上找最长公共前缀路径」。优点是**前缀共享更自然、更细粒度**（尤其多轮对话/多分支生成场景），命中时直接复用整条路径的 KV。

> 一句话：**vLLM 用「哈希表 + 定长块」找前缀，SGLang 用「基数树」找前缀。** 二者都实现了「能复用的 KV 就别重算」，但 SGLang 的树结构天然表达前缀的层级共享关系。详见 06 篇。
