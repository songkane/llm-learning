# 05 · 部署场景分析：单机 / 多机 / PD 分离

> 本篇重点分析 SGLang 三种典型部署形态：**单机**、**多机（TP/DP/PP/EP）**、**PD 分离（Prefill-Decode Disaggregation）**，讲清各自的进程/通信模型与数据流。
>
> **代码版本**：`sgl-project/sglang` @ **tag `v0.5.16`**（2026-07-24 发布）。详见 [00 篇 · 分析的代码库版本](./00-导读与索引.md)。

## 零、先分清两件不同的事：并行 ≠ PD 分离

很多人把「多机并行」和「PD 分离」混在一起，其实它们解决**两个不同层面的问题**：

| | 多机/多卡并行（TP/PP/DP/EP） | PD 分离（Disaggregation） |
|---|---|---|
| 解决什么 | 一个模型/一批请求，一台机器算不动 → **把同一份计算摊到多卡/多机** | prefill 和 decode 负载特征不同 → **拆成两组实例分别扩容** |
| 拆的维度 | 把**模型或数据**切开 | 把**请求的两个阶段**切开 |
| 关键抽象 | `parallel_state.py` 的并行组 + `GroupCoordinator` | `disaggregation/` 的 `KVSender`/`KVReceiver` + `DisaggregationMode` |
| 通信内容 | 激活值 / 权重分片（NCCL） | **KV cache**（跨实例 RDMA 搬运） |
| 关键参数 | `--tp/pp/dp/ep-size` `--nnodes` `--node-rank` | `--disaggregation-mode` `--disaggregation-transfer-backend` |

一句话记忆：
- **并行**是「一份活多人一起干」；
- **PD 分离**是「流水线上两道工序拆到两个车间」。

两者**可以叠加**：一个 prefill 实例内部也可以是 TP=8 的多卡并行。本篇「六」节会给出四种机制（并行 + PD 分离 + RadixCache + 连续批处理）同时起作用的叠加图。

## 一、单机部署（Single Node）

### 1.1 场景
模型能放进单机（1~8 卡）显存，最常见的开发/中小规模生产形态。

### 1.2 启动示例
```bash
# 单卡
python -m sglang.launch_server --model-path Qwen/Qwen2.5-7B-Instruct --port 30000

# 单机 4 卡张量并行
python -m sglang.launch_server --model-path Qwen/Qwen2.5-72B-Instruct \
    --tp-size 4 --port 30000
```

### 1.3 进程与通信模型
```
主进程: HTTP Server + TokenizerManager
  │ ZMQ (ipc://临时文件, 本机)
  ▼
Scheduler 子进程 × tp_size   ← 每个 TP rank 一个
  └ TpModelWorker → ModelRunner
       │ NCCL (本机 NVLink/PCIe)
       ▼  TP rank 之间做 all-reduce / all-gather
DetokenizerManager 子进程
```

- **ZMQ 走 `ipc://`**（Unix domain socket，本机高效）。
- **TP rank 间走 NCCL**，本机通过 NVLink 或 PCIe 通信。
- `tp_size=4` 表示每个 Transformer 层的权重矩阵被切成 4 份，分布在 4 张卡上，每次前向做一次 all-reduce 汇总。

### 1.4 关键点
- 单机 TP 通信成本低（NVLink），扩展性好。
- `--mem-fraction-static` 控制每卡 KV 池大小。
- RadixCache 在单机内全局共享（同一个 Scheduler 进程组）。

## 二、多机部署（Multi-Node）

### 2.1 场景
模型太大（如 DeepSeek-V3 671B），单机装不下，需跨多台机器。

### 2.2 并行维度组合

| 并行 | 参数 | 切什么 | 通信模式 |
|------|------|--------|----------|
| **TP**（张量并行） | `--tp-size` | 每层权重矩阵横/纵切 | all-reduce（频繁，需高带宽） |
| **PP**（流水线并行） | `--pp-size` | 按层切成多段 | 点对点（stage 间传激活） |
| **DP**（数据并行） | `--dp-size` | 复制多份模型，分摊请求 | 请求级，几乎无通信 |
| **EP**（专家并行） | `--ep-size` | MoE 专家分到不同卡 | all-to-all（token 路由） |

**总 GPU 数 ≈ `tp_size × pp_size × dp_size`**，分布在 `nnodes` 台机器上。

### 2.3 启动示例（2 机 16 卡，TP=16）
```bash
# 节点 0（head，IP=192.168.0.2）
python -m sglang.launch_server --model-path deepseek-ai/DeepSeek-V3 \
    --tp-size 16 --nnodes 2 --node-rank 0 \
    --dist-init-addr 192.168.0.2:25000 --port 30000

# 节点 1
python -m sglang.launch_server --model-path deepseek-ai/DeepSeek-V3 \
    --tp-size 16 --nnodes 2 --node-rank 1 \
    --dist-init-addr 192.168.0.2:25000 --port 30000
```

- 两台机器用**同一个 `--dist-init-addr`**（head 节点地址）做 rendezvous。
- `--node-rank` 每台不同（0、1）。

### 2.5 并行组的管理：`GroupCoordinator`

`parallel_state.py:216` 的 `GroupCoordinator` 封装一个进程组的集合通信（all_reduce/all_gather/broadcast），并自动挑选最优通信器（pynccl / custom all-reduce / symmetric memory）。各组通过全局单例获取：
- TP：`get_tp_group()`（第 1792 行）
- PP：`get_pp_group()`（第 1851 行）
- EP：`_MOE_EP` 组（第 1826 行）
- World：`get_world_group()`（第 1709 行）

Scheduler 侧引用（`scheduler.py:901` 起）：
```python

self.pp_group = get_pp_group()

```

### 2.6 DP Attention（重要优化）

大规模 TP 下，attention 层的 all-reduce 通信会成为瓶颈。**DP attention**（`--enable-dp-attention`，要求 `dp_size==tp_size`）让：
- **attention 层走数据并行**（各 rank 处理不同请求，无需 all-reduce）；
- **FFN/MoE 层走张量并行**。

实现：`layers/dp_attention.py`
- `compute_dp_attention_world_info()`（第 293 行）：由 tp_rank 推算 `(attn_tp_rank, attn_dp_rank, ...)`；
- `dp_gather_partial()` / `dp_scatter()`（第 616 / 632 行）：attention 前后做数据的聚集/散播。

适用于 DeepSeek-V2/V3、Qwen MoE 等，显著降低通信开销。此时某些 rank 若无请求会走 `IDLE` 模式保持同步。

## 三、PD 分离（Prefill-Decode Disaggregation）

### 3.1 为什么要 PD 分离

Prefill 和 Decode 的资源特征截然不同：
- **Prefill**：计算密集（一次算整段 prompt），吃算力。
- **Decode**：访存密集（每步读全部 KV），吃显存带宽，且持续时间长。

混在一起会互相干扰：长 prefill 会拖慢正在 decode 的请求的 TPOT（每 token 延迟）。**PD 分离**把二者拆到不同节点，各自独立扩缩容、各自优化，互不干扰。

### 3.2 核心开关

`--disaggregation-mode`（`server_args.py:2519`）：
- `null`：不分离（普通模式）
- `prefill`：本节点只做 prefill
- `decode`：本节点只做 decode

对应枚举（`disaggregation/utils.py:68`，中译）：
```python
class DisaggregationMode(Enum):
    NULL = "null"        # 非分离（普通模式）
    PREFILL = "prefill"  # Prefill 节点
    DECODE = "decode"    # Decode 节点
```
Scheduler 中转成枚举（`scheduler.py:1116`），**贯穿全 Scheduler 数十处分支判断**，决定创建哪些队列、跑哪个事件循环、请求进哪个队列。

### 3.3 启动示例
```bash
# Prefill 节点
python -m sglang.launch_server --model-path <model> \
    --disaggregation-mode prefill \
    --disaggregation-transfer-backend mooncake \
    --disaggregation-bootstrap-port 8998 --port 30000

# Decode 节点
python -m sglang.launch_server --model-path <model> \
    --disaggregation-mode decode \
    --disaggregation-transfer-backend mooncake --port 30001
```
（前面通常还有一个 router/负载均衡分发请求）

### 3.4 整体数据流

```
Client 请求
   │
   ▼
┌──────────────── Prefill 节点 ────────────────┐
│ 1. bootstrap 握手 (ZMQ/HTTP) 与 decode 端建连  │
│ 2. 前向计算，生成整段 prompt 的 KV Cache        │
│ 3. KVSender.send() 分块 RDMA 传输 KV           │
└──────────────────┬───────────────────────────┘
                   │  KV Cache 跨节点传输
                   │  (Mooncake / NIXL, 走 RDMA/InfiniBand)
                   ▼
┌──────────────── Decode 节点 ─────────────────┐
│ 4. DecodePreallocQueue 预分配 KV 空间          │
│    + 创建 KVReceiver 连接 prefill bootstrap    │
│ 5. KVReceiver 接收 KV，poll 到 Success         │
│ 6. DecodeTransferQueue commit → 进 running batch│
│ 7. 自回归 decode，流式输出 token                │
└───────────────────────────────────────────────┘
```

#### 事件循环分发（`dispatch_event_loop()`，`scheduler.py:4478`）

v0.5.16 把分发逻辑独立成一个模块级函数 `dispatch_event_loop(scheduler)`，由 `Scheduler.run_event_loop()`（`scheduler.py:1469`）调用。真实代码（第 4482-4506 行，已加中文注释）：
```python
if disaggregation_mode == DisaggregationMode.NULL:          # 普通模式（不分离）
    if scheduler.enable_pdmux:
        scheduler.event_loop_pdmux()                         # PD 复用
    elif server_args.pp_size > 1:
        scheduler.event_loop_pp()                            # 流水线并行
    elif scheduler.enable_overlap_mlx:
        scheduler.event_loop_overlap_mlx()                   # MLX 后端重叠
    elif scheduler.enable_overlap:
        scheduler.event_loop_overlap()                       # ★ 生产默认：CPU/GPU 重叠
    else:
        scheduler.event_loop_normal()                        # ★ 标准循环
elif disaggregation_mode == DisaggregationMode.PREFILL:      # 仅 prefill 节点
    if server_args.pp_size > 1:
        scheduler.event_loop_pp_disagg_prefill()
    elif scheduler.enable_overlap:
        scheduler.event_loop_overlap_disagg_prefill()
    else:
        scheduler.event_loop_normal_disagg_prefill()
elif disaggregation_mode == DisaggregationMode.DECODE:       # 仅 decode 节点
    if server_args.pp_size > 1:
        scheduler.event_loop_pp_disagg_decode()
    elif scheduler.enable_overlap:
        scheduler.event_loop_overlap_disagg_decode()
    else:
        scheduler.event_loop_normal_disagg_decode()
```

【逻辑】这是「一个开关决定整机行为」的集中体现：`disaggregation_mode` 选大方向（不分离/仅 prefill/仅 decode），再按 `pp_size`、`enable_overlap` 等选具体实现。共 3×N 种事件循环，但内在结构高度对称。

### 3.6 KV 传输状态机

`KVPoll`（`base/conn.py:84`）：
```python
Failed = 0
Bootstrapping = 1     # 握手中
WaitingForInput = 2   # 等待输入
Transferring = 3      # 传输中
Success = 4           # 完成
```

`KVArgs`（`base/conn.py:38`）描述 KV Cache 内存布局（`kv_data_ptrs`、`kv_item_lens`、`page_size`、TP/PP 切片信息）传给传输后端，后端据此做点对点 RDMA。

### 3.9 TP 一致性保证

PD 分离下有多个 TP rank，必须保证它们**状态同步推进**（否则部分 rank 提前 commit 会死锁/错乱）。`poll_and_all_reduce()`（`utils.py:129`）用 `ReduceOp.MIN` 归约所有 rank 的 `KVPoll` 状态——**只有所有 rank 都到某状态，才整体推进**。

## 四、三种场景对比

| 维度 | 单机 | 多机 | PD 分离 |
|------|------|------|---------|
| 适用 | 中小模型 | 超大模型 | 高并发/延迟敏感生产 |
| 进程通信 | ZMQ ipc + NCCL(本机) | ZMQ tcp + NCCL(跨机) | + KV RDMA 传输 |
| 关键参数 | `--tp-size` `--mem-fraction-static` | `--tp/pp/dp/ep-size` `--nnodes` `--node-rank` `--dist-init-addr` | `--disaggregation-mode` `--disaggregation-transfer-backend` |
| KV Cache | 单进程组共享 | 各 TP rank 分片 | 跨节点单向传输 (P→D) |
| 核心优化 | RadixCache | DP attention、EP | Prefill/Decode 独立扩缩容 |
| 复杂度 | 低 | 中 | 高 |

---

## 五、部署选型建议

1. **模型放得下单机** → 单机 + 合适 `--tp-size`，开 RadixCache，够用且简单。
2. **模型放不下单机** → 多机 TP（+PP）；MoE 模型加 EP + DP attention。
3. **超高并发 / 严格 SLA（TTFT 和 TPOT 都要保证）** → PD 分离，Prefill 池和 Decode 池按各自负载独立扩缩容。
4. **需要 KV RDMA 的 PD 分离** → 准备好 InfiniBand/RDMA 网络，选 `mooncake` 或 `nixl` 后端，配 `--disaggregation-ib-device`。

## 六、四种机制叠加图（把统一示例放到 TP=2 + PD 分离下）★

回到 00 篇的 A、B 两请求，看它们在「TP=2 + PD 分离」的部署下同时经历哪些机制：

```
                     Prefill 实例 (disaggregation-mode=prefill, 内部 TP=2)
                   ┌───────────────────────────────────────────┐
  A(8 tok) ───────▶│ 一次算完 8 token → 产出首 token + KV         │
  B(共享A前缀)─────▶│ B 只算新增 4 token（RadixCache 前缀复用,06篇）│
                   │ 每层计算摊在 2 张卡并行，逐层 all-reduce(NCCL) │
                   └──────────────┬────────────────────────────┘
                                  │ KVSender.send() 分块 RDMA 搬 KV
                                  │ (mooncake/nixl, KVPoll 状态机跟踪)
                                  ▼
                     Decode 实例 (disaggregation-mode=decode, 内部 TP=2)
                   ┌───────────────────────────────────────────┐
  逐 step 吐字 ◀────│ KVReceiver 收 KV → 直接续写：每步只算 1 token │
  (连续批处理,03篇) │ A、B 合并成 batch 一起 decode，共享资源       │
                   │ 每层计算摊在 2 张卡并行，逐层 all-reduce(NCCL) │
                   └───────────────────────────────────────────┘
```

**四层机制在这里同时起作用，各管各的一层，互不冲突：**

| 机制 | 作用位置 | 详见 |
|------|---------|------|
| **张量并行 TP=2** | 每个实例内部，每层计算摊到 2 卡，逐层 all-reduce | 本篇 二 |
| **PD 分离** | A/B 的 prefill 在左实例、decode 在右实例，KV 跨实例搬 | 本篇 三 |
| **RadixCache 前缀复用** | 即使在 Prefill 实例内，B 仍命中 A 的前缀省重算 | 06 篇 |
| **连续批处理** | 在 Decode 实例里，A/B 按预算合并成 batch 逐步吐字 | 03 篇 |

> 这张图揭示了 SGLang 的架构美感：不同机制正交解耦，可自由组合。理解了每一层，就理解了整个系统在任意部署形态下的行为。
