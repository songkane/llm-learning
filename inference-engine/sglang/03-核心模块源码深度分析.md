## 一、Scheduler 调度决策

文件：`python/sglang/srt/managers/scheduler.py`

### 1.1 两种主循环

Scheduler 有两种事件循环，通过 `--disable-overlap-schedule` 切换：

- `event_loop_normal`（第 1520 行）—— 标准循环，逻辑清晰，适合理解。
- `event_loop_overlap`（第 1554 行）—— 生产默认，CPU/GPU 重叠。

#### `event_loop_normal` 源码（第 1520-1552 行，含中译）

```python
def event_loop_normal(self):
    """A normal scheduler loop."""    # 一个标准的调度器循环
    while True:
        if self.gracefully_exit:
            break
        # Receive requests                          （接收请求）
        recv_reqs = self.request_receiver.recv_requests()
        self.process_input_requests(recv_reqs)
        if self._engine_paused:
            continue
        # Get the next batch to run                 （获取下一个要运行的 batch）
        plan = self.get_next_batch_to_run(
            running_batch=self.running_batch, last_batch=self.last_batch
        )
        self.running_batch = plan.running_batch
        batch = plan.batch_to_run
        # Launch the current batch                  （启动当前 batch）
        if batch:
            result = self.run_batch(batch)
            self.process_batch_result(batch, result)
        else:
            # When the server is idle, do self-check and re-init some states.
            # （服务空闲时，做自检并重新初始化一些状态）
            self._sched_idled = True
            self.on_idle()
        # Update last_batch                          （更新 last_batch）
        self.last_batch = batch
```

**逐行精读：**
- `def event_loop_normal(self):`
  - 【Python】`self` 是「当前对象自己」（相当于 this）。Python 方法第一个参数永远显式写 `self`。
- `while True:`
  - 【逻辑】死循环，就是引擎「一直活着等活干」的心跳。每转一圈推进「一步」。
  - 【Python】`while True:` 是标准的「靠内部 break/return 退出」的无限循环写法。Python 用缩进（4 空格）表示代码块归属，没有大括号。
- `recv_reqs = self.request_receiver.recv_requests()`
  - 【逻辑】从 ZMQ 收新到达的请求（TokenizerManager 发来的 token 化请求）。
- `self.process_input_requests(recv_reqs)`
  - 【逻辑】把新请求构造成 `Req` 对象、入 `waiting_queue`。
- `if self._engine_paused: continue`
  - 【Python】`continue` 跳过本轮剩余、直接进入下一轮循环。
- `plan = self.get_next_batch_to_run(...)`
  - 【逻辑】**调度决策**：决定这一轮 GPU 跑哪些请求（prefill 优先，否则 decode），返回一个 `NextBatchPlan`。
- `batch = plan.batch_to_run`
  - 【逻辑】取出本轮实际要执行的批次；可能为 `None`（无事可做）。
- `if batch: result = self.run_batch(batch); self.process_batch_result(batch, result)`
  - 【逻辑】**执行 + 记账**：`run_batch` 送 GPU 前向 + 采样；`process_batch_result` 把新 token 写回、判停、写回前缀缓存、发给 Detokenizer。
- `else: ... self.on_idle()`
  - 【逻辑】空闲时做自检、重置状态。
- `self.last_batch = batch`
  - 【逻辑】记录上一轮批次，供下一轮把 prefill 批合并进 decode 的 `running_batch`。

**★ 一句话总结 event_loop：** 收请求 → `get_next_batch_to_run` 挑活 → `run_batch` 算 → `process_batch_result` 记账。三步一循环，每循环一次每个请求前进一个 token。这与 vLLM 的 `EngineCore.step()`（schedule→execute→update）是同一套思想。

#### `event_loop_overlap` 的重叠技巧（第 1600-1627 行，含中译）

```python
# Launch the current batch                          （启动当前 batch）
if batch:
    batch_result = self.run_batch(batch)
    # Fence result processing behind this forward's shared reads.
    # （在本次前向的共享读操作之后，为结果处理设置栅栏）
    self._apply_war_barrier()
    self.result_queue.append((batch.copy(), batch_result))

# Process the last batch                             （处理上一批）
if self.last_batch:
    if not disable_overlap_for_batch:
        pop_and_process()   # 此刻 GPU 正在算当前批，CPU 同时处理上一批结果
```

第 1632 行注释（中译）：

> 「对于连续两个 prefill 批，我们禁用 overlap，以改善第一批的 TTFT（首 token 延迟）。这可能轻微损害吞吐，因此用环境变量控制。」

> 教学要点：overlap 的本质是**软件流水线**——GPU 算第 N 批时，CPU 已在准备第 N+1 批并回收第 N-1 批的结果，三者交叠，GPU 不空转。

### 1.2 批次决策：`get_next_batch_to_run`（第 2687 行）

核心是 **prefill 优先** 策略。关键决策分支（第 2796-2805 行）逻辑：

```
if new_batch is not None:          # 有新 prefill 可跑
    ret = new_batch                #   → 优先跑 prefill
else:                              # 否则
    if running_batch 非空 且 非 prefill_only:
        running_batch = self.update_running_batch(running_batch)
        ret = running_batch        #   → 跑 decode
    else:
        ret = None                 #   → 空闲

return NextBatchPlan(batch_to_run=ret, running_batch=running_batch)  # 第3061行
```

其中：
- `get_new_batch_prefill`（第 2829 行）：用 `PrefillAdder` 从 `waiting_queue` 挑请求，做 token 预算与内存检查，命中 RadixCache 前缀，然后 `prepare_for_extend`。
- `update_running_batch`（第 3140 行）：`filter_batch` 移除已完成请求；做 decode OOM 检查，不足时 `retract_decode` 抢占回收 KV；最后 `prepare_for_decode` 给每个请求分配 1 个新槽。

**prefill 优先的原因**：尽快把新请求的 prompt 处理完（降低 TTFT），让它们尽早进入 decode 流水线，提高整体并发。

### 1.3 抢占（Retract）机制

decode 阶段显存可能不够（因为序列在增长，KV 越来越大）。`update_running_batch`（第 3150-3216 行）中，若 `check_decode_mem()` 失败，会调用 `batch.retract_decode()`：**回收部分请求的 KV 缓存、把它们重新塞回等待队列**，腾出显存给其余请求继续。这保证了系统在高负载下不 OOM，代价是被抢占请求需重新排队。`schedule_conservativeness` 参数越大越保守，可减少抢占频率。

## 二、RadixCache 前缀缓存（见专篇）

RadixCache 是 SGLang 的招牌技术，涉及基数树结构、`match_prefix`/`_split_node` 匹配分裂算法、`lock_ref` 引用计数状态机、LRU 逐出等，内容较多，已独立成 **[06-RadixCache 深度剖析](./06-RadixCache深度剖析.md)** 专篇（含真实源码逐行注释与统一示例演示）。

这里只强调 Scheduler 与它的交互点：
- 组 prefill 批时，`get_new_batch_prefill` → `PrefillAdder` 会对每个候选请求调 `RadixCache.match_prefix()`，命中的前缀 KV 直接复用（填入 `Req.prefix_indices`），只需 prefill 未命中的部分。
- 请求运行期间，其命中的前缀节点被 `inc_lock_ref` 锁定（`lock_ref>0`），不会被逐出。
- 请求结束时，`process_batch_result` 调 `cache_finished_req` 把完整序列 KV 写回树、并 `dec_lock_ref` 解锁。
- 显存紧张时，`evict` 按 LRU 逐出未锁定的叶子释放 KV 槽。

> `extra_key`（LoRA id / 采样 salt / RAG 上下文等）保证只有**语义上确实相同**的前缀才复用 KV，不同上下文绝不串味。

## 三、ModelRunner 前向

文件：`python/sglang/srt/model_executor/model_runner.py`

### 3.1 调用链

```
Scheduler.run_batch()
  → TpModelWorker.forward_batch_generation()   [tp_worker.py:529]
      → ModelRunner.forward(forward_batch)      [model_runner.py:1232]
          → _forward_raw()                      [model_runner.py:1376]
              → 模型 forward（各层，Attention 通过 attn_backend）
      → ModelRunner.sample()                    采样 next_token_ids
```

### 3.2 `forward` 按模式分派

`ModelRunner.forward()`（第 1232 行）根据 `forward_batch.forward_mode` 选择路径：
- EXTEND / MIXED → prefill 路径；
- DECODE → decode 路径（通常配合 CUDA Graph 加速）；
- IDLE → 空跑（DP attention 下保持各 rank 同步）。

### 3.3 Attention 后端初始化

`init_attention_backends()`（第 819 行）根据 `--attention-backend` 等参数创建 `self.attn_backend`（第 837 行）。支持按 prefill/decode 分别指定不同后端（`--prefill-attention-backend` / `--decode-attention-backend` 优先级高于 `--attention-backend`）。

### 3.4 CUDA Graph 加速 decode

decode 阶段每步计算量小、kernel launch 开销占比高。SGLang 用 **CUDA Graph** 把整个 decode 前向录制成一张图，之后每步直接 replay，省掉反复的 kernel launch 开销。这也是为什么 Attention 后端要区分「capture（录制）」和「replay（回放）」两套元数据准备逻辑（见下文）。

## 四、Attention 后端

文件：`python/sglang/srt/layers/attention/base_attn_backend.py`

### 4.1 抽象基类 docstring（第 18-39 行，含中译）

```
class AttentionBackend(ABC):
    """所有 attention 后端的基类。

    前向数据初始化契约（3 个方法）：

      - init_forward_metadata(fb) —— eager（即时）模式入口。默认是一个包装器，
        先调 _out_graph(fb) 再调 _in_graph(fb)。后端可覆盖以保留独立的 eager 主体。
      - init_forward_metadata_out_graph(fb, in_capture=False) —— 每次迭代的元数据准备，
        运行在 `with graph.capture():` 之外。capture 场景传 in_capture=True；
        replay/eager 用默认 False。仅当 capture / replay 主体分叉时后端才需读 in_capture。
      - init_forward_metadata_in_graph(fb) —— 可被图录制的静态形状 GPU 操作，
        在 capture 时运行于 `with graph.capture():` 内，并由 graph.replay() 自动回放。默认为空操作。

    旧版 init_forward_metadata_capture_cuda_graph 和 ..._replay_cuda_graph 覆盖已完全废弃
    并从 ABC 移除：树外后端需迁移到 init_forward_metadata_out_graph(fb, in_capture)。
    """
```

> 教学要点：这三个方法把「与 CUDA Graph 相关的元数据准备」拆成了 **图外（out_graph，每次都跑，形状可变）** 和 **图内（in_graph，录进图里，静态形状）** 两部分。这是让 attention 兼容 CUDA Graph 的关键设计。

### 4.2 核心接口

| 方法 | 行号 | 作用 |
|------|------|------|
| `init_forward_metadata()` | 47 | 前向前准备元数据（如各请求的 KV 起止位置、页表） |
| `forward()` | 168 | 前向总入口，内部按模式分派 |
| `forward_extend()` | 225 | prefill 的注意力计算 |
| `forward_decode()` | 212 | decode 的注意力计算 |

### 4.3 为什么 prefill / decode 分开

- **prefill（forward_extend）**：一次算多个新 token 的 QKV，做完整的因果注意力。计算密集，适合用 FlashAttention 类 kernel 融合。
- **decode（forward_decode）**：只有 1 个新 query token，但要对**全部历史 KV**做注意力。访存密集，且形状规整（每步 1 token），非常适合 CUDA Graph 固化。

具体后端实现（`layers/attention/` 目录）：`flashinfer_backend.py`、`flashattention_backend.py`、`triton_backend.py`、`flashinfer_mla_backend.py`（DeepSeek MLA）、`trtllm_mla_backend.py` 等，通过 `attention_registry.py` 注册与选择。

## 五、KV Cache 内存池

文件：`python/sglang/srt/mem_cache/memory_pool.py`

| 类 | 行号 | 作用 |
|----|------|------|
| `ReqToTokenPool` | 244 | 请求 → token 槽位映射表（`req_to_token[req_pool_idx, pos] = kv_slot`），记录每个请求占用了哪些 KV 槽 |
| `KVCache`（抽象） | 1562 | KV 池抽象基类 |
| `MHATokenToKVPool` | 1683 | 标准多头注意力 KV 池（存 K 和 V） |
| `MLATokenToKVPool` | 3800 | DeepSeek MLA 专用（KV 压缩为低秩潜向量，大幅省显存） |

分配器在 `mem_cache/allocator/`，`TokenToKVPoolAllocator` 负责 KV 槽位的分配与回收。RadixCache 逐出时调用它的 `free_segment` 释放槽位。

> 两级映射关系：`ReqToTokenPool`（请求→逻辑 token 位置）+ `TokenToKVPool`（token→物理 KV 存储）。RadixCache 里存的 `value` 就是 KV 池里的物理槽位索引。
