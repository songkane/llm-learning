# 05 · 多机推理与 PD 分离

> 前四篇讲的都是**单实例、单机**里请求怎么跑。这一篇把镜头拉远：
> 当一台机器装不下模型、或者想把「预填充」和「解码」拆到不同机器上跑时，vLLM 是怎么组织的。
> 依旧沿用 00 篇的统一示例（A、B 两个请求），只是这次它们会被拆到多张卡、甚至多台机器上。

---

## 一、先分清两件不同的事

很多人把「多机推理」和「PD 分离」混在一起，其实它们解决的是**两个不同层面的问题**：

| | 多机/多卡推理（并行） | PD 分离（disaggregation） |
|---|---|---|
| 解决什么 | 一个模型/一批请求，一台机器算不动 → **把同一份计算摊到多张卡/多台机** | 预填充（prefill）和解码（decode）负载特征不同 → **拆成两组实例分别扩容** |
| 拆的维度 | 把**模型或数据**切开（TP / PP / DP） | 把**请求的两个阶段**切开（先在 P 实例算前缀，再把 KV 搬到 D 实例续写） |
| 关键抽象 | `ParallelConfig`（TP/PP/DP）+ Executor | `KVTransferConfig` + `KVConnectorBase_V1` |
| 通信内容 | 激活值 / 权重分片（NCCL） | **KV cache**（跨实例搬运） |

一句话记忆：
- **并行**是「一份活多人一起干」；
- **PD 分离**是「流水线上两道工序拆到两个车间」。

两者**可以叠加**：一个 prefill 实例内部也可以是 TP=8 的多卡并行。

---

## 二、多机推理：三种并行维度

vLLM 的并行配置全在 `vllm/config/parallel.py` 的 `ParallelConfig` 里，三个核心字段：

| 参数（CLI） | 字段 | 默认 | 切的是什么 |
|---|---|---|---|
| `--tensor-parallel-size` | `tensor_parallel_size` | 1 | **TP**：把**每一层的权重矩阵**按列/行切到多卡，每卡算一部分，逐层 all-reduce 合并 |
| `--pipeline-parallel-size` | `pipeline_parallel_size` | 1 | **PP**：把**模型的层**分段，第 0~k 层在卡组1，第 k+1~ 层在卡组2，像流水线一样传递 |
| `--data-parallel-size` | `data_parallel_size` | 1 | **DP**：**整份模型复制多份**，各自处理不同请求（MoE 层会按 DP 分片） |

源码里有个关键等式（`parallel.py`）：

```
world_size          = tensor_parallel_size × pipeline_parallel_size     # 一个模型副本要多少 GPU
world_size_across_dp = world_size × data_parallel_size                   # 全局总进程数
```

> 直觉：TP × PP 决定「一份模型摊在几张卡上」，再 × DP 决定「这样的副本有几套」。

### 2.1 什么时候需要哪个

| 场景 | 建议 |
|---|---|
| 模型权重单卡放不下（如 70B/单卡 80G 装不下） | 先加 **TP**（同机多卡，NVLink 带宽高） |
| 单机卡数不够 / 想跨机扩模型 | 再加 **PP**（跨机时 PP 比 TP 省带宽，因为只在 stage 边界传激活值） |
| 吞吐不够、但单副本已够放模型 | 加 **DP**（多复制几套，各接各的请求） |

一个常见的多机配方：`TP=8`（单机 8 卡）+ `PP=2`（两台机器）= 一份模型占 16 卡、横跨 2 台机器。

### 2.2 谁来协调多机：Executor 后端

进程怎么起、跨机怎么连，由 `distributed_executor_backend` 决定（`parallel.py`）：

| 后端 | 何时用 | 说明 |
|---|---|---|
| `"uni"` | `world_size == 1` | 单进程，最简单 |
| 多进程（mp） | 单机多卡（默认） | `world_size` 能塞进本机 GPU 时，默认用多进程拉起多个 Worker |
| `"ray"` | 跨机 / 放在 Ray 集群里 | 多节点场景用 Ray 做进程编排与跨机通信 |

回顾 00 篇的进程模型：**多机时，`EngineCore` 仍是那个「调度大脑」，但它下面挂的 Worker 变成了跨卡、甚至跨机的一组进程**。调度决策（02 篇）在一个地方做，做完把 `SchedulerOutput` 广播给所有 Worker，各 Worker 算自己那一份。

### 2.3 PP 下 step 心跳的变化（承接 01 篇）

01 篇讲过 `EngineCore.step` 是「心跳」。开了 **PP** 之后，为了不让流水线空转，vLLM 会让**多个 microbatch（虚拟引擎）在不同 stage 上错峰前进**：当 stage-2 在算第 N 个 microbatch 时，stage-1 已经在算第 N+1 个。这样各段 GPU 都不闲着，代价是调度与状态管理更复杂（每个 in-flight microbatch 都要各自记账）。

> 记忆点：**TP 是「同一层横向切、逐层同步」；PP 是「按层纵向切、流水线错峰」。** TP 通信频繁（每层都要 all-reduce），所以偏好同机高带宽；PP 只在段边界通信，更适合跨机。

## 三、PD 分离：为什么要拆 Prefill 和 Decode

回顾 00/02 篇的统一示例：请求 A 有 48 个 prompt token。它的一生分两段：

1. **Prefill（预填充）**：一次性把 48 个 prompt token 全部算完，产出第 1 个输出 token + 这 48 个 token 的 **KV cache**。这一步**算力密集**（一次算几十上百个 token）。
2. **Decode（解码）**：之后每步只算 1 个新 token，但要**反复读取**前面所有 token 的 KV。这一步**访存密集、算力利用率低**。

问题来了：这两种负载塞在同一个实例里会互相拖累——

- Prefill 是「大块头」，一进来就吃满算力，会**卡住**正在逐 token 吐字的 decode 请求（延迟抖动）；
- Decode 又填不满 GPU 算力，浪费。

**PD 分离**的思路：把它们拆成两组独立实例——

```
       ┌─────────────┐   把 A 的 KV cache 搬过去   ┌─────────────┐
请求 A →│  Prefill 实例 │ ─────────────────────────→ │  Decode 实例  │→ 逐 token 吐字给用户
       │ (kv_producer)│      (KV connector)         │(kv_consumer) │
       └─────────────┘                              └─────────────┘
```

- **Prefill 实例（P）**：只干预填充，算完把 KV「生产」出来。角色 `kv_producer`。
- **Decode 实例（D）**：接住 KV，只干解码续写。角色 `kv_consumer`。

好处：两边可以**按各自负载独立扩容**（比如 prefill 算力紧就多加几个 P 实例，decode 访存紧就多加 D），互不干扰。

## 四、PD 分离怎么落地：KV Connector

vLLM v1 把「跨实例搬 KV」这件事抽象成一个统一接口 **`KVConnectorBase_V1`**（`vllm/distributed/kv_transfer/kv_connector/v1/base.py`）。配置入口是 `KVTransferConfig`（`vllm/config/kv_transfer.py`）。

### 4.1 配置字段（`KVTransferConfig`）

| 字段 | 取值 | 含义 |
|---|---|---|
| `kv_connector` | 如 `"NixlConnector"` | 用哪个 connector 实现来搬 KV |
| `kv_role` | `kv_producer` / `kv_consumer` / `kv_both` | 本实例是生产 KV、消费 KV、还是两者都做 |
| `kv_buffer_device` | `cuda`/`cpu`/`xpu` | KV 中转缓冲放哪 |
| `kv_ip` / `kv_port` | 默认 `127.0.0.1` / `14579` | 建立跨实例连接的地址 |
| `kv_connector_extra_config` | dict | 各 connector 自己的额外配置 |
| `kv_load_failure_policy` | `recompute` / `fail`（默认 `fail`） | KV 加载失败时：重算 or 直接失败 |

> `kv_both` 用于「既能对外供 KV、也能吃别人 KV」的对等场景（如分层缓存）。

### 4.2 一个 connector 分身两处（关键设计）

同一个 connector 逻辑上分两半跑在不同进程（`KVConnectorRole`）：

- **`SCHEDULER` 侧**：跟着调度器（02 篇）跑，负责「**决策类**」工作——判断某请求有多少 token 的 KV 能从外部拿到、要不要为它预留块、把搬运计划打包成 `KVConnectorMetadata` 发给 worker。
- **`WORKER` 侧**：跟着 Worker（04 篇）跑，负责「**搬运类**」工作——真正把 KV 从/向显存读写、跨实例传输。

调度器侧决策 → 通过 `KVConnectorMetadata` 下发 → worker 侧执行。这跟 02→04 篇「调度决策与执行分离」是同一套思想。

### 4.3 完整时序（以请求 A：P 实例算、D 实例续为例）

结合基类里的接口方法，一条请求走 PD 分离的完整链路是：

**在 Decode 实例这一侧（消费者，请求实际是发到 D 的）：**

```
调度器侧（SCHEDULER role）:
  ① get_num_new_matched_tokens(request)
        → connector 报告：「A 的这 48 个 token 的 KV，我能从 P 实例那边拿到」
  ② update_state_after_alloc(request, blocks, num_external_tokens)
        → 调度器据此为这些外部 KV 预留好 KV block（对接 03 篇 allocate_slots）
  ③ build_connector_meta(scheduler_output)
        → 把「要从 P 拉哪些 KV、放进哪些块」打包成 KVConnectorMetadata 下发

Worker 侧（WORKER role），在 execute_model 前后：
  ④ start_load_kv(forward_context)     → 开始把 A 的 KV 从 P 实例拉进本地显存
  ⑤ wait_for_layer_load(layer_name)    → 逐层等待对应层 KV 到位（可与计算重叠）
  ⑥ 模型正常前向（04 篇），直接复用拉来的 KV，跳过对这 48 个 token 的重算
```

**在 Prefill 实例这一侧（生产者）：**

```
Worker 侧:
  save_kv_layer(layer_name, ...)   → 每算完一层，就把该层 KV 存/发出去
  wait_for_save()                  → 一步结束时，确保所有 KV 都已发出

调度器侧:
  request_finished(request, ...)   → 请求在 P 侧算完，决定它的块能否立刻释放
                                     （若 KV 还在传，要等传完，见 requires_kv_delivery）

两侧共有:
  get_finished(finished_req_ids)   → 报告哪些请求的「收 / 发」KV 操作已彻底完成
```

> 核心一句：**D 实例调度 A 时，不是从头算 prompt，而是先问 connector「这段 KV 现成的有没有」，有就预留块、把 KV 拉过来直接接着解码——省掉了整段 prefill 的重算。**

### 4.4 和 03 篇前缀缓存的关系

03 篇的**前缀缓存**是「**同一实例内**，B 复用 A 已经在显存里的 KV」；
PD 分离的 connector 是「**跨实例**，把 KV 从 P 搬到 D」。

其实是同一个思想在不同尺度的延伸：**能复用的 KV 就别重算**。`get_num_new_matched_tokens` 这个方法名里的 "matched"，正呼应 03 篇前缀匹配——只不过匹配源从「本地缓存」扩展到了「远端实例」。

## 五、有哪些现成的 Connector 实现

`vllm/distributed/kv_transfer/kv_connector/v1/` 下已有多种实现，按用途分几类：

| Connector | 定位 |
|---|---|
| `NixlConnector` | 基于 NIXL 的高性能 RDMA 传输，PD 分离主力方案之一 |
| `MooncakeConnector` / mooncake store | Mooncake 传输引擎 / KV 存储池 |
| `LMCacheConnector` | 对接 LMCache，支持多级 KV 缓存与复用 |
| `SharedStorageConnector`（示例类） | 通过共享存储中转 KV，简单、便于理解与测试 |
| `OffloadingConnector` / `SimpleCPUOffloadConnector` | 把 KV 卸载到 CPU 等，扩容 KV 容量 |
| `MultiConnector` | 组合多个 connector（如同时挂缓存 + 传输） |

> 学习建议：想读源码理解机制，从**示例类**（`example_connector.py` / 共享存储型）入手最省心；生产部署再看 Nixl / Mooncake / LMCache。

## 六、把两件事串到统一示例上

回到 A、B 两个请求，看看它们在「TP=2 + PD 分离」的部署下会经历什么：

```
                     Prefill 实例 (kv_producer, 内部 TP=2)
                   ┌───────────────────────────────────┐
  A(48 tok) ──────→│ 一次算完 48 token → 产出首 token+KV  │
  B(命中A前缀)─────→│ B 只算新增 18 token（03篇前缀复用）  │
                   └──────────────┬────────────────────┘
                                  │ KV connector 搬 KV（NCCL/RDMA/...）
                                  ▼
                     Decode 实例 (kv_consumer, 内部 TP=2)
                   ┌───────────────────────────────────┐
  逐 step 吐字 ←────│ 拉到 KV，直接续写：每步只算 1 token   │
  (02篇连续批处理)   │ A、B 合并成 batch，共享 decode 资源   │
                   └───────────────────────────────────┘
```

- **并行（TP=2）**：每个实例内部，A/B 的每一层计算都摊在 2 张卡上并行算，逐层 all-reduce。
- **PD 分离**：A/B 的 prefill 在左边实例做，KV 搬到右边实例做 decode。
- **前缀缓存（03 篇）**：即使在 P 实例内，B 仍能命中 A 的前缀省下 32 token 的重算。
- **连续批处理（02 篇）**：在 D 实例里，A/B 依旧按 token 预算合并成 batch，一步步吐字。

**四层机制在这里同时起作用，各管各的一层，互不冲突。**

## 七、必记要点

1. **并行 ≠ PD 分离**：前者切「模型/数据」摊到多卡多机（TP/PP/DP），后者切「请求的 prefill/decode 两阶段」到不同实例。
2. **`world_size = TP × PP`，再 × DP = 全局进程数**：这决定要起多少 Worker、怎么组网。
3. **跨机用 Ray、单机多卡用多进程**：由 `distributed_executor_backend` 决定，单卡是 `uni`。
4. **PD 分离的核心是 KV connector**：配置在 `KVTransferConfig`（`kv_connector` + `kv_role`），接口是 `KVConnectorBase_V1`。
5. **connector 分身两处**：SCHEDULER 侧做决策（`get_num_new_matched_tokens` / `build_connector_meta`），WORKER 侧做搬运（`start_load_kv` / `save_kv_layer`）。
6. **本质仍是「能复用的 KV 就别重算」**：PD 分离是 03 篇前缀复用从「本地」到「跨实例」的延伸。

## 八、动手验证建议

- **并行**：起一个 `LLM(model=..., tensor_parallel_size=2)`（需 2 张卡），观察拉起了几个 Worker 进程、显存怎么分摊。
- **PD 分离**：看官方示例 `examples/` 下 disaggregated 相关脚本 + `docs/features/disagg_prefill.md`，用**共享存储型 connector** 跑一个最小 1P1D，断点打在：
  `get_num_new_matched_tokens`（D 侧决策）→ `start_load_kv`（D 侧拉 KV）→ `save_kv_layer`（P 侧存 KV），把本篇 4.3 的时序一格一格印证一遍。
