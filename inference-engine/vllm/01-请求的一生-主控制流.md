# 01 · 请求的一生 —— vLLM 主控制流导读

> 本文档不修改任何源码，只摘录 vLLM 真实代码片段并逐行加中文注释。
> 注释分两类：`【逻辑】`讲 vLLM 在做什么；`【Python】`讲 Python 语法（面向不熟悉 Python 的读者）。

## 0. 先看一张全景图

一个请求（比如 "你好，帮我写首诗"）从进入到吐出全部文字，经过的核心函数链条：

```
用户调用
  LLM.generate(prompts)                      vllm/entrypoints/llm.py
        │  把字符串包装成请求，进入引擎
        ▼
  LLMEngine.add_request(...)                 vllm/v1/engine/llm_engine.py
        │  分词、构造内部 Request 对象
        ▼
  EngineCore.add_request(request)            vllm/v1/engine/core.py
        │  塞进调度器的 waiting 队列
        ▼
  ┌──────────── 循环，直到所有请求完成 ────────────┐
  │  EngineCore.step()                       vllm/v1/engine/core.py
  │     1. scheduler.schedule()   决定这一轮跑哪些请求
  │     2. executor.execute_model()  GPU 前向计算 + 采样
  │     3. scheduler.update_from_output()  更新状态、判断结束
  └───────────────────────────────────────────────┘
        │
        ▼
  LLMEngine.step() 收集输出
        │  detokenize（token id → 文字）
        ▼
  返回 RequestOutput 给用户
```

**关键直觉**：`step()` 每执行一次，运行中的每个请求只往前生成 **一个 token**。
生成 100 个 token，就要循环 `step()` 大约 100 次。这就是「自回归」和「连续批处理」的本质。

> 建议先读 `00-全局架构与数据流总览.md`，本篇会用到那里约定的**统一示例**（A/B 两请求）。

## 0.5 主控制流时序图（含进程边界）

上面的全景图是「函数调用链」，下面这张**时序图**强调**两个进程之间怎么协作**——
这是理解 vLLM 的关键，很多人卡在「为什么请求要序列化」上，看懂这张图就通了。

```
 用户代码          LLMEngine            [IPC队列]          EngineCore子进程         GPU
（主进程）        （主进程）           ZMQ socket        run_busy_loop         Worker
    │                 │                    │                   │                 │
    │ generate([A,B]) │                    │                   │                 │
    ├────────────────▶│                    │                   │                 │
    │                 │ add_request(A)      │                   │                 │
    │                 │ 分词+构造Request     │                   │                 │
    │                 ├─EngineCoreRequest──▶│                   │                 │
    │                 │  (序列化字节流)      ├──入input_queue───▶│                 │
    │                 │ add_request(B)      │                   │ 转成Request     │
    │                 ├─EngineCoreRequest──▶├──────────────────▶│ 入waiting队列   │
    │                 │                    │                   │                 │
    │                 │                    │        ┌──────────┤ step() #1        │
    │                 │                    │        │ schedule()│ 挑A,B进batch    │
    │                 │                    │        │ execute  ─┼────forward─────▶│
    │                 │                    │        │          │◀───logits───────┤
    │                 │                    │        │ sample   │ A吐"4" B吐"Paris"│
    │                 │                    │        │ update   │ 记账             │
    │                 │                    │◀─EngineCoreOutputs─┤ 放output_queue  │
    │ step()          │                    │        └──────────┤                 │
    │ (循环取结果)     │◀─get_output()──────┤                   │ step() #2 ...    │
    │                 │ detokenize          │                   │ (继续decode)     │
    │◀─RequestOutput──┤ "4"/"Paris"→文字    │                   │                 │
    │                 │                    │                   │                 │
```

要点：
- 左侧主进程只做**门面 + 翻译**（分词、detokenize），不碰 GPU。
- 右侧子进程 `run_busy_loop` 独立地一轮轮 `step()`，与主进程通过 **IPC 队列**解耦。
- 中间那条 `EngineCoreRequest`（序列化字节流）就是「过河的船」——因为要跨进程，对象必须先序列化。

## 1. 入口：`LLM.generate`

文件：`vllm/entrypoints/llm.py`（约第 460 行）

这是离线批量推理最常用的入口。核心其实就是转发给内部方法。

```python
        if sampling_params is None:
            sampling_params = self.get_default_sampling_params()

        return self._run_completion(
            prompts=prompts,
            params=sampling_params,
            output_type=RequestOutput,
            use_tqdm=use_tqdm,
            lora_request=lora_request,
            tokenization_kwargs=tokenization_kwargs,
            priority=priority,
            mm_processor_kwargs=mm_processor_kwargs,
        )
```

**逐行解释：**

- `if sampling_params is None:`
  - 【逻辑】`sampling_params` 控制怎么采样（温度、top_p、最多生成多少 token）。用户没传就用默认。
  - 【Python】`None` 是 Python 的「空值」，相当于其他语言的 `null`。判断空值用 `is None`，不要用 `== None`。
- `sampling_params = self.get_default_sampling_params()`
  - 【Python】`self` 是「当前对象自己」，相当于 Java/C++ 的 `this`。Python 里方法的第一个参数永远显式写成 `self`。
- `return self._run_completion(...)`
  - 【逻辑】真正干活的是 `_run_completion`，它内部会调用 `add_request`（加请求）+ 反复 `step`（推进）。
  - 【Python】方法名前面的下划线 `_run_completion` 是约定俗成的「私有方法」标记——表示「内部用，外部别直接调」。Python 没有真正的私有，全靠约定。
  - 【Python】`prompts=prompts` 这种写法叫「关键字参数」，等号左边是形参名，右边是传入的值。好处是调用处一眼能看出每个参数的含义。

> 记住这一层只是「门面（facade）」：把用户友好的 API 转成引擎内部调用。真正的逻辑在下一层。

## 2. 引擎门面：`LLMEngine.add_request`

文件：`vllm/v1/engine/llm_engine.py`（第 218 行起）

这一步把「用户的原始输入」变成「引擎能处理的内部请求对象」。

```python
    def add_request(
        self,
        request_id: str,
        prompt: EngineCoreRequest | PromptType | EngineInput,
        params: SamplingParams | PoolingParams,
        arrival_time: float | None = None,
        lora_request: LoRARequest | None = None,
        tokenization_kwargs: dict[str, Any] | None = None,
        trace_headers: Mapping[str, str] | None = None,
        priority: int = 0,
        session_id: str | None = None,
        prompt_text: str | None = None,
    ) -> str:
```

**先讲这段函数签名（Python 类型注解重点）：**

- `def add_request(self, ...)` — `def` 是定义函数的关键字。
- `request_id: str` — 冒号后面是「类型注解」，表示这个参数应该是字符串（`str`）。
  - 【Python】**注意：类型注解只是给人和工具看的提示，Python 运行时并不强制检查**。传错类型不会自动报错（除非代码里手动检查）。
- `prompt: EngineCoreRequest | PromptType | EngineInput`
  - 【Python】竖线 `|` 表示「或」，即这个参数可以是这几种类型中的任意一种（联合类型 Union）。
- `arrival_time: float | None = None`
  - 【Python】`| None` 表示「也可以是空值」，`= None` 表示「不传的话默认是 None」。这就是「可选参数」。
- `priority: int = 0`
  - 【逻辑】请求优先级，默认 0。调度器可以按优先级排序。
- `) -> str:`
  - 【Python】`->` 后面是「返回值类型注解」，表示这个函数返回一个字符串（这里返回的是 request_id）。

**再看函数体核心逻辑：**

```python
        # Validate the request_id type.
        if not isinstance(request_id, str):
            raise TypeError(f"request_id must be a string, got {type(request_id)}")
```

- 【逻辑】校验请求 id 必须是字符串。
- 【Python】`isinstance(x, str)` 判断 x 是不是 str 类型；`not` 表示取反。
- 【Python】`raise` 是「抛出异常」，相当于其他语言的 `throw`。
- 【Python】`f"...{type(request_id)}"` 是 **f-string**（格式化字符串）：字符串前加 `f`，里面 `{}` 中的表达式会被求值并嵌进字符串。是 vLLM 里极高频的语法。

```python
        else:
            request = self.input_processor.process_inputs(
                request_id,
                prompt,
                params,
                supported_tasks=self.get_supported_tasks(),
                arrival_time=arrival_time,
                lora_request=lora_request,
                tokenization_kwargs=tokenization_kwargs,
                trace_headers=trace_headers,
                priority=priority,
                session_id=session_id,
            )
```

- 【逻辑】**这是关键一步：`process_inputs` 做分词（tokenization）**——把文字 "你好" 变成模型能吃的 token id 列表 `[151644, 108386, ...]`，并打包成内部 `Request` 对象。这是文字进入数字世界的分界线。

```python
        n = params.n if isinstance(params, SamplingParams) else 1

        if n == 1:
            # Make a new RequestState and queue.
            self.output_processor.add_request(request, prompt_text, None, 0)
            # Add the request to EngineCore.
            self.engine_core.add_request(request)
            return req_id
```

- `n = params.n if isinstance(params, SamplingParams) else 1`
  - 【逻辑】`n` 表示「一个 prompt 要生成几个不同的回答」。比如 `n=3` 就是同一个问题要 3 个候选答案。
  - 【Python】这是「三元表达式」：`A if 条件 else B`，条件成立取 A，否则取 B。等价于其他语言的 `条件 ? A : B`。
- `self.output_processor.add_request(...)`
  - 【逻辑】在「输出处理器」里登记这个请求，准备接收它未来产出的 token。
- `self.engine_core.add_request(request)`
  - 【逻辑】**把请求真正交给引擎核心**（下一层）。到这里请求就进入引擎内部了。
- `return req_id`
  - 【逻辑】返回请求 id，用户可以用它来查询/取消这个请求。

（`n > 1` 的分支是「扇出」成多个子请求，每个子请求独立生成，原理相同，初学可跳过。）

### 2.1 统一示例：数据在这一层的形态变化 ★

用 00 篇约定的例子，看请求 A 从「字符串」到「引擎内部对象」的三次变形：

**① 用户传入（Python str）：**
```python
req_A = "You are a helpful assistant. Answer concisely. What is 2+2?"
```

**② 经 `process_inputs` 分词后（list[int]）：**
文字被切成 token id 列表（数字才是模型能吃的东西）：
```python
prompt_token_ids = [128000, 2675, 527, 264, ..., 220, 17, 10, 17, 30]
#                    └─ SYS 部分(前40个) ─┘  └─ "What is 2+2?"(后8个) ─┘
len(prompt_token_ids) == 48   # 约定长度 48
```

**③ 打包成 `EngineCoreRequest`（可跨进程序列化的结构体）：**
这是「过河的船」，字段来自真实源码 `vllm/v1/engine/__init__.py`：
```python
EngineCoreRequest(
    request_id      = "A",
    prompt_token_ids= [128000, 2675, ..., 30],   # 上面那 48 个
    sampling_params = SamplingParams(max_tokens=5, temperature=0),
    mm_features     = None,      # 没有多模态输入
    arrival_time    = 1699999999.9,
    lora_request    = None,
    cache_salt      = None,
    ...
)
```
> 为什么用 `msgspec.Struct` 而不是普通类？因为它要通过 ZMQ **跨进程发送**，
> `msgspec` 序列化/反序列化比 `pickle` 快得多。这呼应了 0.5 节时序图里那条「船」。

**④ 到 EngineCore 子进程后转成内部 `Request`（`vllm/v1/request.py`）：**
增加了「运行时状态」字段，这些是引擎调度时要读写的：
```python
Request(
    request_id         = "A",
    prompt_token_ids   = [...48个...],
    status             = RequestStatus.WAITING,  # 初始：等待被调度
    num_computed_tokens= 0,        # 已经算了几个 token（03/02 会频繁更新它）
    sampling_params    = SamplingParams(max_tokens=5),
    arrival_time       = 1699999999.9,
    ...
)
```

**这一层的数据变形一句话总结：**
```
str  ──分词──▶  list[int](48)  ──打包──▶  EngineCoreRequest  ──跨进程+加状态──▶  Request(status=WAITING)
                                                                                          │
                                                                          进入 scheduler.waiting 队列，交给 02 篇
```
请求 B 同理，只是 `prompt_token_ids` 长度是 50，其余结构完全一样。

## 3. 引擎门面的推进：`LLMEngine.step`

文件：`vllm/v1/engine/llm_engine.py`（第 298 行）

`add_request` 只是把请求「放进去」，真正让它前进要靠反复调用 `step`。注意这一层的 `step` 是**取结果**，真正的计算在 EngineCore 里。

```python
    def step(self) -> list[RequestOutput | PoolingRequestOutput]:
        ...
        # 1) Get EngineCoreOutput from the EngineCore.
        with record_function_or_nullcontext("llm_engine step: get_output"):
            outputs = self.engine_core.get_output()

        # 2) Process EngineCoreOutputs.
        with record_function_or_nullcontext("llm_engine step: process_outputs"):
            ...
            processed_outputs = self.output_processor.process_outputs(
                outputs.outputs,
                engine_core_timestamp=outputs.timestamp,
                iteration_stats=iteration_stats,
            )
            ...

        # 3) Abort any reqs that finished due to stop strings.
        with record_function_or_nullcontext("llm_engine step: abort_requests"):
            self.engine_core.abort_requests(processed_outputs.reqs_to_abort)
        ...
        return processed_outputs.request_outputs
```

**逐段解释：**

- `with record_function_or_nullcontext("..."):`
  - 【Python】`with` 是「上下文管理器」语法，常用于「进入时做点事、退出时自动收尾」的场景（比如开关文件、计时）。这里是性能打点：进入代码块开始计时，离开时自动结束。**你可以先忽略 `with` 这一层，直接看它内部的逻辑。**
- 【逻辑】`get_output()` 从引擎核心拿到「这一轮新产出的 token」。
- 【逻辑】`output_processor.process_outputs(...)` 做 **detokenize**——把 token id 变回人类文字，并判断是否触发了停止条件（比如遇到句号、达到 max_tokens）。
- 【逻辑】`abort_requests(...)` 把已经结束的请求告诉引擎，让它释放显存。
- `return processed_outputs.request_outputs`
  - 【逻辑】返回给用户的最终结果（含新生成的文字）。

> 小结这一层的分工：`add_request` 送入、`step` 取出并翻译成文字。真正的 GPU 计算在 EngineCore（下一节）。

## 4. 引擎心脏：`EngineCore.step`  ★最重要

文件：`vllm/v1/engine/core.py`（第 580 行）

**这是整个 vLLM 的心跳。** 每调用一次，所有运行中的请求前进一个 token。请务必精读。

```python
    def step(self) -> tuple[dict[int, EngineCoreOutputs], bool]:
        """Schedule, execute, and make output.

        Returns tuple of outputs and a flag indicating whether the model
        was executed.
        """

        # Check for any requests remaining in the scheduler - unfinished,
        # or finished and not yet removed from the batch.
        if not self.scheduler.has_requests():
            return {}, False
        scheduler_output = self.scheduler.schedule(self._should_throttle_prefills())
        future = self.model_executor.execute_model(scheduler_output, non_block=True)
        grammar_output = self.scheduler.get_grammar_bitmask(scheduler_output)
        with (
            self.capture_iteration_details(scheduler_output) as iteration_details,
            self.log_error_detail(scheduler_output),
        ):
            model_output = future.result()
            if model_output is None:
                model_output = self.model_executor.sample_tokens(grammar_output)

        # Before processing the model output, process any aborts that happened
        # during the model execution.
        self._process_aborts_queue()
        engine_core_outputs = self.scheduler.update_from_output(
            scheduler_output, model_output
        )
        self._attach_iteration_details(engine_core_outputs, iteration_details)

        return engine_core_outputs, scheduler_output.total_num_scheduled_tokens > 0
```

**逐行精读：**

- `def step(self) -> tuple[dict[int, EngineCoreOutputs], bool]:`
  - 【Python】返回类型是 `tuple[..., bool]`：一个「元组」，含两个元素。元组是「不可修改的定长列表」，用逗号分隔。
  - 【逻辑】返回 `(输出内容, 是否真的执行了模型)`。

- `"""Schedule, execute, and make output. ..."""`
  - 【Python】三引号 `"""..."""` 是「文档字符串（docstring）」，写在函数开头，是这个函数的官方说明。这里明说了三步：调度、执行、产出。

- `if not self.scheduler.has_requests():`
  - `    return {}, False`
  - 【逻辑】如果调度器里一个请求都没有，直接返回空、没执行。
  - 【Python】`{}` 是空字典（dict）；`return {}, False` 一次返回两个值，会自动打包成元组 `({}, False)`。

- `scheduler_output = self.scheduler.schedule(...)`
  - 【逻辑】**第一步：调度**。调度器决定「这一轮 GPU 要处理哪些请求、每个请求处理多少 token」。产出 `scheduler_output`（一张任务清单）。这是「连续批处理」的核心决策点，详见 02 文档。

- `future = self.model_executor.execute_model(scheduler_output, non_block=True)`
  - 【逻辑】**第二步：执行**。把任务清单交给执行器，在 GPU 上跑模型前向计算。
  - 【逻辑】`non_block=True` 表示「非阻塞」：不等它算完就先返回一个「凭证」`future`（未来会有结果）。这样 CPU 可以先去干别的（比如下面构造 grammar）。
  - 【Python】`future` 是「异步结果的占位符」，类似「取餐号」——先给你号，饭好了凭号取。

- `grammar_output = self.scheduler.get_grammar_bitmask(scheduler_output)`
  - 【逻辑】结构化输出（比如强制生成合法 JSON）用的掩码。普通场景可忽略。

- `with (self.capture_iteration_details(...) as iteration_details, self.log_error_detail(...)):`
  - 【Python】一个 `with` 同时管理两个上下文（性能统计 + 错误日志）。`as iteration_details` 把上下文对象取个名字备用。
  - 【逻辑】进入这个块 = 开始本轮计时并准备好「出错时 dump 详细信息」。

- `model_output = future.result()`
  - 【逻辑】**这里才真正「等」GPU 算完**——凭 future 取结果（阻塞直到有结果）。拿到的是模型输出（下一个 token 的概率分布等）。

- `if model_output is None:`
  - `    model_output = self.model_executor.sample_tokens(grammar_output)`
  - 【逻辑】某些执行路径下前向和采样分开：如果前一步没直接给出 token，就单独做一次采样（从概率分布里挑出具体 token）。

- `self._process_aborts_queue()`
  - 【逻辑】处理「模型计算期间到达的取消请求」（比如用户中途断开连接）。

- `engine_core_outputs = self.scheduler.update_from_output(scheduler_output, model_output)`
  - 【逻辑】**第三步：更新状态**。把这一轮新生成的 token 写回各请求，判断哪些请求结束了（命中 stop / 到达 max_tokens），并释放对应显存。产出要返回给上层的 `engine_core_outputs`。

- `return engine_core_outputs, scheduler_output.total_num_scheduled_tokens > 0`
  - 【逻辑】返回输出，以及「本轮是否真的处理了 token」（`> 0` 得到一个布尔值）。

**★ 一句话总结 step()：**
> `schedule()` 挑活 → `execute_model()` 算 → `update_from_output()` 记账。三步一循环，每循环一次，每个请求前进一个 token。

## 5. 谁在反复调用 step？—— busy loop

文件：`vllm/v1/engine/core.py`（第 1372 行）

EngineCore 通常跑在**独立进程**里，有一个永不停歇的循环不断调用 step。

```python
    def run_busy_loop(self):
        """Core busy loop of the EngineCore."""
        while self._handle_shutdown():
            # 1) Poll the input queue until there is work to do.
            self._process_input_queue()
            # Publish request counts before and after GPU step to ensure freshness.
            self._maybe_publish_request_counts()
            # 2) Step the engine core and return the outputs.
            self._process_engine_step()
            self._maybe_publish_request_counts()

        raise SystemExit
```

**逐行解释：**

- `while self._handle_shutdown():`
  - 【逻辑】只要没收到关闭信号，就一直循环。这就是引擎「一直活着等活干」的地方。
  - 【Python】`while 条件:` 是循环，条件为真就反复执行缩进块。**Python 用缩进（通常 4 个空格）表示代码块归属，没有大括号 `{}`。缩进错了逻辑就错了，这点对初学者尤其重要。**

- `self._process_input_queue()`
  - 【逻辑】**步骤 1**：从输入队列取出新到达的请求（其他进程通过队列把请求发过来），加进调度器。

- `self._process_engine_step()`
  - 【逻辑】**步骤 2**：里面会调用 `self.step_fn()`（就是上面的 `step()`），跑一轮，并把产出的 token 放进输出队列，供上层取走。

- `raise SystemExit`
  - 【逻辑】跳出循环后（收到关闭）抛出退出信号，进程结束。

看下 `_process_engine_step` 的核心（第 1429 行）印证这点：

```python
    def _process_engine_step(self) -> bool:
        """Called only when there are unfinished local requests."""

        # Step the engine core.
        outputs, model_executed = self.step_fn()
        # Put EngineCoreOutputs into the output queue.
        for output in outputs.items() if outputs else ():
            self.output_queue.put_nowait(output)
        ...
        return model_executed
```

- `outputs, model_executed = self.step_fn()`
  - 【逻辑】调用 step，一次拿到两个返回值。
  - 【Python】这叫「元组解包」：等号左边两个变量，自动接收右边元组的两个元素。
  - 【逻辑】`self.step_fn` 在初始化时被设为 `self.step`（普通）或 `self.step_with_batch_queue`（流水线并行），是一种「策略切换」技巧。
- `for output in outputs.items() if outputs else ():`
  - 【逻辑】把每个输出放进输出队列，让上层的 `LLMEngine.step()`（第 3 节）能取走。
  - 【Python】`for x in 可迭代对象:` 是遍历循环。`outputs.items()` 遍历字典的键值对。`if outputs else ()` 保证 outputs 为空时遍历一个空元组（不报错）。

## 6. 把整条链路串起来（回顾）

```
LLM.generate                         【第1节】用户入口，转发
  └─ _run_completion
       ├─ LLMEngine.add_request      【第2节】分词，构造 Request，送入引擎
       │    └─ EngineCore.add_request      塞进调度器 waiting 队列
       └─ 循环 LLMEngine.step        【第3节】取结果 + detokenize 成文字
                                     （同时，独立进程里 run_busy_loop 在转）
                                          │
   run_busy_loop  【第5节】────────────────┘
     └─ 反复 EngineCore.step         【第4节】★ schedule→execute→update
```

**三个必须记住的点：**

1. **step() 是心跳**：一次 step = 每个活跃请求前进一个 token。
2. **三步走**：调度（挑活）→ 执行（GPU 计算）→ 更新（记账+释放显存）。
3. **进程分离**：EngineCore 在独立进程用 busy loop 死循环跑 step，通过队列和上层通信。这是为了 GPU 计算不被 Python 的 GIL 和 API 层拖累。
