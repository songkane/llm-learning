## 一、为什么需要这样的架构（先理解矛盾）

LLM 推理是**自回归**的：一次前向计算只吐一个 token，然后把它拼回输入再算下一个。
围绕这个特性，vLLM 要同时解决三个工程难题，整个架构就是这三点的答案：

| 难题 | vLLM 的解法 | 主要代码位置 | 对应文档 |
|------|------------|-------------|---------|
| KV Cache 显存碎片化 | **PagedAttention**（按 block 分页管理 KV） | `v1/core/kv_cache_manager.py`、`block_pool.py` | 03 |
| 请求长度/到达时间各异，静态 batch 浪费 | **Continuous Batching**（逐 step 动态调度） | `v1/core/sched/scheduler.py` | 02 |
| 调度决策与 GPU 计算要解耦以便扩展 | **EngineCore + Scheduler + Worker** 三层 | `v1/engine/core.py`、`v1/worker/` | 01/04 |

```
┌─────────────────────────────────────────────────────────────────────┐

│  ┌───────────────────────┐   ┌──────────────────────────────┐        │
│  │ entrypoints/llm.py     │   │ entrypoints/openai/  (在线)   │        │
│  │ LLM 类（离线批处理）    │   │ OpenAI 兼容 API server        │        │
│  └───────────┬───────────┘   └───────────────┬──────────────┘        │
└──────────────┼───────────────────────────────┼───────────────────────┘
               │                                │
┌──────────────▼───────────────────────────────▼───────────────────────┐
│  引擎门面层（跑在【主进程】）                                            │
│  ┌───────────────────────────┐   ┌──────────────────────────────┐    │
│  │ v1/engine/llm_engine.py    │   │ v1/engine/async_llm.py        │    │
│  │ LLMEngine（同步）           │   │ AsyncLLM（异步/高并发）        │    │
│  └───────────┬───────────────┘   └──────────────────────────────┘    │
│              │  ▲                                                       │
│         add_request │ RequestOutput                                    │
│              │  │  (通过 IPC：ZMQ socket 跨进程通信)                    │
└──────────────┼──┼──────────────────────────────────────────────────── ┘
               ▼  │
┌──────────────────────────────────────────────────────────────────────┐
│  引擎核心 EngineCore（跑在【独立子进程】EngineCoreProc）                  │
│  v1/engine/core.py                                                     │
│                                                                        │
│   run_busy_loop() 死循环：                                             │
│      每一轮 = step()  ←────────────── 引擎「心跳」                       │
│         │                                                              │
│         ├─ 1. scheduler.schedule()      → 决定这一轮跑哪些请求          │
│         │      ┌────────────────────┐   ┌──────────────────────┐      │
│         │      │ Scheduler (02)     │──▶│ KVCacheManager (03)   │      │
│         │      │ waiting/running队列 │   │ 分配/释放 block        │      │
│         │      └────────────────────┘   └──────────────────────┘      │
│         │            │ 产出 SchedulerOutput（任务清单）                 │
│         │            ▼                                                 │
│         ├─ 2. executor.execute_model()  → GPU 前向计算                 │
│         │      ┌────────────────────────────────────────────┐        │
│         │      │ Executor → GPUWorker → GPUModelRunner (04)  │        │
│         │      │  _prepare_inputs（变长打平）                 │        │
│         │      │  model.forward → attention backend（分页）   │        │
│         │      │  sample_tokens（采样出 token）               │        │
│         │      └────────────────────────────────────────────┘        │
│         │            │ 产出 ModelRunnerOutput（新 token）              │
│         │            ▼                                                 │
│         └─ 3. scheduler.update_from_output() → 记账、判停、释放显存      │
│                      │ 产出 EngineCoreOutputs                          │
└──────────────────────┼─────────────────────────────────────────────── ┘
                       │ (IPC 回传主进程)
                       ▼
              output_processor + detokenizer  → RequestOutput → 用户
```

**一句话数据流**：
字符串 prompt → `add_request` → `EngineCoreRequest`（跨进程）→ `Request`（引擎内部对象）
→ 进 `Scheduler` 队列 → `step()` 反复：调度 → GPU 算一步 → 更新 →
每步每个请求 +1 token → 完成后 `RequestOutput` 回给用户。

## 三、进程模型图（很多人卡在这里）

vLLM v1 是**多进程**架构，理解这个才能理解为什么请求要序列化成 `EngineCoreRequest`。

```
┌────────────────────────┐         ZMQ IPC          ┌───────────────────────────┐
│  主进程 (你的 Python)    │  ◀───────────────────▶   │  EngineCore 子进程          │
│                        │  序列化的字节流            │  (EngineCoreProc)          │
│  LLM / AsyncLLM        │                          │                           │
│  LLMEngine             │  → EngineCoreRequest      │  run_busy_loop()          │
│  OutputProcessor       │  ← EngineCoreOutputs      │    ├ Scheduler            │
│  Detokenizer           │                          │    ├ KVCacheManager       │
│                        │                          │    └ Executor             │
└────────────────────────┘                          └────────────┬──────────────┘
                                                                  │ (多卡时)
                                                     ┌────────────▼──────────────┐
                                                     │ Worker 子进程 × N (每卡一个) │
                                                     │  GPUWorker                 │
                                                     │  GPUModelRunner            │
                                                     │  模型权重 + KV Cache 显存    │
                                                     └────────────────────────────┘
```

关键认知：
- **为什么请求要变成 `EngineCoreRequest`**？因为它要**跨进程传输**，必须能被序列化
  （vLLM 用 `msgspec.Struct`，比 pickle 快）。这解释了 01 里那次「对象转换」。
- **单卡时**通常 Worker 逻辑内联在 EngineCore 进程；**多卡时**才拆成独立 Worker 进程。
- Detokenizer（token id → 文字）放在**主进程**，不占 GPU 进程资源。

## 四、贯穿全套文档的统一示例（重要，请记住这个设定）

后面每篇文档都会用**这一个例子**，你会看到同一份数据在各层的形态变化。

### 4.1 场景设定

两个用户请求，**共享同一段 system prompt**（故意这样设计，用来演示 03 的前缀缓存）：

```python
llm = LLM(model="...", block_size=16)   # block_size=16 是默认值

# 共同的 system prompt（假设分词后是 40 个 token）
SYS = "You are a helpful assistant. Answer concisely."   # → 40 tokens

req_A = SYS + "What is 2+2?"       # 40 + 8  = 48 个 prompt token
req_B = SYS + "Capital of France?" # 40 + 10 = 50 个 prompt token

llm.generate([req_A, req_B], SamplingParams(max_tokens=5, temperature=0))
```

为了让数字干净，本套文档统一约定（真实分词会有出入，但不影响理解）：

| 量 | 值 | 说明 |
|----|----|----|
| `block_size` | **16** | 每个 KV block 存 16 个 token 的 K/V |
| 请求 A prompt 长度 | **48** token | 恰好 3 个 block（48 = 16×3） |
| 请求 B prompt 长度 | **50** token | 需 4 个 block（50 = 16×3 + 2，最后一块只用了 2 格） |
| 共享前缀 SYS 长度 | **40** token | 前 2 个完整 block（32 token）可被前缀缓存共享 |
| `max_tokens` | **5** | 每个请求最多生成 5 个 token |

### 4.2 数据「一路变形」总览（本套文档的主线）

下面这张表是**全套文档的骨架**，每一行对应一篇文档里会详细展开的「数据形态」：

```
[阶段0/1 用户层→门面层]  01篇
  "You are...2+2?"  (Python str)
        │  分词 tokenizer
        ▼
  prompt_token_ids = [101, 2003, ...]  (list[int], 长度48)
        │  Processor 封装 + 跨进程序列化
        ▼
  EngineCoreRequest(request_id="A", prompt_token_ids=[...48个...],
                    sampling_params=SamplingParams(max_tokens=5), ...)
        │  EngineCore 收到后转成内部对象
        ▼
  Request(request_id="A", status=WAITING, num_computed_tokens=0, ...)
        │  加入 scheduler.waiting 队列

[阶段2 调度器]  02篇
  Scheduler.schedule() 决策：
    A、B 都是新请求(prefill)，token budget 够 → 都调度
    调用 KVCacheManager.allocate_slots 拿到 block
        │
        ▼
  SchedulerOutput(
    scheduled_new_reqs=[
      NewRequestData(req_id="A", num_computed_tokens=0,
                     block_ids=([10,11,12],), ...),   # A 拿到物理块 10,11,12
      NewRequestData(req_id="B", num_computed_tokens=32,  # B 命中A的前缀缓存!
                     block_ids=([10,11,13,14],), ...)] # 前2块复用10,11
    num_scheduled_tokens={"A":48, "B":18})   # B只需算剩下18个(50-32)

[阶段3 KV Cache]  03篇
  BlockPool 物理块状态：
    block 10: hash=H(SYS前16token), ref_cnt=2  ← A、B 共享
    block 11: hash=H(SYS前32token), ref_cnt=2  ← A、B 共享
    block 12: A 独有(2+2? 部分)
    block 13,14: B 独有

[阶段4 GPU执行]  04篇
  _prepare_inputs 把 A、B 打平成一维张量（零 padding）：
    input_ids     = [A的48个token..., B的18个新token...]  (总长66)
    positions     = [0,1,...,47,  32,33,...,49]
    slot_mapping  = [物理槽位, 每个token写到KV cache哪一格...]
    block_table   = [[10,11,12,..],[10,11,13,14,..]]  (读KV时用)
        │  model.forward → flash_attn_varlen_func(block_table=...)
        ▼
  logits → sample_tokens → 
  ModelRunnerOutput(sampled_token_ids=[[张], [巴]])  # A、B 各吐1个token

[回传 阶段5]  01篇尾 + 04篇尾
  update_from_output：A、B 各 num_computed_tokens+1，未到max_tokens，继续
        │  EngineCoreOutputs 回传主进程
        ▼
  detokenizer: token_id → "4" / "Paris"
  RequestOutput(request_id="A", outputs=[CompletionOutput(text="4")])
```

> 上面出现的物理块号（10,11,12...）是**举例**，真实运行会不同；
> 但「B 命中 A 的前缀、共享 block 10/11、ref_cnt=2」这个机制是真实的，03 篇会证明。

### 4.3 step 循环推进示意（decode 阶段）

第一次 step 是 prefill（把整个 prompt 算完，各吐第 1 个 token）。
之后每次 step 是 decode（每个请求各 +1 token）：

```
step #1 (prefill): A算48token→吐"4"      B算18token→吐"Paris"
step #2 (decode) : A算1token →吐token2    B算1token →吐token2
step #3 (decode) : A算1token →吐token3    B算1token →吐token3
step #4 (decode) : ...
step #5 (decode) : A到max_tokens=5→结束    B到max_tokens=5→结束
```

每次 decode step 里，A 和 B 被**合并成一个 batch** 一起送进 GPU（continuous batching），
这就是 vLLM 高吞吐的来源。

## 四点五、启动参数详解（把上面示例的参数讲透）

上面示例里出现了 `LLM(model="...", block_size=16)` 和 `SamplingParams(max_tokens=5, temperature=0)`。
这一节把常用启动参数讲清楚——它们直接决定了后面 02/03/04 篇里那些数字（token 预算、块数、batch 大小）从哪来。
参数分两类：**引擎级**（`LLM(...)` / `vllm serve`，全局生效）和**请求级**（`SamplingParams`，每个请求各自设）。

### 4.5.1 引擎级参数（`LLM(...)` 或 `vllm serve`）

下面默认值均取自真实源码（`vllm/config/`），后一列标出对应哪篇文档的机制：

| 参数 | 默认值 | 作用 | 关联文档 |
|------|-------|------|---------|
| `model` | 必填 | 模型名或本地路径（如 `"meta-llama/Llama-3.1-8B"`） | 01/04 |
| `block_size` | **16** | 每个 KV block 存多少 token 的 K/V。是分页的最小单位 | 03 |
| `gpu_memory_utilization` | **0.92** | 允许 vLLM 用多大比例的显存。剩下的留给系统/其他进程 | 04（§7.1 profiling） |
| `max_num_batched_tokens` | **2048** | 单步 batch 最多处理多少 token，即 02 篇的 **token 预算**（`token_budget` 上限来源） | 02 |
| `max_num_seqs` | **128** | 单步 batch 最多容纳多少个请求（序列数上限） | 02 |
| `max_model_len` | 随模型 | 单个请求 prompt+输出 的最大总长度。超了会报错或被拒 | 03（§算已算 token 时限制） |
| `enable_prefix_caching` | **True** | 是否开启前缀缓存（相同前缀复用 KV）。默认就开 | 03（核心） |
| `tensor_parallel_size` | **1** | 张量并行的 GPU 数。>1 时才拆出多个 Worker 子进程 | 00 进程模型图 / 04 |
| `dtype` | `"auto"` | 权重/计算精度（如 `float16`、`bfloat16`）。`auto` 按模型配置定 | 04 |
| `enforce_eager` | **False** | True 则禁用 CUDA Graph，全程 eager 模式（调试用，慢但好排查） | 04（§7.2 CUDA Graph） |

**几个最常调的参数，直觉解释：**

- **`gpu_memory_utilization`（0.92）**：调大 → 能开更多 KV 块 → 容纳更多并发请求，但太大会 OOM（04 篇 §7.1 讲了它怎么换算成"能开多少块"）。
- **`max_num_batched_tokens`（2048）**：这就是 02 篇反复出现的 **token 预算**的上限。调大 → 单步吞吐更高，但单步延迟也更大——**吞吐与延迟的权衡旋钮**。
- **`max_num_seqs`（128）**：和上面配合限制 batch 规模，一个限"总 token 数"，一个限"请求个数"，谁先到上限就以谁为准。
- **`enable_prefix_caching`（True）**：默认开启，这正是本套统一示例里"B 命中 A 的前缀省 32 token"能成立的前提；关掉它 03 篇的共享机制就不生效了。

### 4.5.2 请求级参数（`SamplingParams`，每个请求独立）

这些跟着每个请求走，不同请求可以不同（示例里 A/B 用了相同的）：

| 参数 | 示例值 | 作用 |
|------|-------|------|
| `max_tokens` | **5** | 这个请求最多生成多少个 token（示例设 5，所以 step #5 就结束） |
| `temperature` | **0** | 采样温度。`0` = 贪心（每次选概率最高，结果确定）；越大越随机 |
| `top_p` / `top_k` | 1.0 / -1 | 核采样 / top-k 采样的截断参数，控制候选 token 范围 |
| `stop` | 无 | 遇到指定字符串就提前停止（02 篇 `update_from_output` 判停会用） |
| `n` | 1 | 一个 prompt 生成几条候选（>1 会"扇出"成多个子请求，见 01 篇） |

> 示例里 `temperature=0` 是**故意**的：贪心采样结果确定，方便你打断点复现"A 吐 4、B 吐 Paris"这种固定结果。

### 4.5.3 参数怎么串起本套文档（一图对应）

```
LLM(block_size=16, gpu_memory_utilization=0.92,
    max_num_batched_tokens=2048, enable_prefix_caching=True)
       │              │                    │                  │
       ▼              ▼                    ▼                  ▼
   03篇:每块       04篇§7.1:能开        02篇:token预算       03篇:B能命中
   存16 token      多少 KV 块           (单步油门上限)       A的前缀
       │
SamplingParams(max_tokens=5, temperature=0)
       │                        │
       ▼                        ▼
   02篇:step#5     04篇:sample_tokens
   到 max 结束      贪心选 token
```

一句话：**引擎级参数决定了"资源池有多大、一步能干多少活"，请求级参数决定了"每个请求怎么生成、生成到什么时候停"。** 后面各篇看到的具体数字，都是这些参数的下游结果。

## 五、文档定位速查

| 篇 | 主题 | 核心问题 | 关键函数 |
|----|------|---------|---------|
| 01 | 请求的一生-主控制流 | 请求怎么从字符串走到 GPU，step 心跳是什么 | `LLM.generate`、`EngineCore.step`、`run_busy_loop` |
| 02 | 调度器-连续批处理 | 每步「挑谁进 batch」，显存不够怎么抢占 | `Scheduler.schedule`、`_preempt_request`、`update_from_output` |
| 03 | PagedAttention 与 KV Cache | 显存怎么像操作系统分页一样管理，前缀怎么复用 | `allocate_slots`、`get_new_blocks`、`hash_block_tokens` |
| 04 | Worker 与模型执行 | 变长请求怎么打平成张量，分页 attention 怎么落地 | `_prepare_inputs`、`execute_model`、`flash_attn_varlen_func` |
| 05 | 多机推理与 PD 分离 | 一台机器装不下怎么并行，prefill/decode 怎么拆到不同实例 | `ParallelConfig`、`KVTransferConfig`、`KVConnectorBase_V1` |

> 01~04 篇讲**单实例、单机**内部机制；05 篇把镜头拉远到**多卡、多机、跨实例**部署。前四篇是基础，05 篇是它们在分布式下的延伸。

## 六、怎么用这套文档（方法建议）

1. **带着「统一示例」读**：每篇都会回到 A/B 两请求，重点看「这一层拿到什么数据、变成什么数据交给下一层」。
2. **对照架构图定位**：看某篇代码时，先回本篇第二节的架构图，确认它在哪一层。
3. **动手打断点**：写个最小脚本 `LLM(...).generate([...], SamplingParams(max_tokens=5))`，
   在 `EngineCore.step` → `schedule` → `allocate_slots` → `_prepare_inputs` → `sample_tokens`
   五个点打断点，`n=2` 请求单步跟，把本篇 4.2 的「数据变形表」一格一格印证一遍。
```
