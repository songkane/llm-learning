# 02 · 调度器 Scheduler —— 连续批处理的大脑

> 承接 01。本文讲 `EngineCore.step()` 里的第一步 `schedule()`：调度器如何决定「这一轮 GPU 处理哪些请求、每个请求处理多少 token」。
> 注释分两类：`【逻辑】`讲 vLLM 原理；`【Python】`讲语法。
> 对应源码：`vllm/v1/core/sched/scheduler.py` 和 `vllm/v1/core/sched/request_queue.py`。

---

## 0. 先理解调度器要解决的问题

传统推理（静态 batch）的痛点：把若干请求凑成一批，一起送进 GPU，**必须等这批里最长的请求全部生成完，整批才能返回**。短请求被长请求拖死，GPU 利用率低。

vLLM 的解法叫 **连续批处理（Continuous Batching）**：
- 不存在「一批算到底」，而是**每一步（step）都重新决策一次**。
- 每步结束，已完成的请求立刻离开、腾出的资源立刻给新请求或等待中的请求。
- 新请求的 prefill（处理 prompt）和老请求的 decode（生成下一个 token）可以**混在同一步**里算。

调度器就是做这个「每步决策」的大脑。它维护两个核心队列：

```
waiting  队列：排队等待的新请求（还没开始算，或被抢占退回来的）
running  队列：正在生成中的请求（已占了 KV Cache 显存）
```

`schedule()` 每次被调用，就从这两个队列里挑出本轮要处理的请求，产出一张「任务清单」`SchedulerOutput` 交给 GPU。

> 本篇沿用 `00` 篇的统一示例（A/B 两请求，共享 40-token 的 system prompt）。

### 0.1 `schedule()` 内部流程图 ★

先建立整体骨架，后面各节是这张图的展开：

```
              ┌─────────────────────────────────────────┐
              │  schedule() 开始                          │
              │  建账本 + token_budget = 本轮 token 预算    │
              └───────────────────┬─────────────────────┘
                                  ▼
        ┌───────────────────────────────────────────────┐
        │ 阶段A：遍历 running 队列（先保在跑的请求）        │
        │   for 每个 running 请求:                         │
        │     num_new = 需算总量 - 已算; 受 budget 限制    │
        │     ┌──────────────────────────────────────┐   │
        │     │ allocate_slots(申请KV显存)  ← 03篇     │   │
        │     └──────────┬───────────────────────────┘   │
        │        成功?   │                                 │
        │      ┌─────────┴─────────┐                       │
        │      ▼ 是                ▼ 否(显存不足)            │
        │  记入本轮调度       抢占最低优先级请求             │
        │                    _preempt_request:            │
        │                      丢KV+清零+退回waiting         │
        │                    (循环重试, 直到能分配或没人可抢) │
        └───────────────────┬─────────────────────────────┘
                            ▼
        ┌───────────────────────────────────────────────┐
        │ 阶段B：遍历 waiting 队列（放新请求）             │
        │   前提: 本轮"没发生过抢占" 才进这里              │
        │   for 队首请求(peek):                            │
        │     ① 前缀缓存命中检查 → num_computed_tokens>0?  │
        │        (B 命中 A 的 SYS 前缀! ← 03篇)            │
        │     ② num_new = num_tokens - 已缓存; 受budget限  │
        │     ③ allocate_slots 申请显存                    │
        │          失败 → break (不抢占, 直接停放新的)      │
        │          成功 → pop出队, 移入 running, 状态RUNNING│
        └───────────────────┬─────────────────────────────┘
                            ▼
        ┌───────────────────────────────────────────────┐
        │ 阶段C：打包 SchedulerOutput（本轮施工图）返回    │
        │   scheduled_new_reqs / cached_reqs              │
        │   num_scheduled_tokens / block_ids ...          │
        └───────────────────────────────────────────────┘
```

两条核心分水岭（全篇最该记住的）：
- **running 显存不足 → 抢占别人**；**waiting 显存不足 → 直接停**。
- **本轮一旦抢占过，就不再放新请求**（阶段 B 的前提），避免显存雪上加霜。

## 1. 关键设计思想：没有 prefill/decode 之分

`schedule()` 开头有一段极其重要的注释（第 440 行），点出 vLLM 调度的核心哲学：

```python
    def schedule(self, throttle_prefills: bool = False) -> SchedulerOutput:
        self.current_step += 1
        # NOTE(woosuk) on the scheduling algorithm:
        # There's no "decoding phase" nor "prefill phase" in the scheduler.
        # Each request just has the num_computed_tokens and
        # num_tokens_with_spec.
        # At each step, the scheduler tries to assign tokens to the requests
        # so that each request's num_computed_tokens can catch up its
        # num_tokens_with_spec.
```

【逻辑】翻译这段设计哲学：

- 每个请求只有两个数字：
  - `num_computed_tokens`：已经算好（KV 已缓存）的 token 数。
  - `num_tokens_with_spec`：这个请求当前总共需要算多少 token（prompt + 已生成的输出 + 投机 token）。
- 调度器每步的唯一目标：**给请求分配一些 token 额度，让 `num_computed_tokens` 往 `num_tokens_with_spec` 追赶**。
- 于是「prefill」不过是「`num_computed_tokens` 从 0 开始追」，「decode」不过是「已经追上、每步再 +1」。二者在代码里是**同一套逻辑**，只是数字不同。

这个统一抽象非常优雅——它一口气覆盖了 chunked prefill（prompt 太长分几步算）、prefix caching（前缀已算好直接跳过）、speculative decoding（一次追多个）。

【Python】`self.current_step += 1` 就是 `self.current_step = self.current_step + 1`，步数计数器自增。Python 没有 `++` 运算符，只能用 `+= 1`。

## 2. 调度前的准备：一堆「账本」

```python
        scheduled_new_reqs: list[Request] = []
        scheduled_resumed_reqs: list[Request] = []
        scheduled_running_reqs: list[Request] = []
        preempted_reqs: list[Request] = []

        req_to_new_blocks: dict[str, KVCacheBlocks] = {}
        num_scheduled_tokens: dict[str, int] = {}
        token_budget = self.max_num_scheduled_tokens
```

【逻辑】开局先建几个空账本，记录这一轮的决策结果：
- `scheduled_new_reqs`：本轮新启动的请求（第一次被调度）。
- `scheduled_resumed_reqs`：之前被抢占、这轮恢复的请求。
- `scheduled_running_reqs`：本来就在跑、这轮继续跑的请求。
- `preempted_reqs`：这轮被「抢占」（踢出去）的请求。
- `req_to_new_blocks`：每个请求这轮新分到的 KV 显存块。
- `num_scheduled_tokens`：每个请求这轮分到多少 token 额度。
- `token_budget`：**本轮总 token 预算**（来自配置 `max_num_scheduled_tokens`）。它限制一步最多处理这么多 token，防止一步塞太多把显存/时间撑爆——是连续批处理调节吞吐与延迟的关键旋钮。

【Python 重点】
- `list[Request] = []` :冒号后是类型注解（「这是一个装 Request 的列表」），等号后 `[]` 是真正赋的空列表值。**注解只是提示，`[]` 才是实际值**。
- `dict[str, KVCacheBlocks] = {}` :类型注解说「键是 str、值是 KVCacheBlocks 的字典」，`{}` 是空字典。
- 这种 `名字: 类型 = 初值` 是 vLLM 里最常见的变量声明写法。

## 3. 第一优先级：先照顾正在跑的请求（running 队列）

【逻辑】调度器**先保住已经在跑的请求**（让它们继续 decode），再考虑放新请求进来。这符合直觉：不能让快生成完的请求饿死。

```python
        # First, schedule the RUNNING requests.
        req_index = 0
        while req_index < len(self.running) and token_budget > 0:
            request = self.running[req_index]
            ...
            num_new_tokens = (
                request.num_tokens_with_spec
                + request.num_output_placeholders
                - request.num_computed_tokens
            )
            ...
            num_new_tokens = min(num_new_tokens, token_budget)
```

【逐行】

- `while req_index < len(self.running) and token_budget > 0:`
  - 【逻辑】遍历 running 队列，直到走完或预算耗尽。**两个终止条件用 `and` 连接，任一不满足就停。**
  - 【Python】`len(x)` 取长度。`and` 是逻辑与。Python 用缩进表示 while 循环体。

- `num_new_tokens = 需要的总量 - 已算的量`
  - 【逻辑】算出这个请求「还差多少 token 没算」。对 decode 中的请求，这通常就是 1（每步生成一个）。

- `num_new_tokens = min(num_new_tokens, token_budget)`
  - 【逻辑】但不能超过剩余的 token 预算，取较小值。这就是 token 预算在起作用。

### 3.1 关键动作：申请 KV 显存（可能触发抢占）

running 请求要继续算，就要为新 token 申请 KV Cache 空间。**如果显存不够，就要抢占别人**——这是调度器最精彩的部分（第 576 行）：

```python
            # Schedule newly needed KV blocks for the request.
            with record_function_or_nullcontext("schedule: allocate_slots"):
                while True:
                    new_blocks = self.kv_cache_manager.allocate_slots(
                        request,
                        num_new_tokens,
                        num_lookahead_tokens=self.num_lookahead_tokens,
                    )

                    if new_blocks is not None:
                        # The request can be scheduled.
                        break

                    # The request cannot be scheduled.
                    # Preempt the lowest-priority request.
                    if self.policy == SchedulingPolicy.PRIORITY:
                        preempted_req = max(
                            self.running,
                            key=lambda r: (r.priority, r.arrival_time),
                        )
                        ...
                    else:
                        preempted_req = self.running.pop()

                    self._preempt_request(
                        preempted_req,
                        scheduled_timestamp,
                        drop_stale_output=self.requires_kv_delivery,
                    )
                    preempted_reqs.append(preempted_req)
                    if preempted_req == request:
                        # No more request to preempt. Cannot schedule this request.
                        break
```

【逐行精读】

- `while True:`
  - 【逻辑】无限循环，直到「分到显存」或「没人可抢了」才 `break`。
  - 【Python】`while True:` 是标准的「先循环，靠内部 break 退出」写法。

- `new_blocks = self.kv_cache_manager.allocate_slots(request, num_new_tokens, ...)`
  - 【逻辑】**向 KV Cache 管理器申请显存块**（详见 03 文档）。成功返回块列表，失败返回 `None`。

- `if new_blocks is not None: break`
  - 【逻辑】申请成功，跳出循环，这个请求本轮能跑。

- 申请失败 → 进入抢占逻辑：
  - `if self.policy == SchedulingPolicy.PRIORITY:` :如果是优先级策略，抢「优先级最低+最晚到达」的那个。
    - `preempted_req = max(self.running, key=lambda r: (r.priority, r.arrival_time))`
      - 【Python 重点】`max(可迭代对象, key=函数)`：按 key 函数的返回值找最大。
      - `lambda r: (r.priority, r.arrival_time)` 是**匿名函数（lambda）**：接收一个参数 `r`，返回元组 `(优先级, 到达时间)`。相当于：
        ```python
        def 临时函数(r):
            return (r.priority, r.arrival_time)
        ```
      - 元组比较是「先比第一个，相等再比第二个」，所以这里效果是「priority 最大的优先，若相同则 arrival_time 晚的优先」被选为牺牲品。
  - `else: preempted_req = self.running.pop()` :默认 FCFS 策略，直接踢掉队尾（最晚加入的）。
    - 【Python】`list.pop()` 不带参数默认弹出并返回**最后一个**元素。

- `self._preempt_request(preempted_req, ...)`
  - 【逻辑】**执行抢占**：把这个倒霉蛋踢回 waiting 队列（下节详解）。

- `if preempted_req == request: break`
  - 【逻辑】**边界情况**：如果连自己都被选中抢占（说明整个队列就剩它了还是塞不下），那没救了，放弃调度这个请求。

【逻辑总结抢占的意义】显存是硬约束。当放不下时，vLLM 宁可「暂停」某些请求（把它们算过的 KV 丢弃、退回 waiting），也要保证被选中的请求能推进。被抢占的请求之后会重新排队、从头 prefill。这是「用重算换显存」的权衡。

## 4. 抢占的实现：`_preempt_request`

文件同上，第 1268 行。这是「散落在类里的一个私有方法」，但对理解调度至关重要，单独讲透。

```python
    def _preempt_request(
        self, request: Request, timestamp: float, drop_stale_output: bool = False
    ) -> None:
        assert request.status == RequestStatus.RUNNING, (
            "Only running requests can be preempted"
        )
        self._free_request_blocks(request)          # 1. 释放它占的 KV 显存
        self.encoder_cache_manager.free(request)      # 2. 释放编码器缓存
        self._inflight_prefills.discard(request)
        request.status = RequestStatus.PREEMPTED      # 3. 状态改为「被抢占」
        request.num_computed_tokens = 0               # 4. 已算 token 清零（关键！）
        ...
        request.num_preemptions += 1                  # 5. 抢占次数 +1（统计）
        ...
        # Put the request back to the waiting queue.
        self.waiting.prepend_request(request)         # 6. 塞回 waiting 队首
        self.reset_preempted_req_ids.add(request.request_id)
```

【逐行精读】

- `def _preempt_request(self, request, timestamp, drop_stale_output=False) -> None:`
  - 【Python】`-> None` 表示这个方法没有返回值（只做副作用）。`_` 开头表示私有方法。

- `assert request.status == RequestStatus.RUNNING, "..."`
  - 【Python】`assert 条件, "错误信息"`：断言。条件为假就抛 `AssertionError` 并打印信息。vLLM 大量用 assert 做「不变量检查」——「代码走到这里，这个条件必须成立，否则是 bug」。

- `self._free_request_blocks(request)`
  - 【逻辑】**归还它占的所有 KV 显存块**，这正是抢占的目的——腾显存。

- `request.num_computed_tokens = 0`
  - 【逻辑】**最关键的一行**：已算 token 清零。意味着这个请求下次被调度时，要**从头重新 prefill**（它的 KV 已经被丢弃了）。这就是抢占的代价——之前的计算白做了。

- `self.waiting.prepend_request(request)`
  - 【逻辑】把它放回 waiting 队列的**队首**（`prepend` = 加到前面），下次优先重新调度它，减少饥饿。

【逻辑】所以「抢占」本质是：**丢弃某请求的中间结果，归还其显存，让它回炉重排队。** 用重算的代价换取显存的即时可用。

## 5. 第二优先级：放新请求进来（waiting 队列）

running 都照顾完、还有预算，才轮到 waiting 队列（第 691 行起）。这段代码分支非常多（涉及 prefix caching、KV connector、encoder、mamba、投机解码填充等），初学**只需抓住主干**：

```python
        # Next, schedule the WAITING requests.
        if not preempted_reqs and self._pause_state == PauseState.UNPAUSED:
            ...
            while (self.waiting or self.skipped_waiting) and token_budget > 0:
                ...
                request = request_queue.peek_request()   # 看一眼队首（不取出）
                ...
                # Get already-cached tokens.（前缀缓存命中检查）
                if request.num_computed_tokens == 0:
                    (new_computed_blocks, num_new_local_computed_tokens, ...) = \
                        self._get_local_prefix_cache_hit(request)
                ...
                # 算出这轮要处理多少个 token
                num_new_tokens = request.num_tokens - num_computed_tokens
                num_new_tokens = min(num_new_tokens, token_budget)
                ...
                # 申请 KV 显存
                new_blocks = self.kv_cache_manager.allocate_slots(request, num_new_tokens, ...)
                if new_blocks is None:
                    break   # 显存不够，停止放新请求（注意这里是 break 不抢占）
                ...
                request = request_queue.pop_request()  # 真正取出队首
                self.running.append(request)           # 移入 running 队列
                ...
                request.status = RequestStatus.RUNNING
                token_budget -= num_new_tokens         # 扣预算
```

【主干逻辑梳理】

1. `if not preempted_reqs and ...:` :**如果这一轮已经发生了抢占，就不再放新请求**——显存本就紧张，不能雪上加霜。这是很聪明的自我保护。

2. `request = request_queue.peek_request()` :先「窥视」队首请求但不取出（因为可能因各种原因跳过它）。

3. **前缀缓存命中检查**（`_get_local_prefix_cache_hit`）：
   - 【逻辑】这是 vLLM 省算力的大杀器。如果新请求的 prompt 前缀，和之前算过的某个请求相同（比如相同的 system prompt），那这段前缀的 KV **直接复用**，`num_computed_tokens` 一上来就 > 0，省去重复计算。详见 03 文档。

4. `num_new_tokens = min(request.num_tokens - num_computed_tokens, token_budget)`
   - 【逻辑】要处理的 token = 总需求 - 已缓存的，再受预算约束。若预算只够处理一部分 prompt，就只算一部分（这就是 **chunked prefill**：长 prompt 分几步吃完）。

5. `new_blocks = allocate_slots(...)`；`if new_blocks is None: break`
   - 【逻辑】给新请求申请显存。**注意这里失败是直接 `break`（停止放新请求），而不是像 running 那样去抢占**——因为新请求还没开始，没必要为它牺牲已在跑的请求。

6. 成功后：`request_queue.pop_request()` 真正取出 → `self.running.append(request)` 移入 running → 状态改 `RUNNING` → 扣预算。

【Python】`peek` 和 `pop` 分开是常见模式：先看看要不要处理，确定要了再真正取出。避免「取出后发现不能处理还得放回去」的麻烦。

## 6. 组装任务清单：`SchedulerOutput`

循环结束后，把所有决策打包成 `SchedulerOutput`（第 1202 行），这是调度器交给执行层的**接口契约**：

```python
        scheduler_output = SchedulerOutput(
            scheduled_new_reqs=new_reqs_data,           # 新请求（含 prompt、分到的块）
            scheduled_cached_reqs=cached_reqs_data,     # 继续跑的老请求
            num_scheduled_tokens=num_scheduled_tokens,  # 每个请求这轮处理几个 token
            total_num_scheduled_tokens=total_num_scheduled_tokens,  # 总量
            scheduled_spec_decode_tokens=scheduled_spec_decode_tokens,  # 投机 token
            num_common_prefix_blocks=num_common_prefix_blocks,  # 公共前缀（cascade attn 用）
            finished_req_ids=self.finished_req_ids,     # 上一步到这步之间完成的请求
            ...
        )
```

【逻辑】`SchedulerOutput` 就是一张详细的「本轮施工图」：GPU 拿到它，就知道要为哪些请求、各处理多少 token、用哪些显存块。它是**调度层（决策）和执行层（GPU 计算）之间唯一的数据接口**。定义在 `vllm/v1/core/sched/output.py`。

### 6.1 统一示例：A/B 两请求的调度决策与数据形态 ★

把 01 篇送进来的 A（48 token）、B（50 token）放进 `schedule()` 走一遍。
两者初始都在 waiting 队列、`num_computed_tokens=0`，假设 `token_budget` 足够大。

**step #1（prefill）的阶段 A**：running 为空，跳过。

**step #1 的阶段 B**（FCFS：先 A 后 B）：

| 请求 | 前缀缓存命中 | num_computed | num_new_tokens | allocate_slots 结果 |
|------|-----------|-----------|-----------|-----------|
| A | 无（第一个请求） | 0 | 48（整个 prompt） | 需 ⌈48/16⌉=3 块 → `[10,11,12]` |
| B | **命中 A 的 SYS 前缀** | **32**（前 2 个完整块） | 50-32=**18** | 前 2 块复用 `[10,11]`，新分 `[13,14]` |

> B 命中 A 的前缀，直接省掉 32 个 token 的 prefill 计算——这就是 prefix caching 的威力，
> 底层机制（block 哈希、ref_cnt）在 03 篇证明。

**产出的 `SchedulerOutput`（step #1）**，字段取自真实源码 `output.py`：
```python
SchedulerOutput(
    scheduled_new_reqs=[
        NewRequestData(req_id="A", prompt_token_ids=[...48个...],
                       block_ids=([10, 11, 12],),        # A 的物理块
                       num_computed_tokens=0),
        NewRequestData(req_id="B", prompt_token_ids=[...50个...],
                       block_ids=([10, 11, 13, 14],),    # 前2块与A共享!
                       num_computed_tokens=32),          # 命中前缀，从32起算
    ],
    scheduled_cached_reqs=CachedRequestData.make_empty(),  # 本轮无老请求
    num_scheduled_tokens={"A": 48, "B": 18},   # 各自本轮要算多少 token
    total_num_scheduled_tokens=66,             # 48 + 18
    finished_req_ids=set(),
    ...
)
```
这张「施工图」交给 04 篇的 `execute_model`，GPU 就知道：为 A 算 48 个 token、为 B 算 18 个 token，各自用哪些 block。

**step #2（decode）时的对比**：A、B 已在 running 队列，各自 `num_computed_tokens` 已到 48/50，每步只需 +1：

```python
SchedulerOutput(
    scheduled_new_reqs=[],                         # 没有新请求了
    scheduled_cached_reqs=CachedRequestData(       # A、B 都是"老请求"，只发增量
        req_ids=["A", "B"],
        num_computed_tokens=[49, 51],              # 上一步各 +1 了
        new_block_ids=[...],                       # 若跨了block边界才分新块
        ...),
    num_scheduled_tokens={"A": 1, "B": 1},         # decode：每个只算 1 个
    total_num_scheduled_tokens=2,
    ...
)
```

**对比记忆**：prefill step 里 `num_scheduled_tokens` 是几十（整段 prompt）；
decode step 里每个请求只有 **1**。这就是 01 篇说的「每步每请求 +1 token」在调度层的体现。
另外注意：新请求走 `scheduled_new_reqs`（发全量），老请求走 `scheduled_cached_reqs`（只发增量 diff），
这是为了减少跨进程通信量——呼应 00 篇的进程模型。

## 7. 一步的收尾：`update_from_output`

GPU 算完后，`EngineCore.step()` 会调 `scheduler.update_from_output()`（第 1665 行）「记账」。核心是遍历每个请求、把新 token 写回、判断是否结束：

```python
    def update_from_output(
        self,
        scheduler_output: SchedulerOutput,
        model_runner_output: ModelRunnerOutput,
    ) -> dict[int, EngineCoreOutputs]:
        sampled_token_ids = model_runner_output.sampled_token_ids  # GPU 采样出的新 token
        ...
        for req_id, num_tokens_scheduled in num_scheduled_tokens.items():
            request = self.requests.get(req_id)
            ...
            req_index = model_runner_output.req_id_to_index[req_id]
            generated_token_ids = (
                sampled_token_ids[req_index] if sampled_token_ids else []
            )
            ...
            # Check for stop and update request status.
            if new_token_ids:
                new_token_ids, stopped = self._update_request_with_output(
                    request, new_token_ids, is_stale=output_is_stale
                )
```

【逐行】

- `for req_id, num_tokens_scheduled in num_scheduled_tokens.items():`
  - 【Python】遍历字典。`.items()` 同时给出键（req_id）和值（该请求这轮的 token 数）。**这是遍历字典最常用的写法。**

- `generated_token_ids = sampled_token_ids[req_index] if sampled_token_ids else []`
  - 【逻辑】取出 GPU 为这个请求新采样的 token。
  - 【Python】又是三元表达式：有采样结果就取，没有就给空列表 `[]`（防止后面出错）。

- `new_token_ids, stopped = self._update_request_with_output(request, new_token_ids, ...)`
  - 【逻辑】**核心记账**：把新 token 追加到请求的输出里，并检查是否命中停止条件（遇到 EOS、达到 max_tokens、命中 stop 字符串）。返回 `(有效token, 是否结束)`。
  - 【Python】元组解包，一次接两个返回值。

后续（第 1804 行起）还会处理：pooling 任务的结束、encoder-only 的结束、结构化输出的语法校验等分支。结束的请求会被移出 running、释放显存，并把结果打包进 `EngineCoreOutputs` 返回给上层。

## 8. 散落的关键实现：`request_queue.py` 全解

调度器用的两个队列（waiting/running）背后，是 `vllm/v1/core/sched/request_queue.py` 里的一套**队列抽象**。这个文件短小精悍，且用到很多 Python 面向对象和特殊语法，非常值得完整讲。

### 8.1 调度策略枚举

```python
class SchedulingPolicy(Enum):
    """Enum for scheduling policies."""
    FCFS = "fcfs"           # 先来先服务
    PRIORITY = "priority"   # 按优先级
```

【Python】`Enum` 是「枚举」，用来定义一组有名字的常量。`SchedulingPolicy.FCFS` 比直接写字符串 `"fcfs"` 更安全（拼错会立刻报错，IDE 也能补全）。

### 8.2 抽象基类：定义「队列」的接口

```python
class RequestQueue(ABC):
    """Abstract base class for request queues."""

    @abstractmethod
    def add_request(self, request: Request) -> None:
        """Add a request to the queue according to the policy."""
        pass

    @abstractmethod
    def pop_request(self) -> Request:
        pass
    ...
```

【Python 重点 —— 这是理解 vLLM 大量代码的关键】

- `class RequestQueue(ABC):` :`ABC` = Abstract Base Class（抽象基类）。继承它表示「这是一个接口/模板，不能直接用，必须被子类实现」。
- `@abstractmethod` :**装饰器**。放在方法上，表示「子类必须实现这个方法，否则子类也不能被实例化」。
  - 【Python】装饰器就是「加在函数/方法上、以 `@` 开头的修饰符」，用来给函数附加额外行为。这里 `@abstractmethod` 的作用是「强制子类实现」。
- `pass` :Python 的「空语句占位符」。抽象方法没有实现，用 `pass` 填充函数体（不能留空）。

【逻辑】这套抽象的意义：调度器代码只依赖 `RequestQueue` 这个「接口」，不关心底层到底是 FCFS 还是优先级队列。想换策略，换个实现类即可，调度器一行不用改。这是「面向接口编程」。

### 8.3 实现一：FCFS 队列（先来先服务）

```python
class FCFSRequestQueue(deque[Request], RequestQueue):
    """A first-come-first-served queue that supports deque operations."""

    def add_request(self, request: Request) -> None:
        self.append(request)          # 加到队尾

    def pop_request(self) -> Request:
        return self.popleft()         # 从队首取（先进先出）

    def prepend_request(self, request: Request) -> None:
        self.appendleft(request)      # 加到队首（抢占退回时用）
```

【Python】

- `class FCFSRequestQueue(deque[Request], RequestQueue):`
  - **多重继承**：同时继承 `deque`（Python 内置的双端队列）和 `RequestQueue`（接口）。
  - `deque` 提供了高效的两端增删（`append`/`appendleft`/`popleft`），FCFSRequestQueue 直接复用它的能力。
- `self.append` / `self.popleft` / `self.appendleft` :都是从 `deque` 继承来的方法。
  - 【逻辑】FCFS = 队尾进（`append`）、队首出（`popleft`），就是普通排队。被抢占的请求用 `appendleft` 插队到最前，优先重新处理。

### 8.4 实现二：优先级队列（用堆实现）

```python
class PriorityRequestQueue(RequestQueue):
    def __init__(self) -> None:
        self._heap: list[Request] = []

    def add_request(self, request: Request) -> None:
        heapq.heappush(self._heap, request)      # 入堆

    def pop_request(self) -> Request:
        if not self._heap:
            raise IndexError("pop from empty heap")
        return heapq.heappop(self._heap)         # 弹出最小（最高优先级）
```

【Python / 数据结构】

- `def __init__(self):` :**构造函数**（对象创建时自动调用），相当于其他语言的 constructor。这里初始化一个空列表 `self._heap` 作为堆的底层存储。
- `heapq` :Python 内置的「堆」模块。堆是一种能高效取出「最小元素」的结构。
  - `heapq.heappush(堆, 元素)`：入堆，自动维持堆序。
  - `heapq.heappop(堆)`：弹出并返回**最小**元素。
- 【逻辑】要「优先级最高先处理」，就让 `Request` 定义比较规则为「priority 小的算小」（见 Request 类），堆顶就永远是最该处理的请求。

### 8.5 生成器：`__iter__` 里的 `yield`

```python
    def __iter__(self) -> Iterator[Request]:
        """Iterate over the queue according to priority policy."""
        heap_copy = self._heap[:]
        while heap_copy:
            yield heapq.heappop(heap_copy)
```

【Python 重点 —— 生成器】

- `heap_copy = self._heap[:]` :`[:]` 是「切片」，这里表示复制整个列表（避免遍历时破坏原堆）。
- `yield heapq.heappop(heap_copy)`
  - `yield` 是「生成器」关键字。含 `yield` 的函数不是普通函数，而是**生成器**：调用它不立即执行，而是每次要一个值时才执行到下一个 `yield`，「吐出」一个值后暂停，下次再继续。
  - 【逻辑】这里的效果：**按优先级顺序，一个一个地「懒惰」产出请求**。不需要一次性排好全部，用一个吐一个，省内存。
  - 【对比】和 `return` 的区别：`return` 一次性返回后函数就结束；`yield` 可以多次产出、每次暂停保留状态。

### 8.6 工厂函数：根据策略创建队列

```python
def create_request_queue(policy: SchedulingPolicy) -> RequestQueue:
    """Create request queue based on scheduling policy."""
    if policy == SchedulingPolicy.PRIORITY:
        return PriorityRequestQueue()
    elif policy == SchedulingPolicy.FCFS:
        return FCFSRequestQueue()
    else:
        raise ValueError(f"Unknown scheduling policy: {policy}")
```

【逻辑】这是「**工厂函数**」模式：给它一个策略枚举，它返回对应的队列实现。调度器初始化时调用它（我们在第 5 节见过 `create_request_queue(self.policy)`），拿到的是抽象接口 `RequestQueue`，后续用起来完全一致。这就是 8.2 抽象基类的价值兑现。

【Python】`elif` = else if。`raise ValueError(...)` 对不认识的策略抛异常，属于「防御式编程」。

## 9. 全流程回顾

```
schedule() 被 EngineCore.step() 调用
  │
  ├─ 1. 建账本 + 设 token_budget（本轮 token 预算）
  │
  ├─ 2. 遍历 running 队列（优先保住在跑的）
  │      每个请求：算需处理 token → allocate_slots 申请显存
  │        └─ 显存不足 → 抢占最低优先级请求（_preempt_request，丢KV退回waiting）
  │
  ├─ 3. 若本轮没抢占，遍历 waiting 队列（放新请求）
  │      每个请求：前缀缓存命中检查 → 算 token → 申请显存
  │        └─ 显存不足 → break（不抢占，直接停止放新的）
  │      成功 → 移入 running
  │
  └─ 4. 打包成 SchedulerOutput（施工图）返回
        ↓ 交给 execute_model 在 GPU 上算（04 文档）
        ↓ 算完 update_from_output 记账、判断结束、释放显存
```

**三个必记要点：**

1. **running 优先于 waiting**：先保在跑的，再放新的。
2. **两种「放不下」处理不同**：running 放不下 → 抢占别人；waiting 放不下 → 直接停。
3. **token_budget 是本轮 token 预算**：控制一步的工作量，是连续批处理平衡吞吐与延迟的旋钮。
