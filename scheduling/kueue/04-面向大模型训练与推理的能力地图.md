# 面向大模型训练与推理的能力地图

> 前三篇讲「Kueue 怎么工作」，本篇讲「**大模型场景该用它的哪些能力、怎么配**」。按训练、推理、训推混部三条线组织，并给出与 Volcano 的取舍建议。
>
> 源码基线：**v0.19.1**

---

## 1. 训练侧

### 1.1 需求 → 能力 → 配置

| 训练场景的真实需求 | Kueue 能力 | 配置位置 |
|------------------|-----------|---------|
| N 个 Pod 必须同时起（建 NCCL 通信域） | **Workload 整体准入**（gang 是结构性保证） | 无需配置。`RepresentativeMode()` 取所有 PodSet 最小值 |
| 资源不够时不创建 Pod | **suspend 机制** | webhook 自动设 `suspend=true` |
| 多角色作业（1 master + 7 worker） | **多 PodSet**（最多 18 个） | 由 JobSet / PyTorchJob / TrainJob 的 replica 定义自动展开 |
| 8 机 64 卡落在同一个网络 block | **TAS 硬约束** | `kueue.x-k8s.io/podset-required-topology: <block-label>` |
| TP=4 的每组 4 卡同机，组间可跨机 | **PodSet slice** | `podset-slice-required-topology: kubernetes.io/hostname` + `podset-slice-size: "4"` |
| 优先用包年机器，不够用竞价机器 | **ResourceFlavor + FlavorFungibility** | CQ 的 flavor 有序列表 |
| 部门/团队配额，闲时互借忙时抢回 | **Cohort + borrowingLimit/lendingLimit + reclaimWithinCohort** | ClusterQueue |
| 弹性训练（能起多少先起多少） | **PartialAdmission** | `podSets[*].minCount` |
| 运行中改并行度 | **Elastic Jobs（workload slice）** | `ElasticJobsViaWorkloadSlices` gate |
| 等集群扩容出机器再开始 | **ProvisioningRequest AdmissionCheck** | AdmissionCheck + ProvisioningRequestConfig |
| 单集群资源不够，派到别的集群 | **MultiKueue** | MultiKueueConfig / MultiKueueCluster |
| 作业跑太久要自动杀 | `maximumExecutionTimeSeconds` | Workload spec 或 Job label `kueue.x-k8s.io/max-exec-time-seconds` |
| Pod 一直起不来要重排 | **waitForPodsReady + requeuingStrategy** | Configuration |
| 节点故障自动换机器 | **TASFailedNodeReplacement** | feature gate（Beta 默认开） |
| 部分 Pod 完成后归还配额 | **ReclaimablePods** | `JobWithReclaimablePods` 接口，Beta 默认开 |

### 1.2 gang 语义的对比（重要）

这是 Kueue 与 Volcano 最本质的差别，值得单独说清：

| | Kueue | Volcano |
|--|-------|---------|
| 实现方式 | Workload 是**一个不可分割的申请单**，`RepresentativeMode` 取最小值 | `Statement` 事务：累积 Allocate，`JobReady` 才 Commit，否则 Discard |
| 「装不下」时的状态 | Pod **一个都没创建**（Job 还 suspend） | Pod **已经创建并 Pending**，只是不 Bind |
| apiserver 压力 | 极低（pending 作业只有 1 个 Workload 对象） | 较高（pending 作业有 N 个 Pending Pod） |
| 与 kube-scheduler 的关系 | 放行后 Pod 由 kube-scheduler 独立调度，**Kueue 不保证它们真的都能落位** | Volcano 自己决定落位，保证一致 |

**Kueue gang 的一个隐含风险**：Kueue 确认「配额够 8 个 Pod」并放行后，kube-scheduler 可能因为**碎片**（每台机器剩 3 卡，凑不出 8 卡的整机需求）而调度失败。这时 Pod 会 Pending，靠 `waitForPodsReady` 超时驱逐兜底。

**解法有三条**：

1. **开 TAS**：让 Kueue 在准入时就按真实节点容量算拓扑分配，注入 nodeSelector，从根上避免碎片问题（**推荐**）；
2. **Kueue + Volcano 叠加**：Pod 的 `schedulerName: volcano`，让 Volcano 做节点级 gang；
3. 靠 `waitForPodsReady.timeout` 兜底重排（会浪费一轮）。

> 结论：**在 GPU 集群里用 Kueue，TAS 几乎是必开项**，不只是为了通信性能，更是为了准入准确性。

管理员侧（沿用系列统一示例）：

# ① 拓扑定义

kind: Topology
metadata: {name: gpu-topology}
spec:
  levels:
  - nodeLabel: cloud.provider.com/topology-block
  - nodeLabel: cloud.provider.com/topology-rack
  - nodeLabel: kubernetes.io/hostname
---
# ② flavor：包年机器（启用 TAS）
apiVersion: kueue.x-k8s.io/v1beta2
kind: ResourceFlavor
metadata: {name: a100-ondemand}
spec:
  nodeLabels: {instance-type: on-demand}
  topologyName: gpu-topology
---
# ③ flavor：竞价机器（有污点，flavor 自带 toleration）
apiVersion: kueue.x-k8s.io/v1beta2
kind: ResourceFlavor
metadata: {name: a100-spot}
spec:
  nodeLabels: {instance-type: spot}
  topologyName: gpu-topology
  nodeTaints:
  - key: cloud.provider.com/spot
    value: "true"
    effect: NoSchedule
  tolerations:
  - key: cloud.provider.com/spot
    operator: Equal
    value: "true"
    effect: NoSchedule
---
# ④ Cohort：两个团队共享
apiVersion: kueue.x-k8s.io/v1beta2
kind: Cohort
metadata: {name: llm-pool}
---
# ⑤ 团队 A 的队列
apiVersion: kueue.x-k8s.io/v1beta2
kind: ClusterQueue
metadata: {name: team-a}
spec:
  namespaceSelector: {}                 # ★ 必须显式写，默认 null = 全部拒绝
  cohortName: llm-pool
  queueingStrategy: BestEffortFIFO
  resourceGroups:
  - coveredResources: ["cpu", "memory", "nvidia.com/gpu"]
    flavors:
    - name: a100-ondemand               # ★ 顺序即优先级
      resources:
      - {name: cpu,             nominalQuota: 320}
      - {name: memory,          nominalQuota: 2560Gi}
      - {name: nvidia.com/gpu,  nominalQuota: 20, borrowingLimit: 12, lendingLimit: 8}
    - name: a100-spot
      resources:
      - {name: cpu,             nominalQuota: 192}
      - {name: memory,          nominalQuota: 1536Gi}
      - {name: nvidia.com/gpu,  nominalQuota: 12, borrowingLimit: 12}
  flavorFungibility:
    whenCanBorrow: MayStopSearch
    whenCanPreempt: TryNextFlavor
  preemption:
    reclaimWithinCohort: LowerPriority  # 要回被别人借走的 nominal 配额
    withinClusterQueue: LowerPriority   # 队列内高优可抢低优
---
apiVersion: kueue.x-k8s.io/v1beta2
kind: LocalQueue
metadata: {namespace: team-a, name: default}
spec: {clusterQueue: team-a}

### 1.4 WorkloadPriorityClass vs PriorityClass

Kueue 有**两套优先级**，`priorityClassRef.group` 区分：

| | `scheduling.k8s.io/PriorityClass` | `kueue.x-k8s.io/WorkloadPriorityClass` |
|--|----------------------------------|---------------------------------------|
| 作用域 | 既影响 Kueue 排队/抢占，**也影响 kube-scheduler 的 Pod 抢占** | **只影响 Kueue** |
| 指定方式 | Pod template 的 `priorityClassName` | Job label `kueue.x-k8s.io/priority-class` |
| 可变性 | 有配额预留后不可变 | **label 始终可变**（源码注释：*"always mutable because it might be useful for the preemption"*） |
| 建议 | 生产 Pod 保护 | **作业排队优先级，首选** |

> 用 `WorkloadPriorityClass` 的好处：它把「作业在队列里的优先级」和「Pod 在节点上的抢占优先级」解耦。一个低优训练作业可以在 Kueue 队列里排后面，但一旦跑起来它的 Pod 就和别人一样，不会被 kubelet 优先驱逐。

## 2. 推理侧

### 2.1 需求 → 能力 → 配置

| 推理场景需求 | Kueue 能力 | 配置 |
|------------|-----------|------|
| 用 Deployment / LWS 部署也要走配额 | **Deployment / StatefulSet / LeaderWorkerSet 集成** | label `kueue.x-k8s.io/queue-name` |
| 多机 TP：一个副本的 N 个 Pod 全起或不起 | **LeaderWorkerSet → 1 个 Workload** | LWS 天然映射 |
| 一个副本的 4 个 rank 同机 | **PodSet slice** | `podset-slice-required-topology: kubernetes.io/hostname` + `slice-size: "4"` |
| PD 分离：prefill / decode 池分开 | **两个 flavor 或两个 CQ** | flavor `nodeLabels` 区分 |
| 在线服务必须有保底资源 | **lendingLimit** | `nominalQuota − lendingLimit` = 不可被借走的保底 |
| 在线优先，可抢离线 | **priority + reclaimWithinCohort** | 推理 CQ 高优 + 训练 CQ 允许被 reclaim |
| 副本扩缩容不重建整个服务 | **Elastic Jobs（workload slice）** | `ElasticJobsViaWorkloadSlices` |
| RayService 部署的推理 | **RayService 集成** | 内置 |

### 2.2 长服务与批作业的差异

`Deployment` / `StatefulSet` 没有 `suspend` 字段，Kueue 的处理方式不同：

```text
批作业（Job/JobSet/RayJob）：
    改 spec.suspend  →  Job controller 决定是否创建 Pod

长服务（Deployment/StatefulSet/LWS）：
    webhook 给 Pod 加 scheduling gate  →  准入后摘掉 gate
    （Pod 对象已创建但不可调度，等 Kueue 放行）
```

带来两个实践差异：

1. **长服务的 Pod 会以「gated」状态存在**，`kubectl get pod` 能看到但 `STATUS` 是 `SchedulingGated`；
2. **缩容到 0 有专门处理**：`WorkloadOnHold` 这个 `QuotaReserved=False` 的 reason，注释明确说 *"currently used by StatefulSet scale-to-zero"* —— 配额被主动释放且**不重新排队**。

### 2.3 vLLM 多机 TP 的推荐做法

```yaml
apiVersion: leaderworkerset.x-k8s.io/v1
kind: LeaderWorkerSet
metadata:
  name: vllm-tp4
  labels:
    kueue.x-k8s.io/queue-name: default
    kueue.x-k8s.io/priority-class: high-serve
spec:
  replicas: 2                     # 2 个副本
  leaderWorkerTemplate:
    size: 4                       # ★ 每副本 4 个 Pod（TP=4）
    leaderTemplate:
      metadata:
        annotations:
          # ★ 每个 slice（= 一个副本的 4 个 Pod）必须同机
          kueue.x-k8s.io/podset-slice-required-topology: kubernetes.io/hostname
          kueue.x-k8s.io/podset-slice-size: "4"
      spec:
        containers:
        - name: vllm-leader
          image: vllm/vllm-openai:latest
          resources: {limits: {nvidia.com/gpu: 1}}
    workerTemplate:
      metadata:
        annotations:
          kueue.x-k8s.io/podset-slice-required-topology: kubernetes.io/hostname
          kueue.x-k8s.io/podset-slice-size: "4"
      spec:
        containers:
        - name: vllm-worker
          image: vllm/vllm-openai:latest
          resources: {limits: {nvidia.com/gpu: 1}}
```

> LWS 会自己创建 PodGroup 语义，Kueue 把 leader + workers 映射成一个 Workload 的多个 PodSet；`slice` 注解保证每个副本的 4 卡不跨机。这套组合是目前 Kubernetes 上部署多机 TP 推理最干净的方案。

## 3. 训推混部：Kueue 在 MaaS 平台的核心价值

目标：**一个 GPU 池，训练与推理共享，闲时互借，忙时抢回，推理有保底**。

```yaml
# 推理队列：有保底、高优、不许被抢
apiVersion: kueue.x-k8s.io/v1beta2
kind: ClusterQueue
metadata: {name: serve}
spec:
  namespaceSelector: {}
  cohortName: llm-pool
  queueingStrategy: BestEffortFIFO
  resourceGroups:
  - coveredResources: ["cpu", "memory", "nvidia.com/gpu"]
    flavors:
    - name: a100-ondemand
      resources:
      - name: nvidia.com/gpu
        nominalQuota: 24
        lendingLimit: 8          # ★ 只借出 8，保底 16 卡永远属于推理
        borrowingLimit: 40       # 闲时可以借到 64 卡
  preemption:
    reclaimWithinCohort: Any     # ★ 不看优先级，要回自己的 nominal 配额
    withinClusterQueue: Never    # 推理副本之间不互相抢
---
# 训练队列：可被回收、低优
apiVersion: kueue.x-k8s.io/v1beta2
kind: ClusterQueue
metadata: {name: train}
spec:
  namespaceSelector: {}
  cohortName: llm-pool
  queueingStrategy: BestEffortFIFO
  resourceGroups:
  - coveredResources: ["cpu", "memory", "nvidia.com/gpu"]
    flavors:
    - name: a100-ondemand
      resources:
      - name: nvidia.com/gpu
        nominalQuota: 40
        # lendingLimit 不设 = 全部可外借
        borrowingLimit: 24
  preemption:
    reclaimWithinCohort: LowerPriority
    withinClusterQueue: LowerPriority
```

配套优先级：

```yaml
apiVersion: kueue.x-k8s.io/v1beta2
kind: WorkloadPriorityClass
metadata: {name: high-serve}
value: 100000
description: "online inference"
---
apiVersion: kueue.x-k8s.io/v1beta2
kind: WorkloadPriorityClass
metadata: {name: low-train}
value: 100
description: "offline training"
```

**回收链路**（对应 02 篇 §6）：

```text
serve 提交新副本，nominal 配额被 train 借走了
  → flavorassigner：mode = Preempt（配额上可行）
  → classicalPreemptions：serve 对这份配额有"层级优势"（是它的 nominalQuota）
    ⇒ Hierarchy candidate，不看优先级也能抢
  → CandidatesOrdering：先抢 train（不在 serve 队列里）→ 优先级低的 → 后拿到配额的
  → issuePreemptions：驱逐 train 的 Workload（Evicted reason=Preempted,
     Preempted reason=InCohortReclamation）
  → 本轮结束；下一轮 serve 被 admit
  → train 的 Workload 走退避重排队
```

**训练侧要做的准备**：

```yaml
# Configuration：让被抢的训练作业能优雅重排
waitForPodsReady:
  enable: true
  timeout: 15m                 # 大镜像 + 模型加载要留足
  blockAdmission: true
  requeuingStrategy:
    timestamp: Eviction        # 被抢后按驱逐时间重排（更公平）
    backoffLimitCount: 10      # 允许被抢 10 次
    backoffBaseSeconds: 120
    backoffMaxSeconds: 1800
```

> 训练作业最好自己做 checkpoint —— Kueue 的抢占是「直接驱逐 Pod」，没有 Volcano `cdp`（冷却保护）那样的插件，只有退避机制。

## 4. 与 Volcano 的组合方案

三种典型部署形态：

### 4.1 只用 Kueue

```text
适用：配额管理 + 作业排队是主要诉求，节点级碎片不严重
必开：TopologyAwareScheduling（保证准入准确性）
风险：整机型作业可能因碎片在 kube-scheduler 阶段失败
```

### 4.2 只用 Volcano

```text
适用：需要 GPU 共享（vGPU）、NUMA 亲和、自定义打分插件
缺失：多集群、ResourceFlavor 级的异构 fallback、AdmissionCheck 外部集成
```

### 4.3 Kueue + Volcano 叠加（推荐用于大型平台）

```yaml
# Kueue 管准入配额，Volcano 管节点级调度
apiVersion: batch/v1
kind: Job
metadata:
  labels:
    kueue.x-k8s.io/queue-name: default     # Kueue 准入
spec:
  template:
    spec:
      schedulerName: volcano               # Volcano 调度
      # Volcano 侧的 PodGroup 由 podgroup controller 自动创建
```

职责划分：

| 层 | 组件 | 负责 |
|----|------|------|
| 作业准入 | Kueue | 配额、排队、跨队列借用与回收、多集群派发、等扩容 |
| 节点调度 | Volcano | gang 落位、GPU 共享、NUMA、binpack、拓扑亲和 |

注意事项：

1. **两边的 gang 语义会叠加**：Kueue 放行后 Volcano 还会做一次 `JobReady` 判定，装不下就全不 Bind。这实际上补上了 §1.2 提到的碎片风险。
2. **抢占要选一边做**：两边都开抢占会互相打断。建议 Kueue 做跨队列配额回收，Volcano 关掉 `preempt`/`reclaim` action。
3. **TAS 与 HyperNode 不要同时开**：两者都会往 Pod 上写落位约束，会冲突。选一个（用 Volcano 时用 HyperNode，只用 Kueue 时用 TAS）。

> **`TopologyAwareScheduling` 与 `MultiKueue` 在近几个版本已默认开启**，这与很多老资料不一致，配置前先确认版本。

## 6. 坑与取舍清单

| 项 | 说明 |
|----|------|
| **`namespaceSelector` 默认 `null` = 全拒绝** | 必须显式 `{}` 或写 selector，否则作业永远 `Misconfigured` |
| **`borrowingLimit` 与空 cohort 冲突** | `cohortName` 为空时 `borrowingLimit` 必须为 null（CEL 校验） |
| **`podSets` 不可变** | 改并行度要靠 workload slice；直接改 Job 的 `parallelism` 会导致 Workload 与 Job 不同步（`Finished` reason=`OutOfSync`） |
| **一轮只取每个 CQ 队头** | `StrictFIFO` 下大作业会阻塞整个队列。混合负载建议 `BestEffortFIFO` + 抢占防饥饿 |
| **抢占跨两轮** | 本轮驱逐、下轮准入。看到 `Pending the preemption of N workload(s)` 是正常的 |
| **`ExceedsMaxQuota` 等不会好** | 这是配额天花板问题，必须改 `nominalQuota`/`borrowingLimit`；`WaitingForQuota` 才是等就行 |
| **Kueue 不管碎片** | 放行后 Pod 可能因节点碎片调度失败。开 TAS 或叠 Volcano |
| **`manageJobsWithoutQueueName: true` 很危险** | 会挂起所有 Job（包括系统组件），必须配 `managedJobsNamespaceSelector` 白名单 |
| **`blockAdmission: true` 降吞吐** | 一个作业 Pod 起不来会阻塞全部准入。好处是保护大作业，坏处是小作业受连累 |
| **Fair Sharing 与 `borrowWithinCohort` 互斥** | 后者只支持经典抢占 |
| **一个 CQ 只能有一个 MultiKueue AdmissionCheck** | 且不能与 ProvisioningRequest 同时用（`MultiKueueWithProvisioningRequest` 会让 CQ `Active=False`） |
| **`WorkloadPriorityClass` 的 label 可变** | 可以给排太久的作业临时提优先级，但要注意这会改变抢占关系 |
| **cohort 成环会静默停止准入** | `Snapshot()` 里 `hasCycle` 直接跳过整棵子树，日志里才有痕迹 |
| **`Workload` 对象会累积** | Elastic Jobs 每次伸缩产生新 slice，注意 GC 与 etcd 容量 |

## 7. 与相邻方案的关系

| 方案 | 定位 | 与 Kueue 的关系 |
|------|------|----------------|
| **Volcano** | Pod 级批调度器 | 互补，可叠加（见 §4.3） |
| **YuniKorn** | 批调度器（YARN 风格队列） | 同时具备准入与调度，属于「另一种整体方案」 |
| **kube-scheduler + coscheduling** | 原生框架里的基础 gang | 只有 gang，无配额/借用/异构 |
| **Kubeflow Trainer / training-operator** | 作业编排与框架适配 | 互补：`TrainJob` / `PyTorchJob` 是 Kueue 的一等集成 |
| **KubeRay** | Ray 集群编排 | 互补：`RayJob` / `RayCluster` / `RayService` 均内置集成 |
| **JobSet** | 多 Job 组合的 workload API | 互补，且是 Kueue 官方推荐的多角色训练载体 |
| **LeaderWorkerSet** | 多机推理副本 API | 互补，多机 TP 推理首选 |
| **cluster-autoscaler / Karpenter** | 节点扩容 | 通过 `ProvisioningRequest` AdmissionCheck 集成 |
| **DRA（Dynamic Resource Allocation）** | K8s 原生设备管理 | `pkg/dra` 已 Beta 集成，可对 DeviceClass 做配额 |

> 一句话选型：**「多租户共享 GPU 池 + 作业需要排队 + 有异构机型 / 多集群」→ Kueue。若还需要节点级 GPU 切分与精细打分，再叠一层 Volcano。**
