# 面向大模型训练与推理的能力地图

> 前三篇讲「Volcano 怎么工作」，本篇讲「**大模型场景该用它的哪些能力**」。按训练、推理、训推混部三条线组织，每条线给出需求 → 能力 → 配置的映射。
>
> 源码基线：**v1.15.1**

---

## 1. 训练侧

### 1.1 需求到能力的映射

| 训练场景的真实需求 | Volcano 能力 | 配置位置 |
|------------------|-------------|---------|
| N 个 Pod 必须同时起（建 NCCL 通信域） | **Gang 调度** | `job.spec.minAvailable` → `PodGroup.minMember`；`gang` 插件 |
| 资源不够时不要创建 Pod，别刷 apiserver | **Inqueue 两级准入** | `PodGroup.minResources` + `enqueue` action |
| 每个角色各自的最小数（1 master + 7 worker） | **task 级 minAvailable** | `job.spec.tasks[*].minAvailable` → `minTaskMember` |
| 8 机 64 卡要在同一个交换机下 | **网络拓扑感知调度** | `job.spec.networkTopology` + `HyperNode` CRD + `network-topology-aware` 插件 |
| TP=4 的每组 4 卡要同机，组间可跨机 | **子组亲和（partitionPolicy / subGroupPolicy）** | `tasks[*].partitionPolicy` → `PodGroup.subGroupPolicy` |
| CPU/内存/网卡与 GPU 同 NUMA | **NUMA 感知** | `tasks[*].topologyPolicy` 或 `volcano.sh/numa-topology-policy` + `numaaware` 插件 |
| 自动注入 `MASTER_ADDR` / `RANK` / `WORLD_SIZE` | **Job 框架插件** | `job.spec.plugins.pytorch` |
| 节点间免密 SSH（MPI / DeepSpeed launcher） | **ssh 插件** | `job.spec.plugins.ssh` |
| Pod 挂了要重启整个作业（AllReduce 语义） | **生命周期策略** | `job.spec.policies` / `tasks[*].policies` |
| 弹性训练：能起多少先起多少 | **minAvailable < replicas** | 加上 `allocate` 里的「作业放回队列继续分配」 |
| 多阶段流水（预处理 → 训练 → 评估） | **JobFlow / JobTemplate** | `flow.volcano.sh` CRD |
| 部门/团队配额，闲时互借 | **Queue deserved + capability** | `capacity` 插件 |
| 高优作业插队 | **优先级 + 抢占** | `priorityClassName` + `priority` 插件 + `preempt` action |

### 1.2 Job 框架插件都注入了什么

`pkg/controllers/job/plugins/factory.go`：

```go
RegisterPluginBuilder("ssh", ssh.New)                 // 生成 SSH 密钥对 Secret，挂到所有 Pod，配好 authorized_keys
RegisterPluginBuilder("env", env.New)                 // 注入 VK_TASK_INDEX / VC_TASK_INDEX 等索引变量
RegisterPluginBuilder("svc", svc.New)                 // 建 headless Service + ConfigMap（host 列表），让 Pod 能互相 DNS 解析
RegisterPluginBuilder("tensorflow", tensorflow.New)   // 注入 TF_CONFIG
RegisterPluginBuilder("mpi", mpi.New)                 // MPI hostfile / mpirun 相关
RegisterPluginBuilder("pytorch", pytorch.New)         // 注入 MASTER_ADDR/MASTER_PORT/WORLD_SIZE/RANK
RegisterPluginBuilder("hcclrank", hcclrank.New)       // 昇腾 HCCL rank table
RegisterPluginBuilder("ray", ray.New)                 // Ray head/worker
```

以 `pytorch` 为例（`distributed-framework/pytorch/pytorch.go`）：

```go
const (
    EnvMasterPort = "MASTER_PORT"
    EnvMasterAddr = "MASTER_ADDR"
    EnvWorldSize  = "WORLD_SIZE"
    EnvRank       = "RANK"
)

func (pp *pytorchPlugin) OnPodCreate(pod *v1.Pod, job *batch.Job) error {
    masterAddr := pp.generateMasterAddr(job.Spec.Tasks[masterIndex], job.Name)
    // master rank = 0；worker rank = podIndex + 1
    if taskType == pp.workerName {
        workerRank = index + 1
        pp.addWaitForMasterInitContainer(pod, masterAddr)   // 可选：initContainer 等 master 端口就绪
    }
    totalReplicas := pp.getTotalReplicas(job)               // WORLD_SIZE = master + worker replicas
    for i := range pod.Spec.Containers {
        pp.openContainerPort(&c, i, pod)
        pod.Spec.Containers[i].Env = append(..., MASTER_ADDR, MASTER_PORT, WORLD_SIZE, RANK)
    }
}
```

参数：`--master`、`--worker`、`--port`、`--wait-master-enabled`、`--wait-master-timeout`、`--wait-master-image`。

> 这解决了一个很实际的问题：**不引入 Kubeflow training-operator，也能跑分布式 PyTorch**。`plugins: {pytorch: [...], svc: []}` 两行就够了。当然，如果已经在用 Kubeflow / Ray / KubeRay，也可以只把 Volcano 当调度器（设置 `schedulerName: volcano` + 让 operator 建 PodGroup 或让 `podgroup controller` 自动建）。

### 1.3 拓扑约束的三层粒度

```yaml
# ① Job 级：整个作业不许跨 tier 2
spec:
  networkTopology:
    mode: hard
    highestTierAllowed: 2

# ② Task 级分组：worker 每 4 个一组同机，至少 2 组资源满足才调度
  tasks:
  - name: worker
    replicas: 16
    partitionPolicy:
      totalPartitions: 4
      partitionSize: 4
      minPartitions: 2
      networkTopology:
        mode: hard
        highestTierName: node
```

`partitionPolicy` 会被 job controller 翻译成 `PodGroup.spec.subGroupPolicy`（`subGroupSize` / `minSubGroups` / `networkTopology`），最终由 `allocate` 的 `allocateForSubJob` + `network-topology-aware` 的 `HyperNodeGradientForSubJobFn` 落地。

`mode` 语义（`NetworkTopologySpec`）：

- `hard`：**硬约束**，超过 `highestTierAllowed` / `highestTierName` 的方案不生成，宁可 Pending。适合对通信极敏感的预训练。
- `soft`：**软约束**，先试低 tier，装不下逐级放宽。适合微调、推理等。

### 1.4 弹性与容错

```yaml
spec:
  minAvailable: 4          # replicas=8 时：先起 4 个就算 Ready
  maxRetry: 5
  ttlSecondsAfterFinished: 3600
  policies:
  - event: PodFailed
    action: RestartJob     # AllReduce 训练：一个挂了整体重启
  - event: PodEvicted
    action: RestartJob
  tasks:
  - name: worker
    replicas: 8
    maxRetry: 3
    policies:
    - event: TaskCompleted
      action: CompleteJob
```

注意 `minAvailable` 的双刃剑：

- `minAvailable == replicas`：刚性 gang，**跑起来就不会被抢**（`gang.PreemptableFn` 保护），适合大规模预训练；
- `minAvailable < replicas`：弹性，超出部分**可能被抢走**，适合支持动态 world size 的框架（torch elastic、DeepSpeed elastic）。

## 2. 推理侧

### 2.1 需求到能力的映射

| 推理场景需求 | Volcano 能力 | 配置 |
|------------|-------------|------|
| 用 Deployment / LWS 部署，也想要队列配额 | **podgroup controller 自动建 PodGroup** | Pod template 上 `schedulerName: volcano` + `scheduling.volcano.sh/queue-name` |
| 多机 TP：一个副本的 N 个 Pod 要么全起要么不起 | **Gang（自建 PodGroup 或 group-min-member 注解）** | `scheduling.volcano.sh/group-min-member` |
| 一个副本的 4 个 rank 要同机/同 rack | **subGroupPolicy + 网络拓扑** | 自建 PodGroup 写 `subGroupPolicy` |
| PD 分离：prefill 池与 decode 池分开 | **多队列 + nodegroup 亲和** | 两个 Queue + `volcano.sh/nodegroup-name` label |
| 小模型/调试共享一张卡 | **deviceshare vGPU** | `volcano.sh/vgpu-number` + `vgpu-memory` + `vgpu-cores` |
| 在线服务必须有保底资源 | **Queue guarantee** | `queue.spec.guarantee.resource` |
| 在线优先，可抢离线 | **priority + preempt / reclaim** | 高 `priorityClassName` + 离线 Pod 打 `volcano.sh/preemptable: "true"` |
| 刚扩容的副本不要被立刻抢走 | **cdp 冷却保护** | `volcano.sh/cooldown-time: 600s` + `cdp` 插件 |
| 驱逐时尊重可用性下限 | **pdb 插件** | PodDisruptionBudget + `pdb` 插件 |
| 卡型隔离（A100 给推理，V100 给训练） | **nodegroup 插件 + Queue affinity** | Node label + `queue.spec.affinity` |

### 2.2 推理服务接入 Volcano 的三种姿势

**姿势一：普通 Deployment（单卡/单 Pod 副本）**

```yaml
template:
  metadata:
    annotations:
      scheduling.volcano.sh/queue-name: serve
  spec:
    schedulerName: volcano
```

`podgroup controller` 按 ownerReference 为这一组 Pod 生成 PodGroup（`helpers.GeneratePodgroupName`），并回写 `scheduling.k8s.io/group-name` 注解。默认 `minMember` 由控制器推导，可用 `scheduling.volcano.sh/group-min-member` 显式指定。

**姿势二：LeaderWorkerSet / 自建 PodGroup（多机 TP、PD 分离）**

LWS 这类 workload 自己会建 PodGroup，`pg_controller_handler.go` 显式跳过：

```go
// If the pod is already associated with a podgroup, skip creating a new one. This scenario is applicable to
// LeaderWorkerSet, which will create podgroups by itself, and Volcano does not need to create a podgroup.
if pgName := pod.Annotations[scheduling.KubeGroupNameAnnotationKey]; pgName != "" { return }
```

自建 PodGroup 的好处是可以写全 `minMember` / `minResources` / `networkTopology` / `subGroupPolicy`，把「每副本 TP 组同机」表达清楚。

**姿势三：vcjob（离线批量推理 / 评测）**

批量打分、离线蒸馏数据生成这类「跑完就退出」的任务，直接用 vcjob + `minSuccess`。

### 2.3 GPU 共享的落地要点

```yaml
resources:
  limits:
    volcano.sh/vgpu-number: 1       # 用 1 张（虚拟）卡
    volcano.sh/vgpu-memory: 8000    # 限制 8000 MB 显存
    volcano.sh/vgpu-cores: 30       # 限制 30% 算力
```

配套：

```yaml
- name: deviceshare
  arguments:
    deviceshare.VGPUEnable: true
    deviceshare.NodeLockEnable: true      # 高频扩缩容时开启，避免并发分配同一张卡
    deviceshare.SchedulePolicy: binpack   # 提高单卡利用率；延迟敏感场景改 spread
```

三条硬性约束（来自 `enablePredicate` 的 `klog.Fatal`）：

- `GPUSharingEnable` 与 `GPUNumberEnable` **不能同时开**；
- `gpu-share`（`volcano.sh/gpu-memory` / `gpu-number`）与 `vgpu` **不能同时开**；
- 必须部署对应 device plugin，且资源写在 `limits` 里。

## 3. 训推混部：Volcano 在 MaaS 平台里的核心价值

目标：**一个 GPU 池，训练与推理共享，闲时互借，忙时抢回，推理有保底**。

```yaml
# 推理队列：有保底，优先级高，不可被回收
apiVersion: scheduling.volcano.sh/v1beta1
kind: Queue
metadata: {name: serve}
spec:
  reclaimable: false          # ★ 借出去的不算，自己的不许被抢
  priority: 100
  deserved:   {nvidia.com/gpu: "24"}
  guarantee:
    resource: {nvidia.com/gpu: "16"}   # ★ 16 卡永远为推理预留
  capability:  {nvidia.com/gpu: "64"}
---
# 训练队列：可被回收，优先级低
kind: Queue
metadata: {name: train}
spec:
  reclaimable: true           # ★ 超出 deserved 的部分可被抢回
  priority: 10
  deserved:   {nvidia.com/gpu: "40"}
  capability: {nvidia.com/gpu: "64"}
```

调度器配置：

```yaml
actions: "enqueue, allocate, preempt, reclaim, backfill"
tiers:
- plugins:
  - name: priority
  - name: gang
    enablePreemptable: false
  - name: conformance
  - name: cdp                       # 保护新起的推理副本
- plugins:
  - name: overcommit
  - name: predicates
  - name: capacity
    enableHierarchy: false
  - name: nodeorder
  - name: binpack
    arguments:
      binpack.weight: 10
      binpack.resources: nvidia.com/gpu
      binpack.resources.nvidia.com/gpu: 5
  - name: network-topology-aware
    arguments:
      weight: 20
```

训练 Pod 上必须标记可被抢占，否则 `reclaim` 找不到受害者：

```yaml
metadata:
  annotations:
    volcano.sh/preemptable: "true"
    volcano.sh/cooldown-time: "300s"   # 起来 5 分钟内免抢，避免刚跑就被杀
```

回收链路（对应 02 篇）：

```text
serve 有作业饥饿(JobStarving)
  → capacity.PreemptiveFn：serve.allocated(0) < serve.deserved(24) ✅ 有资格
  → 找节点上 queue != serve 且 task.Preemptable 且 train.reclaimable=true 的 Running Pod
  → capacity.ReclaimableFn：只把 train 超出 deserved(40) 的部分列为 victim
  → gang.ReclaimableFn：不把 train 作业打到 minAvailable 以下
  → cdp：冷却期内的 Pod 排除
  → nodeStmt.Evict(victims) + Pipeline(推理 Pod)
  → JobPipelined ✅ → Commit（真正驱逐）；否则 Discard（一个都不杀）
```

## 4. 坑与取舍清单

| 项 | 说明 |
|----|------|
| **`minResources` 不填 = 没有入队门禁** | `enqueue` 里 `job.PodGroup.Spec.MinResources == nil` 直接放行。vcjob 由 webhook 推导，自建 PodGroup 必须手写 |
| **带 `networkTopology` 的作业暂不支持 preempt** | `preempt.Execute` 里显式跳过（源码注释指向 issue #4374）。需要「拓扑 + 抢占」请评估 `gangpreempt` |
| **`proportion` 与 hierarchy 版 `drf` 冲突** | `UnmarshalSchedulerConf` 直接返回 error，调度器起不来 |
| **`gpu-share` 与 `vgpu` 互斥** | 冲突时 `klog.Fatal` |
| **`shuffle` action 慎用** | 直接 `ssn.Evict`，不走 Statement，对训练是灾难性的 |
| **队列配额被静默夹逼** | `guarantee ≤ deserved ≤ realCapability ≤ capability`，配错不报错只是不生效 |
| **`Overused` 是 `continue` 不是 `break`** | 队列超用后本轮跳过，但下一轮还会尝试，不会永久饿死 |
| **插件实例每轮重建** | 别指望在插件里做跨轮缓存（deviceshare 的 `persistedGPUs` 是刻意的例外） |
| **`capability` 里 CPU/内存写 0 等于无限** | `attr.capability.MilliCPU <= 0` 会被置成 `math.MaxFloat64` |
| **弹性作业的超额 Pod 会被抢** | `minAvailable < replicas` 时要接受 world size 波动 |

## 5. 和相邻方案的关系

| 方案 | 定位 | 与 Volcano 的关系 |
|------|------|------------------|
| `kube-scheduler` + coscheduling 插件 | 在原生调度框架里补最基本的 gang | 只有 gang，没有队列配额/拓扑/GPU 共享/抢占体系 |
| Kueue | **准入控制器**：管作业排队与配额，把 Pod 交给某个调度器 | 定位互补。Kueue 管「什么时候允许作业进入集群」，Volcano 既管准入（`enqueue`）也管调度（`allocate`）。两者可组合，也可只用 Volcano |
| YuniKorn | 另一个批调度器，队列模型偏 YARN | 同类竞品 |
| Kubeflow training-operator / KubeRay | 管作业编排与框架适配 | 互补：operator 建 Pod，Volcano 负责调度（`schedulerName: volcano`） |
| HAMi | GPU 虚拟化与隔离 | Volcano 的 `deviceshare` vGPU 与其生态同源（`hami-core` / known geometries） |

> 一句话选型：**只要「作业是一组 Pod」+「多租户共享 GPU 池」这两个条件同时成立，Volcano 就是最直接的答案。**
