# 扩展实战：自定义调度插件开发

> 前面五篇讲「kube-scheduler 怎么工作」，本篇讲「**怎么在它上面加自己的逻辑**」。
>
> 每个扩展点给一个**可编译、有实际用途**的 demo（不是 `return nil` 的空壳），全部围绕大模型场景：GPU 碎片、镜像预热、租户配额、成组调度、拓扑亲和。
>
> 涉及源码：`staging/src/k8s.io/kube-scheduler/framework/interface.go`（接口定义）、`pkg/scheduler/framework/runtime/registry.go`（注册）、`cmd/kube-scheduler/app/server.go`（启动）
>
> 源码基线：**v1.36.3**

---

## 1. 先搞清楚三件事

### 1.1 v1.36 的包路径变了

**这是入门第一个坑**。老教程里的 `framework.FilterPlugin`、`framework.Status` 现在分家了：

| 内容 | v1.36 的位置 | import 别名惯例 |
|------|-------------|----------------|
| **扩展点接口、Status、CycleState、NodeInfo** | `k8s.io/kube-scheduler/framework`（staging，独立发布） | `fwk` |
| 框架运行时、Registry、PluginFactory | `k8s.io/kubernetes/pkg/scheduler/framework/runtime` | `runtime` |
| 内置插件的 helper | `k8s.io/kubernetes/pkg/scheduler/framework/plugins/helper` | `helper` |
| 启动命令、WithPlugin | `k8s.io/kubernetes/cmd/kube-scheduler/app` | `app` |

```go
import (
    fwk "k8s.io/kube-scheduler/framework"                        // ★ 接口都在这
    "k8s.io/kubernetes/pkg/scheduler/framework/runtime"
)
```

把接口挪到 staging 的好处：**写 out-of-tree 插件只需依赖 `k8s.io/kube-scheduler` 这个轻量模块**，不必 vendor 整个 `k8s.io/kubernetes`（后者的依赖地狱是老版本插件开发最大的痛点）。

### 1.2 两种扩展方式

| 方式 | 做法 | 适用 |
|------|------|------|
| **In-tree**（不推荐） | 改 `pkg/scheduler/framework/plugins/registry.go`，重新编译 k8s | 只有想给上游提 PR 时 |
| **Out-of-tree**（推荐） | 自己写 `main.go` 调 `app.NewSchedulerCommand(app.WithPlugin(...))` | ✅ 绝大多数场景 |

Out-of-tree 的本质是**复用官方的整个调度器主体，只把自己的插件注册进 Registry**：

```go
// cmd/kube-scheduler/app/server.go
type Option func(runtime.Registry) error

func NewSchedulerCommand(registryOptions ...Option) *cobra.Command { ... }

func WithPlugin(name string, factory runtime.PluginFactory) Option {
    return func(registry runtime.Registry) error {
        return registry.Register(name, factory)
    }
}
```

`PluginFactory` 的签名（`pkg/scheduler/framework/runtime/registry.go`）：

```go
type PluginFactory = func(ctx context.Context, configuration runtime.Object, f fwk.Handle) (fwk.Plugin, error)
```

三个参数分别是：上下文、**该插件的 `args` 配置**（来自 `KubeSchedulerConfiguration.pluginConfig`）、**Handle**（框架能力入口）。

### 1.3 Handle 给了你什么

`fwk.Handle` 是插件访问外部世界的唯一合法通道（`interface.go`）：

```go
SnapshotSharedLister() SharedLister              // ★ 读节点/Pod 快照（不要自己 List apiserver）
ClientSet() clientset.Interface                  // 需要写 API 时用（PreBind 里）
SharedInformerFactory() informers.SharedInformerFactory  // 监听自定义 CRD
EventRecorder() events.EventRecorderLogger       // 打 Event
Parallelizer() Parallelizer                      // 并行工具（别自己起 goroutine）
IterateOverWaitingPods(callback func(WaitingPod)) // ★ Permit 型 gang 的核心
GetWaitingPod(uid types.UID) WaitingPod
RejectWaitingPod(uid types.UID) bool
RunFilterPluginsWithNominatedPods(...) *Status    // 写自定义抢占时用
SharedDRAManager() SharedDRAManager              // DRA 设备信息
```

**铁律：不要在插件里直接调 `ClientSet().List()`。** 调度周期是串行的，一次 API 往返就拖慢整个集群的调度吞吐。要读集群状态就用 `SnapshotSharedLister()`（内存快照），要读自定义资源就用 informer 的 Lister（本地缓存）。

## 2. 骨架：一个插件实现多个扩展点

所有 demo 都基于这个骨架。**一个 struct 可以同时实现多个扩展点接口**，`MultiPoint` 会自动把它注册到全部对应位置。

```go
package gpufrag

import (
    "context"

    v1 "k8s.io/api/core/v1"
    "k8s.io/apimachinery/pkg/runtime"
    fwk "k8s.io/kube-scheduler/framework"
)

const Name = "GPUFragmentation"

// 编译期断言：明确声明本插件实现了哪些扩展点。
// ★ 强烈建议加，否则接口签名写错时只会「插件静默不生效」，极难排查。
var (
    _ fwk.PreFilterPlugin = &Plugin{}
    _ fwk.FilterPlugin    = &Plugin{}
    _ fwk.ScorePlugin     = &Plugin{}
)

type Plugin struct {
    handle fwk.Handle
    args   *Args
}

func (p *Plugin) Name() string { return Name }

func New(_ context.Context, obj runtime.Object, h fwk.Handle) (fwk.Plugin, error) {
    args, err := parseArgs(obj)      // 见 §11
    if err != nil {
        return nil, err
    }
    return &Plugin{handle: h, args: args}, nil
}
```

入口 `main.go`：

```go
package main

import (
    "os"

    "k8s.io/component-base/cli"
    "k8s.io/kubernetes/cmd/kube-scheduler/app"

    "example.com/sched-plugins/pkg/gpufrag"
)

func main() {
    command := app.NewSchedulerCommand(
        app.WithPlugin(gpufrag.Name, gpufrag.New),
        app.WithPlugin(tenantquota.Name, tenantquota.New),
        // ... 想注册多少个都行
    )
    code := cli.Run(command)
    os.Exit(code)
}
```

启用（`--config` 指向的 `KubeSchedulerConfiguration`）：

```yaml
apiVersion: kubescheduler.config.k8s.io/v1
kind: KubeSchedulerConfiguration
profiles:
- schedulerName: gpu-scheduler
  plugins:
    multiPoint:
      enabled:
      - name: GPUFragmentation      # 一行注册到它实现的全部扩展点
        weight: 5                   # 只对 Score 生效
```

## 3. PreEnqueue：入队门禁

**签名**：

```go
PreEnqueue(ctx context.Context, p *v1.Pod) *Status
```

**语义**：Pod 进 activeQ / backoffQ **之前**调用。返回非 Success 则 Pod 停在 `unschedulablePods`，**连调度周期都不进**。

**Demo：模型权重未就绪的推理 Pod 不进队列**

推理服务启动前要等模型从对象存储同步到本地 PVC。让这类 Pod 进调度队列纯属浪费 —— 它就算被调度到节点上也只会 CrashLoop。

```go
const (
    Name = "ModelReadyGate"
    // Pod 声明依赖的模型
    modelAnnotation = "ai.example.com/model"
)

var (
    _ fwk.PreEnqueuePlugin  = &Plugin{}
    _ fwk.EnqueueExtensions = &Plugin{}   // ★ 必须配套实现，见 §4
)

func (p *Plugin) PreEnqueue(ctx context.Context, pod *v1.Pod) *fwk.Status {
    model := pod.Annotations[modelAnnotation]
    if model == "" {
        return nil                         // 不关我事，放行
    }

    // 从 informer 本地缓存读自定义 CRD，不走 apiserver
    m, err := p.modelLister.Models(pod.Namespace).Get(model)
    if err != nil {
        return fwk.NewStatus(fwk.UnschedulableAndUnresolvable,
            "model "+model+" not found")
    }
    if m.Status.Phase != "Ready" {
        return fwk.NewStatus(fwk.Unschedulable,
            "model "+model+" is still syncing (phase="+m.Status.Phase+")")
    }
    return nil
}
```

**三个要点**：

1. **必须轻量**。源码注释明确写了：*"it's not expected to involve expensive calls like accessing external endpoints; otherwise it'd block other Pods' enqueuing in event handlers"* —— 它跑在 event handler 里，慢一下会堵住所有 Pod 的入队。
2. **必须配套实现 `EnqueueExtensions`**，否则 Pod 可能永远卡在 `unschedulablePods` 里。
3. 与 `SchedulingGates` 的区别：`schedulingGates` 是 **Pod spec 字段**，由外部控制器摘除（Kueue 就用这个）；`PreEnqueue` 是**调度器内的逻辑判断**，不需要改 Pod。

## 4. EnqueueExtensions：告诉框架「什么事件能救我」

**签名**：

```go
EventsToRegister(context.Context) ([]ClusterEventWithHint, error)
```

**语义**：这不是一个「会被调用来做决策」的扩展点，而是**注册期的声明**。它决定「被我拒绝的 Pod，在什么集群事件发生后值得重试」。

**这是最容易被忽略、但对性能影响最大的扩展点。** 源码注释说得很直白：

> Plugins that make pod unschedulable (PreEnqueue, PreFilter, Filter, Reserve, and Permit plugins) **must** implement this interface, otherwise the default implementation will be used, which is less efficient in requeueing Pods rejected by the plugin.
>
> Also, if EventsToRegister returns an empty list, that means the Pods failed by the plugin are not requeued by any events, which doesn't make sense in most cases (**very likely misuse**) since the pods rejected by the plugin could be stuck in the unschedulable pod pool forever.

**Demo：只在相关事件发生时才重试**

```go
func (p *Plugin) EventsToRegister(_ context.Context) ([]fwk.ClusterEventWithHint, error) {
    return []fwk.ClusterEventWithHint{
        // ① 自定义 CRD 变化 —— 只有变成 Ready 才值得重试
        {
            Event: fwk.ClusterEvent{
                Resource:   "models.ai.example.com",
                ActionType: fwk.Add | fwk.Update,
            },
            QueueingHintFn: p.isModelReady,
        },
        // ② 节点资源变化 —— GPU 相关插件才关心
        {
            Event: fwk.ClusterEvent{
                Resource:   fwk.Node,
                ActionType: fwk.Add | fwk.UpdateNodeAllocatable,
            },
            QueueingHintFn: p.hasGPUCapacity,
        },
        // ③ 别的 Pod 被删 —— 腾出了资源
        {
            Event: fwk.ClusterEvent{
                Resource:   fwk.Pod,
                ActionType: fwk.Delete,
            },
            QueueingHintFn: p.deletedPodUsedGPU,
        },
    }, nil
}
```

`QueueingHintFn` 的签名与取值（`framework/types.go`）：

```go
type QueueingHintFn func(logger klog.Logger, pod *v1.Pod, oldObj, newObj interface{}) (QueueingHint, error)

const (
    QueueSkip QueueingHint = iota   // 这个事件跟我无关，别唤醒
    Queue                           // 可能有救，唤醒重试
)
```

具体实现：

```go
// 只有「模型从非 Ready 变成 Ready」才唤醒
func (p *Plugin) isModelReady(logger klog.Logger, pod *v1.Pod, oldObj, newObj interface{}) (fwk.QueueingHint, error) {
    newModel, ok := newObj.(*v1alpha1.Model)
    if !ok {
        return fwk.Queue, fmt.Errorf("unexpected object type %T", newObj)  // ★ 出错时返回 Queue，宁可多试
    }
    if newModel.Name != pod.Annotations[modelAnnotation] {
        return fwk.QueueSkip, nil        // 不是这个 Pod 等的模型
    }
    if newModel.Status.Phase != "Ready" {
        return fwk.QueueSkip, nil        // 还没好
    }
    // oldObj 为 nil 说明是 Add 事件
    if oldModel, ok := oldObj.(*v1alpha1.Model); ok && oldModel.Status.Phase == "Ready" {
        return fwk.QueueSkip, nil        // 本来就 Ready，这次 Update 无关
    }
    return fwk.Queue, nil
}

// 删除的 Pod 用了 GPU 才唤醒（删一个纯 CPU Pod 对 GPU Pod 毫无帮助）
func (p *Plugin) deletedPodUsedGPU(logger klog.Logger, pod *v1.Pod, oldObj, newObj interface{}) (fwk.QueueingHint, error) {
    deleted, ok := oldObj.(*v1.Pod)      // Delete 事件：newObj 为 nil
    if !ok {
        return fwk.Queue, fmt.Errorf("unexpected object type %T", oldObj)
    }
    for _, c := range deleted.Spec.Containers {
        if _, has := c.Resources.Limits[gpuResourceName]; has {
            return fwk.Queue, nil
        }
    }
    return fwk.QueueSkip, nil
}
```

**为什么这个扩展点值得认真写**：一个 5000 节点集群里 Pod 删除事件每秒可能几十次。如果你的插件不实现 hint，每次都会把它拒绝过的所有 Pod 全部唤醒重试 —— 这些 Pod 大概率再次失败，纯粹烧 CPU。详见 [02 篇 §3](02-核心代码分析-调度队列与缓存.md)。

**返回错误时务必返回 `Queue`**（如上面代码所示）：宁可多试几次，也不要让 Pod 永远卡死。

## 5. QueueSort：队列排序

**签名**：

```go
Less(QueuedPodInfo, QueuedPodInfo) bool
```

**语义**：activeQ 的堆比较函数。⚠️ **一个 profile 内只能启用一个** —— 要用自定义的就必须先 `disabled` 掉 `PrioritySort`。

**Demo：同优先级下，先跑「快要超 SLA」的作业**

```go
const (
    Name         = "SLAAwareSort"
    slaAnnotation = "ai.example.com/sla-deadline"     // RFC3339 时间
)

var _ fwk.QueueSortPlugin = &Plugin{}

func (p *Plugin) Less(pi1, pi2 fwk.QueuedPodInfo) bool {
    p1, p2 := pi1.GetPodInfo().GetPod(), pi2.GetPodInfo().GetPod()

    // 第一优先级：仍然尊重 PriorityClass
    prio1, prio2 := corev1helpers.PodPriority(p1), corev1helpers.PodPriority(p2)
    if prio1 != prio2 {
        return prio1 > prio2
    }

    // 第二优先级：deadline 早的先来（EDF, Earliest Deadline First）
    d1, ok1 := parseDeadline(p1)
    d2, ok2 := parseDeadline(p2)
    switch {
    case ok1 && ok2 && !d1.Equal(d2):
        return d1.Before(d2)
    case ok1 && !ok2:
        return true          // 有 deadline 的优先于没有的
    case !ok1 && ok2:
        return false
    }

    // 第三优先级：回落到入队时间，保证 FIFO、避免饿死
    return pi1.GetTimestamp().Before(pi2.GetTimestamp())
}

func parseDeadline(pod *v1.Pod) (time.Time, bool) {
    s := pod.Annotations[slaAnnotation]
    if s == "" {
        return time.Time{}, false
    }
    t, err := time.Parse(time.RFC3339, s)
    return t, err == nil
}
```

启用时必须显式关掉默认排序：

```yaml
plugins:
  queueSort:
    enabled:
    - name: SLAAwareSort
    disabled:
    - name: PrioritySort        # ★ 不关掉会启动失败
```

**坑**：`Less` 必须是**严格弱序**（同时满足传递性与反对称性），否则 `container/heap` 行为未定义，可能 panic 或死循环。上面代码最后一定回落到时间戳比较，就是为了保证任何两个 Pod 都有确定的先后。

## 6. PreFilter + PreFilterExtensions：预计算与抢占模拟

**签名**：

```go
PreFilter(ctx context.Context, state CycleState, p *v1.Pod, nodes []NodeInfo) (*PreFilterResult, *Status)
PreFilterExtensions() PreFilterExtensions

// PreFilterExtensions:
AddPod(ctx, state, podToSchedule *v1.Pod, podInfoToAdd PodInfo, nodeInfo NodeInfo) *Status
RemovePod(ctx, state, podToSchedule *v1.Pod, podInfoToRemove PodInfo, nodeInfo NodeInfo) *Status
```

**两个职责**：① 把「与节点无关的重复计算」做一次，存进 `CycleState`；② 可选返回节点子集。

**Demo：预解析 GPU 请求，并处理拓扑硬约束**

```go
const stateKey fwk.StateKey = Name

// ★ 必须实现 StateData 接口
type preFilterState struct {
    gpuCount     int64
    needSameNUMA bool
    // 已放置的同作业 Pod 所在节点（供 Score 阶段做亲和）
    siblingNodes map[string]int
}

func (s *preFilterState) Clone() fwk.StateData {
    // 源码注释：对不受 AddPod/RemovePod 影响的成员做浅拷贝即可
    return &preFilterState{
        gpuCount:     s.gpuCount,
        needSameNUMA: s.needSameNUMA,
        siblingNodes: s.siblingNodes,      // 浅拷贝：本例中 AddPod/RemovePod 不改它
    }
}

func (p *Plugin) PreFilter(ctx context.Context, state fwk.CycleState,
    pod *v1.Pod, nodes []fwk.NodeInfo) (*fwk.PreFilterResult, *fwk.Status) {

    gpu := gpuRequestOf(pod)
    if gpu == 0 {
        // ★ 返回 Skip：本轮的 Filter 与 PreFilterExtensions 都会被跳过，省 CPU
        return nil, fwk.NewStatus(fwk.Skip)
    }

    // 统计同作业已放置的 Pod（一次算完，避免每个节点重复算）
    siblings := map[string]int{}
    if job := pod.Labels["job-name"]; job != "" {
        for _, n := range nodes {
            for _, pi := range n.GetPods() {
                if pi.GetPod().Labels["job-name"] == job {
                    siblings[n.Node().Name]++
                }
            }
        }
    }

    state.Write(stateKey, &preFilterState{
        gpuCount:     gpu,
        needSameNUMA: pod.Annotations["ai.example.com/numa"] == "required",
        siblingNodes: siblings,
    })

    // 可选：返回节点子集。只在能 O(1) 算出来时才值得做
    if pinned := pod.Annotations["ai.example.com/pinned-nodes"]; pinned != "" {
        return &fwk.PreFilterResult{
            NodeNames: sets.New(strings.Split(pinned, ",")...),
        }, nil
    }
    return nil, nil
}
```

> ⚠️ 返回 `PreFilterResult` 裁掉的节点，框架视为 **`UnschedulableAndUnresolvable`** —— 它们**不会成为抢占候选**。所以只能用来排除「无论怎么抢都不可能用的节点」，不能用来做资源判断。
>
> 参考 [01 篇 §6.3](01-核心原理-调度周期与扩展点.md)：v1.36 全部内置插件里只有 `nodeaffinity` 用了这个能力，而且仅限 `matchFields: metadata.name`。

**`PreFilterExtensions` 什么时候必须实现？**

抢占模拟时，框架会「假装移除某些 Pod」再重跑 `Filter`（[03 篇 §4](03-核心代码分析-过滤打分与抢占.md) 的 `SelectVictimsOnNode`）。如果你的 `CycleState` 里缓存了**与节点上现有 Pod 相关**的信息，就必须实现它来做增量更新：

```go
func (p *Plugin) PreFilterExtensions() fwk.PreFilterExtensions { return p }

func (p *Plugin) AddPod(ctx context.Context, state fwk.CycleState,
    podToSchedule *v1.Pod, podInfoToAdd fwk.PodInfo, nodeInfo fwk.NodeInfo) *fwk.Status {
    s, err := getPreFilterState(state)
    if err != nil {
        return fwk.AsStatus(err)
    }
    if podInfoToAdd.GetPod().Labels["job-name"] == podToSchedule.Labels["job-name"] {
        s.siblingNodes[nodeInfo.Node().Name]++
    }
    return nil
}

func (p *Plugin) RemovePod(ctx context.Context, state fwk.CycleState,
    podToSchedule *v1.Pod, podInfoToRemove fwk.PodInfo, nodeInfo fwk.NodeInfo) *fwk.Status {
    s, err := getPreFilterState(state)
    if err != nil {
        return fwk.AsStatus(err)
    }
    if podInfoToRemove.GetPod().Labels["job-name"] == podToSchedule.Labels["job-name"] {
        s.siblingNodes[nodeInfo.Node().Name]--
    }
    return nil
}

func getPreFilterState(state fwk.CycleState) (*preFilterState, error) {
    c, err := state.Read(stateKey)
    if err != nil {
        return nil, fmt.Errorf("reading %q from CycleState: %w", stateKey, err)
    }
    s, ok := c.(*preFilterState)
    if !ok {
        return nil, fmt.Errorf("%+v convert to preFilterState error", c)
    }
    return s, nil
}
```

不需要就返回 `nil`（大多数插件如此）。

## 7. Filter：硬约束过滤

**签名**：

```go
Filter(ctx context.Context, state CycleState, pod *v1.Pod, nodeInfo NodeInfo) *Status
```

**语义**：对每个候选节点调用一次（跨节点并行）。返回非 Success 即淘汰该节点。

**Demo：禁止大作业占用「已经有碎片」的节点**

目标：让 8 卡整机作业只落在完整空闲的机器上，避免把它塞进「7 卡空闲」的机器后永远调度不了。

```go
var (
    _ fwk.FilterPlugin      = &Plugin{}
    _ fwk.EnqueueExtensions = &Plugin{}    // ★ Filter 会拒绝 Pod，必须实现
)

func (p *Plugin) Filter(ctx context.Context, state fwk.CycleState,
    pod *v1.Pod, nodeInfo fwk.NodeInfo) *fwk.Status {

    s, err := getPreFilterState(state)
    if err != nil {
        return fwk.AsStatus(err)
    }

    node := nodeInfo.Node()
    total := node.Status.Allocatable[gpuResourceName]
    used := nodeInfo.GetRequested().ScalarResources[gpuResourceName]
    free := total.Value() - used

    if free < s.gpuCount {
        // ★ 用 Unschedulable：资源不足，抢占可能有救
        return fwk.NewStatus(fwk.Unschedulable,
            fmt.Sprintf("insufficient gpu: need %d, free %d", s.gpuCount, free))
    }

    // 整机作业（请求 == 整机卡数）要求节点完全空闲
    if s.gpuCount == total.Value() && used > 0 {
        return fwk.NewStatus(fwk.Unschedulable,
            fmt.Sprintf("whole-node job requires empty node, but %d gpu in use", used))
    }

    // NUMA 硬约束：节点没上报拓扑 → 抢占也解决不了
    if s.needSameNUMA {
        if _, ok := node.Labels["ai.example.com/numa-topology"]; !ok {
            // ★ 用 UnschedulableAndUnresolvable：驱逐任何 Pod 都不会让节点长出 NUMA 标签
            return fwk.NewStatus(fwk.UnschedulableAndUnresolvable,
                "node does not report NUMA topology")
        }
    }
    return nil
}
```

**Filter 里最重要的决策是选对 Status Code**：

| 情况 | Code | 后果 |
|------|------|------|
| 资源不够、端口冲突 | `Unschedulable` | 该节点进入抢占候选 |
| label/污点/拓扑能力缺失 | `UnschedulableAndUnresolvable` | **排除出抢占候选**，省掉无用的模拟 |
| 内部错误（读 state 失败等） | `fwk.AsStatus(err)` → `Error` | 中止调度，Pod 进 backoffQ |

选错的代价：把污点类问题报成 `Unschedulable`，抢占阶段会在这些注定失败的节点上做昂贵的 `DryRunPreemption`。

**另外注意两点**：

1. **必须用传入的 `nodeInfo`，不要用 `SnapshotSharedLister()` 去查同一个节点**。源码注释解释了原因：抢占模拟时传入的是「移除了部分 Pod 的副本」，从快照里查会拿到未修改的原始数据 → 模拟结果错误。
2. **v1.36 建议检查 context 取消**。当已找到足够多可行节点时框架会 cancel：

```go
if err := ctx.Err(); err != nil {
    return fwk.NewStatus(fwk.UnschedulableAndUnresolvable, context.Cause(ctx).Error())
}
```

## 8. PostFilter：兜底与自定义抢占

**签名**：

```go
PostFilter(ctx context.Context, state CycleState, pod *v1.Pod,
    filteredNodeStatusMap NodeToStatusReader) (*PostFilterResult, *Status)
```

**语义**：**仅当可行节点为 0** 时调用。这是实现自定义抢占的地方。

**Demo A：诊断型（最实用、最安全）**

大多数团队真正需要的不是自定义抢占，而是「**让我知道为什么调不上去**」：

```go
const Name = "SchedulingDiagnosis"

var _ fwk.PostFilterPlugin = &Plugin{}

func (p *Plugin) PostFilter(ctx context.Context, state fwk.CycleState,
    pod *v1.Pod, m fwk.NodeToStatusReader) (*fwk.PostFilterResult, *fwk.Status) {

    // 按拒绝原因归类统计
    reasons := map[string]int{}
    m.ForEachExplicitNode(func(node string, s *fwk.Status) {
        key := s.Plugin() + ":" + s.Code().String()
        reasons[key]++
    })

    var sb strings.Builder
    for k, v := range reasons {
        fmt.Fprintf(&sb, "%s×%d ", k, v)
    }

    // 打成 Event，用户 kubectl describe pod 就能看到聚合结论
    p.handle.EventRecorder().Eventf(pod, nil, v1.EventTypeWarning,
        "SchedulingDiagnosis", "Scheduling", "rejection summary: %s", sb.String())

    if gpuQuotaExceeded(pod, p.handle) {
        p.handle.EventRecorder().Eventf(pod, nil, v1.EventTypeWarning,
            "QuotaHint", "Scheduling",
            "tenant %s has exhausted its GPU quota; scale down other jobs first",
            pod.Labels["tenant"])
    }

    // ★ 诊断型插件必须返回 Unschedulable（源码注释：
    //   "Informational plugins should be configured ahead of other ones,
    //    and always return Unschedulable status"）
    return nil, fwk.NewStatus(fwk.Unschedulable, "diagnosis recorded: "+sb.String())
}
```

配置时**放在 `DefaultPreemption` 之前**，这样即使真的发生抢占，诊断信息也已经记录下来了。

**Demo B：自定义抢占（只挑同租户的受害者）**

原生抢占是全局按优先级挑受害者，可能杀掉别的租户的 Pod。多租户平台通常希望「**只在自己租户内部抢**」：

```go
func (p *Plugin) PostFilter(ctx context.Context, state fwk.CycleState,
    pod *v1.Pod, m fwk.NodeToStatusReader) (*fwk.PostFilterResult, *fwk.Status) {

    tenant := pod.Labels["tenant"]
    if tenant == "" {
        return nil, fwk.NewStatus(fwk.Unschedulable, "no tenant label, skip preemption")
    }

    nodes, err := p.handle.SnapshotSharedLister().NodeInfos().List()
    if err != nil {
        return nil, fwk.AsStatus(err)
    }

    for _, ni := range nodes {
        // 跳过 UnschedulableAndUnresolvable 的节点 —— ★ 这是插件自己的责任，
        // 源码注释明确说框架不会替你过滤
        if s := m.Get(ni.Node().Name); s != nil && s.Code() == fwk.UnschedulableAndUnresolvable {
            continue
        }

        victims := p.pickSameTenantVictims(ni, pod, tenant)
        if len(victims) == 0 {
            continue
        }

        // 模拟移除后能否放下（复用框架的 Filter）
        trial := ni.Snapshot()
        for _, v := range victims {
            trial.RemovePod(klog.FromContext(ctx), v)
        }
        if !p.handle.RunFilterPluginsWithNominatedPods(ctx, state, pod, trial).IsSuccess() {
            continue
        }

        // 真正驱逐
        for _, v := range victims {
            if err := p.handle.ClientSet().CoreV1().Pods(v.Namespace).
                Delete(ctx, v.Name, metav1.DeleteOptions{}); err != nil {
                return nil, fwk.AsStatus(err)
            }
            p.handle.EventRecorder().Eventf(v, pod, v1.EventTypeNormal,
                "Preempted", "Preempting", "preempted by %s/%s within tenant %s",
                pod.Namespace, pod.Name, tenant)
        }

        // 返回 nominatedNodeName，让框架记住这个 Pod 该去哪
        return fwk.NewPostFilterResultWithNominatedNode(ni.Node().Name), fwk.NewStatus(fwk.Success)
    }
    return nil, fwk.NewStatus(fwk.Unschedulable, "no same-tenant victim found")
}
```

> ⚠️ 自定义抢占很难写对：要处理 PDB、`preemptionPolicy: Never`、`cooldown`、以及「抢完被别人捡走」的竞态（[01 篇 §4.2](01-核心原理-调度周期与扩展点.md)）。**除非有强需求，优先考虑复用 `DefaultPreemption` 或直接上 Volcano/Kueue。**

## 9. PreScore + Score + NormalizeScore：打分

**签名**：

```go
PreScore(ctx context.Context, state CycleState, pod *v1.Pod, nodes []NodeInfo) *Status
Score(ctx context.Context, state CycleState, p *v1.Pod, nodeInfo NodeInfo) (int64, *Status)
ScoreExtensions() ScoreExtensions
// ScoreExtensions:
NormalizeScore(ctx context.Context, state CycleState, p *v1.Pod, scores NodeScoreList) *Status
```

**Demo：GPU 碎片最小化打分**

比 `MostAllocated` 更精细：让「放完之后剩余卡数正好等于常见作业规格」的节点得高分。

```go
var (
    _ fwk.PreScorePlugin   = &Plugin{}
    _ fwk.ScorePlugin      = &Plugin{}
    _ fwk.ScoreExtensions  = &Plugin{}
)

const preScoreKey fwk.StateKey = Name + "-prescore"

type preScoreState struct {
    // 集群中常见的作业规格（从历史统计或配置来）
    commonShapes []int64
}

func (s *preScoreState) Clone() fwk.StateData { return s }

func (p *Plugin) PreScore(ctx context.Context, state fwk.CycleState,
    pod *v1.Pod, nodes []fwk.NodeInfo) *fwk.Status {

    if gpuRequestOf(pod) == 0 {
        return fwk.NewStatus(fwk.Skip)     // ★ Score 也会被跳过
    }
    state.Write(preScoreKey, &preScoreState{commonShapes: p.args.CommonShapes})
    return nil
}

func (p *Plugin) Score(ctx context.Context, state fwk.CycleState,
    pod *v1.Pod, nodeInfo fwk.NodeInfo) (int64, *fwk.Status) {

    s, err := getPreScoreState(state)
    if err != nil {
        return 0, fwk.AsStatus(err)
    }

    total := nodeInfo.Node().Status.Allocatable[gpuResourceName].Value()
    used := nodeInfo.GetRequested().ScalarResources[gpuResourceName]
    remaining := total - used - gpuRequestOf(pod)

    switch {
    case remaining == 0:
        return 1000, nil                  // 完美装满，最高分
    case isCommonShape(remaining, s.commonShapes):
        return 800, nil                   // 剩余量还能放下一个标准作业
    default:
        return 1000 / (remaining + 1), nil // 碎片越大分越低
    }
}

// ★ 返回值超出 [0,100] 就必须实现 NormalizeScore
func (p *Plugin) ScoreExtensions() fwk.ScoreExtensions { return p }

func (p *Plugin) NormalizeScore(ctx context.Context, state fwk.CycleState,
    pod *v1.Pod, scores fwk.NodeScoreList) *fwk.Status {
    // 直接复用内置 helper：把最大值映射到 100，其余等比缩放
    return helper.DefaultNormalizeScore(fwk.MaxNodeScore, false, scores)
}
```

**四个要点**：

1. **`Score` 返回值不在 `[0, 100]` 就必须实现 `NormalizeScore`**，否则框架直接报错。上面故意返回 1000/800 来演示这一点。
2. **`helper.DefaultNormalizeScore(max, reverse, scores)`** 的 `reverse` 参数值得记住 —— 它在「所有原始分都是 0」时行为完全不同：`reverse=true` 全给满分，`reverse=false` 全给 0（[01 篇 §6.6](01-核心原理-调度周期与扩展点.md) 分析过 `TaintToleration` 与 `NodeAffinity` 的这个差异）。
3. **`Score` 会被并行调用**，插件内部有共享可变状态就必须加锁 —— 或者干脆别有。
4. **权重在配置里给**，不在代码里：`multiPoint.enabled[].weight` 或 `score.enabled[].weight`。

## 10. Reserve / Unreserve、Permit、PreBind / Bind / PostBind

### 10.1 Reserve + Unreserve：占用有状态资源

**签名**：

```go
Reserve(ctx context.Context, state CycleState, p *v1.Pod, nodeName string) *Status
Unreserve(ctx context.Context, state CycleState, p *v1.Pod, nodeName string)
```

**Demo：预留租户 GPU 配额（内存计数）**

```go
var _ fwk.ReservePlugin = &Plugin{}

type Plugin struct {
    handle fwk.Handle
    mu     sync.Mutex
    // tenant → 已预留卡数
    reserved map[string]int64
}

func (p *Plugin) Reserve(ctx context.Context, state fwk.CycleState,
    pod *v1.Pod, nodeName string) *fwk.Status {

    tenant := pod.Labels["tenant"]
    gpu := gpuRequestOf(pod)

    p.mu.Lock()
    defer p.mu.Unlock()

    if p.reserved[tenant]+gpu > p.args.QuotaOf(tenant) {
        return fwk.NewStatus(fwk.Unschedulable,
            fmt.Sprintf("tenant %s quota exceeded", tenant))
    }
    p.reserved[tenant] += gpu       // ★ 只改内存，绝不调 API
    return nil
}

// ★ 必须幂等：即使 Reserve 没被调用过，框架也可能调它
func (p *Plugin) Unreserve(ctx context.Context, state fwk.CycleState,
    pod *v1.Pod, nodeName string) {

    tenant := pod.Labels["tenant"]

    p.mu.Lock()
    defer p.mu.Unlock()

    if v, ok := p.reserved[tenant]; ok {
        p.reserved[tenant] = max(0, v-gpuRequestOf(pod))   // 防止减成负数
    }
}
```

**两条铁律**（源码注释明确要求）：

- **`Reserve` 必须快** —— 它在串行的调度周期里，慢一毫秒全集群吞吐就掉。**不要调 apiserver。**
- **`Unreserve` 必须幂等** —— *"The Unreserve method implementation must be idempotent and may be called by the scheduler even if the corresponding Reserve method for the same plugin was not called."*

> 这个 demo 只是演示 `Reserve` 的用法。**真要做租户配额，用 Kueue 而不是自己写** —— 内存计数在调度器重启后就丢了，而 Kueue 的配额账本是持久化在 CRD 状态里的。

### 10.2 Permit：延迟绑定（gang 的原生做法）

**签名**：

```go
Permit(ctx context.Context, state CycleState, p *v1.Pod, nodeName string) (*Status, time.Duration)
```

**Demo：简易 gang 调度**

这就是官方 `gangscheduling` 插件（v1.36 Alpha）与 scheduler-plugins `coscheduling` 的核心思路：

```go
var _ fwk.PermitPlugin = &Plugin{}

const (
    gangNameLabel = "ai.example.com/gang"
    gangSizeLabel = "ai.example.com/gang-size"
)

func (p *Plugin) Permit(ctx context.Context, state fwk.CycleState,
    pod *v1.Pod, nodeName string) (*fwk.Status, time.Duration) {

    gang := pod.Labels[gangNameLabel]
    if gang == "" {
        return nil, 0                       // 不是 gang 成员，直接放行
    }
    size, err := strconv.Atoi(pod.Labels[gangSizeLabel])
    if err != nil || size <= 1 {
        return nil, 0
    }

    // 数一下已经在 Permit 里等待的同 gang 成员（+1 是自己）
    waiting := 1
    p.handle.IterateOverWaitingPods(func(wp fwk.WaitingPod) {
        if wp.GetPod().Labels[gangNameLabel] == gang {
            waiting++
        }
    })

    if waiting < size {
        // ★ 人还不够，挂起等待
        return fwk.NewStatus(fwk.Wait, fmt.Sprintf("waiting for gang %s (%d/%d)", gang, waiting, size)),
            p.args.PermitTimeout        // 建议可配，官方插件硬编码 5min
    }

    // 人齐了，放行所有等待中的同伴
    p.handle.IterateOverWaitingPods(func(wp fwk.WaitingPod) {
        if wp.GetPod().Labels[gangNameLabel] == gang {
            wp.Allow(Name)
        }
    })
    return nil, 0
}
```

**这个 demo 同时暴露了原生 Permit-gang 的根本缺陷**：

```text
Permit 返回 Wait 时，Pod 已经在上一步 assume 过了 → 节点资源已被占用
    ↓
gang A 等 gang B 释放资源，gang B 等 gang A → 互等
    ↓
唯一的解法是超时（官方插件 permitTimeoutDuration = 5 * time.Minute，不可配）
```

对比 Volcano：整组算完才 `Commit`，不成立就 `Discard` **立即释放**，不存在互等窗口。详见 [00 篇 §6.3](00-kube-scheduler总览与架构.md) 与 [04 篇 §4.3](04-面向大模型场景的能力与局限.md)。

超时/被拒时的清理，靠 `Unreserve`（框架会自动调用所有 ReservePlugin 的 `Unreserve`）。

### 10.3 PreBind：慢操作的正确位置

**签名**（v1.36 **有两个方法**）：

```go
PreBindPreFlight(ctx context.Context, state CycleState, p *v1.Pod, nodeName string) (*PreBindPreFlightResult, *Status)
PreBind(ctx context.Context, state CycleState, p *v1.Pod, nodeName string) *Status
```

⚠️ **`PreBindPreFlight` 是 v1.36 新增的必需方法**。老教程里的 `PreBindPlugin` 只有一个 `PreBind`，照抄会编译失败。它的作用是**快速判断「这个 Pod 需不需要我做 PreBind」**：

```go
var _ fwk.PreBindPlugin = &Plugin{}

// 必须轻量：源码注释要求 "shouldn't do any actual operation, e.g., creating a volume etc."
func (p *Plugin) PreBindPreFlight(ctx context.Context, state fwk.CycleState,
    pod *v1.Pod, nodeName string) (*fwk.PreBindPreFlightResult, *fwk.Status) {

    if pod.Annotations[modelAnnotation] == "" {
        return nil, fwk.NewStatus(fwk.Skip)   // ★ 返回 Skip，PreBind 不会被调用
    }
    return nil, nil                            // Success：我要处理这个 Pod
}

// Demo：绑定前给节点打上「需要预热模型」的标记，由 DaemonSet 提前拉取权重
func (p *Plugin) PreBind(ctx context.Context, state fwk.CycleState,
    pod *v1.Pod, nodeName string) *fwk.Status {

    model := pod.Annotations[modelAnnotation]

    // ★ 这里可以调 API：PreBind 在异步的绑定周期里，不阻塞主调度循环
    patch := fmt.Sprintf(
        `{"metadata":{"annotations":{"ai.example.com/prefetch-%s":"true"}}}`, model)
    if _, err := p.handle.ClientSet().CoreV1().Nodes().
        Patch(ctx, nodeName, types.StrategicMergePatchType,
            []byte(patch), metav1.PatchOptions{}); err != nil {
        return fwk.AsStatus(err)              // 失败会触发 Unreserve + Pod 回队列
    }
    return nil
}
```

### 10.4 Bind：接管绑定动作

**签名**：

```go
Bind(ctx context.Context, state CycleState, p *v1.Pod, nodeName string) *Status
```

**语义**：按配置顺序调用，**返回 `Skip` 表示「我不管」**，第一个不返回 Skip 的插件负责绑定，其余被跳过。

```go
var _ fwk.BindPlugin = &Plugin{}

func (p *Plugin) Bind(ctx context.Context, state fwk.CycleState,
    pod *v1.Pod, nodeName string) *fwk.Status {

    // 只接管特定 Pod，其余交还 DefaultBinder
    if pod.Annotations["ai.example.com/custom-bind"] != "true" {
        return fwk.NewStatus(fwk.Skip)       // ★ 关键
    }

    binding := &v1.Binding{
        ObjectMeta: metav1.ObjectMeta{Namespace: pod.Namespace, Name: pod.Name, UID: pod.UID},
        Target:     v1.ObjectReference{Kind: "Node", Name: nodeName},
    }
    if err := p.handle.ClientSet().CoreV1().Pods(binding.Namespace).
        Bind(ctx, binding, metav1.CreateOptions{}); err != nil {
        return fwk.AsStatus(err)
    }
    // 顺便记录到外部系统
    p.recordPlacement(ctx, pod, nodeName)
    return nil
}
```

配置时要保证 `DefaultBinder` 仍然启用且排在后面，否则不被你接管的 Pod 就没人绑了。

### 10.5 PostBind：只能做通知

**签名**：

```go
PostBind(ctx context.Context, state CycleState, p *v1.Pod, nodeName string)
```

**注意没有返回值** —— 它纯粹是信息性的，无法影响任何结果。

```go
var _ fwk.PostBindPlugin = &Plugin{}

func (p *Plugin) PostBind(ctx context.Context, state fwk.CycleState,
    pod *v1.Pod, nodeName string) {

    // 上报放置结果给外部平台（异步，失败也无所谓）
    go func() {
        if err := p.reporter.Report(pod, nodeName); err != nil {
            klog.FromContext(ctx).Error(err, "failed to report placement",
                "pod", klog.KObj(pod), "node", nodeName)
        }
    }()
}
```

**别在这里做关键逻辑** —— 绑定已经完成，出错也没法回滚。

## 11. v1.36 新增的四个扩展点（Alpha）

前面 15 个是稳定扩展点。v1.36 随 workload-aware scheduling 又加了四个，**默认关闭**（`GenericWorkload` / `TopologyAwareWorkloadScheduling` / `OpportunisticBatching` gate），API 仍可能变，这里只说清用途。

### 11.1 SignPlugin：为批量优化生成签名

```go
SignPod(ctx context.Context, pod *v1.Pod) ([]SignFragment, *Status)
```

`OpportunisticBatching`（**Beta，v1.36 默认开启**）的基础：把「调度结果可复用」的 Pod 归为一类。相同签名的后续 Pod 可以直接从上一轮排好序的节点堆里 `Pop` 下一个节点，跳过整轮 Filter + Score（[01 篇 §6.7](01-核心原理-调度周期与扩展点.md)）。

各插件返回的 fragment 合并成一个签名，**同一 key 只保留一个**。返回 `Unschedulable` 表示「这个 Pod 不适合批量优化」。

> 源码注释建议：实现了 `PreFilter` / `Filter` / `PreScore` / `Score` 的插件都应该顺带实现 `SignPlugin`。因为如果你的插件会因 Pod 的某个字段做出不同决策，而这个字段没进签名，批量复用就会给出错误结果。**写自定义插件时这是个隐蔽的正确性陷阱。**

### 11.2 PlacementGenerate / PlacementScore：PodGroup 级的节点集选择

```go
GeneratePlacements(ctx, state PodGroupCycleState, podGroup PodGroupInfo, parentPlacement *Placement) (*GeneratePlacementsResult, *Status)
ScorePlacement(...)                    // PlacementScorePlugin
NormalizePlacementScore(...)           // PlacementScoreExtensions
```

这是**扩展点粒度上的质变**：前 15 个都是「单 Pod × 单节点」，这三个是「**一组 Pod × 一组节点**」。

`Placement` 表示一个候选资源域（比如「rack-a 的 8 台机器」）。`GeneratePlacements` 逐层生成候选域，`ScorePlacement` 给整个域打分 —— 这才是拓扑感知调度需要的抽象：判断「这一组能不能整体放进同一个交换机下」，单 Pod 视角根本表达不了。

内置实现：`topologyaware`（生成）+ `podgrouppodscount`（打分）。

> Volcano 的 `HyperNodeOrderFn` + `HyperNodeGradientForJobFn` 是同一思路的成熟版本（[Volcano 03 篇 §5](../volcano/03-核心代码分析-关键插件.md)）。原生这套目前还是 Alpha，生产上做拓扑感知仍应选 Volcano 或 Kueue TAS。

## 12. 插件参数：接收自定义配置

`PluginFactory` 的第二个参数就是配置。要让 `args` 能被解析，得注册进 scheme：

```go
// pkg/apis/config/v1/types.go
type GPUFragArgs struct {
    metav1.TypeMeta `json:",inline"`

    CommonShapes  []int64       `json:"commonShapes,omitempty"`
    PermitTimeout time.Duration `json:"permitTimeout,omitempty"`
    Quotas        map[string]int64 `json:"quotas,omitempty"`
}
```

```go
func parseArgs(obj runtime.Object) (*GPUFragArgs, error) {
    if obj == nil {
        return defaultArgs(), nil                    // ★ 允许不配
    }
    args, ok := obj.(*GPUFragArgs)
    if !ok {
        return nil, fmt.Errorf("want *GPUFragArgs, got %T", obj)
    }
    if err := validateArgs(args); err != nil {
        return nil, err                              // ★ 返回 err → 调度器启动失败，尽早暴露
    }
    return args, nil
}
```

对应 YAML：

```yaml
profiles:
- schedulerName: gpu-scheduler
  pluginConfig:
  - name: GPUFragmentation
    args:
      apiVersion: kubescheduler.config.k8s.io/v1
      kind: GPUFragArgs
      commonShapes: [1, 2, 4, 8]
      permitTimeout: 10m
```

> 偷懒做法：不注册 scheme，直接用 `runtime.Unknown` 里的 raw JSON 自己 `json.Unmarshal`。能跑，但失去了 API 校验和默认值机制，不推荐用于生产。

```dockerfile
COPY --from=builder /out/kube-scheduler /usr/local/bin/kube-scheduler
USER nonroot
ENTRYPOINT ["/usr/local/bin/kube-scheduler"]
```

**作为第二调度器部署**（推荐 —— 不动原生调度器，出问题影响面可控）：

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: gpu-scheduler
  namespace: kube-system
spec:
  replicas: 1                       # 多副本需 leader election
  selector:
    matchLabels: {app: gpu-scheduler}
  template:
    metadata:
      labels: {app: gpu-scheduler}
    spec:
      serviceAccountName: gpu-scheduler
      containers:
      - name: scheduler
        image: registry.example.com/gpu-scheduler:v0.1.0
        args:
        - --config=/etc/kubernetes/sched-config.yaml
        - --leader-elect=false
        - --v=4
        volumeMounts:
        - name: config
          mountPath: /etc/kubernetes
          readOnly: true
      volumes:
      - name: config
        configMap: {name: gpu-scheduler-config}
```

RBAC 最省事的做法是绑定内置 ClusterRole：

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata: {name: gpu-scheduler}
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: system:kube-scheduler         # 内置角色
subjects:
- kind: ServiceAccount
  name: gpu-scheduler
  namespace: kube-system
```

⚠️ **访问自定义 CRD 需要额外授权**（`system:kube-scheduler` 不含），另建一个 ClusterRole 补上 `get/list/watch`。同时注意 `--leader-elect=true` 时需要 `leases` 权限，且 `--lock-object-name` 不能与原生调度器冲突。

Pod 侧指定使用：

```yaml
spec:
  schedulerName: gpu-scheduler      # ★ 与 profiles[].schedulerName 一致
```

## 14. 验证插件真的生效了

**这是最容易踩空的一步** —— 插件没生效时调度器不会报错，只是静默地什么都不做。

```bash
# ① 确认插件被注册且启用（--v=2 起）
kubectl -n kube-system logs deploy/gpu-scheduler | grep -i "GPUFragmentation"

# ② 看每个节点的过滤/打分细节（--v=5）
kubectl -n kube-system logs deploy/gpu-scheduler | grep -A5 "Calculated node's final score"

# ③ 看 Pod 事件里的拒绝原因（Filter 返回的 message 会出现在这里）
kubectl describe pod <pod> | tail -20

# ④ 插件耗时指标（定位性能问题）
kubectl -n kube-system port-forward deploy/gpu-scheduler 10259:10259 &
curl -sk https://localhost:10259/metrics | grep plugin_execution_duration_seconds | grep GPUFrag
```

| 症状 | 原因 |
|------|------|
| 插件完全不生效，日志无痕迹 | `schedulerName` 与 profile 不匹配；或 `MultiPoint` 里没 enable |
| 只有 Score 生效，Filter 不生效 | 接口签名写错 → 类型断言失败。**加 `var _ fwk.FilterPlugin = &Plugin{}` 就能在编译期发现** |
| 调度器启动即崩 | `args` 解析返回 error；或启用了两个 QueueSort |
| Pod 卡在 Pending 且无事件 | `PreEnqueue` 拒绝了它但没实现 `EnqueueExtensions` → 卡在 unschedulablePods |
| `PreBind` 从不执行 | `PreBindPreFlight` 返回了 `Skip` |
| Bind 后 Pod 没有 nodeName | 自定义 `Bind` 没返回 `Skip` 也没真正绑定 |
| 编译报「missing method PreBindPreFlight」 | v1.36 新增的必需方法（§10.3） |

## 15. 扩展点选择速查

| 我想…… | 用哪个扩展点 | 注意 |
|--------|-------------|------|
| 让某些 Pod 完全不进调度队列 | `PreEnqueue` | 必须配 `EnqueueExtensions` |
| 改调度顺序（SLA / 公平性） | `QueueSort` | 一个 profile 只能一个 |
| 减少无效重试 | `EnqueueExtensions` | **性能收益最大，最常被漏** |
| 硬性排除节点 | `Filter` | 选对 Code：能否抢占取决于它 |
| 预计算、避免每节点重复算 | `PreFilter` + CycleState | 缓存了节点上 Pod 信息就要实现 `PreFilterExtensions` |
| O(1) 缩小候选节点集 | `PreFilter` 返回 `PreFilterResult` | 被裁的节点视为 `UnschedulableAndUnresolvable`，不参与抢占 |
| 影响节点偏好（装箱/亲和） | `Score` (+ `NormalizeScore`) | 越界 [0,100] 必须归一化；权重写在配置里 |
| 诊断「为什么调不上去」 | `PostFilter` | 返回 `Unschedulable`，配在抢占插件之前 |
| 自定义抢占 | `PostFilter` | 难写对，优先考虑 Volcano/Kueue |
| 占用有状态资源、防并发 | `Reserve` + `Unreserve` | 只改内存；Unreserve 必须幂等 |
| Gang / 成组调度 | `Permit` + `IterateOverWaitingPods` | **等待期占资源**，需超时兜底 |
| 绑定前做慢操作（调 API） | `PreBind` (+ `PreBindPreFlight`) | v1.36 两个方法都要实现 |
| 自己完成绑定 | `Bind` | 不接管的 Pod 要返回 `Skip` |
| 上报 / 审计 | `PostBind` | 无返回值，不能影响结果 |

## 16. 什么时候不该写插件

写插件之前先问一遍，能省很多工作量：

| 需求 | 更好的方案 |
|------|-----------|
| 多租户配额、借用、排队 | **Kueue** —— 配额账本持久化在 CRD 里，自己写的内存计数重启就丢 |
| Gang 调度 + 拓扑感知 + GPU 共享 | **Volcano** —— 事务式 gang 比 Permit 挂起更可靠 |
| 装箱 / 打散策略调整 | **改 `scoringStrategy` 配置**，不用写代码（[04 篇 §2.1](04-面向大模型场景的能力与局限.md)） |
| 只让部分负载用特殊策略 | **多 profile**（[05 篇 §2](05-实战Demo.md)） |
| GPU 显存/算力切分 | **HAMi / Volcano deviceshare** —— 需要 device plugin 配合，光调度器做不到 |
| 简单的节点选择约束 | `nodeSelector` / `nodeAffinity` / 污点，够用就别写代码 |

**真正适合自己写插件的场景**：业务语义强、无法用通用方案表达的规则 —— 比如「按机型代次和模型精度匹配」「碎片形状与历史作业规格对齐」「与内部资源管理系统联动」。
