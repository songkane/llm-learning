# 面向大模型场景的能力与局限

> 前三篇讲「kube-scheduler 怎么工作」，本篇讲「**大模型训练/推理场景下它能做什么、做不到什么、以及怎么和 Volcano/Kueue 配合**」。
>
> 源码基线：**v1.36.3**

---

## 1. 先把结论摆出来

用**默认配置的 kube-scheduler** 跑 00 篇的统一示例（8×8 卡 A100）：

| 需求 | 原生能力 | 评价 |
|------|---------|------|
| 8 个 Pod 必须同时起（NCCL 通信域） | `GangScheduling` Alpha 默认关 | ⚠️ 生产不可用 |
| 4 卡 TP 组同机 | `PodAffinity` 可近似表达，无硬性成组 | ⚠️ 不可靠 |
| 同 rack / 同交换机 | `TopologyAwareWorkloadScheduling` Alpha 默认关 | ⚠️ 生产不可用 |
| 团队配额、闲时互借 | ❌ 只有 `ResourceQuota`（硬上限、不可借） | ❌ 完全缺失 |
| GPU 装箱减少碎片 | ✅ `NodeResourcesFit: MostAllocated` | ✅ 配一下就好 |
| 大镜像亲和 | ✅ `ImageLocality` | ✅ 默认就有 |
| 在线优先抢离线 | ✅ `PriorityClass` + `DefaultPreemption` | ⚠️ 单 Pod 视角，会白杀 |
| 推理副本打散 | ✅ `PodTopologySpread` | ✅ 很好用 |
| GPU 显存/算力共享 | ❌ 整卡整数分配 | ❌ 需 Volcano/HAMi |
| 精细设备选择（型号/NVLink 组） | ✅ **DRA（v1.35 GA）** | ✅ 新方向，值得投入 |

**一句话**：kube-scheduler 把「**单个 Pod 放哪台机器最合适**」这件事做到了极致，但「**一组 Pod 作为整体的资源契约**」这件事在 v1.36 之前完全不管，v1.36 起才有 Alpha 实现。

## 2. 能做好的部分（应该充分利用）

### 2.1 GPU 装箱：最容易被忽略的一分钱

默认 `NodeResourcesFit` 用 `LeastAllocated`（打散），这对 GPU 集群是**反向优化**：

```text
场景：8 台机各 8 卡，来 8 个单卡 Pod
LeastAllocated → 每台放 1 个，8 台机器各剩 7 卡
                 → 接下来一个 8 卡整机作业：没有任何一台机器能装下 ❌
MostAllocated  → 前 1 台放满 8 个，其余 7 台完整空闲
                 → 8 卡整机作业可以放 ✅
```

配置（05 篇有完整示例）：

```yaml
pluginConfig:
- name: NodeResourcesFit
  args:
    scoringStrategy:
      type: MostAllocated
      resources:
      - {name: nvidia.com/gpu, weight: 10}   # GPU 主导
      - {name: cpu, weight: 1}
      - {name: memory, weight: 1}
```

同时要把 `NodeResourcesBalancedAllocation` 关掉或降权 —— 它的目标（各维度均衡）与 GPU 装箱冲突。

### 2.2 ImageLocality：大模型镜像的隐形优化

vLLM / PyTorch 镜像动辄 10~30 GB，冷启动拉镜像可能要几分钟。`ImageLocality` 默认权重 1，GPU 集群可以调高：

```yaml
plugins:
  score:
    enabled:
    - name: ImageLocality
      weight: 5
```

> 注意它有上限保护：镜像大小对分数的贡献有 `maxContainerThreshold`（1000MB）截断，且只有「已有该镜像的节点数 / 总节点数」比例较低时加分才明显 —— 防止所有 Pod 都挤到少数节点。

### 2.3 PodTopologySpread：推理副本打散

推理服务要抗节点/机架故障，这是原生最好用的能力：

```yaml
topologySpreadConstraints:
- maxSkew: 1
  topologyKey: topology.kubernetes.io/zone
  whenUnsatisfiable: DoNotSchedule           # 硬约束
  labelSelector:
    matchLabels: {app: vllm}
- maxSkew: 1
  topologyKey: kubernetes.io/hostname
  whenUnsatisfiable: ScheduleAnyway          # 软约束
  labelSelector:
    matchLabels: {app: vllm}
```

配套的 `NodeInclusionPolicyInPodTopologySpread`（v1.33 GA）让你控制「计算 skew 时是否算上不可调度的节点」。

### 2.4 DRA：v1.35 已 GA 的设备管理新范式

```go
DynamicResourceAllocation: {
    {Version: version.MustParse("1.26"), Default: false, PreRelease: featuregate.Alpha},
    {Version: version.MustParse("1.32"), Default: false, PreRelease: featuregate.Beta},
    {Version: version.MustParse("1.34"), Default: true, PreRelease: featuregate.GA},
    {Version: version.MustParse("1.35"), Default: true, PreRelease: featuregate.GA, LockToDefault: true},
},
```

**DRA 已经 GA 且不可关闭**，这是很多资料还没更新的重要事实。

它解决 device plugin 的根本局限：`nvidia.com/gpu: 2` 这种「可数扩展资源」无法表达「我要 2 张**通过 NVLink 互联**的 A100-80G」。DRA 用结构化参数描述设备与约束：

```yaml
apiVersion: resource.k8s.io/v1
kind: ResourceClaimTemplate
metadata: {name: nvlink-pair}
spec:
  spec:
    devices:
      requests:
      - name: gpus
        exactly:
          deviceClassName: gpu.nvidia.com
          count: 2
          selectors:
          - cel:
              expression: 'device.attributes["gpu.nvidia.com"].productName == "A100-SXM4-80GB"'
        # 约束：这些设备必须共享同一个 NVLink domain
      constraints:
      - matchAttribute: "gpu.nvidia.com/nvlinkDomain"
---
# Pod 侧引用
spec:
  resourceClaims:
  - name: gpus
    resourceClaimTemplateName: nvlink-pair
  containers:
  - name: trainer
    resources:
      claims:
      - name: gpus
```

调度器侧实现在 `pkg/scheduler/framework/plugins/dynamicresources/`，参与 `PreFilter`（找候选设备）/ `Filter`（节点上能否满足）/ `Reserve`（占住设备）/ `PreBind`（写 ResourceClaim 的 allocation）。

注意它被特意插在 `DefaultPreemption` **之前**：

```go
// pkg/scheduler/apis/config/v1/default_plugins.go
// This plugin should come before DefaultPreemption because if
// there is a problem with a Pod and PostFilter gets called to
// resolve the problem, it is better to first deallocate an
// idle ResourceClaim than it is to evict some Pod that might
// be doing useful work.
```

**先释放闲置的 ResourceClaim，再考虑杀 Pod** —— 很合理的优先级。

相关的子 gate（都依赖 `DynamicResourceAllocation`）：`DRADeviceTaints`、`DRAExtendedResource`、`DRAResourceClaimDeviceStatus`、`DRAResourcePoolStatus`、`DRASchedulerFilterTimeout`、`DRAListTypeAttributes`。

> **DRA 与 GPU 共享的关系**：DRA 本身不做「一张卡切给多个 Pod」，但它提供了表达能力（`ResourceSlice` 里可以声明可共享设备、`DRAConsumableCapacity` 方向）。目前生产上做 GPU 显存切分仍然要靠 HAMi / Volcano deviceshare / MPS / MIG。

### 2.5 多 profile：一个进程多套策略

```yaml
profiles:
- schedulerName: default-scheduler
  # 默认策略：打散
- schedulerName: gpu-binpack-scheduler
  pluginConfig:
  - name: NodeResourcesFit
    args:
      scoringStrategy:
        type: MostAllocated
        resources: [{name: nvidia.com/gpu, weight: 10}]
```

Pod 用 `spec.schedulerName: gpu-binpack-scheduler` 选择。**同一个调度器进程内**按 profile 分派，比部署第二个调度器轻量得多。

> 这是很多人不知道的能力：想给 GPU 负载单独一套打分策略，不需要装 Volcano，配个 profile 就行（当然 gang 还是没有）。

## 3. 做不到的部分（为什么需要 Volcano / Kueue）

### 3.1 没有 gang → 资源死锁

```text
作业 T（8 Pod × 8 卡 = 64 卡）提交
集群剩 40 卡
→ 5 个 Pod 调度成功，占住 40 卡
→ 3 个 Pod Pending
→ 5 个已起的 Pod 在 dist.init_process_group() 上永久阻塞
→ 40 卡被无产出地占用，直到人工介入
```

更糟的是**两个作业互锁**：作业 T 占 40 卡等 24 卡，作业 T2 占 24 卡等 40 卡，双方永久等待。

`PodAffinity` 帮不上忙 —— 它表达「和某类 Pod 在一起」，不表达「我们 8 个必须一起被调度」。

### 3.2 没有多租户配额

原生只有 `ResourceQuota`：

| | `ResourceQuota` | Kueue ClusterQueue | Volcano Queue |
|--|----------------|-------------------|---------------|
| 作用域 | namespace | 跨 namespace | 跨 namespace |
| 超出后 | **Pod 创建直接被拒** | 排队等 | 排队等 |
| 闲时借用 | ❌ | ✅ `borrowingLimit` | ✅ 超 deserved 借 |
| 保底 | ❌ | ✅ `lendingLimit` | ✅ `guarantee` |
| 抢回 | ❌ | ✅ `reclaimWithinCohort` | ✅ `reclaim` action |
| 排队 | ❌ 没有队列概念 | ✅ | ✅ |

「team-b 晚上不用卡的时候 team-a 能借来跑，白天 team-b 要用时抢回来」—— 这个 MaaS 平台最基本的需求，原生完全无法表达。

### 3.3 抢占是单 Pod 视角 → 白杀

```text
作业 T 的 Pod-1 触发抢占，杀掉 3 个低优 Pod 腾出 8 卡
→ Pod-1 调度成功
→ Pod-2..Pod-8 仍然没资源
→ 3 个低优 Pod 白死了，作业 T 还是起不来
```

源码注释对此是坦白的（`schedulingAlgorithm`）：

> *"It is also possible that a different pod will schedule into the resources that were preempted, but this is harmless."*

对单体服务确实 harmless，对 gang 作业是灾难。Volcano 的 `JobPipelined` 判定、Kueue 的「抢占后能否 Admitted」判定，都是为了避免这个。

### 3.4 不理解 GPU 互联拓扑

`nvidia.com/gpu: 4` 只表达「4 张卡」，不表达：

- 4 张卡是否在同一 NVLink domain（决定 TP 通信带宽）
- 8 台机是否在同一个 leaf switch 下（决定 DP/PP 的 all-reduce 性能）

DRA 解决了前者（`matchAttribute` 约束），后者要靠 v1.36 的 `TopologyAwareWorkloadScheduling`（Alpha）或 Volcano HyperNode / Kueue TAS。

## 4. v1.36 workload-aware：现在该怎么看

00 篇 §6 详细讲了实现，这里只谈**取舍**。

### 4.1 可以做什么

开启 `GenericWorkload` + `GangScheduling` 后：

```yaml
apiVersion: scheduling.k8s.io/v1alpha2
kind: PodGroup
metadata: {name: pretrain-t, namespace: default}
spec:
  schedulingPolicy:
    gang:
      minCount: 8
---
apiVersion: v1
kind: Pod
spec:
  schedulingGroup:
    podGroupName: pretrain-t      # ★ 声明归属（不可变）
```

机制（`plugins/gangscheduling/gangscheduling.go`）：`PreEnqueue` 挡住人数不够的组，`Permit` 让先到的 Pod 挂起等同伴，凑够 `minCount` 一起 `Allow`。

### 4.2 为什么现在还不能用于生产

| 问题 | 说明 |
|------|------|
| **Alpha 默认关闭** | 需要显式开 gate；托管 K8s（EKS/GKE/ACK）通常不允许改 |
| **API 是 `v1alpha2`** | 字段还会变，升级可能不兼容 |
| **Permit 等待占资源** | `Wait` 期间 Pod 已 assume，多个 gang 互等会死锁，只能靠 5 分钟硬编码超时解 |
| **超时不可配** | `permitTimeoutDuration = 5 * time.Minute` 写死在代码里 |
| **仍无配额** | gang 解决了「一起起」，没解决「谁能用多少」 |
| **拓扑与抢占互斥** | `runWorkloadAwarePreemption` 明确拒绝带 `schedulingConstraints.topology` 的 PodGroup |

关于最后一条，源码写得很直接：

```go
if pg.Spec.SchedulingConstraints != nil && len(pg.Spec.SchedulingConstraints.Topology) > 0 {
    return fwk.NewStatus(fwk.Unschedulable, "workload aware preemption is not supported for pod groups with scheduling constraints")
}
```

> 有意思的是 **Volcano 有完全相同的限制**（`preempt.Execute` 跳过带 `networkTopology` 的作业）。「拓扑约束 + 抢占」的组合是个公认的难题：抢占要模拟「杀了谁之后能否放下」，而拓扑约束让这个搜索空间爆炸。

### 4.3 Permit-gang vs 事务-gang（值得记住的对比）

```text
kube-scheduler（Permit 型）：
  Pod-1 调度成功 → assume（占 8 卡）→ Permit Wait（挂起）
  Pod-2 调度成功 → assume（占 8 卡）→ Permit Wait
  ...
  Pod-5 调度成功 → assume → 但只剩 40 卡，Pod-6 无资源
  → Pod-1..5 挂起占着 40 卡，等 5 分钟超时才释放  ⚠️

Volcano（事务型）：
  Pod-1..5 在快照里 Allocate
  Pod-6 分配失败 → JobReady 判定失败
  → stmt.Discard() 立即回滚，资源马上可用于别的作业  ✅
```

**这是原生 gang 目前最大的架构性短板。** 它源于 kube-scheduler「Pod 独立、无回滚」的基础假设 —— Permit 是在既有框架上能做到的最好方案，但不如为成组设计的事务模型。

## 5. 三种落地形态

### 5.1 只用 kube-scheduler + 上层框架自己处理

适用：**小规模、单租户、作业不大**。

```yaml
# 用 Job 的 completions/parallelism + 应用层重试容忍"部分起来"
# 或用 torchrun 的 elastic 模式（world size 动态）
```

配上：GPU 装箱 profile + `ImageLocality` 加权 + `PodTopologySpread`。

风险：一旦有多个大作业并发提交，资源死锁几乎必然发生。

### 5.2 kube-scheduler + Kueue（推荐给多租户平台）

```yaml
metadata:
  labels:
    kueue.x-k8s.io/queue-name: team-a-queue   # Kueue 管配额与排队
spec:
  template:
    spec:
      # schedulerName 留空 = default-scheduler
      # Kueue 放行后由 kube-scheduler 选节点
```

分工：

| 层 | 组件 | 负责 |
|----|------|------|
| 准入 | Kueue | 配额、排队、gang（作业级）、跨队列借用回收、TAS 拓扑 |
| 调度 | kube-scheduler | 节点过滤打分、DRA、装箱、亲和 |

**注意碎片风险**：Kueue 确认「配额够 8 个 Pod」后放行，但 kube-scheduler 可能因碎片放不下（每台剩 3 卡凑不出 8 卡）。解法是**开 Kueue TAS**，让它在准入时就按真实节点容量算拓扑分配并注入 nodeSelector。

### 5.3 kube-scheduler + Volcano 并存（推荐给 GPU 精细化场景）

```yaml
# 系统组件走默认调度器
spec: {}                          # schedulerName 默认

# 训练/推理走 Volcano
spec:
  schedulerName: volcano          # 节点级 gang + GPU 共享 + NUMA
```

两个调度器**按 `schedulerName` 分流**，互不干扰（01 篇提过 `responsibleForPod` 的过滤）。

Volcano 复用了 kube-scheduler 的插件代码，所以 `NodeAffinity`、`PodTopologySpread`、`VolumeBinding` 这些判定行为完全一致 —— 迁移不会有语义意外。

### 5.4 三层全上（大型 MaaS 平台）

```text
Kueue（配额准入） → Volcano（成组落位 + GPU 共享） → kubelet
                 ↘ kube-scheduler（系统组件与普通服务）
```

注意事项（重复 Kueue 04 篇的提醒）：

1. **抢占只在一边做**：建议 Kueue 做跨队列配额回收，Volcano 关掉 `preempt`/`reclaim`。
2. **拓扑只用一套**：Kueue TAS 与 Volcano HyperNode 都往 Pod 写落位约束，会冲突。
3. **gang 会叠加**：Kueue 的作业级 + Volcano 的节点级，实际上正好互补（补上 5.2 的碎片风险）。

## 6. 关键指标

`pkg/scheduler/metrics/metrics.go`（前缀 `scheduler_`）：

| 指标 | 用途 |
|------|------|
| `scheduler_schedule_attempts_total{result,profile}` | 调度尝试，`result` = scheduled / unschedulable / error |
| `scheduler_scheduling_attempt_duration_seconds` | **端到端调度延迟**（调优基线） |
| `scheduler_scheduling_algorithm_duration_seconds` | 算法阶段（Filter+Score）耗时 |
| `scheduler_pending_pods{queue}` | 各队列深度，`queue` = active / backoff / unschedulable / gated |
| `scheduler_pod_scheduling_duration_seconds` | 从 Pod 创建到调度成功（含排队与重试） |
| `scheduler_pod_scheduling_attempts` | 一个 Pod 被尝试了几次（**gang 缺失时会很高**） |
| `scheduler_plugin_execution_duration_seconds{plugin,extension_point}` | 单插件耗时（采样，`pluginMetricsSamplePercent`） |
| `scheduler_framework_extension_point_duration_seconds` | 各扩展点总耗时 |
| `scheduler_preemption_attempts_total` / `scheduler_preemption_victims` | 抢占规模 |
| `scheduler_queue_incoming_pods_total{queue,event}` | 队列流入，按触发事件分类（**看 QueueingHint 效果**） |
| `scheduler_unschedulable_pods{plugin,profile}` | 被哪个插件卡住 |
| `scheduler_goroutines{operation}` | 并行 worker 数 |
| v1.36 新增 | `scheduler_pod_group_scheduling_*`（PodGroup 相关，需开 gate） |

**GPU 集群重点看三个**：

1. `scheduler_pending_pods{queue="unschedulable"}` 持续高 → 资源不足或碎片严重；
2. `scheduler_pod_scheduling_attempts` p99 很高 → 大概率是 gang 缺失导致反复重试；
3. `scheduler_queue_incoming_pods_total{event="UnschedulableTimeout"}` 占比高 → QueueingHint 没起作用（可能是自定义插件没实现 `EventsToRegister`）。

## 7. 坑与取舍清单

| 项 | 说明 |
|----|------|
| **默认打散不装箱** | `NodeResourcesFit` 默认 `LeastAllocated`，GPU 集群会造成碎片，必须改 `MostAllocated` |
| **`BalancedAllocation` 与装箱冲突** | 改装箱时记得同时降权或关掉它 |
| **采样只看部分节点** | 大集群 `percentageOfNodesToScore` 自适应最低到 5%，「最优节点」是局部最优 |
| **退避上限只有 10s** | 大量 Pending Pod 时调度器会持续繁忙 |
| **抢占跨轮且无强预留** | `nominatedNodeName` 可能被插队，会出现「白杀」 |
| **`ResourceQuota` 超出直接拒绝创建** | 不是排队，而是 Pod 创建失败 —— 上层控制器会反复重试刷事件 |
| **PDB 只影响抢占排序，不是硬保证** | `SelectVictimsOnNode` 会优先不违反 PDB，但没有 non-violating 方案时仍会违反 |
| **`preemptionPolicy: Never` 在 PriorityClass 上** | 不是 Pod 字段，容易配错位置 |
| **v1.36 gang 的 Permit 占资源** | 挂起期间不释放，可能死锁，超时 5 分钟不可配 |
| **拓扑约束 + 抢占不兼容** | 原生与 Volcano 都有此限制 |
| **多 profile 共享同一份 Cache/队列** | profile 只切换插件与参数，不隔离资源视图 |
| **`manageJobsWithoutQueueName`（Kueue）会挂起系统 Job** | 叠加 Kueue 时注意白名单 |

## 8. 三系列对照总结

| 能力 | kube-scheduler v1.36 | Volcano v1.15.1 | Kueue v0.19.1 |
|------|---------------------|-----------------|---------------|
| 层次 | Pod 级调度 | Pod 级调度 | 作业级准入 |
| Gang | Alpha（Permit 型，占资源） | ✅ 事务型（Discard 释放） | ✅ 结构性（Pod 不创建） |
| 多租户配额 | ❌ | ✅ Queue | ✅ ClusterQueue + Cohort |
| 借用/抢回 | ❌ | ✅ deserved/capability | ✅ borrowing/lendingLimit |
| 网络拓扑 | Alpha（Placement） | ✅ HyperNode | ✅ TAS |
| GPU 共享 | ❌（DRA 不做切分） | ✅ vGPU | ❌ |
| NUMA 感知 | ❌（kubelet 侧有 TopologyManager） | ✅ numaaware | ❌ |
| DRA | ✅ **GA** | 配额侧对接 | 配额侧对接 |
| 多集群 | ❌ | ❌ | ✅ MultiKueue |
| 弹性作业 | ❌ | ✅ minAvailable<replicas | ✅ workload slice |
| 节点打分插件生态 | ✅ **标准来源** | ✅ 复用 + 自有 | ❌ 不做 |
| 生产成熟度 | ✅✅✅ | ✅✅ | ✅✅ |
