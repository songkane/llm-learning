## 一、这个系列在回答什么问题

如果你读过本仓库的 [vLLM 05 篇 · 多机推理与 PD 分离](../../inference-engine/vllm/05-多机推理与PD分离.md) 和 [SGLang 05 篇 · 部署场景](../../inference-engine/sglang/05-部署场景-单机-多机-PD分离.md)，你会发现两套笔记都在同一个地方「收住了」：

> Prefill 实例算完 KV，**通过 RDMA 传给 Decode 实例** —— 然后呢？这个「传」具体是谁在做、怎么做的？

再往前一步，[SGLang 06 篇 · RadixCache](../../inference-engine/sglang/06-RadixCache深度剖析.md) 的前缀缓存只活在**单实例的 GPU 显存**里：实例一重启，缓存全丢；实例 A 算过的前缀，实例 B 用不上。

**Mooncake 就是补这两个缺口的基础设施**：

| 缺口 | Mooncake 的answer | 本系列篇目 |
|------|------------------|-----------|
| KV 怎么跨实例/跨节点高效搬运？ | **Transfer Engine**：统一抽象 RDMA / TCP / NVLink / NVMe-oF 等多种介质，多网卡聚合、零拷贝 | [01](./01-TransferEngine传输引擎.md) |
| 前缀缓存怎么跨实例共享、怎么活过重启？ | **Mooncake Store**：集群级 KV 缓存池，把各节点的空闲 DRAM 聚合成一个共享池 | [02](./02-MooncakeStore缓存池.md) |
| 显存/内存装不下的冷 KV 放哪？ | **分层存储**：内存 → 本地 SSD → 分布式文件系统（3FS / SPDK） | [03](./03-分层存储与持久化.md) |
| 元数据服务挂了怎么办？读的时候数据被淘汰了怎么办？ | **Master 高可用 + 租约机制** | [04](./04-高可用与元数据管理.md) |
| vLLM / SGLang 具体怎么接进来？ | **KV Connector / HiCache L3 backend** | [05](./05-与推理引擎集成.md) |

一句话定位：

> **vLLM / SGLang 管「算」，Mooncake 管「存」与「搬」。**

## 二、一张图看懂 Mooncake

Mooncake 源自 Kimi 的生产实践（FAST'25 论文），核心主张是 **KVCache-centric**：不再把 KV Cache 当成 GPU 显存里的临时副产品，而是当作**一等公民资源**，独立于计算实例被池化、调度、复用。

```
┌──────────────────────── 推理集群 ────────────────────────────────────┐
│                                                                       │
│  ┌─────────────────┐   ┌─────────────────┐   ┌─────────────────┐     │
│  │ Prefill 实例 P0  │   │ Decode 实例 D0   │   │ Decode 实例 D1  │     │
│  │ (vLLM / SGLang) │   │                 │   │                 │     │
│  │   L1: GPU HBM   │   │   L1: GPU HBM   │   │   L1: GPU HBM   │     │
│  │   L2: Host DRAM │   │   L2: Host DRAM │   │   L2: Host DRAM │     │
│  └────────┬────────┘   └────────┬────────┘   └────────┬────────┘     │
│           │  Mooncake Client    │                     │              │
│           ▼                     ▼                     ▼              │
│  ══════════════════════ Transfer Engine ══════════════════════        │
│    统一抽象：RDMA(多网卡聚合) / TCP / NVLink / CXL / NVMe-oF          │
│  ═══════════════════════════════════════════════════════════════      │
│           │                     │                     │              │
│           ▼                     ▼                     ▼              │
│  ┌──────────────────────────────────────────────────────────────┐    │
│  │       Mooncake Store（L3：集群级共享 KV 缓存池）              │    │
│  │  把每台机器 mount 进来的 DRAM segment 聚成一个全局池          │    │
│  │  ┌──────────┐  ┌──────────┐  ┌──────────┐                    │    │
│  │  │ segment0 │  │ segment1 │  │ segment2 │  ← 各节点贡献的内存 │    │
│  │  └──────────┘  └──────────┘  └──────────┘                    │    │
│  └───────────────────────────┬──────────────────────────────────┘    │
│                              │ 冷数据下沉                             │
│                              ▼                                        │
│  ┌──────────────────────────────────────────────────────────────┐    │
│  │   分层存储：本地文件 / io_uring / 3FS / SPDK NVMe             │    │
│  └──────────────────────────────────────────────────────────────┘    │
│                                                                       │
│  ┌────────────────────────────────┐                                  │
│  │  Master（元数据服务，独立进程） │  ← 只管元数据，不碰数据面        │
│  │  key → [replica, segment, off] │                                  │
│  │  + 租约 / 淘汰 / segment 生命周期│                                  │
│  └────────────────────────────────┘                                  │
└───────────────────────────────────────────────────────────────────────┘
```

**三个必须记住的设计要点**：

1. **控制面与数据面彻底分离**。Master 只保存「key → 副本位置」的元数据，客户端拿到位置后**直接用 RDMA 点对点读写目标节点内存**，数据一个字节都不经过 Master。这是它能扩展的根本原因。
2. **存储池由客户端「捐献」**。没有专门的存储服务器：每个推理实例启动时 `mount_segment()` 把自己一部分 DRAM 贡献出来，聚合成全局池。谁都是消费者，谁也都是提供者。
3. **多介质统一抽象**。上层只管发 `TransferRequest{opcode, source, target_id, target_offset, length}`，底层自动选 RDMA / TCP / NVLink —— 详见 01 篇。

## 四、核心概念速查表

| 概念 | 一句话解释 | 详见 |
|------|-----------|------|
| **Transfer Engine** | 统一的多协议数据搬运引擎，上层不关心底层是 RDMA 还是 TCP | 01 |
| **Segment** | 一段被注册（RDMA pin 住）的连续内存，是传输与分配的基本单位 | 01 / 02 |
| **SegmentID / SegmentHandle** | `openSegment(name)` 返回的 64 位句柄，标识远端一段内存 | 01 |
| **TransferRequest** | 一次搬运请求：`{opcode(READ/WRITE), source, target_id, target_offset, length}` | 01 |
| **Slice** | 请求被切分后的最小传输单元（默认按 `slice_size` 切），是 RDMA WR 的载体 | 01 |
| **BatchID / BatchDesc** | 一批传输的句柄，异步提交后靠它轮询状态 | 01 |
| **Topology** | 网卡与存储位置的亲和矩阵，决定「这段内存该用哪张网卡发」 | 01 |
| **Mooncake Store** | 集群级 KV 对象池，`Put/Get` 语义，底层走 Transfer Engine | 02 |
| **Master** | 独立的元数据服务进程，只存 `key → 副本位置`，不碰数据 | 02 / 04 |
| **Replica** | 一个对象的一个副本，有 `MEMORY / DISK / LOCAL_DISK / NOF_SSD` 之分 | 02 / 03 |
| **PutStart / PutEnd** | 写入的两阶段协议：先向 Master 要空间，写完再提交 | 02 |
| **Lease（租约）** | 读取时授予的短期保护，防止对象在读的过程中被淘汰 | 04 |
| **Soft pin / Hard pin** | 软钉（优先保留）/ 硬钉（永不淘汰） | 04 |
| **HiCache L1/L2/L3** | SGLang 的三级缓存：GPU 显存 / Host 内存 / Mooncake 分布式池 | 05 |
| **KV Connector** | vLLM v1 的 KV 传输插件接口，Mooncake 以此接入 | 05 |

## 五、贯穿全系列的统一示例（请记住这个设定）

为了能和 vLLM / SGLang 两套笔记**直接对照**，本系列沿用完全相同的示例设定。

### 5.1 场景设定

集群里跑一个 **PD 分离 + 共享 KV 池**的部署：

```bash
# ① 启动 Mooncake Master（元数据服务，独立进程）
mooncake_master --port 50051

# ② Prefill 实例 P0（节点 192.168.0.2）
vllm serve Qwen/Qwen2.5-7B-Instruct --port 8100 \
  --kv-transfer-config '{"kv_connector":"MooncakeStoreConnector","kv_role":"kv_producer"}'

# ③ Decode 实例 D0（节点 192.168.0.3）
vllm serve Qwen/Qwen2.5-7B-Instruct --port 8200 \
  --kv-transfer-config '{"kv_connector":"MooncakeStoreConnector","kv_role":"kv_consumer"}'
```

两个实例启动时各自 `mount_segment()` 贡献 16 GB DRAM，全局池共 32 GB。

### 5.2 两个共享前缀的请求

与 vLLM / SGLang 笔记**完全一致**的 A / B 请求：

```python
SYSTEM = "You are a helpful assistant. Answer concisely."   # 共享前缀，约 10 token

# 请求 A
prompt_A = SYSTEM + "What is the capital of France?"
# 请求 B（稍后到达）
prompt_B = SYSTEM + "What is the capital of Japan?"
```

### 5.3 这份 KV 在 Mooncake 里的完整旅程

后面每一篇都会回到这条时间线上的某一段：

```
t0  请求 A 到达 P0
     └─ P0 先问 Mooncake Store：这个前缀的 KV 有没有现成的？
        Client.isExist("kvcache:hash(SYSTEM)")  →  false（冷启动）        【02 篇】

t1  P0 执行 prefill，GPU 算出 A 的完整 KV（约 20 token）

t2  P0 把 KV 写入 Store：
     ├─ PutStart(key, slice_length) → Master 分配空间，返回副本位置       【02 篇】
     ├─ Transfer Engine 把 KV 从 GPU/Host 内存 WRITE 到目标 segment      【01 篇】
     │   └─ 切成 Slice → selectDevice 选网卡 → ibv_post_send → poll CQ
     └─ PutEnd(key) → Master 标记副本 COMPLETE，可被他人读取             【02 篇】

t3  A 的 KV 需要送到 D0 做 decode：
     └─ D0 GetReplicaList(key) → Master 返回位置 + 授予租约              【04 篇】
        Transfer Engine READ 直接从 P0 的内存拉走，不经过 Master          【01 篇】

t4  请求 B 到达 P0（或任意其他实例）：
     └─ isExist("kvcache:hash(SYSTEM)") → true！命中共享前缀
        直接 Get 回来，省掉这 10 个 token 的 prefill 计算                 【02/05 篇】
        ★ 这是 Mooncake 相对 SGLang RadixCache 的关键增量：
          跨实例、跨重启的前缀复用

t5  池子快满了（到 eviction_high_watermark_ratio = 0.90）：
     └─ Master 触发淘汰，先淘汰无租约、未 soft pin 的对象                 【04 篇】
        或把冷对象 offload 到 SSD，内存只留热的                          【03 篇】
```

**对照记忆**：t1 那一步在 vLLM 笔记里是 `EngineCore.step()`，在 SGLang 笔记里是 `Scheduler.event_loop_normal()`；t4 的前缀命中在 SGLang 里是 `RadixCache.match_prefix()`——只不过那是**单实例显存内**的匹配，而这里是**跨实例集群级**的匹配。

## 六、Mooncake ↔ vLLM ↔ SGLang 机制对照表

这张表是本系列与另两套笔记的「接缝」，建议读完各系列 00 篇后回来对照。

| 维度 | vLLM | SGLang | Mooncake |
|------|------|--------|----------|
| **定位** | 推理引擎 | 推理引擎 | KV 基础设施（不做推理） |
| **KV 组织单位** | Block（定长 16 token）+ 哈希链 | RadixTree 节点（变长） | Object（`key → value`），key 通常是前缀哈希 |
| **前缀缓存作用域** | 单实例 GPU 显存 | 单实例 GPU 显存（+ HiCache 扩展） | **整个集群，跨实例、跨重启** |
| **淘汰机制** | `ref_cnt` 引用计数 + LRU | `lock_ref` + protected/evictable | **租约（lease）+ soft/hard pin + 水位淘汰** |
| **防止读中被删** | 引用计数 | `lock_ref` 加锁 | **读时授予租约**，租约内不可淘汰 |
| **跨节点传输** | KV Connector 插件（可插 Mooncake） | PD 分离内建 + HiCache L3 | **Transfer Engine 就是干这个的** |
| **存储层级** | GPU 显存（+ CPU offload） | L1 GPU / L2 Host（HiCache） | **L3 集群 DRAM + SSD + 3FS/SPDK** |
| **元数据管理** | 进程内 Python 数据结构 | 进程内 Python 数据结构 | **独立 Master 进程 + etcd 高可用** |
| **心跳/主循环** | `EngineCore.step()` | `Scheduler.event_loop_*()` | `WorkerPool::transferWorker()` 轮询 CQ |
| **实现语言** | Python + CUDA | Python + CUDA | **C++**（Python/Go/Rust 绑定） |

**最值得记住的一句**：vLLM 的 PagedAttention 和 SGLang 的 RadixAttention 解决的是「**单卡显存怎么省**」，Mooncake 解决的是「**整个集群的 KV 怎么共享**」。三者是叠加关系，不是替代关系。

## 八、编译与运行（最小可跑）

```bash
# 依赖（Ubuntu）
bash dependencies.sh

# 编译
mkdir build && cd build
cmake .. && make -j$(nproc)

# 或直接装 wheel（免编译，推荐初学者）
pip install mooncake-transfer-engine
```

最小验证（两个终端）：

```bash
# 终端 1：起 Master
mooncake_master --port 50051

# 终端 2：Python 里跑通 Put/Get
python -c "
from mooncake.store import MooncakeDistributedStore
store = MooncakeDistributedStore()
store.setup('127.0.0.1:12345', 'P2PHANDSHAKE',
            global_segment_size=256*1024*1024,
            local_buffer_size=64*1024*1024,
            protocol='tcp', master_server_addr='127.0.0.1:50051')
store.put('kvcache:demo', b'hello mooncake')
print(store.get('kvcache:demo'))
"
```

> 没有 RDMA 网卡也能跑：`protocol='tcp'`。`P2PHANDSHAKE` 表示不依赖 etcd，用点对点握手做元数据交换（详见 01 篇）。

### 9.2 该版本的几个重要背景

- **Transfer Engine 正在演进出 TENT 新实现**：`TransferEngine` 内部持有 `impl_`（旧）与 `impl_tent_`（新）两套后端，由环境变量 `MC_USE_TENT` 切换（`src/transfer_engine.cpp:370`）。本系列分析**默认的旧实现路径**，这也是目前生产在用的。
- **协议支持极其庞杂**：除 RDMA/TCP，还有 NVLink、CXL、NVMe-oF、EFA（AWS）、CXI（HPE）、Ascend（华为 NPU）、MACA（沐曦）、HIP（AMD）等十余种，全部由编译期宏控制（见 01 篇 `MultiTransport::installTransport`）。
- **多租户与配额是较新的特性**（`tenant_id.h`、`tenant_quota*.h`），本系列在 04 篇简要提及，不做深入。

## 十、必记要点

1. **Mooncake 不是推理引擎**，是 KV Cache 的「搬运工 + 仓库」。它和 vLLM/SGLang 是叠加关系。
2. **控制面与数据面分离**是它能扩展的根本：Master 只管元数据，数据走客户端点对点 RDMA。
3. **存储池由客户端捐献 DRAM 聚合而成**，没有独立存储服务器。
4. **两个核心模块**：Transfer Engine（怎么搬）+ Store（存哪里、谁在用）。
5. **相对 SGLang RadixCache 的关键增量**：前缀缓存从「单实例显存内」升级为「跨实例、跨重启、集群级」。
6. **租约（lease）机制**是它保证「读的时候数据不会被淘汰」的手段，对应 vLLM 的 `ref_cnt` / SGLang 的 `lock_ref`，但因为是分布式的，必须带 TTL。
