## 一、租约：分布式版的引用计数

### 1.1 问题：读到一半数据被淘汰了

回到统一示例 t3：D0 向 Master 查到「A 的 KV 在 P0 的 segment0 偏移 1024」，然后发起 RDMA READ。但这中间有个窗口：

```
D0: GetReplicaList(key) ──▶ Master 返回位置
                              │
                              │  ← ★ 此刻池子满了，Master 淘汰了这个对象，
                              │      P0 上那块内存被分配给了别的 key
                              ▼
D0: RDMA READ segment0+1024 ──▶ 读到【别人的数据】！
```

在 vLLM / SGLang 里这个问题不存在 —— 它们是单进程，`ref_cnt++` / `lock_ref++` 一加就锁住了。但 Mooncake 是分布式的：**读者在另一台机器上，可能崩溃、可能网络分区**。如果用纯引用计数，一个崩掉的读者会让对象**永久无法淘汰**。

**答案是租约（lease）：带 TTL 的引用计数。**

### 1.2 三层保护

`include/master_service.h:929-937`（挂在 Master 内存中的 `ObjectMetadata` 上）：

```cpp
        mutable SpinLock lock;
        // Default constructor, creates a time_point representing
        // the Clock's epoch (i.e., time_since_epoch() is zero).
        mutable std::chrono::system_clock::time_point lease_timeout
            GUARDED_BY(lock);  // hard lease
        mutable std::optional<std::chrono::system_clock::time_point>
            soft_pin_timeout GUARDED_BY(lock);  // optional soft pin, only
                                                // set for vip objects
        const bool hard_pinned{false};          // immutable, set at creation
```

三层是**并列**关系，不是递进：

| 机制 | 字段 | TTL 默认 | 语义 |
|------|------|---------|------|
| **硬租约** | `lease_timeout` | 10 秒 | 「有人正在读」，租约内**绝对不能淘汰** |
| **软钉** | `soft_pin_timeout` | 30 分钟 | 「这是重要对象」，**优先保留**但紧急时可淘汰 |
| **硬钉** | `hard_pinned` | 永久 | **永不淘汰**，创建时定死不可改 |

> **【C++】`mutable` 关键字**：允许在 `const` 成员函数里修改该字段。这里的用意是「授予租约在逻辑上不改变对象内容」，所以 `GrantLease()` 可以是 const 方法却仍能改 `lease_timeout`。`GUARDED_BY(lock)` 是 Clang 线程安全分析注解 —— 编译期检查「访问这个字段时是否持有 lock」，忘了加锁会编译警告。这是很值得学的工程实践。

配置成员（`master_service.h:1581-1584`）：

```cpp

    const uint64_t default_kv_lease_ttl_;     // in milliseconds
    const uint64_t default_kv_soft_pin_ttl_;  // in milliseconds
    const bool allow_evict_soft_pinned_objects_;
```

默认值集中在 `include/types.h:87-97`：


### 1.3 核心方法

`include/master_service.h:1097-1149`：

```cpp
        // Grant a lease with timeout as now() + ttl, only update if the new
        // timeout is larger
        void GrantLease(const uint64_t ttl, const uint64_t soft_ttl) const {
            SpinLocker locker(&lock);
            std::chrono::system_clock::time_point now =
                std::chrono::system_clock::now();
            lease_timeout =
                std::max(lease_timeout, now + std::chrono::milliseconds(ttl));
            //  【逻辑】★ std::max：租约只延长不缩短，并发续期安全
            if (soft_pin_timeout) {
                soft_pin_timeout =
                    std::max(*soft_pin_timeout,
                             now + std::chrono::milliseconds(soft_ttl));
            }
        }

        bool NeedsLeaseRefresh(const uint64_t ttl,
                               const uint64_t soft_ttl) const {
            SpinLocker locker(&lock);
            const auto now = std::chrono::system_clock::now();
            if (lease_timeout <= now + std::chrono::milliseconds(ttl / 2)) {
                return true;
                //  【逻辑】★ 剩余不足一半 TTL 才续期 —— 避免每次读都写元数据
            }
            return soft_pin_timeout &&
                   *soft_pin_timeout <=
                       now + std::chrono::milliseconds(soft_ttl / 2);
        }

        // Check if the lease has expired
        bool IsLeaseExpired() const {
            SpinLocker locker(&lock);
            return std::chrono::system_clock::now() >= lease_timeout;
        }
```

**三个设计细节**：

1. **`std::max` 保证租约单调不回退**。设想两个读者并发续期：读者 1 授予 `now+10s`，读者 2 稍慢一点授予 `now+9.9s`。如果直接赋值，读者 2 会把租约缩短，可能导致读者 1 的读被打断。用 `max` 就避免了。

2. **`NeedsLeaseRefresh` 用「剩余 < TTL/2」作为续期条件**，这是重要优化。热点对象每秒被读几千次，如果每次都更新 `lease_timeout`，就是几千次带锁写。加了这个门槛后，10 秒 TTL 内最多续期 2 次。**用「精度损失」换「写放大消除」。**

3. **`lease_timeout` 默认构造 = epoch（1970）**，意味着**新对象天生就是「租约已过期」状态**。这正是 02 篇 §5.4 里 `GrantLease(0, soft_ttl)` 那个 `0` 的配合 —— 刚写完的对象不给硬租约，因为没人在读。

### 1.4 完整时序

```
D0 要读 A 的 KV：
  │
  ├─ GetReplicaList(key)
  │    └─ Master 内部：
  │         ├─ 找到对象，检查 status == COMPLETE
  │         ├─ if (NeedsLeaseRefresh(ttl, soft_ttl))
  │         │      GrantLease(default_kv_lease_ttl_, default_kv_soft_pin_ttl_)
  │         │      ★ 现在 lease_timeout = now + 10s
  │         └─ 返回 Replica::Descriptor[]
  │
  ├─ RDMA READ（耗时 μs ~ ms，远小于 10 秒）
  │    ★ 这期间即使池子满了，淘汰逻辑看到 !IsLeaseExpired() 会跳过此对象
  │
  └─ 读完，什么都不用做 —— 租约会自己过期
     ★ 对比 vLLM：那边必须显式 ref_cnt--，忘了就泄漏
```

**【逻辑】「不需要显式释放」是租约相对引用计数的最大优势**：读者崩溃、超时、网络分区，都不会造成永久泄漏，最多浪费 10 秒。这是分布式系统里「故障是常态」这一假设的直接产物。

代价是**不精确**：读者读完了但租约还有 8 秒，这 8 秒对象白占位置。10 秒这个默认值就是在「保护足够」和「浪费不多」之间取的折中。

## 二、淘汰：什么时候淘汰谁

### 2.1 双水位触发

回顾 `types.h:92-93`：

```cpp
static constexpr double DEFAULT_EVICTION_RATIO = 0.05;
static constexpr double DEFAULT_EVICTION_HIGH_WATERMARK_RATIO = 0.90;
```

```
使用率
100% ┤
     │
 90% ┼━━━━━━━━━━━ eviction_high_watermark_ratio ← 超过就触发淘汰
     │     ↓ 一次淘汰 eviction_ratio = 5% 的量
 85% ┤ ────────── 淘汰后回到这里
     │
```

**【逻辑】和 03 篇的 offset 后端双水位（0.90 → 0.80）是同一个模式**，目的都是避免抖动：一次批量腾出 5% 空间，接下来一段时间不用再触发。

不同的是这里用「触发水位 + 淘汰比例」表达，03 篇用「高水位 + 低水位」表达 —— 两种等价写法。

### 2.2 淘汰候选的优先级

按可淘汰性从高到低：

| 优先级 | 对象特征 | 判断依据 |
|-------|---------|---------|
| 1（最先淘汰） | 无租约、无软钉 | `IsLeaseExpired() && !soft_pin_timeout` |
| 2 | 无租约、有软钉，且允许淘汰软钉对象 | `allow_evict_soft_pinned_objects_ == true` |
| 3（不淘汰） | **租约未过期** | `!IsLeaseExpired()` → 跳过 |
| 4（永不淘汰） | **硬钉** | `hard_pinned == true` → 跳过 |

**【逻辑】`allow_evict_soft_pinned_objects_` 默认为 `true` 的含义**：软钉是「优先保留」而非「保证保留」。当池子实在满了、优先级 1 的对象淘光了还不够，就会开始淘汰软钉对象 —— **宁可牺牲重要对象，也不能让写入失败**。

如果你的场景不能接受这个（某些对象必须常驻），要用 `with_hard_pin = true`（`ReplicateConfig`，见 02 篇 §2.5）。但 hard pin 用多了会导致池子无空间可用，写入直接失败 —— `types.h:117-119` 那个提示字符串就是为此准备的：

```cpp
constexpr const char* PUT_NO_SPACE_HELPER_STR =  // A helpful string
    " due to insufficient space. Consider lowering "
    "eviction_high_watermark_ratio or mounting more segments.";
```

**【逻辑】这种「错误信息里直接给出可执行建议」的做法值得学**：用户看到 "Put failed due to insufficient space. Consider lowering eviction_high_watermark_ratio or mounting more segments." 就知道该干什么，不用去翻文档。

### 2.3 淘汰策略：LRU 与 FIFO

`include/eviction_strategy.h:16-41` 定义抽象：

```cpp
/**
 * @brief Abstract interface for eviction strategy, responsible for choosing
 *        which kvcache object to be evicted before pool overflow.
 * 【中译】淘汰策略抽象接口，负责在池子溢出前选出要淘汰的 kvcache 对象。
 */
class EvictionStrategy : public std::enable_shared_from_this<EvictionStrategy> {
   public:
    virtual ~EvictionStrategy() = default;
    virtual ErrorCode AddKey(const std::string& key) = 0;
    virtual ErrorCode UpdateKey(const std::string& key) = 0;
    virtual ErrorCode RemoveKey(const std::string& key) {
        // Remove key from the list and map
        auto it = all_key_idx_map_.find(key);
        if (it != all_key_idx_map_.end()) {
            all_key_list_.erase(it->second);      // 【逻辑】O(1) 从链表摘除
            all_key_idx_map_.erase(it);
        }
        return ErrorCode::OK;
    }
    virtual std::string EvictKey(void) = 0;
    virtual size_t GetSize(void) { return all_key_list_.size(); }

   protected:
    std::list<std::string> all_key_list_;                    // 【逻辑】★ 双向链表
    std::unordered_map<std::string, std::list<std::string>::iterator>
        all_key_idx_map_;                                    // 【逻辑】★ key → 链表位置
};
```

**【逻辑】`list` + `unordered_map<key, list::iterator>` 是实现 O(1) LRU 的经典组合**：
- 链表维护顺序（头部最热、尾部最冷）；
- 哈希表存「每个 key 在链表中的位置」，使得「把某个 key 移到头部」不需要 O(n) 查找。

这是 LeetCode 146 的标准解法，也是所有生产 LRU 缓存的底层结构。

`LRUEvictionStrategy`（`:43-77`）：

```cpp
class LRUEvictionStrategy : public EvictionStrategy {
   public:
    virtual ErrorCode AddKey(const std::string& key) override {
        // Add key to the front of the list
        if (all_key_idx_map_.find(key) != all_key_idx_map_.end()) {
            all_key_list_.erase(all_key_idx_map_[key]);   // 【逻辑】已存在则先摘除
            all_key_idx_map_.erase(key);
        }
        all_key_list_.push_front(key);                    // 【逻辑】插到最热端
        all_key_idx_map_[key] = all_key_list_.begin();
        return ErrorCode::OK;
    }

    virtual ErrorCode UpdateKey(const std::string& key) override {
        // Move the key to the front of the list
        auto it = all_key_idx_map_.find(key);
        if (it != all_key_idx_map_.end()) {
            all_key_list_.erase(it->second);
            all_key_list_.push_front(key);                // 【逻辑】★ 被访问 → 移到最热端
            all_key_idx_map_[key] = all_key_list_.begin();
        }
        return ErrorCode::OK;
    }

    virtual std::string EvictKey(void) override {
        // Evict the last key in the list
        if (all_key_list_.empty()) { return ""; }
        std::string evicted_key = all_key_list_.back();   // 【逻辑】★ 淘汰最冷端
        all_key_list_.pop_back();
        all_key_idx_map_.erase(evicted_key);
        return evicted_key;
    }
};
```

另有 `FIFOEvictionStrategy`（`:79`），区别是 `UpdateKey` 什么都不做（访问不改变顺序，纯按插入顺序淘汰）。

**【逻辑】KV Cache 场景该选哪个？** 一般 LRU 更优：前缀缓存有明显的时间局部性（同一段 system prompt 会被连续多个请求命中）。FIFO 的优势是开销更低（无需在读路径上改链表），适合读极多写极少、且访问模式接近随机的场景。

> **【C++】`class X : public std::enable_shared_from_this<X>`**
> 这让类的成员函数内部能安全地获取指向自己的 `shared_ptr`（通过 `shared_from_this()`）。为什么需要它？直接 `shared_ptr<X>(this)` 会创建**第二个独立的引用计数**，导致对象被析构两次。`enable_shared_from_this` 让对象共享原有的引用计数块。这是 C++ 智能指针的一个经典陷阱点。

### 2.4 客户端失联的 segment 回收

`types.h:97`：

```cpp
static constexpr int64_t DEFAULT_CLIENT_LIVE_TTL_SEC = 10;       // in seconds
```

客户端要定期 `Ping(client_id)`（`master_service.h:617`）。超过 10 秒没心跳，Master 认为它挂了，会：

1. 把它 mount 的所有 segment 标记不可用；
2. 这些 segment 上的所有副本标记失效；
3. 只剩这一个副本的对象 → 从元数据里移除。

**【逻辑】这是「捐献式存储池」的必然代价**：存储节点就是计算节点，计算节点重启（滚动升级、OOM、驱逐）就意味着存储容量波动。所以 Mooncake 从设计上就假定「segment 随时会消失」—— 这也是为什么它对 KV Cache 这种「丢了能重算」的数据合适，而不适合当通用持久存储。

## 三、Master 高可用

Master 是单点：它挂了，整个池子的元数据就没了。所以必须有高可用。

| 后端 | 选主机制 | 适用 |
|------|---------|------|
| **etcd** | etcd 租约 + CAS 写入 leader key | 通用，最常见 |
| **redis** | Redis SETNX + 过期 | 已有 Redis 的环境 |
| **k8s** | **`coordination.k8s.io/Lease` 对象**（`include/k8s_lease_helper.h`） | K8s 部署，无需额外组件 |

**【逻辑】K8s Lease 这个选项对云原生部署非常友好**：不用再单独部署 etcd 集群，直接用 K8s APIServer 背后的 etcd。这和 kube-scheduler / controller-manager 自己的选主机制完全一致 —— 如果你读过本仓库的 [kube-scheduler 系列](../../scheduling/kube-scheduler/00-kube-scheduler总览与架构.md)，会觉得非常熟悉。

**注意：Mooncake 没有用 Raft。** 它把一致性问题外包给了 etcd / Redis / K8s，自己只做「谁是 leader」的租约竞争。这是明智的工程决策 —— 自己实现 Raft 是巨大的复杂度和 bug 来源。

### 3.2 MasterView：view 版本号

`ViewVersionId` 在 etcd 后端下就是 etcd revision（`types.h:192-199`）：


> **【C++】`GoInt64`** 来自 `libetcd_wrapper.h` —— **Mooncake 的 etcd 客户端是用 Go 写的**，通过 cgo 编译成 C 库再链进 C++。原因是 etcd 官方只有 Go 客户端最完善（C++ 的 etcd-cpp-apiv3 依赖 gRPC，很重）。这是「用 cgo 桥接生态」的实用做法。

**【逻辑】`view_version` 的作用是防「脑裂」**：老 leader 因为 GC 停顿被误判为死亡，新 leader 上任（view_version + 1）。老 leader 恢复后仍以为自己是 leader，继续处理请求 —— 但客户端会发现它的 view_version 比新 leader 小，拒绝它的响应。**这是 Raft term 的同等机制。**

**【逻辑】`observed_view` 的设计很贴心**：竞选失败不是简单返回 false，而是**告诉你现在谁是 leader** —— standby 节点可以立刻转向跟随，不用再查一次。

### 3.4 Master 运行状态机

`ha_types.h:118-144`，这是理解 Master 生命周期的关键：

```cpp
enum class MasterRuntimeState {
    kStarting,       // 启动中
    kStandby,        // 备用（跟随 leader）
    kCandidate,      // 竞选中
    kRecovering,     // 从 snapshot 恢复
    kCatchingUp,     // 追 oplog 增量
    kLeaderWarmup,   // 当选后预热（等客户端 ReMount）
    kServing,        // ★ 正常服务
};
```

状态流转：

```
kStarting
   │
   ▼
kStandby ◀────────────────────┐
   │  发现 leader 租约过期      │ 竞选失败（CONTENDED）
   ▼                          │
kCandidate ───────────────────┘
   │ 竞选成功（ACQUIRED）
   ▼
kRecovering    ← 加载最近的 snapshot
   │
   ▼
kCatchingUp    ← 重放 snapshot 之后的 oplog
   │
   ▼
kLeaderWarmup  ← ★ 等各客户端 ReMountSegment 重新登记
   │
   ▼
kServing       ← 开始正常处理请求
```

**【逻辑】`kLeaderWarmup` 这个状态是 Mooncake 特有的**，Raft 里没有对应物。原因是：Master 恢复元数据后，**还需要知道「哪些 segment 现在真的可用」**。这个信息只有客户端知道（客户端可能在切主期间重启过）。所以要等一轮客户端心跳 + ReMount，才能确保元数据与实际状态一致。

如果跳过这一步直接服务，可能把对象分配到一个已经消失的 segment 上。

### 3.5 元数据持久化：oplog + snapshot

`include/ha/` 目录结构：

```

├── leadership/             # 选主（etcd / redis / k8s lease 三套实现）

```

相关组件与配置：

| 组件 | 头文件 | 作用 |
|------|-------|------|
| `MasterSnapshotManager` | `include/master_snapshot_manager.h` | 定期把全量元数据落盘 |
| `MasterSnapshotRepository` | `include/master_snapshot_repository.h` | 快照文件的存取与保留策略 |

快照相关默认值（`types.h:101-108`）：

```cpp
static constexpr uint64_t DEFAULT_SNAPSHOT_INTERVAL_SEC =
    60 * 10;  // in seconds                           【逻辑】10 分钟一次全量快照
static constexpr uint64_t DEFAULT_SNAPSHOT_CHILD_TIMEOUT_SEC =
    60 * 5;   // in seconds                           【逻辑】★ 子进程超时
static constexpr uint32_t DEFAULT_SNAPSHOT_RETENTION_COUNT =
    2;        // Keep 2 recent snapshots by default   【逻辑】保留最近 2 个
static const std::string DEFAULT_SNAPSHOT_BACKUP_DIR = "";
constexpr const char* DEFAULT_CLUSTER_ID = "mooncake_cluster";
```

**【逻辑】`SNAPSHOT_CHILD_TIMEOUT` 里的 "child" 暗示快照是 fork 子进程做的**（类似 Redis BGSAVE）。好处是主进程不阻塞（利用 COW 写时复制）；代价是 fork 瞬间可能内存翻倍。5 分钟超时是防止子进程卡死。

**oplog + snapshot 的经典组合**：
- snapshot 是**全量**但**低频**（10 分钟），恢复时作为起点；
- oplog 是**增量**但**高频**（每次写操作），恢复时重放 snapshot 之后的部分。

对应 3.4 状态机里的 `kRecovering`（加载 snapshot）→ `kCatchingUp`（重放 oplog）两步。

### 3.6 cluster_id 的注入防护

`types.h:70-86` 有一段值得单独说的安全代码：

```cpp
// Cluster ID validation utilities.
//
// cluster_id is used to construct etcd key prefixes (e.g.
// "/oplog/<cluster_id>/..."). To avoid key-prefix injection / accidental
// cross-cluster overlap, we restrict the allowed characters to a conservative
// safe set.
// 【中译】cluster_id 用于构造 etcd key 前缀（如 "/oplog/<cluster_id>/..."）。
//    为避免 key 前缀注入 / 意外的跨集群重叠，我们把允许字符限制在保守的安全集合内。
inline bool IsValidClusterIdComponent(const std::string& cluster_id) {
    if (cluster_id.empty()) { return false; }
    if (cluster_id.size() > 128) { return false; }
    for (unsigned char c : cluster_id) {
        const bool ok = (c >= '0' && c <= '9') || (c >= 'A' && c <= 'Z') ||
                        (c >= 'a' && c <= 'z') || c == '_' || c == '-' ||
                        c == '.';
        if (!ok) { return false; }
    }
    return true;
}
```

**【逻辑】这是「路径注入」防护的教科书示例**。如果不校验，一个 `cluster_id = "../other_cluster"` 就能让 A 集群写到 B 集群的 key 空间下 —— 相当于 etcd 版的目录穿越。作者用**白名单**（只允许字母数字和 `_-.`）而不是黑名单（禁止 `../`），这是正确的做法：白名单不会遗漏未知的攻击变体。

**顺带一提，这也是我们自己写代码时该有的习惯**：任何用户输入拼进「路径、key 前缀、SQL、命令行」之前，都要先白名单校验。

## 四、客户端如何感知切主

```
客户端定期 Ping(client_id)
  │
  └─ 响应里带 PingResponse { view_version, ... }
       │
       ├─ view_version 与本地一致 → 一切正常
       │
       └─ view_version 变大了 → ★ 发生过切主
            ├─ 重新解析新 leader 地址
            ├─ 重连 MasterClient
            └─ ReMountSegment(自己的所有 segment)   ← 对应 Master 的 kLeaderWarmup
```

Master 视图租约（`types.h:96`）：

```cpp
static constexpr int64_t DEFAULT_MASTER_VIEW_LEASE_TTL_SEC = 5;  // in seconds
```

**【逻辑】5 秒 master view 租约 vs 10 秒客户端心跳**：leader 每 < 5 秒续一次自己的租约；如果它挂了，5 秒后租约过期，standby 开始竞选。整个切主的可观测中断时间大约是「5 秒（发现）+ 恢复时间 + warmup」。

**这段时间内数据面并不受影响**：正在进行的 RDMA 传输不经过 Master，照常完成。只有需要新 `Put`/`Get` 元数据的操作会阻塞或失败重试。**这是控制面/数据面分离的又一个红利。**

## 五、多租户与配额（简述）

该版本新增了多租户支持，相关头文件：

| 头文件 | 作用 |
|-------|------|
| `tenant_id.h` | `TenantId` 类型与校验 |

| `tenant_quota_policy_store.h` | 配额策略存储 |
| `tenant_quota_sharded.h` / `_impl.h` | 分片配额计数（避免单点热锁） |

在 02 篇 §5.3 的 `PutStart` 里能看到它的痕迹：

```cpp
    auto normalized_tenant_result = ResolveTenantIdForWrite(tenant_id);
    // ...
    const uint64_t requested_quota_charge =
        RequestedMemoryQuotaCharge(slice_length, config);
```

**【逻辑】「分片配额」（sharded quota）解决的是热点锁问题**：如果所有租户的配额计数都在一个原子变量上，高并发下这个变量会成为 cache line 争抢的热点。分片后每个 shard 独立计数，只在需要精确总量时才汇总。这是高并发计数器的标准优化（对比 Java 的 `LongAdder`）。

本系列不深入这部分，因为 KV Cache 场景通常单租户。

最后两个值得注意（`types.h:120-122`）：

```cpp
static constexpr uint64_t DEFAULT_PUT_START_DISCARD_TIMEOUT = 30;  // 30 seconds
static constexpr uint64_t DEFAULT_PUT_START_RELEASE_TIMEOUT =
    600;  // 10 minutes
```

**【逻辑】这是两阶段写入的「悬挂事务」兜底**：客户端调了 `PutStart` 拿到空间，但还没 `PutEnd` 就崩了 —— 这块空间会一直是 `INITIALIZED` 状态占着。30 秒后丢弃、10 分钟后强制释放，就是防止这种泄漏。

**任何两阶段协议都必须有这个超时兜底**，否则参与者故障会导致资源永久锁定。这和数据库的事务超时、TCC 的悬挂补偿是同一类问题。

## 七、与 vLLM / SGLang 的对照

| 机制 | vLLM | SGLang | Mooncake |
|------|------|--------|----------|
| 「正在用」保护 | `ref_cnt++/--` | `lock_ref++/--` | **租约（TTL 10s，无需显式释放）** |
| 忘记释放的后果 | 永久泄漏 | 永久泄漏 | **最多浪费 10 秒** |
| 淘汰策略 | LRU（free block 队列） | LRU（evictable 叶子节点） | **LRU / FIFO 可选 + 三层 pin** |
| 淘汰触发 | 分配失败时 | 分配失败时 | **水位触发（0.90 → 淘 5%）** |
| 元数据持久化 | ✗ | ✗ | **✓ oplog + snapshot** |
| 高可用 | 不适用（单进程） | 不适用（单进程） | **✓ etcd / Redis / K8s Lease 选主** |
| 脑裂防护 | 不适用 | 不适用 | **✓ view_version（≈ Raft term）** |

**核心差异的根源只有一句话**：vLLM / SGLang 的缓存元数据活在**一个进程的内存**里，进程即边界，不存在故障中间态；Mooncake 的元数据要跨进程、跨节点、跨重启，所以必须引入租约、水位、选主、持久化这一整套分布式机制。

**这也解释了为什么不该「把 Mooncake 的机制照搬进 vLLM」** —— 在单进程内引入 TTL 租约只会带来无谓的不精确和开销。**机制要匹配故障模型。**

## 九、必记要点

1. **租约 = 带 TTL 的引用计数**，解决分布式环境下「持有者可能永久消失」的问题。读者无需显式释放。
2. **三层保护并列**：硬租约（10 s，绝对不淘汰）/ 软钉（30 min，优先保留但可让）/ 硬钉（永不淘汰）。
3. **`GrantLease` 用 `std::max` 保证租约单调不回退**，并发续期安全。
4. **`NeedsLeaseRefresh` 用「剩余 < TTL/2」门槛**避免热点对象的写放大。
5. **新对象天生「租约已过期」**（`lease_timeout` 默认 epoch），配合 `PutEnd` 里的 `GrantLease(0, ...)`。
6. **淘汰双水位（0.90 触发，淘 5%）** 避免抖动 —— 与 03 篇 offset 后端同模式。
7. **`allow_evict_soft_pinned_objects` 默认 true**：软钉是「优先保留」不是「保证保留」。
8. **LRU 用 `list` + `map<key, iterator>` 实现 O(1)**。
9. **客户端失联 10 秒 → 其 segment 全部失效**，这是捐献式存储池的必然代价。
10. **Master 高可用不用 Raft**，把一致性外包给 etcd / Redis / K8s Lease，自己只竞争 leader 租约。
11. **`view_version` 相当于 Raft term**，防止老 leader 脑裂。
12. **状态机有 `kLeaderWarmup` 这一步**：恢复元数据后还要等客户端 ReMount 才能确认 segment 真实可用。
13. **oplog（增量高频）+ snapshot（全量低频，fork 子进程）** 的经典组合。
14. **切主期间数据面不受影响**（RDMA 不经过 Master），只有元数据操作会短暂失败。
15. **两阶段写入必须有超时兜底**（30 s 丢弃 / 600 s 强制释放），否则客户端崩溃会永久锁定空间。
16. **`cluster_id` 用白名单校验防 key 前缀注入** —— 值得抄进自己的代码习惯。
