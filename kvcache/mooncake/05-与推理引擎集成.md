## 一、两种截然不同的接法

Mooncake 接入推理引擎有两条完全不同的路径，混淆它们是最常见的困惑来源：

| | **路径 A：PD 分离传输** | **路径 B：共享 KV 池** |
|--|----------------------|---------------------|
| 用到的 Mooncake 模块 | **只有 Transfer Engine**（01 篇） | **Transfer Engine + Store**（01+02+03+04 篇） |
| vLLM 侧组件 | `MooncakeConnector` | `MooncakeStoreConnector` |
| SGLang 侧组件 | PD 分离内建后端 | **HiCache L3 backend** |
| 需要 Master 进程吗 | **不需要** | **需要**（`mooncake_master`） |
| 数据流向 | Prefill 实例 → **直接** → Decode 实例 | 实例 → **池子** → 任意实例 |
| 解决什么问题 | 「KV 怎么从 P 送到 D」 | 「前缀缓存怎么跨实例、跨重启共享」 |
| 统一示例对应 | t3（A 的 KV 送到 D0） | t2 / t4（存进池子、B 命中前缀） |

**【逻辑】关键区别在于「有没有中间落脚点」**：
- 路径 A 是**点对点直传**：P0 算完直接推给 D0，KV 不在任何地方停留。像快递直送。
- 路径 B 是**经过仓库**：P0 存进池子，谁需要谁来取，还能存很久。像快递入库。

两者**可以同时启用**（vLLM 的 `MultiConnector` 就是干这个的），也确实推荐同时用：PD 分离解决当前请求的流转，共享池解决历史前缀的复用。

## 二、路径 A：vLLM PD 分离（MooncakeConnector）

### 2.1 vLLM KV Connector 接口

vLLM v1 定义了 `KVConnectorBase_V1` 抽象，Mooncake 实现它。核心方法（vLLM 侧定义，Mooncake 侧实现）：

| 方法 | 时机 | Mooncake 的动作 |
|------|------|----------------|
| `register_kv_caches(kv_caches)` | 引擎启动，KV 池分配完 | ★ 调 `TransferEngine::registerLocalMemory()` 把 GPU KV 池注册给 RDMA |
| `get_num_new_matched_tokens()` | 调度前 | 查询远端有多少 token 的 KV 可用 |
| `start_load_kv()` | Decode 侧，前向前 | 发起 RDMA READ 把 KV 拉过来 |
| `wait_for_layer_load()` | 逐层等待 | 轮询该层 KV 是否到位（支持层级流水） |
| `save_kv_layer()` | Prefill 侧，每层算完 | ★ 该层 KV 算完立刻发出去（**不等整个前向结束**） |
| `wait_for_save()` | Prefill 侧，前向后 | 确认全部发送完成 |
| `get_finished()` | 每步 | 返回已完成收/发的请求 ID |

**【逻辑】`save_kv_layer` 的「逐层发送」是性能关键**。朴素做法是等 28 层全算完再一次性发 1.8 GB，那么「计算」和「传输」完全串行：

```
朴素： [────── 28 层前向计算 ──────][──── 传 1.8GB ────]   总耗时 = 计算 + 传输

逐层： [层0][层1][层2]...[层27]
            [传0][传1]...      [传27]                     总耗时 ≈ max(计算, 传输) + 一层
```

**逐层发送让传输与计算重叠**，总耗时从「计算+传输」降到约「max(计算, 传输)」。这和 01 篇 Transfer Engine 的异步接口（`submitTransfer` 提交后立即返回）是配套设计 —— 正因为传输是异步的，才能边算边发。

### 2.2 注册 GPU KV 池：零拷贝的前提

`register_kv_caches` 这一步最值得理解。vLLM 的 KV 池是一大块 GPU 显存，Mooncake 要把它**整块注册给 RDMA 网卡**：

```python
# 概念代码：Mooncake connector 在 register_kv_caches 里做的事
for layer_name, kv_tensor in kv_caches.items():
    engine.register_memory(
        kv_tensor.data_ptr(),          # GPU 显存地址
        kv_tensor.numel() * kv_tensor.element_size(),
        location="cuda:0",             # ★ 位置标签，供 Topology 选网卡（01 篇 §5.3）
    )
```

注册之后，**网卡可以直接 DMA 读写 GPU 显存**（GPUDirect RDMA），KV 数据从 P0 的 GPU 直达 D0 的 GPU，全程不经过 CPU 内存。这就是「零拷贝」的完整含义。

**【逻辑】`location="cuda:0"` 这个标签在这里终于闭环了**：01 篇讲 Topology 亲和矩阵时说「按内存位置选最近的网卡」，这个「位置」就是这里传进去的。GPU 0 的 KV 会用与 GPU 0 同 PCIe switch 的网卡发送 —— 如果标签传错，性能会莫名腰斩。

### 2.3 部署配置

单机双实例最小配置：

```bash
# Prefill 实例（生产者）
vllm serve Qwen/Qwen2.5-7B-Instruct --port 8100 \
  --kv-transfer-config '{"kv_connector":"MooncakeConnector","kv_role":"kv_producer"}'

# Decode 实例（消费者）
vllm serve Qwen/Qwen2.5-7B-Instruct --port 8200 \
  --kv-transfer-config '{"kv_connector":"MooncakeConnector","kv_role":"kv_consumer"}'

# 代理（把请求先送 P 再送 D）
python disagg_proxy.py \
  --prefiller-host 192.168.0.2 --prefiller-port 8010 \
  --decoder-host 192.168.0.3 --decoder-port 8020
```

关键参数（来自 `docs/source/deployment/integrations/vllm/disagg-prefill-decode.md`）：

| 参数 | 说明 |
|------|------|
| `kv_role` | `kv_producer`（prefill 侧）/ `kv_consumer`（decode 侧）/ `kv_both`（两者兼任） |
| `num_workers` | 「Thread pool size in each prefiller worker to send kvcache (default 10)」—— prefill 侧发送线程池大小 |

**性能参考**（官方文档数据）：「achieving up to **142.25 GB/s** peak bandwidth (71.1% utilization of 8x RoCE)」—— 8 张 RoCE 卡打到 71% 利用率。这个数字印证了 01 篇讲的多网卡聚合 + Topology 亲和确实有效（如果选网卡是随机的，跨 NUMA 会让利用率掉到 30% 以下）。

## 三、路径 B-1：vLLM 共享 KV 池（MooncakeStoreConnector）

### 3.1 它解决什么

`docs/source/deployment/integrations/vllm/kv-cache-storage.md` 的 Overview 说得很清楚：

> This guide demonstrates how to use `MooncakeStore` / `MooncakeStoreConnector` with vLLM to build a distributed KV cache storage pool. It enables KV cache offloading to CPU/SSD, **hash-based prefix caching across multiple vLLM instances**, and flexible **XpYd** disaggregated deployment — where you can dynamically adjust prefill and decode group sizes at runtime.
>
> 【中译】本指南演示如何用 `MooncakeStore` / `MooncakeStoreConnector` 与 vLLM 构建分布式 KV 缓存池。它支持 KV 卸载到 CPU/SSD、**跨多个 vLLM 实例的哈希前缀缓存**、以及灵活的 **XpYd** 分离部署 —— 可在运行时动态调整 prefill 与 decode 组的大小。
>
> Compared to Redis-based backends, MooncakeStore achieves significantly lower TTFT (e.g., **~32% improvement** in mean TTFT for 2P2D tp=2 under RDMA).
>
> 【中译】相比基于 Redis 的后端，MooncakeStore 的 TTFT 显著更低（如 2P2D tp=2 在 RDMA 下平均 TTFT 改善约 32%）。

**三个能力对应到前面的篇目**：
1. 「offloading to CPU/SSD」→ 03 篇分层存储；
2. 「hash-based prefix caching across instances」→ 02 篇的 `key = hash(前缀)`，这是**相对 SGLang RadixCache 的核心增量**；
3. 「XpYd 动态调整」→ 因为 KV 在共享池而非绑定在某个实例上，P 和 D 的数量可以随时变。

**【逻辑】「相比 Redis 快 32%」这个对比很有价值**：Redis 也能当 KV 池，但它的数据面走 TCP + 内核协议栈 + Redis 单线程模型；Mooncake 走 RDMA 点对点 + 元数据/数据面分离。**这 32% 就是 Transfer Engine 那一整套设计的变现。**

### 3.2 版本对应

| vLLM 版本 | Connector 名 | 状态 |
|----------|-------------|------|
| **V1** | `MooncakeStoreConnector` | **推荐** |
| V0（≤ v0.6.4.post1） | `MooncakeStore` | Legacy，仅维护存量部署 |


**② 写配置文件** `mooncake_config.json`：

```json

  "metadata_server": "P2PHANDSHAKE",
  "protocol": "rdma",
  "device_name": "mlx5_0,mlx5_1",
  "master_server_address": "127.0.0.1:50051",
  "global_segment_size": 17179869184,
  "local_buffer_size": 1073741824

```

这些字段直接对应 02 篇 §3.1 的 `setup_real()` 参数。

**③ 启动 vLLM**：

```bash

vllm serve Qwen/Qwen2.5-7B-Instruct --port 8000 \

```

**注意 `kv_role: kv_both`** —— 共享池场景下每个实例既写也读（既是生产者也是消费者），这与 PD 分离的单向角色不同。

### 3.4 两条路径同时启用：MultiConnector

`docs/.../vllm-mooncakestoreconnector.md:81-116` 展示了怎么叠加：

```jsonc
// Prefill 实例
{
    "kv_connector": "MultiConnector",
    "kv_role": "kv_producer",
    "kv_connector_extra_config": {
        "connectors": [
            { "kv_connector": "MooncakeConnector",      "kv_role": "kv_producer" },
            { "kv_connector": "MooncakeStoreConnector", "kv_role": "kv_producer" }
        ]
    }
}

// Decode 实例
{
    "kv_connector": "MultiConnector",
    "kv_role": "kv_consumer",
    "kv_connector_extra_config": {
        "connectors": [
            { "kv_connector": "MooncakeConnector",      "kv_role": "kv_consumer" },
            { "kv_connector": "MooncakeStoreConnector", "kv_role": "kv_consumer" }
        ]
    }
}
```

**【逻辑】这个组合是生产推荐姿势**：
- `MooncakeConnector`（路径 A）负责**当前请求**的 P→D 直传，延迟最低；
- `MooncakeStoreConnector`（路径 B）负责**历史前缀**的持久化共享，命中率最高。

两者互补：直传解决「这一次」，共享池解决「下一次」。

## 四、路径 B-2：SGLang HiCache L3

这是本篇最值得细读的部分，因为它与本仓库 [SGLang 06 篇 RadixCache](../../inference-engine/sglang/06-RadixCache深度剖析.md) 直接衔接。

### 4.1 三级缓存的类比

`docs/source/design/hicache-design.md:11` 用了一个绝妙的类比：

> In many modern CPU architectures, the small but fast L1 and L2 caches are private to each core, enabling rapid access to the hottest data, while the larger L3 cache is shared across all cores to significantly reduce redundancy within the cache. Similarly, in HiCache, the L1 and L2 KV caches are private to each inference instance, whereas **the L3 KV cache is shared among all inference instances within the cluster**.
>
> 【中译】在现代 CPU 架构中，小而快的 L1/L2 缓存是每个核心私有的，用于快速访问最热数据；而更大的 L3 缓存被所有核心共享，以显著减少缓存内的冗余。类似地，在 HiCache 中，L1 和 L2 KV 缓存是每个推理实例私有的，而 **L3 KV 缓存被集群内所有推理实例共享**。

```
        ┌─────────────────────────────────────────────────┐
        │  L1 = GPU 显存      （实例私有，RadixTree 节点） │  ← SGLang 06 篇
        │  L2 = Host 内存     （实例私有，HiRadixTree 标记）│  ← HiCache 扩展
        ├─────────────────────────────────────────────────┤
        │  L3 = Mooncake      （★ 集群共享）              │  ← 本系列 02/03 篇
        └─────────────────────────────────────────────────┘
```

**【逻辑】这个类比精确的地方在于「共享消除冗余」**：CPU 的 L3 共享是为了避免同一份数据在多个核心的 L2 里各存一份；HiCache 的 L3 共享同理 —— 100 个实例都在处理带相同 system prompt 的请求，如果各存一份，浪费 99 份内存。

### 4.2 HiRadixTree：RadixTree 的分层扩展

`hicache-design.md:19` 解释了元数据组织：

> HiRadixTree extends this idea: each node corresponds to the KV cache of a span of consecutive tokens and **records where that KV cache is stored**—whether in local GPU memory, CPU memory, L3 storage, or multiple of these tiers. If stored locally, HiRadixTree maintains precise metadata, including the exact storage address. However, to reduce overhead, **HiRadixTree does not store or continuously synchronize metadata for L3 KV cache. Instead, when accessing L3 data, it queries the backend in real time**.
>
> 【中译】HiRadixTree 扩展了这一思想：每个节点对应一段连续 token 的 KV，并**记录该 KV 存储在哪里** —— 本地 GPU 内存、CPU 内存、L3 存储，或其中多层。若存在本地，HiRadixTree 维护精确元数据（含确切地址）。但为降低开销，**HiRadixTree 不存储也不持续同步 L3 的元数据，而是在访问 L3 时实时查询后端**。

**【逻辑】「不同步 L3 元数据，实时查询」是一个重要的架构决策**，值得展开：

- **如果同步**：每个实例都要维护「全集群哪些前缀在 L3」的视图。100 个实例 × 频繁变动 = 元数据同步风暴，而且必然有一致性延迟（查到的可能已被淘汰）。
- **实时查询**：多一次 RPC（~100 μs），但视图永远准确，且**零同步开销**。

因为 prefetch 本身就是异步的（不在关键路径上），多 100 μs 完全可以接受。**这是「用一次查询延迟换掉整套同步机制」的典型权衡** —— 对照 02 篇的 `batch_query`（只取元数据不取数据），那个接口就是为这里设计的。

### 4.3 三个核心操作

`hicache-design.md:23`：

> The workflow of HiCache mainly involves three key operations: **local match**, **prefetch** and **write-back**.

```
请求到达
  │
  ├─① Local match：在本地 HiRadixTree 匹配 L1/L2
  │     └─ 纯内存遍历，不拷数据，极快
  │        返回：前一段在 L1，后一段在 L2
  │
  ├─② Prefetch from L3：本地没匹配上的部分，问 Mooncake
  │     ├─ batch_query() 查 L3 命中多少 token         ← 02 篇 §7.1
  │     ├─ 命中 > 阈值（默认 256 token）才触发预取
  │     └─ batch_get_into() 用 RDMA 并行从多节点拉    ← 01 篇
  │
  ├─③ GPU 前向：L1 + 已取到的数据 → prefill，剩余部分重算
  │
  └─④ Write-back：新算出的 KV 往下写（L1 → L2 → L3）
```

### 4.4 Prefetch 的三种终止策略（调优核心）

`hicache-design.md:49-52` 提出了一个本质问题：

> Prefetching operations face a fundamental challenge of timing uncertainty: **how long should we wait for the prefetch operation before proactively terminating it?** ... If the waiting time is too long, prefill computation will be significantly delayed. Conversely, if the waiting time is too short, the prefetch operation may be terminated before completion, preventing the use of prefetched results and wasting computation and I/O overhead.
>
> 【中译】预取面临一个根本性的时序不确定难题：**应该等多久才主动终止预取？** 等太久，prefill 计算被显著延迟；等太短，预取可能在完成前被终止，结果无法使用，白白浪费计算和 IO 开销。

三种策略：

| 策略 | 行为 | 适用 |
|------|------|------|
| `best_effort` | GPU 一能算就立刻终止，零等待 | 极端延迟敏感 |
| `wait_complete` | 必须等全部预取完成 | 要求高命中率 |
| **`timeout`** | 超时或完成即止 | **推荐**，平衡两者 |

超时公式（`hicache-design.md:61-65`）：

```
timeout = prefetch_timeout_base + prefetch_timeout_per_ki_token * num_token_to_fetch / 1024
```

- `prefetch_timeout_base`：与 token 数无关的固定开销（调度、同步）；
- `prefetch_timeout_per_ki_token`：每千 token 的增量时间。

**【逻辑】这个线性模型的合理性**：预取耗时 ≈ 固定开销 + 数据量/带宽。数据量与 token 数成正比，所以「基础 + 每千 token 增量」能较好拟合。取 8K token 和 128K token 用同一个固定超时显然不合理 —— 前者会被判超时太宽松，后者太严苛。

官方结论（`hicache-design.md:66`）：

> We find that in real-world deployments, the `timeout` strategy tends to be more practical. On one hand, prefetch latency is inherently unpredictable; on the other hand, **the prefetch deadline is constrained by the Service Level Objective (SLO)**.
>
> 【中译】实践中 `timeout` 策略更实用。一方面预取延迟本身不可预测；另一方面**预取的截止时间受 SLO 约束**。

### 4.5 Write-back 的三种策略

`hicache-design.md:73-77`：

| 策略 | 行为 | 权衡 |
|------|------|------|
| `write_through` | 每次访问立刻写回下一级 | 「When bandwidth is sufficient, this strategy provides the strongest caching benefit」—— 带宽够时收益最大 |
| `write_through_selective` | 访问频率超阈值才写回 | 「backs up only hot data, reducing I/O overhead」—— 只备份热数据 |
| `write_back` | 只在从上层被淘汰时才写回下一级 | 「alleviates storage pressure」—— 缓解存储压力 |

**【逻辑】这三种策略正是操作系统/CPU 缓存的经典三态**（write-through / write-back），HiCache 加了个 selective 中间档。选择依据：

- 网络带宽富裕（RDMA 多卡）→ `write_through`，最大化后续命中；
- 带宽紧张或 L3 容量小 → `write_back`，只在必要时写；
- 折中 → `write_through_selective`。

**注意这个选择与 04 篇的淘汰机制是耦合的**：如果用 `write_back`，L1/L2 淘汰时才写 L3，那么 L3 的写入是突发的（一批淘汰一起写）；如果用 `write_through`，L3 写入是平滑的。突发写入更容易撞上 L3 的水位淘汰，导致「刚写进去就被淘汰」。

### 4.6 部署配置

`docs/.../sglang/hicache-quick-start.md`：

```bash
# ① 起 Master（带 HTTP 元数据服务，省掉 etcd）
mooncake_master --enable_http_metadata_server=true

# ② 启动 SGLang
python -m sglang.launch_server \
    --model-path Qwen/Qwen2.5-7B-Instruct \
    --enable-hierarchical-cache \
    --hicache-size 64gb \
    --hicache-storage-prefetch-policy timeout \
    --hicache-storage-backend mooncake        # ★ 关键开关
```

关键参数：

| 参数 | 说明 |
|------|------|
| `--hicache-storage-backend mooncake` | ★ 指定 L3 后端为 Mooncake |
| `--hicache-storage-prefetch-policy` | `best_effort` / `wait_complete` / `timeout`（文档建议 `timeout`） |
| `--hicache-size` | L2（host 内存）大小 |
| `MOONCAKE_GLOBAL_SEGMENT_SIZE` | 本实例向 L3 池捐献的大小（对应 02 篇 `global_segment_size`） |
| `MC_MMAP_ARENA_POOL_SIZE` | mmap arena 池大小（对应 03 篇 `mmap_arena.h`），**默认关闭**，设了才启用（gflag 方式默认 8 GB） |
| `MC_DISABLE_MMAP_ARENA=1` | 强制走基线 `mmap()` 路径 |

**HugeTLB 需要预留**（`hicache-quick-start.md:13`）：

> If you want HugeTLB-backed host KV memory, reserve the hugepages on the host before launching SGLang. The helper `python3 scripts/check_hicache_hugepage_requirements.py ...` can size the required budget from your `--hicache-size`, `MOONCAKE_GLOBAL_SEGMENT_SIZE`, and `MC_MMAP_ARENA_POOL_SIZE` values.

```bash
python3 scripts/check_hicache_hugepage_requirements.py \
    --hicache-size 64gb ...
```

**【逻辑】为什么要 HugeTLB（大页）？** 64 GB 内存用 4 KB 页需要 1600 万个页表项，TLB 根本装不下，会频繁 TLB miss。用 2 MB 大页只需 3.2 万项。对于「RDMA 注册的大块内存」，大页还能减少 IOMMU 映射条目数。**这是大内存场景的必备优化，但需要提前在宿主机预留**（运行时无法动态凑出连续大页）。

### 4.7 PD 分离 + HiCache 同时启用

`hicache-quick-start.md:62-93` 给出了组合部署：

```bash
# Prefill worker：既做 PD 分离的生产者，又往 L3 写
python -m sglang.launch_server ... \
    --hicache-storage-prefetch-policy timeout \
    --hicache-storage-backend mooncake \
    --disaggregation-mode prefill ...

# Decode worker
python -m sglang.launch_server ... --disaggregation-mode decode ...

# Router（前缀感知路由）
python -m sglang_router.launch_router ...
```

**【逻辑】Router 这一环值得注意**：它做「前缀感知路由」—— 把带相同前缀的请求路由到同一个实例，最大化 L1/L2 本地命中。这与 02 篇 §5.4 提到的 `PublishKvStored` 事件（`include/kv_event/`）是配套的：Mooncake 向外发布「哪个节点存了哪些 KV」，Router 据此决策。

**完整的三层优化叠加**：
1. Router 前缀感知 → 尽量本地命中（L1/L2，最快）；
2. 本地没有 → L3 共享池预取（Mooncake，快）；
3. L3 也没有 → 重算（慢）。

## 七、统一示例的完整闭环

现在把 00 篇的时间线用真实组件名重写一遍：

```
【部署】
  mooncake_master --port 50051                       ← 04 篇：Master + 选主
  vLLM P0：MooncakeStoreConnector, kv_role=kv_producer
  vLLM D0：MooncakeStoreConnector, kv_role=kv_consumer
  两者 setup 时各 mount 16 GB segment                 ← 02 篇 §3

【t0】请求 A 到达 P0
  Connector.get_num_new_matched_tokens()
    └─ Client.batch_query(["kvcache:hash(SYSTEM)"])   ← 02 篇 §7.1
       └─ Master.BatchExistKey() → false（冷启动）     ← 02 篇 §4.1

【t1】P0 执行 prefill，逐层算出 KV

【t2】Connector.save_kv_layer(layer_i) 逐层写入（★ 与计算重叠）
  ├─ Client.put_from(key, gpu_ptr, size)              ← 02 篇 §5.5
  │   ├─ Master.PutStart() → Replica::Descriptor[]    ← 02 篇 §5.3
  │   ├─ TransferEngine::submitTransfer(WRITE)        ← 01 篇 §5
  │   │    ├─ 切 Slice（merge_final_slice）
  │   │    ├─ selectDevice() → Topology 亲和选网卡
  │   │    └─ worker 线程 ibv_post_send + poll CQ
  │   └─ Master.PutEnd() → 状态 COMPLETE              ← 02 篇 §5.4
  │        └─ GrantLease(0, soft_ttl) + PublishKvStored
  └─ Connector.wait_for_save() 确认发完

【t3】A 的 KV 送到 D0
  Connector.start_load_kv() → Client.batch_get_into()
    ├─ Master.GetReplicaList() → ★ 授予 10 秒租约      ← 04 篇 §1.4
    └─ TransferEngine::submitTransfer(READ)            ← 01 篇
  Connector.wait_for_layer_load() 逐层等待

【t4】请求 B 到达（任意实例）
  batch_query("kvcache:hash(SYSTEM)") → ★ true！
    └─ batch_get_into() 拉回共享前缀 KV
       ★ 省掉 10 个 token 的 prefill —— 这就是 Mooncake 的核心价值
       （SGLang 场景下这一步由 HiCache prefetch 线程完成，见 §4.3）

【t5】池子到 90% 水位
  ├─ Master 挑淘汰候选：无租约 + 非 pin 优先             ← 04 篇 §2.2
  ├─ LRUEvictionStrategy::EvictKey() 选最冷的            ← 04 篇 §2.3
  └─ 若开了 SSD offload：
       StorageBackendInterface::BatchOffload()          ← 03 篇 §4.2
       └─ 副本类型 MEMORY → DISK，对象仍可读（慢一点）
```

## 八、选型与调优建议

### 8.1 我该用哪条路径

```
只做 PD 分离，不需要跨实例前缀共享
  └─▶ 路径 A：MooncakeConnector（vLLM）/ SGLang 内建 PD
      不用起 Master，最简单

需要跨实例 / 跨重启的前缀缓存
  └─▶ 路径 B：MooncakeStoreConnector（vLLM）/ HiCache backend（SGLang）
      要起 Master

两个都要（生产推荐）
  └─▶ vLLM：MultiConnector 组合两者
      SGLang：--disaggregation-mode + --hicache-storage-backend mooncake
```

### 8.2 常见坑

| 现象 | 可能原因 | 对应篇章 |
|------|---------|---------|
| 带宽只跑到单卡水平 | `location` 标签没传对，Topology 选错网卡 | 01 篇 §5.3 |
| `AddressNotRegistered` 错误 | buffer 没 `registerLocalMemory` | 01 篇 §3 |
| Put 报 insufficient space | 水位太高 / hard pin 太多 / segment 太小 | 04 篇 §2.2 |
| 命中率低 | prefetch 策略选了 `best_effort`；或 write-back 策略太保守 | 05 篇 §4.4/4.5 |
| 大内存下性能抖动 | 没预留 HugeTLB | 05 篇 §4.6 |
| 切主后短暂报错 | 正常，客户端会 ReMount 后恢复 | 04 篇 §4 |
| 读到一半失败 | 租约 TTL 太短（默认 10 s，超大对象可能不够） | 04 篇 §1 |

### 8.3 调优优先级

1. **先确认 Topology 正确**（`location` 标签 + `showLinks()` 检查）—— 这一项错了，其他优化都是白费；
2. **HugeTLB 预留**（大内存必做）；
3. **prefetch 策略选 `timeout`** 并按 SLO 调 `prefetch_timeout_base` / `_per_ki_token`；
4. **write-back 策略**按带宽富裕度选（富裕 → `write_through`）；
5. **水位与租约**：命中率低就调低 `eviction_high_watermark_ratio` 或加 segment；大对象读失败就调大 `default_kv_lease_ttl`。

## 九、必记要点

1. **两条路径本质不同**：路径 A（PD 直传）只用 Transfer Engine、不需要 Master；路径 B（共享池）用完整 Store、需要 Master。
2. **生产推荐两条同时用**：vLLM 用 `MultiConnector` 组合，直传解决「这一次」，共享池解决「下一次」。
3. **`save_kv_layer` 逐层发送让传输与计算重叠**，总耗时从「计算+传输」降到约「max(计算, 传输)」。
4. **`register_kv_caches` 是零拷贝的前提**，且 `location` 标签直接决定 Topology 选网卡是否正确。
5. **HiCache 的 L1/L2 私有、L3 共享**，正对应 CPU 的 L1/L2/L3 设计哲学 —— 共享的目的是消除冗余。
6. **HiRadixTree 不同步 L3 元数据，改为实时查询** —— 用一次 RPC 延迟换掉整套同步机制。
7. **prefetch 三策略**：`best_effort` / `wait_complete` / **`timeout`（推荐）**，超时按 token 数线性计算。
8. **write-back 三策略**对应 CPU 缓存的 write-through / write-back，按带宽富裕度选。
9. **大内存必须预留 HugeTLB**，否则 TLB miss 会吃掉收益。
10. **`--hicache-storage-backend mooncake` 是 SGLang 侧的一个开关**，`MooncakeStoreConnector` 是 vLLM 侧的对应物。
11. **Router 前缀感知路由 + L3 共享池 + 本地 L1/L2 是三层叠加优化**，靠 `kv_event` 发布的事件串联。
12. **Transfer Engine 已成为事实标准件**（TensorRT-LLM、vLLM-Ascend、xLLM、checkpoint-engine 都在用），因为它的抽象边界只做「搬数据」。
