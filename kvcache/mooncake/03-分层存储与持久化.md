## 一、为什么必须有 SSD 这一层

回到统一示例：集群两个实例各捐 16 GB，全局池 32 GB。听起来不少，但算一下 KV Cache 的实际体量：

> Qwen2.5-7B，28 层，KV head 4，head_dim 128，FP16 →
> 单 token KV ≈ 28 × 2 × 4 × 128 × 2 B ≈ **57 KB**
> 一个 32K 上下文的请求 ≈ 57 KB × 32768 ≈ **1.8 GB**

**32 GB 池子只能装 18 个长上下文请求的 KV。** 而 Agentic Coding 这类场景动辄几十并发、上下文反复复用 —— 内存池瞬间就满。

此时有三个选择：

| 选择 | 后果 |
|------|------|
| 直接淘汰冷数据 | 下次命中不了，要重算 prefill（几百 ms ~ 数秒） |
| **落到 SSD** | 读回来几 ms（NVMe），**远快于重算** |
| 加机器扩内存 | 贵 |

**【逻辑】关键判断：只要「从 SSD 读回来」比「重新 prefill」快，这一层就值得做。** NVMe 顺序读 3~7 GB/s，读 1.8 GB 约 300~600 ms；而 32K token 的 prefill 在 A100 上要 1~3 秒。所以 SSD 层是明确的净收益 —— 这就是 `ssd-offload.md` 这个设计文档存在的原因。

## 二、存储后端抽象：StorageBackendInterface

`mooncake-store/include/storage_backend.h:345-400`：

```cpp
class StorageBackendInterface {
   public:
    StorageBackendInterface(const FileStorageConfig& file_storage_config);

    using EvictionHandler = std::function<tl::expected<void, ErrorCode>(
        const std::vector<std::string>& evicted_keys)>;
    //  【逻辑】★ 淘汰回调：后端淘汰了哪些 key，要回调通知 Master 更新元数据

    virtual tl::expected<void, ErrorCode> Init() = 0;

    virtual tl::expected<int64_t, ErrorCode> BatchOffload(
        const std::unordered_map<std::string, std::vector<Slice>>& batch_object,
        std::function<ErrorCode(const std::vector<std::string>& keys,
                                std::vector<StorageObjectMetadata>& metadatas)>
            complete_handler,
        EvictionHandler eviction_handler = nullptr) = 0;
    //  【逻辑】★ 内存 → 磁盘（下沉）

    virtual tl::expected<void, ErrorCode> BatchLoad(
        std::unordered_map<std::string, Slice>& batched_slices) = 0;
    //  【逻辑】★ 磁盘 → 内存（读回）

    virtual tl::expected<bool, ErrorCode> IsExist(const std::string& key) = 0;

    virtual tl::expected<bool, ErrorCode> IsEnableOffloading() = 0;

    virtual tl::expected<void, ErrorCode> ScanMeta(
        const std::function<ErrorCode(
            const std::vector<std::string>& keys,
            std::vector<StorageObjectMetadata>& metadatas)>& handler) = 0;
    //  【逻辑】★ 扫描已落盘的对象元数据 —— 重启后重建索引用
```

**【逻辑】接口设计的两个要点**：

1. **全部是 Batch 语义**，没有单个 `Put`/`Get`。原因和 02 篇 §7.1 一样：KV Cache 一次涉及几十上百个 key，逐个做 IO 会被 syscall 开销吃掉。
2. **`ScanMeta` 的存在意味着磁盘数据是可以「认领」的**：进程重启后扫一遍磁盘，把已落盘的对象重新登记回 Master —— **这让 SSD 层成为跨重启的持久缓存**，而不只是临时溢出区。

> **【C++】`std::function<ErrorCode(const std::vector<std::string>&, std::vector<StorageObjectMetadata>&)>`**
> 这是类型擦除的可调用对象包装器，可以装函数指针、lambda、成员函数绑定等。这里用作**回调**：后端完成 offload 后，通过 `complete_handler` 把「哪些 key 写成功了、元数据是什么」回传给调用方。代价是有一次间接调用开销（不能内联），但换来了模块解耦。

### 2.1 三种后端布局

`storage_backend.h:162-167`：

```cpp
enum class StorageBackendType {
    kFilePerKey,      // 一个 key 一个文件
    kBucket,          // 多个 key 攒进一个 bucket 文件（默认）
    kOffsetAllocator, // 单个大文件 + 偏移分配
    kDistributed      // 分布式后端
};
```

对应实现类：

| 类型 | 实现类 | 行号 | 布局 | 优缺点 |
|------|-------|------|------|-------|
| `kFilePerKey` | `StorageBackendAdaptor` → `StorageBackend` | `:744` / `:409` | 一 key 一文件 | 简单、易调试；**小文件多时 inode 压力大、元数据开销高** |
| `kBucket` | `BucketStorageBackend` | `:816` | 多 key 打包成 bucket 文件 | **默认选项**，摊薄文件数；淘汰粒度是整个 bucket |
| `kOffsetAllocator` | `OffsetAllocatorStorageBackend` | `:1164` | 一个大文件 + 偏移分配器 | 类似裸设备管理，碎片可控、支持持久化元数据 |
| `kDistributed` | `include/storage/distributed/` | — | 分布式（多节点共享） | 跨节点共享盘 |

默认是 `kBucket`（`:295`）：

```cpp
struct FileStorageConfig {
    // type of the storage backend
    StorageBackendType storage_backend_type = StorageBackendType::kBucket;

    // Path where data files are stored on disk
    std::string storage_filepath = "/data/file_storage";

    // Size of the local client-side buffer (used for caching or batching)
    int64_t local_buffer_size = 1280 * kMB;  // ~1.2 GB
```

**【逻辑】为什么默认选 Bucket？** KV Cache 的 key 数量极大（一个请求几十个 block key），如果一 key 一文件，几百万个小文件会把文件系统压垮（ext4 的 inode 查找、目录项遍历都会退化）。Bucket 把 500 个 key（默认）打包进一个 256 MB 文件，文件数直接降三个数量级。

### 2.2 Bucket 后端的配置与淘汰

`storage_backend.h:183-205`：

```cpp
enum class BucketEvictionPolicy {
    NONE,  // No eviction (default)
    FIFO,  // Evict oldest bucket first (by creation order)
    LRU,   // Evict least recently read bucket first
};

struct BucketBackendConfig {
    int64_t bucket_size_limit =
        256 * kMB;  // Max total size of a single bucket (256 MB)

    int64_t bucket_keys_limit = 500;  // Max number of keys allowed in a single
                                      // bucket, required by bucket backend only

    BucketEvictionPolicy eviction_policy =
        BucketEvictionPolicy::NONE;  // Eviction strategy

    int64_t max_total_size = 0;  // 0 = unlimited; evict when total_size_
                                 // exceeds this threshold (bytes)

    bool Validate() const;
    static BucketBackendConfig FromEnvironment();   // 【逻辑】支持环境变量配置
};
```

**【逻辑】Bucket 的代价在这里显现**：淘汰粒度是**整个 bucket**（256 MB / 500 key）。哪怕这个 bucket 里只有一个 key 是冷的，淘汰时 500 个 key 一起没了。这是「减少文件数」的对价 —— 典型的空间/管理粒度权衡。

如果这个粒度不可接受，就该换 `kOffsetAllocator`。

### 2.3 OffsetAllocator 后端：最精细也最复杂

`storage_backend.h:207-263`，这是唯一支持**元数据持久化**的后端：

```cpp
enum class OffsetEvictionPolicy {
    NONE,  // No eviction
    FIFO,  // Evict oldest key first (by insertion order)
    LRU,   // Approximate LRU via cross-shard sampling (phase 2)
};

enum class OffsetPersistMode {
    kDisabled,  // No persistence (default)
    kRelaxed,   // Periodic checkpoint          【逻辑】定期快照，崩溃丢最近一段
    kStrict,    // Every BatchOffload is durable 【逻辑】每次都 fsync，最慢最安全
};

struct OffsetAllocatorBackendConfig {
    OffsetEvictionPolicy eviction_policy = OffsetEvictionPolicy::NONE;

    // Watermark thresholds: eviction triggers when total_size_ exceeds high,
    // drives down to low. 0 = auto-resolved in Init() from ratios.
    int64_t high_watermark_bytes = 0;
    int64_t low_watermark_bytes = 0;
    double high_ratio = 0.90;      // 【逻辑】★ 超过 90% 触发淘汰
    double low_ratio = 0.80;       // 【逻辑】★ 一直淘到 80% 才停

    // Key-count watermarks (symmetric with byte watermarks).
    int64_t high_watermark_keys = 0;
    int64_t low_watermark_keys = 0;
    double keys_high_ratio = 0.95;
    double keys_low_ratio = 0.90;

    // Eviction caps
    size_t max_evict_per_offload = 4096;   // 【逻辑】单次最多淘汰多少，防长尾停顿
    size_t fallback_evict_batch = 16;
    // ...
    OffsetPersistMode persist_mode = OffsetPersistMode::kDisabled;
    int64_t persist_interval_seconds = 60;
    bool enable_record_crc = true;
};
```

**【逻辑】双水位（high/low watermark）是缓存系统的标准做法**，务必理解为什么不能用单水位：

- 单水位（如「超 90% 就淘汰到 90%」）会导致**抖动**：淘汰一个对象降到 89.9%，写一个又到 90.1%，反复触发淘汰逻辑，每次都要加锁、扫描、更新元数据。
- 双水位（90% 触发 → 淘到 80% 才停）一次性腾出 10% 空间，接下来一大段时间都不用再触发。**用一次批量代价换多次小代价。**

这个模式你会在 04 篇的内存池淘汰里再看到一次（`eviction_high_watermark_ratio = 0.90` / `eviction_ratio = 0.05`）。

`enable_record_crc` 的注释解释了数据完整性的设计取舍（`:254-262`）：

```cpp
    // ---- Record integrity ----
    // When true (default), every written record carries a CRC-32C over
    // header-prefix + key + value (RecordHeader::kFlagHasCrc), verified
    // once on recovery.  Disable only when torn writes are otherwise
    // impossible (kStrict mode on storage that honors fsync ordering,
    // e.g. power-loss-protected NVMe) or when values never pass through
    // the CPU (future DMA/GDS writers): unchecksummed records are then
    // validated by checkpoint ordering (seq guard) alone.
    // 【中译】默认每条记录都带 CRC-32C（覆盖 header 前缀 + key + value），
    //    恢复时校验一次。只在以下情况可关闭：① 撕裂写不可能发生（kStrict 模式 +
    //    尊重 fsync 顺序的存储，如带掉电保护的 NVMe）；② 数据不经过 CPU
    //    （未来的 DMA/GDS 写入路径）。此时仅靠 checkpoint 序号守卫来校验。
    bool enable_record_crc = true;
```

**【逻辑】「撕裂写」（torn write）** 指一次写入只有部分落盘（掉电、崩溃）。CRC 能检测出来，代价是每次写都要算校验和（CPU 开销）。作者留了关闭开关，因为在 GPUDirect Storage 路径下数据根本不过 CPU，算 CRC 反而要先拷回来 —— 那就赔了。

持久化格式还带版本号（`:283-291`）：

```cpp
// Current on-disk format version of OffsetAllocatorPersistedMetadata.
// v2: RecordHeader grew from 8 to 20 bytes (added per-record seq + CRC-32C).
// v3: RecordHeader is 24 bytes (added `flags`; CRC-32C is now optional per
//     record) and the value region is aligned to 4 KiB within the record
//     (zero padding derived from key_len), so that DMA writers (e.g. GDS)
//     can share the layout.
// Older metadata is rejected on load (fresh start) because its data-file
// records cannot be parsed with the current record layout.
inline constexpr uint32_t kOffsetAllocatorPersistVersion = 3;
```

**【逻辑】v3 把 value 区域 4 KiB 对齐**，就是为 DMA / GPUDirect Storage 铺路 —— DMA 引擎通常要求页对齐。这是「为未来硬件能力预留格式空间」的典型做法。

## 三、三条 IO 路径

同一个「写文件」的动作，Mooncake 有三种实现，性能差一个数量级。

### 3.1 抽象：StorageFile

`include/file_interface.h` 定义统一文件接口，各后端实现它。以 3FS 的实现为例（`include/hf3fs/hf3fs.h:85-101`）：

```cpp
class ThreeFSFile : public StorageFile {
   public:
    ThreeFSFile(const std::string &filename, int fd,
                USRBIOResourceManager *resource_manager);
    ~ThreeFSFile() override;

    tl::expected<size_t, ErrorCode> write(const std::string &buffer,
                                          size_t length) override;
    tl::expected<size_t, ErrorCode> write(std::span<const char> data,
                                          size_t length) override;
    tl::expected<size_t, ErrorCode> read(std::string &buffer,
                                         size_t length) override;
    tl::expected<size_t, ErrorCode> vector_write(const iovec *iov, int iovcnt,
                                                 off_t offset) override;
    tl::expected<size_t, ErrorCode> vector_read(const iovec *iov, int iovcnt,
                                                off_t offset) override;
```

**`vector_write` / `vector_read`（向量 IO）是关键**：一次 syscall 提交多段不连续内存的读写。KV Cache 的场景天然如此 —— 一个对象可能由多个 `Slice` 组成，分散在不同地址，向量 IO 让它们一次落盘。

### 3.2 路径一：普通文件 IO + io_uring

`src/uring_file.cpp`（772 行）实现基于 **io_uring** 的异步文件 IO。

**【逻辑】io_uring 为什么比传统 IO 快**：
- 传统 `pwrite`：每次 IO 一次 syscall，用户态/内核态切换开销（~1 μs），高 IOPS 下 CPU 全耗在切换上。
- io_uring：用户态和内核态共享两个环形队列（SQ 提交队列 / CQ 完成队列），**批量提交 + 批量收割**，可以做到「一次 syscall 提交上百个 IO」，甚至 polling 模式下零 syscall。

**你会发现这和 01 篇 RDMA 的 `ibv_post_send` + `ibv_poll_cq` 是同一个思想**：提交队列 + 完成队列 + 批量轮询。现代高性能 IO 无论网络还是存储，都收敛到这个模型。

### 3.3 路径二：3FS USRBIO（用户态绕过内核）

`include/hf3fs/hf3fs.h`。3FS 是 DeepSeek 开源的分布式文件系统，USRBIO 是它的用户态 IO 接口。

```cpp
struct Hf3fsConfig {
    // USRBIO related parameters
    std::string mount_root = "/";  // Mount point root directory
    size_t iov_size = 32 << 20;    // Shared memory size (32MB)
    size_t ior_entries = 16;       // Maximum number of requests in IO ring
    //`0` for no control with I/O depth.
    // If greater than 0, then only when `io_depth` I/O requests are in queue,
    // they will be issued to server as a batch. If smaller than 0, then USRBIO
    // will wait for at most `-io_depth` I/O requests are in queue and issue
    // them in one batch. If io_depth is 0, then USRBIO will issue all the
    // prepared I/O requests to server ASAP.
    size_t io_depth = 0;  // IO batch processing depth
    int ior_timeout = 0;  // IO timeout (milliseconds)
};
```

**【逻辑】`io_depth` 的三态语义很有意思**（注释里说得很清楚）：
- `> 0`：**攒够** `io_depth` 个请求才批量下发 —— 吞吐优先；
- `< 0`：**最多等** `-io_depth` 个就下发 —— 折中；
- `= 0`：**立即下发** —— 延迟优先。

一个参数用正负号编码三种策略，紧凑但需要读注释才懂。

资源管理用了 **thread-local 池**（`hf3fs.h:32-83`）：

```cpp
class USRBIOResourceManager {
   public:
    struct ThreadUSRBIOResource *getThreadResource(const Hf3fsConfig &config);
   private:
    std::mutex resource_map_mutex;
    // ThreadID to resource mapping
    std::unordered_map<std::thread::id, struct ThreadUSRBIOResource *>
        thread_resources;
};

// Thread level USRBIO resource structure
struct ThreadUSRBIOResource {
    struct hf3fs_iov iov_;         // 【逻辑】共享内存区（32 MB）
    struct hf3fs_ior ior_read_;    // 【逻辑】读 IO ring
    struct hf3fs_ior ior_write_;   // 【逻辑】写 IO ring
    bool initialized;
    Hf3fsConfig config_;
    ~ThreadUSRBIOResource() { Cleanup(); }
};
```

**【逻辑】为什么每线程一套 IO ring？** IO ring 本身不是线程安全的（无锁环形队列，多线程并发提交会乱）。给每个线程独立一套，就完全无需加锁 —— 这和 01 篇 `ThreadLocalSliceCache`、`WorkerPool` 每线程独立 CQ 是完全一样的思路：**用「资源复制」换「锁消除」**。

### 3.4 路径三：SPDK（完全用户态 NVMe）

`include/spdk/spdk_wrapper.h`。SPDK 更极端：**连内核块设备层都绕过**，用户态直接驱动 NVMe 控制器，轮询完成队列（no interrupt）。

三条路径的对比：

| 路径 | 内核参与 | 典型延迟 | 适用 |
|------|---------|---------|------|
| 普通 `pwrite` | 完整 VFS + 块层 | ~100 μs | 兼容性最好 |
| **io_uring** | 减少 syscall，仍走块层 | ~20-50 μs | **通用推荐** |
| **3FS USRBIO** | 用户态绕过 VFS | ~10-20 μs | 有 3FS 集群 |
| **SPDK** | 完全绕过内核 | ~5-10 μs | 独占 NVMe，极致性能 |

## 四、SSD offload 的开关与流程

### 4.1 怎么开

客户端 setup 时（`include/real_client.h:91-92`）：

```cpp
        bool enable_ssd_offload = false,
        const std::string &ssd_offload_path = "",
```

Python：

```python
store.setup(
    ...,
    enable_ssd_offload=True,
    ssd_offload_path="/mnt/nvme/mooncake",
)
```

### 4.2 下沉流程

```
内存池水位超过 eviction_high_watermark_ratio（默认 0.90）
  │
  ▼
Master 挑选淘汰候选（04 篇：无租约 + 非 hard pin，优先非 soft pin）
  │
  ├─ 若未开 SSD offload → 直接 Remove，元数据删除，数据丢失（下次重算）
  │
  └─ 若开了 SSD offload：
       │
       ▼
     StorageBackendInterface::BatchOffload(batch_object, complete_handler, eviction_handler)
       ├─ 攒批（bucket 后端：攒到 500 key 或 256 MB）
       ├─ vector_write() 落盘（io_uring / USRBIO / SPDK）
       ├─ complete_handler(keys, metadatas)
       │     └─ Master 把该 key 的副本类型从 MEMORY 改为 DISK
       │        ★ 对象还在，只是位置从内存变成磁盘
       └─ eviction_handler(evicted_keys)
             └─ 若磁盘也满了（触发磁盘水位），回调通知 Master 彻底删这些 key
```

**【逻辑】注意 `complete_handler` 的语义**：offload 不是「删除」，而是**副本类型的迁移**（`MEMORY` → `DISK`）。key 在 Master 里依然存在，`isExist()` 仍返回 true，`GetReplicaList()` 会返回一个 DISK 类型的副本。**上层完全无感知**，只是读延迟从 μs 变成 ms。

### 4.3 读取时的降级顺序

02 篇 §7 提到读取会「选一个副本」。完整的偏好顺序是：

```
① 本机 MEMORY 副本      → memcpy / GPU IPC       ~μs      最优
② 远端 MEMORY 副本      → RDMA READ              ~10 μs
③ NOF_SSD 副本          → RDMA 直达远端 NVMe      ~100 μs
④ LOCAL_DISK 副本       → 经该客户端中转          ~ms
⑤ DISK 副本（共享 FS）  → StorageBackend::BatchLoad  ~ms
⑥ 全都没有              → 返回未命中，上层重算 prefill  ~秒
```

**【逻辑】这个降级链的价值**：每一级都比「重算」便宜。哪怕落到最慢的 ⑤（几 ms），也远好于 ⑥（秒级 prefill）。这就是分层存储在 LLM 推理场景的经济学 —— **存储的边际成本远低于计算的边际成本**。

## 五、本地热缓存与零拷贝辅助设施

`mooncake-store/include/` 下还有几个容易忽略但很关键的组件：

| 头文件 | 作用 | 为什么需要 |
|-------|------|-----------|
| `local_hot_cache.h` | **本机热对象缓存** | 频繁读的对象直接缓存在本地，连 RDMA 都省了 |
| `pinned_buffer_pool.h` / `pinned_host_buffer.h` | **pinned（页锁定）内存池** | GPU DMA 与 RDMA 都要求 pinned 内存；池化避免反复 `cudaHostRegister`（很慢） |
| `mmap_arena.h` | **mmap 竞技场分配器** | 大块内存用 mmap 直接向 OS 要，避开 malloc 的元数据开销 |
| `shm_helper.h` | **共享内存辅助** | 同机多进程（如 vLLM 的多个 worker）共享同一份 KV，零拷贝 |
| `aligned_client_buffer.h` | **对齐缓冲** | DMA / io_uring O_DIRECT 要求 4 KiB 对齐 |
| `count_min_sketch.h` | **Count-Min Sketch** | 用极小内存估计访问频率，供 LRU/LFU 淘汰决策（04 篇） |
| `crc32c.h` | CRC-32C 校验 | 配合 `enable_record_crc` |
| `deadline_scheduler.h` | 截止时间调度 | 给 IO 请求排优先级 |

**【逻辑】`local_hot_cache` 和 `shm_helper` 合起来解释了一个重要优化**：同一台机器上跑 8 个 vLLM worker（TP=8），它们的 KV 前缀是相同的。如果每个 worker 都从远端 RDMA 拉一份，网络流量放大 8 倍。用共享内存让 8 个进程共享一份本地缓存，网络流量降回 1 倍。

`count_min_sketch.h` 值得单独说：

**【逻辑】Count-Min Sketch 是一种概率数据结构**，用 `d` 个哈希函数 × `w` 个计数器的二维数组估计元素频率。特点是**内存占用与元素数量无关**（固定 `d × w`），代价是可能高估（永不低估）。在缓存淘汰场景，「大致知道谁热」就够了，不需要精确计数 —— 用几 KB 替代几百 MB 的精确计数表。

## 七、与 vLLM / SGLang 的对照

| 层级 | vLLM | SGLang HiCache | Mooncake |
|------|------|---------------|----------|
| L1 | GPU 显存 block 池 | GPU 显存（RadixTree 节点） | 不管（由引擎管） |
| L2 | CPU offload（`--swap-space`） | Host 内存（HiRadixTree 标记） | 不管（由引擎管） |
| **L3** | **无**（需外接 connector） | **外接 backend（可以是 Mooncake）** | **★ 本篇：集群 DRAM 池** |
| **L4** | 无 | 无 | **★ 本篇：SSD / 3FS / SPDK** |
| 淘汰粒度 | block（16 token） | 树节点 | 对象 / bucket |
| 跨重启 | ✗ | ✗ | **✓（`ScanMeta` 重建索引）** |

**【逻辑】最值得记的一点**：vLLM 的 `--swap-space`（CPU offload）和 Mooncake 的 SSD offload 看起来像，但性质完全不同：
- `--swap-space` 是**单实例内**的显存溢出区，实例重启即失效，别的实例用不上；
- Mooncake 的分层是**集群级**的，跨实例共享、跨重启存活。

这也解释了为什么 SGLang HiCache 要把 Mooncake 当 L3 而不是自己实现 —— 单实例的缓存层次做到 L2 就到顶了，再往下必须是共享存储。

## 九、必记要点

1. **SSD 层的经济学**：只要「从 SSD 读回」快于「重新 prefill」，这一层就是净收益。NVMe 几百 ms vs prefill 数秒。
2. **接口全是 Batch 语义**（`BatchOffload` / `BatchLoad`），因为 KV Cache 一次涉及几十上百个 key。
3. **`ScanMeta` 让 SSD 层成为跨重启的持久缓存**，而非临时溢出区。
4. **默认 `kBucket` 后端**：500 key / 256 MB 打包一个文件，避免小文件海啸；代价是淘汰粒度粗。
5. **`kOffsetAllocator` 是唯一支持元数据持久化的后端**，有 `kRelaxed`（定期快照）/ `kStrict`（每次 fsync）两档。
6. **双水位（0.90 触发 → 0.80 停止）避免淘汰抖动** —— 这个模式 04 篇还会再见一次。
7. **三条 IO 路径**：io_uring（通用推荐）/ 3FS USRBIO（有 3FS 集群）/ SPDK（极致）。都是「提交队列 + 完成队列 + 批量轮询」模型，与 RDMA 同构。
8. **每线程独立 IO ring**：用资源复制换锁消除，与 01 篇 `ThreadLocalSliceCache` 同思路。
9. **offload 不是删除，是副本类型迁移**（`MEMORY` → `DISK`），上层无感知。
10. **读取降级链有 6 级**，每级都比重算便宜。
11. **Count-Min Sketch 用几 KB 估计访问频率**，供淘汰决策 —— 概率数据结构换内存。
12. **持久化格式 v3 把 value 区 4 KiB 对齐**，为 GPUDirect Storage 预留。
